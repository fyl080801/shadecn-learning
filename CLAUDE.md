# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Language

**Always reply in Chinese (中文).** All user-facing output — answers, explanations, plans, summaries, questions — is written in Chinese. Keep technical terms in their original English form (Vite, Prisma, OIDC, Hono, …) rather than translating them.

Code identifiers, types, and commit messages stay English. **Source comments in `server/` and `src/`, log/error messages shown to a developer or user, and test names are written in Chinese**, matching every existing file. Documentation under `docs/` is Chinese too.

## Project Overview

A Vue 3 learning/experimentation sandbox that combines shadcn-vue UI components, Three.js 3D scenes, and canvas-based mini-games. It serves as a playground for exploring different Vue and web technologies within a single app.

Requirements live in `docs/`, one file per requirement — see `docs/README.md` for the index. This file describes *how the code is built*; `docs/` describes *what it is supposed to do*.

## Commands

- `pnpm dev` — Start the whole app (Node/Hono + Vite as middleware, watch mode) on http://127.0.0.1:3000
- `pnpm build` — Build both halves into `output/`: frontend (`vue-tsc -b` + `vite build`) into `output/public`, backend (esbuild bundle) into `output/server`
- `pnpm build:client` / `pnpm build:server` — Just one half
- `pnpm start` — Run the production server (`NODE_ENV=production node output/server/index.js`)
- `pnpm preview` — `pnpm build && pnpm start`
- `pnpm typecheck:server` — Type-check the `server/` project
- `pnpm test` — Run both Vitest projects once; `pnpm test:watch` for watch mode
- `pnpm test:server` / `pnpm test:client` — Run only the backend / frontend project
- `pnpm test:coverage` — v8 coverage into `coverage/`
- `pnpm lint` / `pnpm lint:fix` — ESLint
- `pnpm db:generate` — Regenerate the Prisma client into `server/generated/prisma` for the *current* provider (also runs on `postinstall`). There is no schema-generation step: the two per-provider schema dirs are hand-written and share one physical copy of the models through a symlink (see below)
- `pnpm db:push` / `pnpm db:studio` — sync the schema into the database (`prisma db push` — **this project keeps no migration files**, see the database section) and the data browser. `pnpm dev` runs `db:push` first

One process, one port: the Node server is the only entry point in both dev and prod — there is no separate Vite dev server and no proxy.

Copy `.env.example` → `.env` before the first run; `server/env.ts` loads it via `process.loadEnvFile()` (no dotenv dependency).

## Architecture

**Stack:** Vue 3 + TypeScript + Vite + Tailwind CSS v4 + shadcn-vue (new-york style)

**Path alias:** `@/` maps to `src/` (configured in both `vite.config.ts` and `tsconfig.app.json`)

**Routing:** `src/router/index.ts` — vue-router 5 (history mode). The route table has exactly two top-level records, one per layout (see below); every page is a *child* of one of them, and the child paths stay flat (`projects/:projectId`, not further nesting). The *views* are grouped into feature folders (see below). It is the only place that imports from `src/views/` and from `src/layouts/`.

**Layout — `src/layouts/`, one component per layout, picked by the route table.** `App.vue` is only `<RouterView />` + the `Toaster` (vue-sonner) mounted once at the root; it contains no layout branch. `SidebarLayout.vue` is `AppSidebar` + a scrolling `<main><RouterView /></main>` and holds almost every route; `BlankLayout.vue` is a bare full-screen `<RouterView />` and holds only `/flows/:flowId`, the canvas editor, which needs the whole screen. Both top-level records use `path: "/"`, so adding a page means putting it under the layout it belongs to — nothing else changes, and there is no `meta.layout` flag anymore. Every SPA route is a logged-in route (the login page is server-rendered and never enters the SPA) — a bare layout is *not* an auth exception. The app fills the viewport height (`h-screen`).

**Auth (frontend):** the gate is on the server (`server/frontend/guard.ts`) — an anonymous browser never receives this bundle in the first place. `src/router/index.ts`'s global `beforeEach` is only the fallback for a session that dies mid-visit: it calls `fetchSession()` (one `GET /api/auth/me`, cached) and, when anonymous, either `goToLoginPage()` — a full-page `location.replace('/login?redirect=<fullPath>')`, because `/login` is server-rendered HTML and not a SPA route — on the *first* navigation (`from === START_LOCATION`, nothing on screen to lose), or `requestReLogin(to.fullPath)` once the user is already inside the app. `src/lib/auth.ts` exposes `useAuth()` (`user` / `roles` / `isAuthenticated` / `authEnabled` / `sessionExpired` / `hasRole`) and `apiFetch()`. There is no token in the browser — login/logout are full-page navigations to `/api/auth/login` and `/api/auth/logout`.
- **An expired session is never a silent redirect.** A 401 from `apiFetch` (or the guard, mid-visit) calls `requestReLogin(redirect)`, which clears the local user, remembers the return url, and flips `sessionExpired`; `SessionExpiredDialog.vue` — mounted once in `App.vue` next to the `Toaster` — asks, and offers two ways out plus "close and do nothing" (× / Esc / overlay → `dismissReLogin()`, the next 401 asks again). **退出** is `logoutFromExpired()` → `/api/auth/logout?redirect=<return url>`, which lands back on `/login?redirect=<return url>` so logging in again returns to the same page. **重新登录** never leaves the page: a second modal runs the whole OIDC flow in an `<iframe>` pointed at `/api/auth/login?redirect=/auth/embedded-done`, and the page — with whatever was typed into it — stays put. Yanking the page away on a 401 both destroys unsubmitted input and hides what happened.
- **The embedded login's success signal has two legs, because the session is an httpOnly cookie the frontend can't read.** `server/frontend/embedded-done-page.ts` renders `/auth/embedded-done` (registered *after* `pageGuard`, so an unauthenticated landing bounces back to `/login` inside the iframe) and it `postMessage`s a same-origin `app-auth:login-done`; the dialog accepts it only when `event.origin === location.origin` *and* the marker matches, then calls `finishReLogin()` → `fetchSession(true)` and only closes if `/api/auth/me` really says logged-in. A 3s poll while the modal is open is the second leg (message blocked, or the user logged in through the 「在新窗口登录」 popup, which reports via `window.opener`). Whether the iframe renders at all is Keycloak's call — its default `X-Frame-Options: SAMEORIGIN` blanks it out, hence the popup fallback and the realm config note in `docs/02-auth-keycloak.md` §4.1.

**UI Components (shadcn-vue):** Located in `src/components/ui/`. Added via the `shadcn-vue` CLI (`pnpm exec shadcn-vue add <name>`, configured in `components.json`) — note the CLI drops new packages into `dependencies`, so move them to `devDependencies` afterwards (see the dependency split below). Icon library is `lucide-vue-next`. The `cn()` utility in `src/lib/utils.ts` merges Tailwind classes via `clsx` + `tailwind-merge`. Two components are edited beyond what the CLI generates and must not be clobbered by a re-`add`: `button` carries an extra `loading` prop (spinner + auto-`disabled`, the visual half of the one-click-one-request rule below) and extra `size` variants (`xs` / `icon-xs`). **The CLI rewrites `Button.vue` whenever it is pulled in as a dependency of another component** (adding `command` does it) — `git diff src/components/ui/button/` after any `add`, and `git checkout` it back.
- **`command` is a filter-it-yourself list.** Its built-in filtering renders *every* item and hides the misses with `v-if`, which is fine for a 20-line command palette and not fine for the 400+ IANA time zones — `TimeZonePicker.vue` therefore drives the list itself (own keyword ref + own matcher + a hard cap) and uses `Command` only for keyboard navigation, feeding the input through reka-ui's `ListboxFilter` directly instead of `CommandInput` (which is hard-wired to the built-in filter state). Two consequences worth remembering: `CommandItem` **must** sit inside a `CommandGroup` (it injects the group context and throws otherwise), and `CommandEmpty` is useless in this mode — it renders off the built-in filter's hit count, which stays 0, so write the empty state by hand.

**Styling:** Tailwind CSS v4 loaded via `@tailwindcss/vite` plugin. CSS variables for theming (light/dark) are defined in `src/styles/tailwind.css` (`src/style.css` only `@import`s it plus `vue-flow.css`) using oklch colors. Uses `tw-animate-css` for animations.
- **Which of the two variable sets applies is `src/lib/theme.ts`'s job — it is the only thing that puts the `.dark` class on `<html>`** (via `useColorMode`, storage key `app:theme`, default "follow the system"). Everything else about theming was already there; nothing reads the preference directly. Three rules that are easy to miss: **the first frame is `index.html`'s inline script**, not this module (by the time the bundle parses, a dark-mode user has already been flashed a white page — both places read the same key in the same raw-string format); **`color-scheme` must be declared in both blocks** (`light` on `:root`, `dark` on `.dark`) or the browser paints a white scrollbar over a dark page; and **vue-sonner doesn't look at the class** — it has its own `theme` prop, which `App.vue` feeds from `resolvedTheme`. The `.dark` palette is deliberately **one step lighter than shadcn's default** (background `0.145 → 0.215`, card `0.205 → 0.255`, …); the login page's own inline CSS carries the same numbers, so keep the two in sync.

**Views — `src/views/` is grouped by feature, one folder per area.** Only `src/router/index.ts` imports from here, so moving a view means touching exactly one other file.
- `views/Home.vue`, `views/Settings.vue` — the shell pages stay at the root (they belong to no feature). `Settings.vue` is the account + appearance + display-preference page (theme lives in `src/lib/theme.ts`, dates in `src/lib/preferences.ts` — both browser-local, both apply with no save button); its only entry point is the sidebar's bottom user menu, which also holds 关于 and 退出登录 — the middle nav list is pages only. **关于 is a modal, not a page** (`src/components/AboutDialog.vue`, no route — it's one paragraph of blurb, not worth a navigation), and **退出登录 asks first** (an `AlertDialog` in `AppSidebar.vue`) because logging out is an irreversible full-page trip through Keycloak sitting one row below 设置.
- `views/canvas/` — REQ-CANVAS, the one non-demo feature: `Projects.vue`, `ProjectHome.vue`, `InviteAccept.vue`, `FlowEditor.vue` (see below).
- `views/three/` — everything 3D: `ThreeEditor.vue` (REQ-3DEDITOR), `3DScene.vue` (REQ-DIRECTOR), `Canvas3D.vue` / `LightScene.vue` (Three.js scaffolds, not implemented), `Emu3DView.vue` (CSS-only 3D cube via `Cube3D.vue`).
- `views/games/` — canvas games: `Demo3.vue` (brick-breaker), `SnakeGame.vue`, `Game2048.vue` (scoped CSS, no shadcn).
- `views/demos/` — single-page capability checks: `FlowChart.vue` (REQ-FLOW, the Vue Flow interaction demo the canvas feature grew out of), `RichEditor.vue` (REQ-PROMPT), `HiC.vue`, `Example.vue`.
- `Example.vue` and `Emu3DView.vue` have **no route** — they're orphaned view files kept around, see `docs/01-app-shell.md` §3.

**Projects & canvases (REQ-CANVAS, `docs/13-flow-canvas-management.md`)** — the one non-demo feature. A **project** owns canvases and is the permission boundary; the only way in is its share link — one per project, unlimited uses, admins open the 分享 dialog and the link is already there (`GET /api/projects/:id/invite` creates it on read). Four views in `src/views/canvas/`: `Projects.vue` (`/projects`, paginated list, sidebar entry「画布项目」), `ProjectHome.vue` (`/projects/:projectId`, one route, same-page Tabs for 画布 / 成员 — switching tabs never touches the URL), `InviteAccept.vue` (`/invite/:token`, preview-then-confirm; anonymous visitors get bounced through `/login` by the page guard and land back here), and `FlowEditor.vue` (`/flows/:flowId`, the one route under `BlankLayout`).
- **The editor is split into a hooks layer and a component layer — the view itself only builds the context and places components.** `provideFlowEditor(props)` (in `src/composables/flow/`) creates the shared payload once and `provide`s it; every child pulls it with `useFlowEditor()`, so there is no prop drilling and adding a panel touches no existing file. The context bundles `store` + three composables: `useFlowDocument` (load / rename / duplicate / delete / save-state text / `flushBeforeLeave`), `useFlowCanvas` (the Vue Flow glue: `nodes`/`edges` bindings, drag→`node.move`, connect→`edge.add`, viewport sync, cursor-anchored ctrl-wheel zoom, `addNode`), and `useFlowSelection` (`selectedNode` + `updateNodeData` + `deleteSelection`). `useFlowShortcuts(ctx)` adds the keybindings and the two don't-lose-work guards. Note `useVueFlow()` is called inside `useFlowCanvas` at the *root* setup, so the later `<VueFlow>` adopts that instance and out-of-canvas components (toolbar, capsule) can still use `screenToFlowCoordinate`.
- **Components live in `src/components/flow/`**, each owning one region and reading the context directly: `FlowCanvas.vue` (Vue Flow + background + minimap, plus a `<slot/>` for extra in-canvas overlays), `FlowViewControls.vue` (zoom/fit/lock + undo/redo, top-right, shifts left when the inspector opens), `FlowTitleCapsule.vue` (top-**left**: logo/home + inline-editable name + save state + menu, owns its delete confirm), `FlowToolbar.vue` (bottom, canvas-content actions), `FlowNodeInspector.vue` (right panel), `ProcessNode.vue` (the node itself).
- **Canvas behaviour is Vue Flow's job, not CSS's.** Anything that has to live *on* the canvas — a label outside a node, a per-node toolbar, a resize handle, an overlay that must follow zoom/pan — is built from the official packages (`@vue-flow/node-toolbar`, `@vue-flow/node-resizer`, `<Panel>`, `<Handle>`, `<NodeToolbar>`, …), following [the guide](https://vueflow.dev/guide/) and [the examples](https://vueflow.dev/examples/). **Do not hand-roll positioning** (`absolute` + `transform`, viewport math, manual `screenToFlowCoordinate` re-anchoring) when a Vue Flow component already does it — a hand-written overlay silently breaks under zoom, and the transform math it duplicates is exactly what the library maintains. Tailwind classes stay for *appearance* (type scale, color, spacing inside the slot); *placement* comes from the component's props (`position` / `align` / `offset`). Missing package → add it as a `devDependency` (it's frontend, see the dependency split) rather than reimplementing it. `ProcessNode.vue`'s external top-left name label is the reference case: `<NodeToolbar :is-visible="true" :position="Position.Top" align="start">`.
- **State: `src/stores/flow/` (Pinia) is a *projection of a Y.Doc*, not a store of record.** The canvas content **is** the Yjs document (shape in `src/lib/flow-doc.ts`, mirrored server-side in `server/collab/flow-doc.ts` — two TS projects, so change one and change the other): `nodes`/`edges` are `Y.Map<id, Y.Map>` and each node's `data` is a nested `Y.Map` again, because Y.Map merges *per key* — one person retitling while another drags merges cleanly, whereas storing a node as one JSON blob would let the later write clobber the earlier one wholesale. The projection is **incremental**: `observeDeep`'s events name which top-level keys changed, only those get re-parsed, and everything else keeps its previous object identity — which Vue Flow relies on to skip re-syncing untouched nodes (a `null` from `changedTopLevelKeys` means "can't tell, redo everything"). The one rule: **every content change goes through `store.mutate()`**, which wraps it in a Y transaction tagged `LOCAL_ORIGIN`; components never touch a Y.Map directly, or the change is neither undoable nor synced. Undo is `Y.UndoManager` with `trackedOrigins: [LOCAL_ORIGIN]` — that single option is what makes Ctrl+Z undo only *your* edits and leave a collaborator's alone; `separateUndo()` (`stopCapturing`) splits operations that would otherwise merge inside the 400ms capture window. There is **no save, no revision, no 409, no dirty state** — edits are live and the server persists the same stream. Drag *intermediates* deliberately stay out of the doc (one drag would otherwise emit dozens of updates and audit rows); only the settled position is committed in `onNodeDragStop`, while the in-flight motion rides the feedback layer. **Panning and zooming are not canvas data and take a second, separate path**: `setViewport()` → `setUserState(key, value)`, which never enters the doc and never touches undo (undo must not yank the viewport back). **`setUserState` only buffers — it sends nothing.** The buffer is flushed to `PATCH /api/flows/:id/user-state` by `noteLocalEdit()`, which every local edit (`mutate`, `undo`, `redo`) calls. The shape is **leading send + debounced tail**: the first edit after a quiet period fires immediately (no window), everything after it goes through a `useDebounceFn` (`USER_STATE_FLUSH_DELAY`) that lands the final state once the hand stops, with a `maxWait` (`USER_STATE_FLUSH_MAX_WAIT`, 10s) so nonstop editing still lands periodically. So a view-only visit produces **zero** write traffic, a burst of editing produces one PATCH at its start and one at its end, and **no edit is dropped**. Neither half alone works: a plain debounce lags (it never fires while someone draws continuously, and this PATCH doubles as a heartbeat that can't wait), a plain throttle discards the tail of the window. The tail flush skips itself when nothing happened after the leading send, so a single edit costs exactly one request. **The window always fires a request, even when the view never moved** (it falls back to sending the current viewport), because that PATCH doubles as the session's heartbeat: content rides the WebSocket and produces no HTTP at all, the collab server's minute-by-minute revalidation is deliberately non-renewing (`loadSession(..., { refresh: false })`), and without this one request someone could be idled out *while actively editing*. Net rule: editing = one PATCH per window = session stays alive; looking = no requests = it idles out as it should. Panning without editing is caught by the flush in `saveNow()` / `reset()` on the way out. This is why the viewport rides editing rather than firing on its own: once Yjs took over content, a self-triggering viewport save was the editor's *only* periodic HTTP request — merely looking at a canvas would PATCH. To persist another per-user thing, add a field to `FlowUserState` (both copies), a parser to the server's `FLOW_USER_STATE_PARSERS`, and call `setUserState` — batching, retry and flush-on-leave are already there. Each viewer gets their own row, so `meta.viewport` in the doc is only the first-open fallback.
- **Collaboration splits into two layers with one question deciding which (`docs/04-realtime-collab.md` §4.0): *should it still be there after a refresh?*** Yes → **data layer**: a Yjs shared type, which means CRDT merge, undo, and persistence. No → **feedback layer**: an awareness field, ephemeral, dropped frames are fine. `useFlowCollab(flowId)` owns the one Yjs connection under both — a `HocuspocusProvider` (room `flow:<flowId>` passed as `name`, not in the URL; identity is the httpOnly `sid` cookie the handshake carries, gated server-side in `server/auth/ws.ts`). The same doc also carries a **`y-indexeddb`** cache (db name = room name), which is what makes edits survive going offline and closing the tab — they re-send on reconnect. Loading is therefore gated on *server-synced **or** local cache has content*, and the offline banner ORs in `navigator.onLine` because the provider needs a heartbeat timeout (tens of seconds) to notice a pulled cable. Teardown order matters: provider → indexeddb → doc. **`vite.config.ts` must keep `resolve.dedupe: ['yjs', 'y-protocols']`**: we and the provider each `import * as Y from 'yjs'`, and Vite's prebundling otherwise ships two copies — `instanceof` across them is always false, which would silently turn `src/lib/flow-doc.ts`'s `value instanceof Y.Map` checks into an empty canvas. and hands out a `session` that changes on reconnect/route-change; the store takes its `doc` and the presence layer takes its `awareness`. Dependency order is a straight line — `selection`/`collab` → `presence` → `canvas` — and `useFlowCanvas` is the **only** thing that knows all three: `useFlowPresence` doesn't import selection or Vue Flow, it just offers "publish" and "read others", which is why a new feedback signal costs one setter plus one computed and touches nothing else.
- **Data layer — the Y.Doc is the source of truth, and the server subscribes to it.** `server/collab/persistence.ts` implements Hocuspocus's `onLoadDocument`/`onStoreDocument`: first joiner loads `Flow.ydoc`, writes are debounced by the framework (2s, 10s ceiling) and skipped entirely when the state vector is unchanged, the derived `graph` projection is written **only in `beforeUnloadDocument`** — not under `onStoreDocument`'s `clientsCount === 0`, because Hocuspocus only re-stores on last-leave if a debounced store is still pending, so "edit, wait two seconds, close the tab" never fires it (verified) — and SIGTERM does `closeConnections()` + a direct per-room store (`flushAllRoomsToDatabase` — **not** `flushPendingStores()`, whose triggered store only reaches our queue after a microtask chain, so a synchronous sample sees an empty queue and the last debounce window is lost) + drains our own write queue. **No y-leveldb** (native module) and no `@hocuspocus/extension-database` (a thin wrapper over the same two hooks): persistence is only load/store, so it writes the existing Prisma tables. **Legacy migration is `onLoadDocument` itself** — a canvas whose `ydoc` is NULL gets its old `graph` JSON poured into the doc on first open, so there is no migration script and no downtime. `Flow.graph` survives as a **read-only projection** the server derives on write (list counts, thumbnails, future read-only previews); the editor never reads it. `FlowOperation` now stores the Yjs update bytes plus the `actorId` the server resolved at handshake — Yjs itself only knows `clientID`, so this table is the only place that knows *which user* made a change. Since content no longer passes through any REST route, validation moved here too: the quota (`server/collab/quota.ts` — limits derived from `GRAPH_LIMITS`: 1MB/message, 2MB/doc, 2000 nodes, 4000 edges) is measured in `onChange` and enforced in `beforeHandleMessage`, and it **can only refuse before applying**, because an applied-and-broadcast Yjs update is unrecallable. Refusal **never throws** — Hocuspocus closes the connection on a thrown message and the reconnecting provider resends the same message forever; it flips the connection `readOnly` instead (writes get NACKed, reads and awareness keep working). The quota is two-tier: over the *soft* limit only marks the room and still accepts writes (deleting is the only way to shrink back, and deletes are writes too — the mark clears once back under), the *hard* ceiling (soft × 1.25) locks the room read-only until it unloads; `onStoreDocument` prunes dangling edges (the legitimate product of one peer deleting a node while another connects to it) under a `'gc'` origin so the cleanup never enters anyone's undo stack. **Anything that mutates the graph must go through the store** — Vue Flow's own defaults will happily bypass it (`deleteKeyCode` under `applyDefault: true` edits its internal nodes/edges directly, so a deleted edge never synced or persisted). `FlowCanvas` passes `:delete-key-code="null"` and `canvas.deleteSelection()` is the single delete path.
- **Feedback layer — awareness carries who's here, where their cursor is, what they're dragging, and what line they're pulling.** `src/lib/presence.ts` is the pure, socket-free half (color hashing, defensive parsing of peer state, occupancy arbitration) and keys elements as `node:<id>` / `edge:<id>` so a third kind costs one `ElementKind` value. **The server rewrites the identity in every awareness update** (`beforeHandleAwareness` → `enforceIdentity`): clients may report any cursor/selection they like, but `user.id`/`name`/`avatarUrl` are replaced with what `onConnect` authenticated, so nobody can impersonate a teammate. Two more guards live on the same path: awareness entries are bound to the socket that first published their `clientID` (`dropForeignClients` — forged entries carrying a teammate's `clientID` are dropped, claims released on disconnect), and membership + session are **re-validated every minute** for live connections (`revalidateConnections`) — being removed from a project kicks an open WebSocket too, not just future handshakes. That sweep passes `{ refresh: false }`: it may only *read* the session, never renew it, or an open tab would keep its own session alive forever and idle timeout would stop meaning anything (renewal is the job of real requests — the handshake itself, then the edit-triggered user-state PATCH). **Occupancy arbitration exists and is tested but is deliberately not wired into the canvas right now** — anyone may edit anything concurrently and the CRDT merges it; the node label only *shows* who else is touching it. To reinstate the restriction, feed `presence.lockedKeys` back into the nodes'/edges' `draggable`/`selectable`/`updatable` in `useFlowCanvas`, and write those flags **explicitly as `true` as well as `false`** — Vue Flow merges node props with `Object.assign(existing, incoming)`, so a key you stop sending keeps its old `false` and the element stays dead after the lock lifts. See `docs/04-realtime-collab.md` §4.0.1.
- **Never rebuild the `:nodes` array while the local user is dragging.** Vue Flow decides whether to re-sync nodes by array *reference*, and a re-sync runs `Object.assign(existing, incoming)` — since drag intermediates deliberately never reach the Y.Doc, `incoming.position` is the pre-drag position and the node snaps back mid-gesture. Something always changes during a drag (this client is publishing its drag position to awareness, which recomputes every presence-derived value), so `useFlowCanvas` keeps a `localDragging` flag and returns `store.nodes` untouched while it's set. Mapping over the array is only safe when a *remote* peer is dragging.
- **Types are duplicated on purpose:** `server/store/flow-types.ts` (with `parseGraph`/`parseTransactions` validation) and `src/types/flow.ts` mirror each other, because `server/` and `src/` are separate TS projects. Change one, change the other.
- **`src/lib/api.ts`** wraps every endpoint over `apiFetch` and throws `ApiError` (carries `status`) on non-2xx — the store needs to tell 409 apart.

**3D:** Three.js is a dependency with types (`@types/three`). The `Cube3D.vue` component is pure CSS 3D transforms (not Three.js). The Three.js views (`Canvas3D`, `LightScene`) are placeholders.

**Backend (`server/`) — the single entry point:** Node + [Hono](https://hono.dev) + `@hono/node-server`, run through `tsx` (no build step). It serves the API, the Yjs WebSocket, *and* the frontend. Layout:
- `server/index.ts` — entry. Loads `.env`, `assertAuthConfig()`, builds the http server with `createAdaptorServer` (no `listen` yet), attaches collab + frontend, starts the hourly expired-session sweep, then listens. Handles SIGINT/SIGTERM cleanup, and `shutdown()` carries a re-entry guard because the two signals can arrive back to back
  - **In dev, the process that actually holds the port is a grandchild, so it also has to notice when it has been orphaned.** `pnpm dev` is four layers — `pnpm` → `sh -c` → `tsx watch` → `node server/index.ts` — and only the last one listens. Ctrl+C in a terminal signals the whole foreground process *group*, so all four get it; stopping the task from an IDE, killing the top-level pid, or closing the terminal tab reaches only the top layer or two, and the listener survives with the port still bound. It gets reparented to init and nothing ever kills it, so the *next* `pnpm dev` dies with `EADDRINUSE` — and since each failure leaves another one behind, they accumulate (found 29 of them once, the oldest three days old, plus one still holding live browser connections). `watchForOrphan()` therefore samples `process.ppid` every 2s and runs the normal `shutdown()` once it changes, so the Y.Doc still gets flushed on the way out. The timer is `unref()`'d — it is a sentinel, not a reason for the process to stay alive — and the check is dev-only (under an init system the server is PID-1-adjacent by design). This is *not* a bug in the shutdown path: a plain SIGTERM to the listener has always exited cleanly in about a second; the signal simply never reached it.
- `server/env.ts` — side-effect module: `process.loadEnvFile()` on the repo-root `.env` (real env vars win). Imported first by `config.ts` and `index.ts`; no dotenv dependency
- `server/runtime.ts` — `isBundle` / `moduleDir` / `appRoot`. `__APP_BUNDLE__` is defined by the esbuild build, so the bundle knows it is a bundle: the app root is then `process.cwd()` (the repo root locally, `/app` in the container) instead of `server/`'s parent
- `server/config.ts` — `rootDir` / `outputDir` / `staticDir` / `isDev` / `port` / `host` / `isApiPath()` / `dataDir` / `dbProvider` / `databaseUrl` / `ensureDatabaseDir()` / `appOrigin` / `authConfig` / `authEnabled` / `assertAuthConfig()` / `clusterMode` / `isClustered` / `redisUrl` / `redisKeyPrefix` / `instanceId` / `assertClusterConfig()`. `isDev` is `NODE_ENV !== 'production'`; `staticDir` defaults to `output/public` (next to the bundle when bundled) and `STATIC_DIR` overrides it
- `server/app.ts` — Hono app typed as `Hono<{ Bindings: HttpBindings; Variables: AuthVariables }>` (the frontend middleware needs node's raw `req`/`res` via `c.env`; the auth middleware puts `session`/`user` in `Variables`). Logger + CORS, `withSession` then a `requireAuth` gate on everything under `/api/*` except `PUBLIC_API` (`/api/health`, `/api/auth`), route mounting, 404/error handlers. Exports `AppType` for optional `hc<AppType>()` RPC typing on the frontend
- `server/db.ts` — the `PrismaClient` singleton (better-sqlite3 driver adapter, cached on `globalThis` so `tsx watch` doesn't leak connections)
- `server/auth/` — the OIDC/session layer (see below)
- `server/frontend/` — how the UI gets served (see below)
- `server/routes/` — one Hono sub-app per resource, mounted under `/api/*`. Routes are chained (`new Hono().get(...).post(...)`) so `AppType` stays inferable
- `server/store/` — data layer; routes never import `prisma`. `store/notes.ts` is still an in-memory `Map` (the API-shape sample); `store/projects.ts` and `store/flows.ts` are the real Prisma-backed ones. `store/flow-types.ts` holds the graph/op types plus `parseGraph`/`parseTransactions`; `store/text.ts` holds `nameContains()`, the one place that papers over a SQLite/PostgreSQL behaviour difference
- `server/auth/project.ts` — project-scoped authorization: `requireProjectMember` / `requireProjectAdmin` / `requireFlowMember`. **Non-members get 404, not 403** (don't leak existence); a member lacking the role gets 403. `currentUserId()` also mints a fixed local dev user when `authEnabled` is false, so the feature runs without a Keycloak
- `server/collab/` — Yjs collaboration over WebSocket (see below)
- `server/cluster/` — the single-replica / multi-replica switch (see below)
- `server/generated/prisma/` — generated Prisma client, gitignored; run `pnpm db:generate` after touching the schema
- `server/tsconfig.json` — separate TS project (Node types, no DOM), referenced from the root `tsconfig.json`. Imports inside `server/` use explicit `.ts` extensions

**Frontend hosting (`server/frontend/`):** `attachFrontend(app, server)` registers a catch-all *after* the `/api` routes, so API routes always win and everything else falls through to the UI.
- `frontend/guard.ts` — the page gate, mounted by `app.ts` right after the `/api` routes and therefore *before* the frontend catch-all. Anything non-`/api` other than `/login`, `/favicon.ico` and `/vite.svg` needs a session: a document request (`Sec-Fetch-Mode: navigate` or `Accept: text/html`) gets a 302 to `/login?redirect=<path>`, everything else (`/assets/*.js`, dev's `/src/**` and `/@vite/*`, XHR) gets a bare 401 — never HTML in place of a script. It also owns `GET /login`
- `frontend/login-page.ts` — the login page as a server-rendered HTML string: inline CSS, no `<script>`, no `/api` call, so it renders without a single byte of the SPA. Takes the sanitized `redirect` and the callback's `?error=` (HTML-escaped)
- `frontend/dev.ts` (dev only, dynamically imported so Vite never loads in prod) — `createServer({ root, appType: 'custom', server: { middlewareMode: true, hmr: { server } } })`. Vite's connect middleware chain is run against `c.env.incoming/outgoing` and the handler returns `RESPONSE_ALREADY_SENT`; if the chain calls `next()`, the SPA fallback renders `index.html` through `vite.transformIndexHtml`. `hmr.server` is what makes HMR ride the same port — with only `middlewareMode: {server}` Vite would still open port 24678
- `frontend/static.ts` (prod) — `serveStatic({ root: <staticDir relative to cwd> })` + `index.html` fallback for unknown paths
- `vite.config.ts` is still the config of record (plugins, `@/` alias) — it's read both by `vite build` and by the middleware-mode `createServer`. `build.outDir` is `output/public`, i.e. the frontend builds straight into the backend's static directory. It has no `server.proxy` anymore because there is nothing to proxy to

**Build (`scripts/build-server.mjs`) — `output/` is a self-contained, runnable app directory.** `pnpm build` fills it with `public/` (frontend, from `vite build`), `server/index.js` (backend, esbuild bundle, ESM/node22), `prisma/` (schema only — no migrations), and — copied verbatim from `scripts/output-image/` — `prisma.config.js`, `Dockerfile`, `.dockerignore`, `README.md`. Copy `output/` anywhere and `npm install --omit=dev && npm run db:push && npm start` runs it; `docker build ./output` images it. No repo source needed.
- `output/package.json` is generated: its `dependencies` are derived from esbuild's *external* list (metafile) — the 8 packages the bundle actually imports plus `prisma` for the startup `db push` — each pinned to the version installed at build time. `vite` is filtered out (`DEV_ONLY`) because it only appears in the never-loaded dev chunk. `node_modules` is deliberately not shipped: better-sqlite3 is native and must be built on the target platform.
- Relative imports are inlined, including the generated Prisma client, so no `prisma generate` in the image and no `tsx` at runtime.
- Two non-negotiables in the esbuild call: `splitting: true`, so `frontend/index.ts`'s `await import('./dev.ts')` stays a real dynamic import and `vite` never becomes a top-level static import (it is not installed in prod); and `define: { __APP_BUNDLE__: true }`, which is how `server/runtime.ts` tells bundle from source.

**Yjs 协同 (`server/collab/`):** the same HTTP server also serves a Yjs sync endpoint at `ws://host:3000/ws/<room>`; one room = one `Y.Doc`, held in memory only.
- `collab/hocuspocus.ts` — the collaboration server: [Hocuspocus](https://tiptap.dev/docs/hocuspocus) (`@hocuspocus/server`, MIT) mounted on our own HTTP server. We never call `listen()` (that would open a second port); instead we own the `upgrade` listener, take **only `/ws`**, and hand it to crossws, which calls `handleConnection()`. Everything else — notably Vite's HMR socket (`vite-hmr`, path `/`) — we simply don't touch, and Node's multi-listener `upgrade` event delivers it to Vite's own listener; crossws registers no listener of its own, so "don't touch" really means untouched. This replaced a 282-line port of y-websocket's `bin/utils.js` that existed only because upstream `@y/websocket-server` statically imports `y-leveldb` → `leveldown` (no node 22/arm64 prebuild). **The room name travels in the message, not the URL** — that's also why the wire protocol is incompatible with y-websocket and the frontend must use `@hocuspocus/provider`.
- `collab/index.ts` — `attachCollabServer(server, { destroyUnmatchedUpgrades, authorize })`: a `ws` server in `noServer` mode; only `/ws/*` upgrades are accepted, room name comes from the path. In dev `destroyUnmatchedUpgrades` is `false` — Vite's HMR socket rides the same `upgrade` event (protocol `vite-hmr`, path `/`) and killing unmatched sockets would break hot reload. `authorize` (wired to `auth/ws.ts`) checks the session cookie on the handshake and answers `401` + destroy when anonymous
- Env: `YWS_PING_TIMEOUT` (30s), `YWS_GC` (`false`/`0` disables Yjs gc — required if you use snapshots), `YWS_STATS_INTERVAL` (30s, `0` disables the stats log)
- `GET /api/collab/rooms` reports live rooms/connections
- Frontend: `new WebsocketProvider('/ws' as absolute ws:// URL, room, doc)` — docs stay in memory, so a server restart drops all content

**单副本 / 多副本 (`server/cluster/`) — one image, two modes, picked by env.** Full write-up in `docs/14-clustering.md`. `CLUSTER_MODE` (`single` | `redis`) resolves exactly like `dbProvider`: explicit variable wins, else infer from whether `REDIS_URL` is set, else the zero-dependency default. **Database and Redis are configured independently** — neither infers the other; `assertClusterConfig()` rejects `redis` without a `REDIS_URL` everywhere (contradictory config), but `redis` + SQLite only *warns* in dev, because SQLite + Redis in one process is a legitimate way to exercise the Redis path locally. Production refuses it.
- The state that used to be module-level `Map`s — audit `seq`, quota marks, awareness clientID ownership, session-refresh mutex — is now three abstract classes in `cluster/shared.ts`: `SharedMap<V>` (`get`/`set`/`claim`/`entries`, TTL), `SharedCounter` (`next(key, seed)`), `SharedLock` (`run(key, task, {fallback})`). Two implementations, `memory.ts` (literally the old `Map`s) and `redis.ts` (`SET NX` / `INCR` / lock+Lua-release), run the same contract test suite (`server/test/cluster/shared.test.ts` — memory always, Redis when `TEST_REDIS_URL` is set).
- **Every method is async even in the memory implementation** — otherwise wiring in Redis later would have meant changing every call site's signature. And **the factories return lazy proxies**: modules declare their tables at module top level (the way they used to write `new Map()`), but picking an implementation needs `await import('ioredis')`, which happens later in `initCluster()`. The proxy resolves against the current backend on first use, so swapping backends just bumps a generation counter.
- **`redis.ts` is dynamically imported**, like the two Prisma adapters in `db.ts` — a single-replica process never loads ioredis. Unlike the adapters, both packages stay in the built artifact: the image supports either mode, only the *database provider* is baked in at build time.
- Multi-replica collab is `@hocuspocus/extension-redis` (pub/sub for updates + awareness, redlock around `onStoreDocument` so only one instance actually writes, `afterLoadDocument` waits for a peer's in-memory state). **socketId gets an `instanceId:` prefix** — Hocuspocus's socketId is only unique within a process, and awareness ownership uses it to tell "is this clientID yours", so a collision would drop the rightful owner's updates as impersonation. No sticky session needed anywhere.
- **The same update fires `onChange` on *every* instance holding the room**, so anything writing per-update rows must filter on `transactionOrigin`: `shouldRecordUpdate()` skips `source === 'redis'`, or the audit table becomes a multiple of the replica count (measured: two instances, 11 edits, 22 rows) with `actorId: null` on the duplicates. Unknown origin shapes count as "record" — better one row too many than losing the author's. Same reasoning applies to any future per-update side effect (webhooks, notifications, metrics).
- **`FlowOperation.serverTs` is stamped when the update arrives**, not inside the write queue: the queue may have several writes ahead of it and, under multi-replica, a Redis round-trip for the sequence number — read the clock after that and you have recorded "when its turn came", not "when it arrived" (measured: rows with a higher `seq` but a lower `serverTs`). Cross-instance clock skew can't be fixed in app code, so **always order by `seq`**, which is globally monotonic.
- **Quota is deliberately eventually-consistent**: `quotaLocked()` is called *synchronously* on every message, so it reads a local `Map`; the verdict is pushed to the shared layer fire-and-forget and pulled back on the byte-remeasure tick (1–5s). That matches what the quota already was — after-the-fact accounting, effective on the *next* message — not a synchronous gate.
- Local: bring up Redis/PostgreSQL yourself (commands are in `.env.example`; the scripts deliberately don't), then `pnpm dev` (single) or `pnpm dev:cluster` (`scripts/dev-cluster.mjs` spawns one `tsx watch` per port from `DEV_CLUSTER_PORTS`, overriding only `PORT` and `INSTANCE_ID` — **it contains no configuration**, everything else comes from `.env`). k8s: `k8s/deployment.yaml` (single, PVC, `Recreate`) or `k8s/deployment.cluster.yaml` (`replicas: 3`, `RollingUpdate`, no PVC) — apply one or the other.

Frontend, `/api/*` and `/ws/*` are same-origin in every mode, so frontend code should always use relative paths.

**Auth (`server/auth/`) — Keycloak OIDC, BFF style.** Full write-up in `docs/02-auth-keycloak.md`. The browser never sees a token: the authorization-code + PKCE exchange happens server-side, tokens live in SQLite, and the client only holds an httpOnly `sid` cookie.
- `auth/oidc.ts` — everything that talks to Keycloak: cached `.well-known/openid-configuration` discovery (endpoints are never hard-coded), PKCE `S256` helpers, `exchangeCode` / `refreshTokens` / `revokeRefreshToken`, RP-initiated `buildLogoutUrl`, and `verifyIdToken` — JWKS fetch (kid miss → one refetch) + `crypto.createPublicKey({format:'jwk'})` signature check for RS/PS/ES, then `iss` / `aud` / `azp` / `exp` / `iat` / `nonce`. No `jose`/`openid-client` dependency
- `auth/session.ts` — session lifecycle. The cookie holds a 32-byte random token; the DB row id is `HMAC-SHA256(SESSION_SECRET, token)`, so a database dump alone can't forge a cookie. `loadSession()` transparently refreshes an access token that is within 30s of expiry (concurrent refreshes for one session are deduped through an in-process promise map), so **the session is kept alive by traffic** — it only really expires once nothing has hit the server for long enough that the refresh token passes Keycloak's SSO Session Idle. `loadSession(token, { refresh: false })` is the read-only variant for callers that are *not* user traffic — currently just the collab server's periodic connection revalidation: it answers "still valid right now?" (a live refresh token counts) without renewing anything, and never deletes a row. A long-lived WebSocket must not be able to keep its own session alive. A failed refresh is **not** uniformly fatal: only a 4xx rejection from Keycloak (`invalid_grant` — logged out, idled out, kicked) destroys the session. Anything that proves nothing — connection refused, timeout, a 5xx, even a local DB write failure — keeps the session and retries on the next request, with a 15s per-session cooldown so a dead Keycloak doesn't make every request eat a timeout. `OidcError` carries `code` + `retryable` to make that call, and every outbound OIDC request has an 8s timeout (node's fetch has none by default). Deleting the session in the network-failure case is the bug this replaced: with a 60s access-token lifespan the refresh runs constantly, so one blip logged the user out. `sweepExpired()` drops timed-out sessions and unused auth requests
- `auth/middleware.ts` — `withSession` (parse, refresh, expose `c.get('user')`, clear a stale cookie; mounted on `*`, not just `/api/*`, because the page gate needs it too), `requireAuth` (401), `requireRole(...)` (403). Keycloak realm roles land in `User.roles` as-is, client roles as `clientId:role`
- `auth/ws.ts` — the same session check for WebSocket handshakes
- `auth/redirect.ts` — `safeRedirect()`, the shared in-site-only check for every `?redirect=`
- `routes/auth.ts` — `GET /api/auth/{config,me,login,callback,logout}`. `/me` always answers 200 (`{enabled, authenticated, user}`) so the router guard has no error branch. `state`/`nonce`/`code_verifier` live in the `AuthRequest` table keyed by a short-lived `oidc_tx` cookie and are consumed exactly once, so a replayed callback fails. `?redirect=` is restricted to in-site paths (`//evil.com` and `/\evil.com` fall back to `/`)
- When `KEYCLOAK_ISSUER`/`KEYCLOAK_CLIENT_ID` are unset, `authEnabled` is `false`: dev warns and lets everything through (so the demo pages still run without a Keycloak), production refuses to boot
- **`auth/profile.ts` — what a user gets *after* login, kept outside the login path.** `upsertUser` does one thing: pour the id_token claims into a `User` row. "And now give this person a default avatar / display name / timezone" is a different, ever-growing concern, so it hangs off the side: `registerProfileHook({name, fill})` adds a rule, `completeUserProfile(user)` runs them all in the callback (and in `auth/project.ts`'s dev-user path, so the no-Keycloak local mode gets the same treatment). Each hook only answers "what's missing" and the mechanism merges the answers into **one** update; a hook that throws is logged and skipped — it must never block a login. **It runs on every login**, which is what backfills existing users: no migration script, and no fallback logic scattered across the read paths. Adding a rule = one new file + one `registerProfileHook`; login code stays untouched.
- **`server/avatar/` — the one hook there is today: no avatar → an identicon.** GitHub-style pixel blocks, generated by [minidenticons](https://github.com/laurentpayot/minidenticons) (MIT, dependency-free). Keycloak's `picture` always wins; the hook only fills the empty ones. **No image is stored**: the DB holds `/api/avatars/<seed>.svg` and `routes/avatars.ts` renders it on demand — no DB read, no notion of who's asking, so it's served `immutable` for a year. The seed is `sha256(issuer + "\n" + subject)` truncated to 16 hex — keyed on `(issuer, subject)` rather than `user.id` so the picture survives a rebuilt database, hashed so a subject never rides in an image URL. The route module is also what *installs* the hook (it imports `avatar/index.ts`), so mounting the route and having default avatars are the same one line in `app.ts`. Wherever a stored avatar is displayed, put a round background under it (`bg-muted` / `bg-sidebar-accent`) — the identicon is transparent-backed, and without it the blocks float on the page instead of sitting in the same circle the no-avatar fallback draws

**Database (`prisma/models.prisma`, SQLite *or* PostgreSQL):** `User` (unique on `(issuer, subject)`, roles as a JSON string), `Session`, `AuthRequest`; plus `Project`, `ProjectMember` (unique on `(projectId, userId)` — the creator's admin row is written for real, never inferred from `createdById`), `ProjectInvite` (the project's one share link — `projectId` is unique; token stored in the clear: it *is* the credential you hand out; unlimited uses, `expiresAt` is the only gate, and "reset" just swaps the token in place), `Flow` (`ydoc` = the Yjs state as bytes and **the source of truth for content**; `graph` = a JSON projection the server derives from it for list counts and previews; `revision` = a monotonic write counter, *not* a lock) and `FlowOperation` (append-only log of Yjs update bytes + the `actorId` the server resolved at handshake, unique on `(flowId, seq)`; `serverTs` is `BigInt` epoch-ms, not `DateTime`, see the time convention below — replaying them in seq order onto an empty doc reconstructs any point in time), and `FlowUserState` (per-user view state, unique on `(flowId, userId, key)` — one row per state partition, value is a JSON string; `viewport` is the first partition and adding another one is a new key, not a migration). Prisma 7 requires a driver adapter — `@prisma/adapter-better-sqlite3` or `@prisma/adapter-pg`, picked in `server/db.ts` — and the client is generated as TypeScript into `server/generated/prisma` (gitignored, `@ts-nocheck`'d, eslint-ignored) rather than into `node_modules`, so it survives `pnpm prune --prod` and gets inlined into the server bundle. `prisma.config.ts` is the CLI config and delegates to `prisma/db-provider.mjs` so the CLI and the server always open the same database: the DB lives at `$DATA_DIR/app.db` (`DATA_DIR` defaults to `<repo>/data`, gitignored), `DATABASE_URL` overrides it outright, and relative `file:` paths in either resolve against the repo root — not the cwd. Both sides `mkdir -p` the parent directory, since better-sqlite3 won't create it.

**Two databases, one model file (`docs/05-data-persistence.md`).** Which one you get is `DB_PROVIDER` (`sqlite` | `postgresql`), or — when unset — the scheme of `DATABASE_URL` (`file:` vs `postgres(ql)://`), defaulting to sqlite. A `DB_PROVIDER` that contradicts the URL's scheme, an unknown value, or `postgresql` with no `DATABASE_URL` all **throw at startup** rather than guessing. That resolution exists twice on purpose: `prisma/db-provider.mjs` (CLI side — `prisma.config.ts`, `scripts/*.mjs`) and `server/config.ts` (`dbProvider` / `databaseUrl`), because `server/` is a separate TS project that can't import a repo-root `.mjs`. Change one, change the other.
- **One copy of the models, two provider dirs — via multi-file schema + a symlink.** Two schemas are unavoidable: `datasource.provider` takes only a literal (`env()` is rejected, the 2.2-era `provider = [...]` array was deprecated, and "make it dynamic" is closed upstream), and one schema can hold only one datasource. But the *models* live once: `prisma/models/{auth,canvas}.prisma` are the only hand-written model files, and `prisma/sqlite/` + `prisma/postgresql/` each contain a 10-line `schema.prisma` (generator + datasource) plus a **`models` symlink pointing at `../models`**. `prisma.config.ts` points `schema` at the *directory*, and Prisma's multi-file schema merges everything in it — so the only difference between the two providers is one `provider = "…"` line. No generated schema files, therefore no drift and no guard script. Notes: Prisma 7 forbids `url` inside a datasource (it lives in `prisma.config.ts`), which is why the block is down to one line; the `generator` must sit in the directory's own `schema.prisma`, so those 4 lines are duplicated; **keep the models provider-agnostic** (no `@db.*` native types, arrays, `Json`, enums) so the two generated clients stay type-identical and business code never forks. **This depends on symlinks** — no native Windows (use a dev container / WSL); `COPY prisma ./prisma` preserves the relative link (verified inside a container), but `scripts/build-server.mjs` copies with `dereference: true` so the *artifact* gets real files, and `scripts/output-image/prisma.config.js` must point `schema` at the **directory** too — pointing it at `prisma/schema.prisma` makes Prisma read that one file, see zero models, and conclude "schema empty, database empty, already in sync", producing a **0-byte database with no tables** (hit this once).
- **There are no migration files.** Schema changes go in via `prisma db push` — no `prisma/migrations/`, no `_prisma_migrations` table, no `migrations` key in `prisma.config.ts`. Dev, tests and the container all take the same path: `pnpm dev` runs `db:push` first, and the image's `CMD` is `npx prisma db push && node server/index.js`. The reason migrations were dropped: they would have to be written **twice**, and not as a wording difference — `migration.sql` is plain DDL generated per provider with no runtime translation, each directory's `migration_lock.toml` pins its provider so the two histories can never merge, and the dialects genuinely differ (`BLOB`/`BYTEA`, `DATETIME`/`TIMESTAMP(3)`, inline foreign keys vs a separate `ALTER TABLE ADD CONSTRAINT`). Worst of all, **SQLite cannot alter or drop a column**: a "drop 5 columns, add 1" change is one `ALTER TABLE` on PG but a full table rebuild on SQLite (`new_` table → copy → `DROP` → `RENAME`). That double bookkeeping only pays for itself when there is production data to carry forward, and there isn't. **The costs, which are real**: no history of schema changes and no rollback scripts; and a destructive change (rename/retype/drop) makes `db push` refuse unless `--accept-data-loss` is passed. Both Dockerfiles and the artifact's `db:push` script deliberately omit that flag — better a failed container start than silent data loss — so assess whether a model change is destructive *before* shipping it. Prisma 7's `db push` does not generate the client (and has no `--skip-generate`), so `db:generate` stays a separate step.
- **The one behavioural difference that needed code**: SQLite's `LIKE` is case-insensitive for ASCII, PostgreSQL's isn't. `server/store/text.ts`'s `nameContains()` adds `mode: 'insensitive'` on PG only (the type assertion in there is load-bearing — `mode` doesn't exist in the sqlite client's `StringFilter`). Any new keyword search goes through it instead of writing `{ contains }` inline.
- **A build artifact is bound to one provider**: the generated client compiles in one query engine, so `pnpm build` follows the build-time `DB_PROVIDER`, `build:server` refuses to run if the generated client disagrees, and the unused adapter is dropped from `output/package.json` (which is why `server/db.ts` imports both adapters *dynamically* — a static import would survive as a top-level require of a package prod never installs).

**Deploy:** two paths to the same image. `pnpm build && docker build ./output` uses the Dockerfile the build drops into `output/` (deps stage: `npm install --omit=dev` off `output/package.json`, compiling better-sqlite3; runtime stage: those `node_modules` + the artifact, `WORKDIR /app`, `prisma db push` then `node server/index.js`). The repo-root `Dockerfile` is the from-source variant: a build stage that runs `pnpm build`, then the exact same deps + runtime stages over `/app/output` — keep the two in sync (edit `scripts/output-image/Dockerfile`, not `output/`). Only the deps stage runs on the target platform, so better-sqlite3 compiles for the right arch. `NODE_ENV=production`, `HOST=0.0.0.0`, port 3000; no source, no pnpm, no tsx in the runtime image. nginx is gone — the Node server serves `public/` itself. The build stage installs `python3 make g++` because better-sqlite3 has no musl prebuild. SQLite lives on a volume at `/app/data` (`DATA_DIR=/app/data`); `k8s/deployment.yaml` adds a PVC + auth Secret, targets container port 3000, probes `/api/health`, and stays at `replicas: 1` with `strategy: Recreate`. A PostgreSQL image is the same two commands with `DB_PROVIDER=postgresql` set for both `db:generate` and `build` (see the database section — the artifact is provider-bound); on the k8s side that drops the PVC and moves `DATABASE_URL` into the Secret. Going past one replica additionally needs `CLUSTER_MODE=redis` + `REDIS_URL` — that's `k8s/deployment.cluster.yaml` (`replicas: 3`, `RollingUpdate`), see the cluster section above. The *image* is mode-agnostic; only the database provider is baked in.

**Tests (Vitest, `vitest.config.ts`):** two projects in one config — `server` (node env, `server/test/**/*.test.ts`) and `client` (jsdom env + the `vue` plugin and `@/` alias, `src/test/**/*.test.ts`). Both are hermetic: each setup file replaces `globalThis.fetch` with a stub that *rejects*, so any test needing the network must `vi.stubGlobal('fetch', …)` — nothing ever reaches a real Keycloak.
- **Backend.** `server/test/global-setup.ts` wipes `data/test/` and runs the real `prisma db push` against it once per run, so the test schema is built the exact same way production's is; `fileParallelism: false` keeps the shared database safe. Point `TEST_DATABASE_URL` at a PostgreSQL connection string and the same suite runs there instead (`server/test/paths.ts` derives the provider from it) — the PG branch adds `--accept-data-loss` (it can't delete a file, so db push has to be allowed to drop mismatched tables/columns), which is why it must be a dedicated test database — SQLite doesn't need the flag since the whole directory is deleted each run. Since the generated client is provider-bound, global-setup compares its `activeProvider` and re-runs `generate` only when it doesn't match. Environment comes entirely from `test.env` in `vitest.config.ts`, and `server/env.ts` is aliased to `server/test/stubs/env.ts` so the developer's own `.env` (real issuer, real client secret) can never leak into a test run. Helpers: `helpers/db.ts` (`resetDb`, `createUser`), `helpers/session.ts` (`signIn` → a ready-to-use `sid` cookie), `helpers/project.ts` (`actor()` → a logged-in browser with `request`/`json` bound to its cookie, plus `createProject` / `createFlow` / `joinViaInvite`), `helpers/oidc.ts` (a fake Keycloak: discovery/JWKS/token/end_session over a stubbed `fetch`, plus a real RSA keypair so `verifyIdToken` is exercised for real). Routes are driven through `app.request()` — the full middleware stack, not mocked handlers.
- **Module-level caches.** `config.ts` (env → consts), `oidc.ts` (10-min discovery/JWKS cache) and `lib/auth.ts` (session singleton) all freeze state at import, so tests that need a different world use `vi.resetModules()` + a dynamic `import()`. `server/test/routes/auth.test.ts` has a `freshApp()` helper for exactly this.
- **Frontend.** `src/test/` covers `lib/utils`, `lib/auth` (the whole `fetchSession`/`apiFetch` contract), the `prompt-input` editor core (`serialize` round-trips + `operations` transforms/undo/batch/muteHistory) and the component itself (`PromptInput.test.ts`: one `<div data-block-path>` per line, the `FEFF`+`<br>` zero-width invariant, and `repairLeafPlaceholders` healing a DOM the browser broke), the real router guard (`@/router` with `/api/auth/me` stubbed), the router guard's full-page bounce to `/login`, and `stores/flow` (`flow.test.ts`: the Y.Doc projection — writes land in the doc, a second `Y.Doc` stands in for a peer so concurrent edits to *different fields of the same node* are shown to merge, undo is proven to skip the peer's changes, and the viewport is proven not to enter the doc; `presence.test.ts`: the pure occupancy/arbitration logic without a socket). `server/test/frontend/guard.test.ts` covers the page gate itself (302 vs 401, the rendered login page, escaping).
- **Component tests** (`src/test/views/`, `@vue/test-utils` + jsdom) mount the real view with only `@/lib/api` stubbed — shadcn-vue and reka-ui run for real, because that's where "clicked it, nothing happened" bugs live. `ProjectHome.test.ts` pins the confirm dialogs: **`AlertDialogAction` closes the dialog *before* the forwarded `@click` runs**, so a confirm dialog needs two refs — one for `open`, one for "which item" — or the handler reads a target that close already cleared and the request is silently never sent. In jsdom: menus/dialogs teleport into `document.body` (not the wrapper), `DropdownMenuTrigger` opens on `click` while `TabsTrigger` switches on `mousedown`, and `PointerEvent` + pointer-capture need stubbing.

**Dependencies — `dependencies` is exactly the production runtime set, everything else is `devDependencies`.** The frontend is bundled into `output/public` and the backend into `output/server/index.js`, so vue/three/tailwind/reka-ui/`@hocuspocus/provider`/`y-protocols`/`lib0` and the whole toolchain (`vite`, `esbuild`, `tsx`, `vue-tsc`, eslint, vitest) are build-time only. `dependencies` holds just the packages the server bundle still needs at runtime: `hono` + `@hono/node-server`, `@hocuspocus/server` + `crossws` + `yjs` (collab server — crossws vendors its own `ws`, so we no longer depend on it directly), `@prisma/client` + both driver adapters (`@prisma/adapter-better-sqlite3`, `@prisma/adapter-pg` — the repo needs both, any one build artifact keeps only one), `ioredis` + `@hocuspocus/extension-redis` (multi-replica mode; both stay in the artifact because the mode is an env switch, not a build flag), `minidenticons` (default avatars are rendered per request, so it is runtime, not build-time), and the `prisma` CLI (the container runs `prisma db push` at startup). `scripts/build-server.mjs` enforces this: if a package the bundle imports is only in `devDependencies`, the build fails. So when a tool (e.g. the `shadcn-vue` CLI) adds a frontend package to `dependencies`, move it to `devDependencies`.

**Key libraries:** `reka-ui` (headless UI primitives behind shadcn-vue), `@vueuse/core`, `class-variance-authority`, `vue-router` 5, `pinia` (only the flow editor's store) and `vue-sonner` (toasts) on the frontend; `hono` on the backend; `vite` for dev middleware + the frontend build; `tsx` only for `pnpm dev`.

## Conventions

- TypeScript strict mode with `noUnusedLocals`, `noUnusedParameters`, `erasableSyntaxOnly`
- All Vue components use `<script setup lang="ts">`
- Package manager: pnpm. New packages go to `devDependencies` unless the *server* imports them at runtime (see the dependency split above)
- Tests live in `server/test/` and `src/test/`, mirroring the directory they cover (`server/test/routes/auth.test.ts` ↔ `server/routes/auth.ts`). Imports inside `server/test/` keep the explicit `.ts` extension like the rest of `server/`.
- Vitest globals are **not** enabled — import `describe`/`it`/`expect`/`vi` from `vitest` explicitly.
- Test names are written as the behaviour being constrained ("未登录 → 401"), not as the function being called.
- **Time is UTC everywhere except on screen.** Prisma stores `DateTime` as an epoch value (UTC by construction) and every store maps rows out through `toISOString()`, so the wire format is always an ISO string with `Z` — never a pre-formatted, timezone-less string. The frontend never formats a date inline: `src/lib/format.ts` is the only place that builds an `Intl.DateTimeFormat`, and by default it follows the browser (`navigator.languages` for the locale, the runtime default for the timezone) rather than a hard-coded `zh-CN`. Use `formatDateTime` / `formatDate` / `formatTime`, or `formatWith(value, options)` for another granularity; all four take a string/number/`Date`/null and render `-` for anything unparseable.
  - **What "follows the browser" means is now a preference, not a constant** — `src/lib/preferences.ts` (a `useStorage` under `app:display-preferences`, browser-local, never sent to the server) holds locale / timeZone / dateStyle / timeStyle / hourCycle, every one of them defaulting to `AUTO` = follow the browser, which is why turning the setting page on changed nothing about existing output. `format.ts` reads the **reactive** `resolvedDisplayPreferences`, so changing a setting re-renders every already-displayed date with no reload and no per-page wiring. Two rules: a **caller-supplied option always wins** (`formatWith(v, { timeZone: "UTC" })` stays UTC no matter the preference — the preference only fills in what the caller didn't say), and the stored value is **validated on read** against a whitelist (localStorage is user-editable, and a misspelled `dateStyle` makes `Intl` throw `RangeError` and takes the page down). The UI is `src/views/Settings.vue`.
- **On the canvas's own path, time is a *number* — UTC epoch milliseconds, not an ISO string.** `FlowOperation.serverTs` is a `BigInt` (`Number()`-ed at the store's exit; epoch ms is well inside 2^53). Numbers compare directly with no timezone, format, or parse step in between. The client's clock is never involved: the timestamp is stamped server-side the moment the update arrives (deliberately *before* it enters the write queue — see the cluster section). **Ordering is `seq`, not `serverTs`** — under multi-replica, two instances stamp from two clocks.
- **One click, one request — every write-side interaction goes through `src/composables/useAsyncAction.ts`.** `const { run, pending } = useAsyncAction(fn, { errorMessage })`: `run()` records the action as pending **synchronously**, before the request is even sent, so a second click in the same event-loop turn is dropped on the spot; the template binds `pending` for the visual half (`<Button :loading="pending">`). The guard has to live in the handler, not in the markup — `:disabled` only takes effect on the next render, and half the entry points (`@keydown.enter`, `DropdownMenuItem @select`, an `@blur` that fires alongside an Enter-submit, `AlertDialogAction`) have no button to disable at all. `run` never rejects, so `@click="submit()"` leaves no unhandled rejection; errors go to `toast.error(err.message ?? errorMessage)` unless `onError` is given, which is why the wrapped action bodies carry no `try/catch`. Lists pass `key: (item) => item.id` so each row locks on its own. **Write `@click="submit()"`, not `@click="submit"`** — the latter hands the MouseEvent to the action as its first argument. Reads are deliberately *not* in scope: dropping a duplicate list load would strand the list on stale parameters.
- **Client-generated ids go through `src/lib/id.ts`'s `createId(prefix)`** — `<prefix>_<base36 timestamp>_<random>`. The timestamp prefix keeps ids roughly sortable by creation; the random tail is the part that matters: two clients can add a node in the same millisecond, and a counter-based suffix (`nodes.length`) would hand both the same id and merge them into one object on sync.
