**Tests (Vitest):** three projects, **one config file per package plus an aggregator at the root** — `apps/server/vitest.config.ts` (project `server`, node env, `apps/server/test/**/*.test.ts`), `apps/web/vitest.config.ts` (project `client`, jsdom env + the `vue` plugin and `@/` alias, `apps/web/src/test/**/*.test.ts`) and `packages/shared/vitest.config.ts` (project `shared`, node env, `packages/shared/test/**`: the pure contract — `flow-graph` upgrade/parse, the `flow-doc` Y.Doc shape, `collab` constants). The root `vitest.config.ts` only lists the three in `projects` and holds coverage; `pnpm test:shared` is `--project=shared`. Server and client are hermetic: each setup file replaces `globalThis.fetch` with a stub that *rejects*, so any test needing the network must `vi.stubGlobal('fetch', …)` — nothing ever reaches a real Keycloak.
- **Backend.** `apps/server/test/global-setup.ts` wipes `data/test/` (at the repo root) and runs the real schema-sync CLI (`tsx db/sync-cli.ts`, cwd `apps/server`) against it once per run, so the test schema is built the exact same way production's is; it runs in a **child process** because the CLI reads the repo-root `.env`, and reading it in Vitest's main process would leak the developer's config (real Keycloak, GitHub) into every worker. `fileParallelism: false` keeps the shared database safe. Point `TEST_DATABASE_URL` at a PostgreSQL connection string and the same suite runs there instead (`apps/server/test/paths.ts` derives the provider from it; it finds the repo root by going **three levels up** from `apps/server/test/`) — the PG branch passes `--reset` (it can't delete a file, so it drops every entity table first and then does a full sync that also drops non-entity tables), which is why it must be a dedicated test database. There is no generate step and nothing provider-bound to switch back and forth any more. Environment comes entirely from `test.env` in `apps/server/vitest.config.ts`, and `apps/server/env.ts` is aliased to `apps/server/test/stubs/env.ts` so the developer's own `.env` (real issuer, real client secret) can never leak into a test run.
- **`TEST_*` is the one exception, and `apps/server/test/paths.ts` has to read `.env` itself to honour it.** (With `TEST_DATABASE_URL` in `.env`, run the SQLite suite as `TEST_DATABASE_URL= pnpm test:server` — an empty value counts as set and `loadEnvFile` won't override it.) Vitest only loads `.env` *after* the config is resolved, but `apps/server/vitest.config.ts` imports `paths.ts` at the top level — so a `TEST_DATABASE_URL` written into `.env` is read too late and the whole run silently stays on SQLite (tables appear in `data/test/app.db`, the PG database you thought you were testing keeps zero relations). `loadTestEnv()` therefore calls `process.loadEnvFile()` on the repo-root `.env` and then **deletes every key it introduced that isn't `TEST_`-prefixed**, so the isolation above still holds; `loadEnvFile` doesn't overwrite existing variables, so a command-line `TEST_DATABASE_URL=… pnpm test:server` still wins.
- **The GitHub provider is deliberately *not* in the global `test.env`** — a config that only has Keycloak is what keeps assertions like "the login page has one button" meaningful. `apps/server/test/routes/auth-github.test.ts` builds a GitHub-enabled app per test with `vi.stubEnv` + `vi.resetModules()` + a dynamic `import`, which is also why the one "GitHub is not configured" case has to call `vi.resetModules()` itself: without it the dynamic import returns the previous test's already-built module graph and the env no longer matters. Helpers: `helpers/db.ts` (`db`/`orm` re-exported for direct assertions, `resetDb` — `nativeDelete` per table, children first — and `createUser` — the users it makes have no `UserIdentity` row, which is exactly the legacy-user shape the backfill path is tested against), `helpers/session.ts` (`signIn` → a ready-to-use `sid` cookie), `helpers/github.ts` (a fake GitHub: token endpoint + `/user` + `/user/emails` over a stubbed `fetch`), `helpers/project.ts` (`actor()` → a logged-in browser with `request`/`json` bound to its cookie, plus `createProject` / `createFlow` / `joinViaInvite`), `helpers/oidc.ts` (a fake Keycloak: discovery/JWKS/token/end_session over a stubbed `fetch`, plus a real RSA keypair so `verifyIdToken` is exercised for real). Routes are driven through `app.request()` — the full middleware stack, not mocked handlers.
- **Module-level caches.** `config.ts` (env → consts), `oidc.ts` (10-min discovery/JWKS cache) and `lib/auth.ts` (session singleton) all freeze state at import, so tests that need a different world use `vi.resetModules()` + a dynamic `import()`. `apps/server/test/routes/auth.test.ts` has a `freshApp()` helper for exactly this.
- **Frontend.** `apps/web/src/test/` covers `lib/utils`, `lib/auth` (the whole `fetchSession`/`apiFetch` contract), the `prompt-input` editor core (`serialize` round-trips + `operations` transforms/undo/batch/muteHistory) and the component itself (`PromptInput.test.ts`: one `<div data-block-path>` per line, the `FEFF`+`<br>` zero-width invariant, and `repairLeafPlaceholders` healing a DOM the browser broke), the real router guard (`@/router` with `/api/auth/me` stubbed), the router guard's full-page bounce to `/login`, and `stores/flow` (`flow.test.ts`: the Y.Doc projection — writes land in the doc, a second `Y.Doc` stands in for a peer so concurrent edits to *different fields of the same node* are shown to merge, undo is proven to skip the peer's changes, and the viewport is proven not to enter the doc; `presence.test.ts`: the pure occupancy/arbitration logic without a socket). `apps/server/test/frontend/guard.test.ts` covers the page gate itself (302 vs 401, the rendered login page, escaping). `apps/web/src/test/lib/sharedYjs.test.ts` and `apps/server/test/collab/shared-yjs.test.ts` pin the single-yjs-copy `instanceof` guarantee of `@shadecn/shared` from each side.
- **Component tests** (`apps/web/src/test/views/`, `@vue/test-utils` + jsdom) mount the real view with only `@/lib/api` stubbed — shadcn-vue and reka-ui run for real, because that's where "clicked it, nothing happened" bugs live. `ProjectHome.test.ts` pins the confirm dialogs: **`AlertDialogAction` closes the dialog *before* the forwarded `@click` runs**, so a confirm dialog needs two refs — one for `open`, one for "which item" — or the handler reads a target that close already cleared and the request is silently never sent. **`@click.prevent` does not stop it**: `DialogClose` calls `onOpenChange(false)` unconditionally and never looks at `event.defaultPrevented`, so reaching for `.prevent` only hides the fact that the two refs are still missing (`ProgressDialog.vue` shipped exactly that and deleted nothing). **A confirm that must stay open — anything multi-step — cannot use `AlertDialogAction` at all**: use a plain `Button` and close the dialog from code. `ModelConfig.vue`'s delete is two-stage (the first call omits `force`; the engine answers 409 *naming who still points at it*, and that sentence has to stay on screen for the "delete anyway" decision) — with `AlertDialogAction` the dialog is already gone by the time the 409 comes back, so there is nowhere left to show it. `GalStoryModelConfig.test.ts` and `GalStoryProgressDialog.test.ts` pin both halves. In jsdom: menus/dialogs teleport into `document.body` (not the wrapper), `DropdownMenuTrigger` opens on `click` while `TabsTrigger` switches on `mousedown`, and `PointerEvent` + pointer-capture need stubbing.
