**Projects & canvases (REQ-CANVAS, `docs/13-flow-canvas-management.md`)** — the one non-demo feature. A **project** owns canvases and is the permission boundary; the only way in is its share link — one per project, unlimited uses, admins open the 分享 dialog and the link is already there (`GET /api/projects/:id/invite` creates it on read). Four views in `apps/web/src/views/canvas/`, the first two wrapped in one workspace shell (**`components/canvas/CanvasWorkspace.vue`**: an in-page second-level sidebar, `w-56`, whose first item is 「个人画布」 and below it a 「项目」 group — a `+` button on the group header opens the new-project dialog, each project row shows a hover `Trash2` (admins only) that goes through an `AlertDialog` with two refs; the app sidebar has a single「画布」 entry → `/personal`, highlighted under `/personal` and `/projects/*` via `NavItem.activePaths`; `/projects` itself is only a `redirect` to `/personal` for old bookmarks, there is no project-list page any more). The project list lives in a **module-level cache**, `composables/useProjectNav.ts` (`projects / loading / error / refresh()`, first use loads, `resetProjectNav()` for tests), because the two pages are separate route components and the shell remounts on every switch — a per-component list would flash a skeleton each time; create / delete / rename call `refresh()`. `PersonalFlows.vue` (`/personal` — see REQ-SOLO below), `ProjectHome.vue` (`/projects/:projectId`, one route, same-page Tabs for 画布 / 成员 — switching tabs never touches the URL), `InviteAccept.vue` (`/invite/:token`, preview-then-confirm; anonymous visitors get bounced through `/login` by the page guard and land back here), and `FlowEditor.vue` (`/flows/:flowId`, the one route under `BlankLayout`).
- **The editor is split into a hooks layer and a component layer — the view itself only builds the context and places components.** `provideFlowEditor(props)` (in `apps/web/src/composables/flow/`) creates the shared payload once and `provide`s it; every child pulls it with `useFlowEditor()`, so there is no prop drilling and adding a panel touches no existing file. The context bundles `store` + `sync` (`useFlowSync`, see below) + three composables: `useFlowDocument` (load / rename / duplicate / delete / save-state text / `flushBeforeLeave`), `useFlowCanvas` (the Vue Flow glue: `nodes`/`edges` bindings, drag→`node.move`, connect→`edge.add`, viewport sync, cursor-anchored ctrl-wheel zoom, `addNode`), and `useFlowSelection` (just `selectedNodeId` + `select` / `clearSelection`), plus `nodeKit` (the node-kit runtime — registry, mode state, action runner — which `provideFlowEditor` also provides for the node hosts; it rides the context because the root component can't `inject` what it provided itself). `useFlowShortcuts(ctx)` adds the keybindings (its own global keys first, then the single-selected node's action shortcuts) and the two don't-lose-work guards. Note `useVueFlow()` is called inside `useFlowCanvas` at the *root* setup, so the later `<VueFlow>` adopts that instance and out-of-canvas components (toolbar, capsule) can still use `screenToFlowCoordinate`.
- **Node types are a registry, not a hardcoded map — `apps/web/src/components/flow/node-types.ts`.** One entry per `type` (`defineNodeType(type, {label, icon, view, features?, parts?, modes?})`) joins the render half — menu label, icon, **`view`** (what it looks like: `body` component, `shell: 'card' | 'frame'`, size `class`, `selectedClass` / `idleClass`, `style(ctx)`, `fallbackLabel`) and **`features`** (which capabilities it enables, *by name*, default `STANDARD_NODE_FEATURES` = rename / duplicate / delete / connectable / status) — to the data half from `@shadecn/shared/flow-node-types` — default `data`, default layout and **port declarations** (`inputs`/`outputs: PortDef[]` — never rendered as extra handles; a type that declares none keeps the single unnamed in/out handle pair, one that declares no inputs loses its left handle). **There is no per-type component**: `flowNodeComponents` maps every type to the one host, `node-kit/NodeHost.vue`, which reads the type's `view` and capabilities from the node-kit registry (next bullet). `useFlowCanvas.addNode(type)` builds the node from the registry (`buildFlowNode`). **Adding a node type touches this file plus the shared entry** and nothing else; the seven port-carrying sample types share `GenericBody.vue` (via `genericType()`, which also enables `output-preview`; the three generators add `runnable`). The toolbar does *not* render one button per entry — types will keep piling up and a row of icons is neither recognisable nor affordable, so the add entry is a single `+` that opens a type menu (`ADDABLE_NODE_TYPES` in `node-types.ts`: every registered type except `group`, label + icon from the registry). `NEW_NODE_TYPE` is what gets created when no type is given — `addNode()`'s default and nodes grown from a port-less node (currently `text`, whose `TextBody` is edited in place on double-click via the `edit-body` capability; `data.text` is its own key, so retitling and rewriting merge per key). That constant is separate from `FALLBACK_NODE_TYPE` (`process`, what an unrecognised `type` renders as — it is the **same constant** `fromYNode` falls back to — defined in `@shadecn/shared/flow-graph`, re-exported from `node-constants.ts` — so the two cannot drift and change the shape of old canvases). `group` is the proof that entries need not resemble each other, and **every difference is in its declaration, none in the host**: `shell: 'frame'`, fixed size, `zIndex: -1` (a background board must paint under every node), `pointer-events-none` in its `view.class` so it doesn't swallow rubber-band selection over the area it covers, background from `data.background` through `view.style`, and features `rename` / `status` / `ungroup` / `resizable` / `drag-strip` — no `connectable`, `duplicate` or `delete`. Resizing is the official `@vue-flow/node-resizer` (its stylesheet is imported in `apps/web/src/styles/vue-flow.css`, or the handles are invisible — and that stylesheet declares no `pointer-events`, so the same file has to hand `.vue-flow__resize-control` its events back or the handles inherit the body's `none` and resizing is silently dead), committed to the doc only on `resize-end` — mid-resize frames are intermediates, exactly like drag. **Its chrome is the same as any other node's**: the name sits *outside*, above the top-left corner, and the toolbar floats top-center — a group used to carry its name inside a title bar, which made it read as a different kind of object when it is just a node with a different body. Its one toolbar button is **ungroup**, not delete — `Ungroup` icon, plain ghost, no destructive red: removing the frame loses nothing and undo brings it back, so both a bin icon and the red would be claiming otherwise. The one thing that can't move out with the label: **dragging**. `NodeToolbar` teleports to the viewport container, so pressing the label never reaches the node's d3-drag — a group therefore keeps a full-width, 24px grab strip inside its own top edge (`drag-strip`, invisible until hover), which is also why a rubber band can't be *started* from that band. Removing a group **detaches its children instead of deleting them** (which is why the button reads as ungroup) (`store.removeElements` clears `parentNode`/`extent` and converts each child's parent-relative position back to canvas coordinates — leave the dangling `parentNode` and the whole group snaps to the origin). Dragging a node *into* an existing group (auto-reparent) is still not wired; the data path is.
- **Node UI is composed from flat registrations, not a component hierarchy — `apps/web/src/components/flow/node-kit/` (REQ-NODEKIT, `docs/21-node-kit.md`).** Four open registries — **parts** (a component mounted in a slot), **actions** (a tool button: icon + label + `run` + `when`/`enabled` + optional `shortcut`), **modes** (an edit state that can `reveal`/`conceal` slots) and **event handlers** — bundled into **features** (`rename`, `duplicate`, `delete`, `connectable`, `status`, `edit-body`, `ungroup`, `resizable`, `drag-strip`, `output-preview`, `runnable`, in `node-kit/features/`) that a type enables by name. **Slots are a closed set owned by the host** (`label` `toolbar` `badge` `header` `body` `footer` `composer` `side` `overlay` `handles`): where a slot sits and *when it may show* is geometry, so only `NodeHost` decides it, and a part's `when` can only narrow that, never widen it. Matching is static per type (`match: {types, features, not}`), so `kit.partsFor(type, slot)` is cached; `replaces` / `hides` name what they displace — there is no implicit priority. Rules that are a bug to break: **features never import each other** — they cooperate only through events and the shared context (the composer emits `composer:submit`, `runnable` turns it into `node:run`, neither knows the other exists); **`protocol.ts` is a type-only leaf** and **only `install.ts` lists the features** (it imports node components, so nothing a node imports may import it — same cycle rule as `editor-context.ts`); **the host knows no concrete type or feature** (no `if (type === 'group')`, no `has('runnable')` branching). Parts take **no props** — they `useNodePart()` for a `NodePartContext` (`id` / `type` / `node` = `useFlowNode` / `label` / `editor` / `selected` / `mode` / `slots` / `emit`), because half of them are teleported by `NodeToolbar`. **A slot with nothing registered for that type does not exist on that node** — the host mounts no `NodeToolbar` for it, so e.g. only `image-config` has a bottom composer (registered through its declaration's `parts` / `modes`, not as a feature, because what goes in a composer varies by type). Events are a typed editor-level bus (`FlowNodeEventMap`, extended by **module augmentation** in each feature's own file; no naming rule is enforced): synchronous broadcast, each handler try/catch'd so one throw never reaches the emitter or the others, depth-capped against ping-pong, and **never a write channel** — handlers still write through `ctx.node.write` / `store.mutate`. **Only one node in the whole canvas is editable at a time**: the mode state is one editor-level value (`node-kit/modes.ts`), entering a mode preempts the previous one, and selecting another node preempts too — `'preempted'` commits the draft (same as blur), only `'cancel'` (Esc) drops it; a part whose overlay unmounts mid-edit must commit on unmount. Actions run through one editor-level runner (`node-kit/actions.ts`, `useAsyncAction` keyed by node × action, emitting `action:invoke` / `action:done`) shared by the buttons and the keyboard: `useFlowShortcuts` handles its own global keys first, then hands the key to the **single-selected** node's visible actions (`Mod` = Meta or Ctrl, exact modifier match; a disabled match is swallowed, not run). Presence avatars are the one part built into the host — every node shows them, no type can turn them off. The registry is not a module singleton: `createNodeKit()` / `createNodeKitRuntime()` give tests a clean one, and `apps/web/src/test/components/node-kit/with-kit.ts` provides the default kit for mounting `NodeHost` directly.
- **The rubber band is full-containment, edges follow their endpoints, and nothing but the highlight moves while it's being dragged.** `:selection-mode="SelectionMode.Full"` (Vue Flow's default, written out because it's a product rule: clip a corner and you'd select every node the band sweeps past). Nodes flip highlight one by one as the band grows — that's live already, since Vue Flow applies selection changes internally on every pointermove. Edges connected to a hit node count as selected, but Vue Flow's own pass **can't be relied on**: it diffs against the previous frame's edge-id set, and `removeSelectedElements()` on pointerdown clears the elements without clearing that cache — so two box selections in a row that hit the same edge leave it unselected the second time. `useFlowCanvas` therefore re-asserts the rule itself (`getConnectedEdges` → `addSelectedElements([...nodes, ...edges])` — pass the nodes too, that action means "the selection is exactly this"), and only **while the band is active**: clicking an edge empties the node selection, so applying the rule outside the gesture would immediately deselect the edge just clicked. Selected edges are styled in `apps/web/src/styles/vue-flow.css` (theme-default's `#555` on a gray line is a state you can't see). **No toolbar is on screen during the drag** — `canvas.boxSelecting` (Vue Flow's `userSelectionActive`) gates both the per-node chrome (the band sweeping over the first node makes it briefly the single selection, so duplicate/delete would flash) and the selection toolbar (which would otherwise chase the moving bounding rect); they appear on release.
- **A group is created by grouping a selection, never from the toolbar** (`canvas.groupSelection()`, reached from `FlowSelectionToolbar`): it grows around nodes that are already selected, so "add an empty group, then drag nodes in" is both backwards and impossible (auto-reparent doesn't exist). The box is the selection's bounding rect (`getRectOfNodes`, i.e. `computedPosition` + measured dimensions) plus padding; nodes already inside another group, and groups themselves, are excluded. Two things it can't be built without. **The group and its children go in one transaction** (`store.groupNodes`, `extent: 'parent'` included) — split them and every child briefly points at a `parentNode` that doesn't exist yet, which is `NODE_MISSING_PARENT` plus a whole group of nodes jumping to the origin, and undo would leave half a group behind. And **`extent: 'parent'` must be withheld from Vue Flow until the parent has been measured** — `extentReady()` in `useFlowCanvas`'s `nodes` adapter, which hands over `extent: undefined` while `findNode(parentNode).dimensions.width` is still 0 (write the key explicitly; a key you stop sending keeps its old value through `Object.assign`). Vue Flow derives that bound from the parent's `dimensions`, so before the group's first render the bound degenerates to a point and every child is clamped to `parent - its own size` — the whole group piles up outside the box's top-left corner. **The gate belongs in the adapter, not in the write path**: delaying the *write* only protects the author, and the bug's real victim is everyone else — a peer reads `extent` straight out of the doc the moment the update lands, long before the new group node has rendered on their side. That is what "打组没同步给别人" actually was: the data arrived intact, the receiver's view mangled it. The doc is correct throughout, which is why a reload "fixes" it and why it is easy to miss.
- **Components live in `apps/web/src/components/flow/`**, each owning one region and reading the context directly: `FlowCanvas.vue` (Vue Flow + background + minimap, plus a `<slot/>` for extra in-canvas overlays), `FlowViewControls.vue` (zoom/fit/lock + undo/redo, top-right), `FlowTitleCapsule.vue` (top-**left**: logo/home + inline-editable name + save state + menu, owns its delete confirm), `FlowToolbar.vue` (bottom, canvas-content actions), `FlowSelectionToolbar.vue` (floats above a **multi-node** selection — `NodeToolbar` takes an id *array* and positions itself over their bounding rect; holds 打组), `node-kit/NodeHost.vue` (the one Vue Flow node component for every type — see the node-kit bullet; its `toolbar` slot shows only when this node is the single selected one, so it and the selection toolbar are never on screen together), `TextBody.vue` / `GenericBody.vue` (type bodies, mounted by the host from `view.body`; shared node logic is `useFlowNode(id)`, which reads `store.nodeById` and writes by group, reached through `useNodePart().node`), `FlowNodeHandles.vue` (at most one unnamed handle per side, mounted by the `connectable` feature), `composer/PromptComposer.vue` (the bottom-composer shell type-specific composers wrap), `FlowSnapGuides.vue` (the drag alignment guides), `FlowConnectionEndedDialog.vue` (the modal for a sync channel the server ended for good — one copy block per reason; the expired-session case is deliberately *not* here, it goes to the app-wide `SessionExpiredDialog`. It is non-dismissible **except for `too-large`**, and that exception is the point: for the other reasons nothing the user does on this page helps, while an over-quota canvas is fixed precisely *by deleting on this page* — a modal you can't close would block the only way out). **There is no property panel**: clicking a node selects it and nothing more. Per-node editing lives on the node (double-click to rename, the toolbar for duplicate/delete), so a selection never steals a third of the canvas.
- **Snapping (`useFlowSnapping` + `apps/web/src/lib/flow-snap.ts`) applies to dragging only — never to nodes already placed.** Both snaps (grid + alignment guides) are **always on: no toggle, no toolbar button, no persisted state** — the grid *is* the visible background dots and the guides only appear when something genuinely lines up, so both are the default feel; a switch would only make you click once to get it and force the docs to explain two states. Grid is `FLOW_GRID_SIZE`, the same constant `<Background :gap>` uses — a grid you snap to but can't see lines up with nothing. The guide tolerance is **6 screen pixels ÷ zoom**, not a flow-coordinate constant, or the magnet grows 4× when you zoom in. **Vue Flow's own `:snap-to-grid` is deliberately unused**: besides dragging it also rounds a node's position at *mount* (`NodeWrapper`'s `clampPosition`), a local-view-only shift that never enters the doc, so someone with snapping on and someone without would see different canvases. Both snaps are computed in one place and produce one delta (guides win over grid — the alignment is the more deliberate intent); multi-select drags snap by the group's bounding box so relative positions survive. The correction runs *in* `onNodeDrag`, after Vue Flow has written the raw pointer position and before the frame paints — it can't accumulate, because every drag event recomputes from the pointer, which is exactly why the magnet releases when your hand moves off the line. Snap first, *then* `publishDrag`, or collaborators watch the unsnapped position. The guide overlay lives in the `#zoom-pane` slot next to the presence cursors (flow coordinates, only stroke width and dash counter-scaled).
- **Canvas behaviour is Vue Flow's job, not CSS's.** Anything that has to live *on* the canvas — a label outside a node, a per-node toolbar, a resize handle, an overlay that must follow zoom/pan — is built from the official packages (`@vue-flow/node-toolbar`, `@vue-flow/node-resizer`, `<Panel>`, `<Handle>`, `<NodeToolbar>`, …), following [the guide](https://vueflow.dev/guide/) and [the examples](https://vueflow.dev/examples/). **Do not hand-roll positioning** (`absolute` + `transform`, viewport math, manual `screenToFlowCoordinate` re-anchoring) when a Vue Flow component already does it — a hand-written overlay silently breaks under zoom, and the transform math it duplicates is exactly what the library maintains. Tailwind classes stay for *appearance* (type scale, color, spacing inside the slot); *placement* comes from the component's props (`position` / `align` / `offset`). Missing package → add it as a `devDependency` (it's frontend, see the dependency split) rather than reimplementing it. `NodeHost.vue`'s external top-left `label` slot is the reference case: `<NodeToolbar :is-visible="true" :position="Position.Top" align="start">`.
- **State: `apps/web/src/stores/flow/` (Pinia) is a *projection of a Y.Doc*, not a store of record.** The canvas content **is** the Yjs document (shape in `@shadecn/shared/flow-doc` — one implementation that both the browser and the server import; the frontend's incremental projection — `changedTopLevelKeys` / `projectMap` / `createNodeProjector` / `readFallbackViewport` — is `apps/web/src/lib/flow-projection.ts` (formerly `flow-doc.ts`), and what is left server-side in `apps/server/collab/flow-doc.ts` is only `readGraphFromDoc` and `pruneDanglingEdges`): `nodes`/`edges` are `Y.Map<id, Y.Map>`, because Y.Map merges *per key* — one person retitling while another drags merges cleanly, whereas storing a node as one JSON blob would let the later write clobber the earlier one wholesale. **A node is five groups (graph schema v3): `type` / `layout` / `metadata` / `data` / `runtime`, plus a derived, never-stored `inputs`** (`docs/13` §3.7). In the doc, `layout` (position, size, zIndex, parentNode, extent, handle positions) stays **flat on the node's top level** (the drag hot path, and Vue Flow's own shape), while `metadata` (label, description, icon, createdAt, createdBy, ui), `data` and `runtime` (status, error, taskId, and each output port's product as a flat `outputs.<portId>` key) are each a nested `Y.Map`. **Business fields sit flat on `data`, never wrapped in a `config` object, and `data` has no reserved keys at all** — the same per-key argument one level down: a single `config` key would let one person's edit to `config.prompt` clobber another's to `config.model`; label/status/createdAt moved out to `metadata` / `runtime`. A node's business type **is** its top-level `type`, which is the key of the node-type registry — whose data half (default `data`, default layout, **port declarations**) lives in `@shadecn/shared/flow-node-types` and is shared with the agent. Edges are the only source of truth for wiring, and **ports live on `edge.data`, not on handles**: every node has at most one unnamed handle per side (left in, right out — a side with no declared port has none), `sourceHandle`/`targetHandle` are always `null`, and `edge.data.sourcePort`/`targetPort`/`index` say which pair got wired (a multi-input port's `index` is max + 1 on connect, never renumbered on delete; an edge between two port-less types carries none of the three). Which pair is chosen automatically by `resolveConnection` in shared — the first (output × input) pair in declaration order, source-major, that is type-compatible, not full and not already wired, else the connection is refused — and that one pure function is what the editor's `Handle` `is-valid-connection`, `onConnect`, grow-a-node and the agent's `connect` (optional explicit `sourcePort`/`targetPort`) all call. **Writes go by group: `store.writeNode(id, 'metadata' | 'data' | 'runtime', {set, remove})`** (node components reach it through `useFlowNode(id)`); layout keeps its own write paths. **A batch of independently-edited elements (3D objects, timeline tracks, a resource list) goes one-element-per-key — `<prefix>.<id>`, flat, plain JSON — never into one `data.scene` blob and never into a nested `Y.Map`** (`apps/web/src/lib/flow-collection.ts`; write and delete land in one transaction via `store.writeNode(id, 'data', {set, remove})`). The blob is the `config` bug one level down: everyone in the batch shares a merge unit, so two people posing two different characters clobber each other. The nested `Y.Map` fixes merging but puts *structure* into the CRDT layer, and that is the one thing this doc can't version: with no version number in a Y.Doc, an old and a new client write **different types to the same key**, the winner is decided by clientID (i.e. randomly), the loser's whole subtree vanishes, and the losing side's code throws `TypeError` — read-time tolerance rescues a changed *shape*, never a changed *type*. Flat prefixed keys are invisible to the CRDT layer instead (shared has **two write doors**: `toYNode`/`toYEdge` for elements the editor creates, and `writeNode`/`writeEdge`/`applyGraphToDoc` for the server's legacy-`graph` migration; `toYEdge` writes `null` for an absent handle while `writeEdge` writes nothing — they read back identically, and a test pins that): `toYNode`/`fromYNode` (one copy, in shared), `duplicateNode` and the whole server are untouched, and an old client passes the unknown keys through as it already does. Measured on the 43.7KB director-console sample: 26,626 B per element edit and guaranteed clobbering → 3,358 B and both edits surviving, for +5% doc bytes. Three rules: **a key's type is fixed from its first write and can never change** — that is the precise form of the rule, so a brand-new key that is `Y.Text` from day one is fine (an old client `toJSON()`s it to a string and passes it through, never writing plain to it), while *upgrading* an existing plain key is the thing that destroys data; **ids must be stable, never array indices** (an index shifts when someone else inserts, and your write lands on their element — mint one with `createId()` if the source data has none, as the sample's 5 uuid-less objects and its id-less keyframes both do); and **prefixes must not nest** (`dc.obj` + `dc.obj.pose` collide — convention only, nothing enforces it). Granularity stops at one element per key; two people editing *the same* element loses one side, and that gap is **deliberately left open**, exactly as it is for every other element on the canvas (§4.0.1: concurrent editing is allowed, presence only *shows* who else is touching a node — `occupantsOf` is already wired into the host's built-in `NodePresence`). Narrowing it belongs on the occupancy/notice side rather than in a finer CRDT, and the cheap forms come first — a soft warning, or a conflict check at commit time — not read-only enforcement, whose lease/TTL/leak handling plus Vue Flow's `Object.assign` trap (write the flags explicitly as `true` *and* `false`, or the element stays dead after the lock lifts) costs far more than this one gap is worth. **v1/v2 data is neither migrated nor upgraded (a product decision), but reading it must never throw**: both the Y.Doc reader and `parseGraph` go through shared's `nodeRecordFromParts`, which only falls back — a missing `metadata`/`runtime` reads as an empty label / `idle`, the old `label`/`status`/`kind`/`config` keys stay in `data` as ordinary fields, and a node without a valid `position` is skipped. **`parseGraph` must keep accepting v1/v2 rows** (their layout fields sit flat on the node, so it reads both places) — `readGraph()` is the only path old canvases take into Yjs, so rejecting them would blank each one on first open. Never write back from the read side, because a projection that writes produces a Yjs transaction that enters everyone's undo stack and broadcasts. The projection is **incremental**: `observeDeep`'s events name which top-level keys changed, only those get re-parsed, and everything else keeps its previous object identity — which Vue Flow relies on to skip re-syncing untouched nodes (a `null` from `changedTopLevelKeys` means "can't tell, redo everything"). `inputs` are derived incrementally on top (`createNodeProjector`): a node gets a new object only if its own record changed, its incoming-edge bucket changed (compared by edge identity), or an upstream's `runtime.outputs` changed *by value*; Vue Flow nodes are then mapped once per projected object (`toVueFlowNode`, WeakMap-cached, layout flattened to the top level with every layout key written explicitly, the other four groups in Vue Flow's `data`), so the identity survives into Vue Flow. The one rule: **every content change goes through `store.mutate()`**, which wraps it in a Y transaction tagged `LOCAL_ORIGIN`; components never touch a Y.Map directly, or the change is neither undoable nor synced. Undo is `Y.UndoManager` with `trackedOrigins: [LOCAL_ORIGIN]` — that single option is what makes Ctrl+Z undo only *your* edits and leave a collaborator's alone; `separateUndo()` (`stopCapturing`) splits operations that would otherwise merge inside the 400ms capture window. There is **no save, no revision, no 409, no dirty state** — edits are live and the server persists the same stream. The one exception is a *notice*, not a state: when the server's write queue starts failing it broadcasts a **stateless** message to the room and the status line reads 「服务器暂时无法保存」 (`onStoreStateChange` → `broadcastStateless` → the transport's `onStateless` → `saveFailed`). Four rules there, each of which is a bug if you skip it: broadcast **only on flip** (good→bad, bad→good — stores are 2–10s apart, so per-store notices are pure noise), **re-send to a joining connection** (`connected` reads `isStoreFailing`, or whoever arrives after the flip sees 「已同步」 on a canvas the server cannot store), **clear `saveFailed` when the transport is replaced** (it describes *that* server; keeping it across a reconnect pins the UI at "cannot save" forever), and **parse defensively** — stateless is a general side channel, and a payload you can't read must never throw, because that kills the connection's message loop. It is deliberately not a `fatal`: that tier means "won't fix itself", and this one will. Drag *intermediates* deliberately stay out of the doc (one drag would otherwise emit dozens of updates and audit rows); only the settled position is committed in `onNodeDragStop`, while the in-flight motion rides the feedback layer. **Panning and zooming are not canvas data and take a second, separate path**: `setViewport()` → `setUserState(key, value)`, which never enters the doc and never touches undo (undo must not yank the viewport back). **`setUserState` only buffers — it sends nothing.** The buffer is flushed to `PATCH /api/flows/:id/user-state` by `noteLocalEdit()`, which every local edit (`mutate`, `undo`, `redo`) calls. The shape is **leading send + debounced tail**: the first edit after a quiet period fires immediately (no window), everything after it goes through a `useDebounceFn` (`USER_STATE_FLUSH_DELAY`) that lands the final state once the hand stops, with a `maxWait` (`USER_STATE_FLUSH_MAX_WAIT`, 10s) so nonstop editing still lands periodically. So a view-only visit produces **zero** write traffic, a burst of editing produces one PATCH at its start and one at its end, and **no edit is dropped**. Neither half alone works: a plain debounce lags (it never fires while someone draws continuously, and this PATCH doubles as a heartbeat that can't wait), a plain throttle discards the tail of the window. The tail flush skips itself when nothing happened after the leading send, so a single edit costs exactly one request. **The window always fires a request, even when the view never moved** (it falls back to sending the current viewport), because that PATCH doubles as the session's heartbeat: content rides the WebSocket and produces no HTTP at all, the collab server's minute-by-minute revalidation is deliberately non-renewing (`loadSession(..., { refresh: false })`), and without this one request someone could be idled out *while actively editing*. Net rule: editing = one PATCH per window = session stays alive; looking = no requests = it idles out as it should. Panning without editing is caught by the flush in `saveNow()` / `reset()` on the way out. This is why the viewport rides editing rather than firing on its own: once Yjs took over content, a self-triggering viewport save was the editor's *only* periodic HTTP request — merely looking at a canvas would PATCH. To persist another per-user thing, add a field to `FlowUserState` (in `@shadecn/shared/flow-graph` — one place now), a parser to the server's `FLOW_USER_STATE_PARSERS` (it is a mapped type over the `FlowUserState` keys, so forgetting the parser is a compile error), and call `setUserState` — batching, retry and flush-on-leave are already there. Each viewer gets their own row, so `meta.viewport` in the doc is only the first-open fallback.
- **Continuously-changing values — a dragged slider, a scrubbed timeline, typed text — take one shape: a local draft owns the screen, the draft is throttled onto awareness if peers should see it, and the doc is written *once* when the gesture ends, bracketed by `separateUndo()`** (`docs/13` §3.7.2). **The no-release kind (rename in place, edit body text) is a composable, not a pattern to copy: `useDraftField` (`apps/web/src/composables/flow/useDraftField.ts`)** — `{current, commit, normalize?, equals?, focus?}` in, `{editing, draft, start, commit, cancel}` out. It owns the draft ref, the `editing` flag and **both `separateUndo()` calls**, and it drops the three no-op cases for you: value unchanged, `normalize` returning `null` (an emptied title is a slip, not a rename), and the double submit you get because **Enter and blur routinely both fire** (the second `commit()` sees `editing` already false). `TextBody.vue`, `node-kit/features/RenameTitle.vue` and `composer/PromptComposer.vue` are its consumers (through `useFlowNode(id).draft(group, key, …)`, which wraps it over one key of one group). The with-a-release kind is still hand-written — copy `onNodeDragStart/Drag/DragStop` in `useFlowCanvas.ts` — and differs by exactly one step, throttling the draft onto awareness; that step is deliberately not in the composable because it needs a new awareness field (`transform` only carries `{x, y}`) and has no consumer yet, and when it does, `watch(draft, useThrottleFn(publish, throttleMs))` in the component is the whole change. **Throttling doc writes instead is the wrong fix**: the cost isn't doc size (60 dragged frames grow it from 33,411 to 33,438 — Yjs GCs overwritten Map keys well), it's broadcast + persistence (1.59MB for those same frames), and throttling can't fix the two things that matter — a half-dragged value shouldn't survive a refresh or be undoable, and the doc's guaranteed-ordered-merged delivery is the wrong channel for data that is *fine to drop*. **One undo item comes from committing once, not from `captureTimeout`** — a >400ms pause mid-gesture splits the window. Four rules for the awareness half: it's a *new* feedback field, not a reuse of `transform` (whose value type is `PresencePoint`); send only the numbers that changed, never the whole element (awareness is a *broadcast* — at 25fps a `{x,y}` packet is 45KB/s in a 10-person room, a 4.8KB object packet is 2.16MB/s, so **shrink the packet before lowering the frame rate**, which costs nothing while a lower rate costs responsiveness); clear it when the gesture ends (y-protocols replays local state every 15s, so a stale draft is rebroadcast forever); and keep **both** throttle edges (`useThrottleFn(fn, ms, trailing, leading)` — awareness is last-writer-wins *state*, not an event stream, so dropping middle packets is free but dropping the last one is a bug; the same property is why lowering the rate costs only smoothness, which is what makes the **adaptive window** safe: `ms` is a getter, `feedbackThrottle(roomSize)` in `apps/web/src/lib/presence.ts`, re-read on every call because VueUse's filter does `toValue(ms)` per invocation. It returns the plain `FEEDBACK_THROTTLE` (60ms — one window, one buffer for every feedback field: cursor, selection, drag geometry and connecting all go through `publish()` in `useFlowPresence`, so however many changed, one window sends at most one packet, and an unchanged value sends nothing) up to `FEEDBACK_THROTTLE_ROOM` people — i.e. unchanged for every realistic room — and widens stepwise beyond that, capped at `FEEDBACK_THROTTLE_MAX` (below ~6fps a peer cursor reads as frozen and you may as well stop publishing). **That curve is a judgement, not a measurement, and it is second-order** — shrink the packet first). Text splits by field: short/atomic commits on blur; long-form wants a debounced commit (accepting that >400ms debounce means finer undo — durability and undo granularity trade off, pick one); character-level co-editing needs `Y.Text`, which must be a brand-new key **and** requires fixing `duplicateNode`, whose projection→`structuredClone`→`toYNode` path silently flattens it back to a plain string. And while dragging locally the panel must read its own draft, never the projection — same reason `useFlowCanvas` freezes the `:nodes` array.
- **Personal canvases are a different *kind* of canvas, not a different transport (REQ-SOLO, `docs/16-personal-flow.md`).** A **personal space** is a `Project` with `kind='personal'` and a unique `personalOwner` (lazily created by `GET /api/projects/personal`, which creates on read); canvases inside it have `mode: 'solo'` — **derived from the owning project, never stored on `Flow`**. Nothing about content forks: same Y.Doc, same `Flow.ydoc` bytes, same projection, **and the same transport** — `apps/web/src/composables/flow/sync/` has exactly one, `collab.ts` (Hocuspocus WebSocket), and a personal canvas opens its room the moment the metadata arrives. (It used to ride HTTP push/pull and switch to the WebSocket only when an agent run started; that switch, the `solo.ts` transport and its client API are gone — the agent writes into the server's live room, so a canvas that isn't in the room can't see what the agent does, and "switch on first send" was a whole hand-off protocol for no remaining benefit. The server's `GET/POST /api/flows/:id/doc` route and `flow-writer.ts`'s `applyFlowUpdate()` still exist but no longer have a frontend caller.) Three rules hold it together. **`mode` now only says what the canvas *is*** — where leaving it lands (`/personal`), the wording of the terminal dialogs and the status line (nothing on a personal canvas may mention 协作 / 协作者), and whether the presence layer runs (`useFlowPresence(sync, mode)`: off for `solo`, so neither your own other tab nor yourself shows up as a collaborator). **The doc and its IndexedDB cache are created immediately; the transport still waits for the metadata** — which is why `context.ts` computes `mode` only when `store.meta.id === flowId` (connecting first would work, but a canvas you can't open would then report itself twice: the page's load error *and* the room's handshake refusal). **The room is owner-only and presence-free on the server too** — `authorizeCollab` lets only the `personalOwner` into a personal room (the client-side split is not an access control; a hand-rolled provider would otherwise put someone else's cursor on your private canvas) and `beforeHandleAwareness` empties every awareness frame for it. The client still has to *send* awareness: on a personal canvas presence resets the local state to `{}`, **never `null`** — y-protocols' 15s local-state replay is the connection's only client→server heartbeat (the server's `timeout` is "time since last message", it sends no ping), and a `null` state stops the replay, so an idle personal canvas would be timed out and reconnected every 30s. Because it is a normal collab room, **every collab rule applies, including one-window-per-user** (`exclusive.ts`): opening the same personal canvas in a second tab knocks the first one offline, and `FlowConnectionEndedDialog` / `syncTextOf` word that as 「这张画布已在另一个窗口打开」 rather than 「协作会话已过期」. Personal spaces reject invites / member changes / delete / rename with **403** and are filtered out of `GET /api/projects`; `PROJECT_LIMITS.flows` does not apply to them. **On the UI side the two share one workspace screen but are separate routes, not two Tabs of one page** (`/personal` vs `/projects/:id`, switched from the in-page sidebar of `CanvasWorkspace`): a Tab bar says "two views of one thing", but a project has a second level under it (members, sharing, roles) and a personal canvas has none — no header button, empty state, or available action is shared between the two sides. Both lists are the same `FlowList` component (a personal space *is* a project to the API, so it only needs a `projectId`), and keeping them separate routes is what lets *both* own their URL query (`syncQuery`) — side-by-side Tabs had to share one `?page=`, so only the project side could keep it. Deleting a project is only offered from the sidebar row (not the project header); deleting the one currently open goes to `/personal`. **Anywhere the UI leaves a canvas, the destination is keyed on `mode`, never on `projectId`** — `useFlowDocument`'s `backPath()` (the capsule's home button, its menu item, and where a delete lands) sends solo to `/personal` (and the collab fallback without a `projectId` too), and its icon/label follow the same check. A personal space *is* a project in the database and `meta.projectId` really does point at it, but following that lands a private canvas on a project home offering members and sharing — three things the server 403s for personal spaces. The reverse door is shut too: `ProjectHome.vue` `replace`s to `/personal` when the loaded project has `kind === 'personal'` (old bookmarks are the only way in).

- **Never rebuild the `:nodes` array while the local user is dragging.** Vue Flow decides whether to re-sync nodes by array *reference*, and a re-sync runs `Object.assign(existing, incoming)` — since drag intermediates deliberately never reach the Y.Doc, `incoming.position` is the pre-drag position and the node snaps back mid-gesture. Something always changes during a drag (this client is publishing its drag position to awareness, which recomputes every presence-derived value), so `useFlowCanvas` keeps a `localDragging` flag and hands back the previous `:nodes` array (`computed`'s `previous`) untouched while it's set. Mapping over the array is only safe when a *remote* peer is dragging.
- **Types are shared, with a deliberately small server-only remainder.** Graph structure types, `GRAPH_SCHEMA_VERSION`, the five-group normalizer (`nodeRecordFromParts`) and `inputs` derivation live in `@shadecn/shared/flow-graph`; port declarations and `resolveConnection` in `@shadecn/shared/flow-node-types`; project / canvas API shapes in `@shadecn/shared/canvas`. What stays in `apps/server/store/flow-types.ts` is only what the server alone uses (and it uses `Buffer`, which shared must not): `parseGraph` / `parseTransactions` / `parseUserStatePatch`, `GRAPH_LIMITS` and the Op types. `metadata.createdAt` is validated with `isTimestamp` on every side (the old lenient-frontend / strict-server drift went away with the v1 upgrade code).
- **`apps/web/src/lib/api.ts`** wraps every endpoint over `apiFetch` and throws `ApiError` (carries `status`) on non-2xx — the store needs to tell 409 apart.
