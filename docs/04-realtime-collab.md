# REQ-COLLAB Yjs 实时协同

> 状态：**部分实现** —— 服务端完整可用；前端已在流程画布（REQ-CANVAS）落地
> **在场状态**与**编辑操作的实时广播**。画布内容本身仍存在服务端的快照 + 操作日志里，
> 没有搬进 CRDT，Yjs 文档也没有持久化。

## 1. 目标

在既有的单进程服务端上提供一个 Yjs 同步端点，验证：

- CRDT 协同能不能复用应用自己的登录态（而不是另起一套 token）；
- 不依赖官方 `@y/websocket-server` 包也能提供标准兼容的服务端；
- awareness 能不能直接拿来做「多人同时在一张画布上」的在场感知。

## 2. 背景：为什么自己实现服务端

`server/collab/setupWSConnection.ts` 是 y-websocket `bin/utils.js` 的移植，**刻意不用**上游 `@y/websocket-server`：

- 该包静态 import `y-leveldb` → `leveldown`，这是个原生模块，在 node 22 / arm64 上没有预编译产物，import 直接抛错；
- 去掉该依赖的 0.1.5 版本要求 yjs 14 beta，而稳定版 `y-websocket@3` 客户端无法与之通信。

移植版**未改动线协议**，标准 y-websocket 客户端可直接连接。

## 3. 功能需求

### 3.1 端点

- 地址：`ws://<host>:<port>/ws/<room>`，与 HTTP 服务同端口同源。
- 一个 room = 一个内存中的 `Y.Doc`；房间名从 URL 路径取。
- 只接受 `/ws/*` 的 upgrade 请求。

### 3.2 握手鉴权

- 握手是普通 HTTP 请求，同源会自动带上 `sid` Cookie。
- 用与 HTTP 相同的会话校验逻辑（`server/auth/ws.ts`）；未登录返回 `401` 并销毁 socket。
- **房间即资源**：房间名形如 `flow:<flowId>` 的，还要再判一次「请求者是不是该画布所属项目的成员」，
  规则与 `requireFlowMember` 一致（画布不存在、非成员一律拒绝，不区分两者）。
  其余房间（演示用）保持「登录即可」。

### 3.3 与 Vite HMR 共存

- 开发环境下 Vite 的 HMR socket 也走同一个 `upgrade` 事件（协议 `vite-hmr`，路径 `/`）。
- 因此开发环境 `destroyUnmatchedUpgrades` 必须为 `false`，否则会把 HMR 连接杀掉。
- 生产环境为 `true`：不匹配 `/ws/*` 的 upgrade 一律销毁。

### 3.4 运行参数

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `YWS_PING_TIMEOUT` | 30s | 心跳超时，超时断开 |
| `YWS_GC` | 开启 | 设为 `false` / `0` 关闭 Yjs GC —— **使用快照功能时必须关闭** |
| `YWS_STATS_INTERVAL` | 30s | 统计日志间隔，`0` 关闭 |

### 3.5 监控端点

`GET /api/collab/rooms` 返回：

```jsonc
{
  "rooms": [{ "name": "…", "connections": 2, "awarenessClients": 2 }],
  "totalRooms": 1,
  "totalConnections": 2
}
```

### 3.6 前端接入约定

- 使用 `y-websocket` 的 `WebsocketProvider`，第一个参数传由当前 `location` 推导出的**绝对 ws:// / wss:// 地址**（路径 `/ws`），不要硬编码 host。
- 文档只在内存中，**服务端重启会丢失全部内容** —— 接入方必须接受这个前提，或先补齐持久化。

## 4. 流程画布的协同（已实现）

第一个落地场景是流程画布（REQ-CANVAS，`/flows/:flowId`），一张画布一个房间：`flow:<flowId>`。
连接层在 `src/composables/flow/useFlowCollab.ts`，一条 WebSocket 上驮两件互不相干的事。

### 4.0 行为规范：数据层 vs 反馈层

协同的一切行为都落在这两层之一。**判断一个新东西该放哪层，只问一句：刷新页面之后它还该在吗？**

| | **数据层** | **反馈层** |
|---|---|---|
| 实现 | `stores/flow` + `useFlowSync` | `useFlowPresence` + `src/lib/presence.ts` |
| 走什么 | `store.apply` → 历史 → 落库 → `Y.Array` 有序广播 | awareness |
| 内容 | 节点、连线、图元数据 | 光标、选中、拖动中几何、正在拉的线 |
| 生命周期 | 持久，可撤销，有 `revision` 乐观锁 | 易失，断线即消失，**绝不落库** |
| 丢一帧会怎样 | 不允许丢，要去重要补 | 无所谓，下一帧覆盖 |
| 刷新后还在吗 | 在 | 不在 |
| 扩展方式 | 加一条 `FlowCommand`（`stores/flow/commands/`） | 加一个 awareness 字段 + 一个 computed |

**画布内容没有搬进 Y.Doc。** 它仍旧存在服务端的「快照 + 操作日志 + revision 乐观锁」里
（见 `docs/13-flow-canvas-management.md`）；`Y.Array` 在这里只当一条**有序广播通道**用。
这么选是因为现有操作本来就是可序列化的 `FlowOp`（要存进 `FlowOperation` 表、要走网络），
拿来广播不用改任何数据结构；真搬进 CRDT 则要重新回答历史、撤销、审计日志怎么办（见 §8）。

**依赖方向是一条直线，不成环**（`composables/flow/context.ts`）：

```
selection ──┐
collab ──┬──┴─→ canvas      canvas 是唯一同时认识三者的接合层
         └─→ presence ──┘
         └─→ sync
```

`presence` 不认识 selection、也不认识 Vue Flow —— 它只提供「上报」和「读别人」两组能力。
本地状态怎么接进去、别人的占用怎么落到画布上，全在 `useFlowCanvas`。
所以加一种新的反馈信号（正在输入标题、框选范围…）只需要动 `presence` 加一对 set/computed，
不用碰选中态和画布。

#### 数据层的广播规则

- **落库只有一方做**：谁发起谁提交。收到的一方只改内存（`store.applyRemote`）——
  不进历史（撤销只该撤自己干的事）、不进待提交队列（两边都提交只会互相撞 409）。
- **提交成功的一方广播新的 `revision`**，其余人 `adoptRevision` 对齐乐观锁基线。
  不对齐的话他们下一次提交必定带着陈旧的 `baseRevision` 撞 409。
- **首次同步之前收到的一律不理**：刚进房间时整条通道会作为一次批量插入到达，
  那些是早已包含在快照里的历史，重放会把画布搞乱。另外按 `transaction.id` 去重兜底。
- 通道有长度上限（200 条）并从头削 —— 它是管道不是账本，历史在 `FlowOperation` 表里。
- **所有变更必须经过 `store.apply`。** Vue Flow 有几个默认行为会绕过它直接改自己内部的
  nodes/edges（`applyDefault: true` 下的 `deleteKeyCode` 就是），必须关掉后自己接管，
  否则本地看着生效了，实际不进历史、不落库、也不广播。

#### 反馈层的 awareness 字段

| 字段 | 内容 |
|---|---|
| `user` | `{ id, name, avatarUrl, color }`，颜色由 id 哈希到固定配色表 |
| `cursor` | 鼠标位置，**画布坐标**（不是屏幕坐标，各人视口不同） |
| `selection` | 选中的元素 key 列表 |
| `transform` | 正在直接操作的元素 → 实时几何（目前是拖动中的位置） |
| `connecting` | 正在拉线的起点；终点跟着 `cursor` 走，不重复发 |

### 4.0.1 占用规范

占用是反馈层驱动、约束数据层的第三个概念，**单位是「元素」**。

> **唯一原则：一个元素正在被某个人编辑时，别人不能同时改它。**
> 判一件事要不要挡，就问：**这个操作会改到那个元素本身吗？**
> 会 → 挡；不会（哪怕操作在它身上发生）→ 放行。

- **元素 = 节点或边**，统一标识 `node:<id>` / `edge:<id>`（`src/lib/presence.ts` 的 `elementKey`）。
  加第三种元素（分组、批注…）只需要在 `ElementKind` 加一个值，下面的规则自动适用。
- **直接占用**（反馈层上报，`occupies()`）三种情况：
  - **选中了它** —— 选中就是「我要动它」的意思，属性面板和删除键都对着它；
  - **正拖着它** —— 否则拖到一半被别人抢走选中，一个节点会被两个人同时搬；
  - **正从它拉线**（还没松手）—— 那条线的起点节点在他手里，别人不能同时删它、搬它。

  拖动 / 拉线结束后 Vue Flow 保持该元素选中，占用因此**延续**到取消选择为止：
  占用不会在松手瞬间凭空消失、逼人重新抢。
- **派生占用**（由图结构推出，`useFlowCanvas` 的 `lockedKeys`）：
  **占住一个节点 = 占住连到它的所有边。** 因为「断开一条接在它上面的线」改的就是这个
  节点的连接关系。这条算在画布层而不是 `lib/presence.ts` —— 那边是纯 presence 逻辑，
  不认识图，「谁连着谁」只有画布知道。
- **仲裁：clientId 最小者胜。** 各端拿同一份状态算出的赢家一致，不需要服务端参与。
  抢输的一方自己把选中态清掉（含 Vue Flow 内部那份），编辑中的输入框也一并收起。

**挡什么、放什么**（节点和边规则一致，差异只在各自才有的那一样）：

| 操作 | 被占用的节点 | 被占用的边 | 为什么 |
|---|---|---|---|
| 选中 | 挡 | 挡 | 选中就是要动它 |
| 拖动 | 挡 | — | 改的是它的位置 |
| 删除 | 挡 | 挡 | 改的是它本身 |
| 改属性 / 改标题 | 挡 | — | 改的是它的数据 |
| 拖端点改连接 | — | 挡 | 改的是这条边 |
| 断开接在它上面的边 | **挡**（派生占用） | — | 改的是它的连接关系 |
| **从它拉出新连线** | **放行** | — | 动的是**一条新的边**，节点本身没变 |
| **把线连到它上面** | **放行** | — | 同上 |

**只读标记必须每次都显式写 `true` / `false`**，不能「锁了才写」。Vue Flow 同步节点用的是
`Object.assign(内部那份, 传进来的这份)`，是**就地合并**：某一次不带 `selectable` 这个键，
上次写的 `false` 就永远留在它内部那份节点上，占用解除后元素从此点不动。

### 4.1 功能需求

- **在场头像栏** —— 标题胶囊右侧一枚同高（`h-10`）的胶囊，头像堆叠展示，最多 5 个、多余收成 `+N`；
  靠左的压在靠右的上面，「我」永远排第一。左侧一颗圆点表示连接状态。
- **他人光标** —— 画布上画出箭头 + 头像 + 用户名，颜色即该用户的身份色。
  鼠标移出画布就收起来，不在别人屏幕上留一个不动的箭头。
- **元素占用** —— 见 §4.0.1。节点画**黄色阴影框**，边画**黄色描边**，规则一致；
  接在被占用节点上的边一并变黄（派生占用），别人断不掉。
- **占用者标识** —— 被占用的节点，名称边上贴上占用者的头像 + 名字。
- **就地改标题** —— 双击节点标题变输入框，回车提交、Esc 取消、失焦即提交。
  改标题就是在编辑这个节点，所以进编辑态会先把它选中（= 占住），别人这时改不了它的标题；
  编辑到一半被抢走（对方 clientId 更小）输入框自动收起且不提交。
  提交走 `store.apply`，因此进历史、能撤销、会落库、会广播。
- **内容实时跟随** —— 一方新增 / 移动 / 删除节点、连线、改属性、撤销重做，
  另一方**不刷新**就能看到（见 §4.0）。
- **拖动过程实时反馈** —— 拖动中的位置逐帧走反馈层，别人看到的是节点跟着手走，
  不是松手瞬间瞬移。松手时**先**发落定的操作、**再**收临时几何，
  反过来的话对方会先退回旧坐标再跳一下，看着就是闪一下。
- **连线过程实时反馈** —— 一方从连接口拉线时，别人看到一条同色虚线从那个连接口连到他的光标。
  路径用 Vue Flow 自己的 `getBezierPath` 算，形状和本地拉线时看到的一致。

### 4.2 数据可信度

awareness 的内容由客户端自己写、服务端只转发，因此前端一律当**不可信输入**解析：
形状不对的整条丢弃，颜色也在本地按 id 重算而不是照抄对方上报的。
真正的边界在握手那一步（§3.2 的房间级授权）——进得来的人本就有权限看见彼此。

## 5. 已知缺口

- **不是真 CRDT**：两人同时改同一个元素的同一个字段是后到者覆盖，没有合并语义。
  占用（§4.0.1）挡住了绝大部分这种情况，但挡不住不涉及选中的操作（如同时往同一个节点连线）。
- **同时提交仍会 409**：两边几乎同时落库时有一方进入冲突态，需要点保存状态重新加载。
- 通道只在内存里，服务端重启即丢（未提交的操作会随之丢失）。
- awareness 里的用户身份没有与服务端会话绑定：同房间的成员之间，客户端可以自称房间内的任意身份。
- 富文本编辑器（REQ-PROMPT）尚未接入。

- [x] 一方选中节点，另一方看到黄色阴影框 + 占用者头像，且拖不动、点不开属性面板、改不了标题。
- [x] 一方选中连线，另一方看到黄色描边，且删不掉、拖不动端点。
- [x] 一方选中节点，接在它上面的边在另一方那里也变黄且断不掉（派生占用）。
- [x] 但另一方**仍能从这个被占用的节点拉出新连线**（那是新的边，节点本身没变）。
- [x] 一方拉线拉到一半（没松手），另一方就看到**起点节点**被占用。
- [x] 双击节点标题能改名，另一方同步看到；被别人占着时双击无效。
- [x] 一方新增 / 拖动节点，另一方不刷新就能看到，且双向都成立。
- [x] **拖动过程中**（还没松手）另一方就能看到节点在动，并已看到它被占用。

- [x] 删除连线会同步给对方，并且刷新后确实没了（不再被 Vue Flow 的默认删除键绕过 `store.apply`）。
- [x] 两人协同编辑后刷新，内容与屏幕上一致，且没有因双方都提交而出现重复节点。
- [ ] 未登录直接连 `/ws/test` 收到 401 并断开。
- [x] 非项目成员连 `flow:<id>` 被拒绝（`server/test/auth/ws.test.ts`）。
