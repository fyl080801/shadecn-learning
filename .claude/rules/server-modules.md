# Server modules & roles (REQ-MODULES, `docs/28-server-modules.md`)

> Phases 1–10 of `docs/28` §7 are in. Phase 9 = the integration protocol (modules plug themselves in); phase 10 = the core is a package (`@shadecn/server-core`) that knows no module, and login (`mod-auth`) is a module too.

- **The core knows modules only as a list handed to it** (`apps/server/modules.ts` → `boot({ modules })` / `prepare(modules)`). Adding a capability = one line there. `@shadecn/server-core` never imports a module package and modules never import the core — never import a module's routes / stores / config into the core, never special-case a module name in `app.ts` / `boot.ts` / `server.ts`. Everything a module needs from the core goes through `ctx` / `@shadecn/server-kit` (`docs/28` §3.1.2). The list is static because esbuild bundles it — config only switches modules off.
- **Business capabilities are modules, including login and projects/canvases.** The core is only the platform: HTTP pipeline, DB, config, logging, cluster/bus, revocation, frontend hosting. `User` lives in `@shadecn/server-kit/identity` (every module's FK target). **Login is a provided platform capability**: `mod-auth` `provides: [AUTH_SERVICE]` and the core's `platform.auth` (pipeline session parsing, login gate, page guard, `userId` / `identify` / `deriveSecret`) forwards to it via the kernel's `onProvide`; with no provider auth is disabled and the gates pass. A module that needs "who is this" must `dependsOn: ['auth']` (canvas does; everything else depends on canvas) so the provider is in place before its `setup`. Origins (`SERVER_ORIGIN(S)`) are core: `platform.origins`.
- **A `mod-*` package never imports `apps/server` or `@shadecn/server-core`, and never reads `process.env`.** Platform facts come from `ctx.platform` / `@shadecn/server-kit/platform` (`auth.userId` / `identify` / `deriveSecret`, `origins.isAllowed` / `of` / `primary`, `runtime`, `log`); the DB from `@shadecn/server-kit/db`'s `db()`. `runtime.envVar()` is only for names chosen elsewhere (SDK key vars, `llm.providers`' `$ENV`, `POD_IP`) — a config value read there can't come from the file and isn't validated. `runtime.llmProviders` is the one config value modules take from the core (the parsed `llm.providers`, read in `config.parse(read, runtime)`) — a section both agent and apps reference can't live in either module. Third-party deps are `peerDependencies` (+ dev for its tests); the runtime copy stays in `apps/server` `dependencies` (the build checks it). A new package needs a `COPY` line in the root `Dockerfile` and an entry in the root `vitest.config.ts`.
- **A module owns its tables, stores, config parsing and auth details.** Entities are declared in `entities` and registered **regardless of switch/role** (a disabled module's vanished tables make `db:push` refuse to boot — `deploy.md`). Table names didn't change when they moved; don't rename one without a migration plan.
- **Routes are declared, then mounted through `ctx.http` — never mounted by the host.** `routes: [{ path, role, access, kind }]` is the single source for the role gate, the login gate's public list, the `dev:cluster` proxy and the ingress check (`@shadecn/server-core/routes-table`, built from the module list). The kernel **throws** on mounting an undeclared path (it would bypass both gates and the proxy) and **skips** a mount whose declared role isn't in this process — so module code never branches on roles (agent's panel exists only on web, its gateway only on agent replicas, collab's WebSocket only with the `collab` role = headless otherwise). A declaration covers its subpaths; the most specific declaration wins; two owners of one path fail at boot. A new non-web entry needs a matching rule in `k8s/variants/roles/ingress.yaml` (`test/k8s/roles-manifests.test.ts` iterates the declarations and goes red otherwise). `access: 'public'` only for entries that authenticate themselves (gateway token, WebSocket cookie check) or must be anonymous (health, login).
- **Flow-scoped routes go under `canvas.flowGuard`**: mount with `underFlowGuard(canvas, routes)` (`@shadecn/mod-canvas/contract`). Hono matches in registration order, so a guard added with `routes.use()` after the handlers never runs. The route then reads identity from `canvas.request` (`FlowRequestPort`) and never re-checks membership or reads context variables. Canvas's own router guards **its own paths explicitly** (no `/:flowId/*` blanket) so other modules' sub-routes aren't checked twice.
- **Dependency direction: storage / collab / agent → canvas; canvas knows none of them.** A module reaches a peer only through the peer's contract entry (`./contract`, `./entities`, storage's `./client` / `./keys`, collab's `./canvas-host` for agent), `ctx.service()` (declared in `provides`) and the bus. "Flush live rooms before copying a canvas" is canvas's bus request (`flushFlowContent`) that collab handles — don't make canvas import collab. A direct import of a peer's internals silently reintroduces "same process" and role deployment breaks without a type error.
- **`dependsOn` can be role-scoped** (`{ module: 'collab', roles: ['agent'] }`): agent needs a live collab only where it executes. An unscoped hard dependency on a module that doesn't load on some of your roles fails that role's boot.
- **Config: one value, two spellings, one parse.** A module declares `config: { schema, parse(read, runtime) }`; the kernel mounts it under `modules.<name>` and **adds `enabled` itself** (declaring your own `enabled` throws). Write it with `defineModuleConfig`, or `read`'s paths aren't narrowed. **Env names are never written in a schema**: `envNameOf(path)` derives them, so a leaf is configurable both ways by existing; the file's shape is the only definition. `read('sandbox.k8s.namespace')` takes a path relative to the section and returns env (even `''`) else the file value as an env-shaped string; defaults and validation live only in `parse` (login's production check included). The core resolves its own sections at import with `modules` **deferred**, and `prepare(modules)` re-validates the whole file with the full schema and parses every module section — a bad value means no listening port. Core settings go `setting()` in `config-source.ts` + `cfg('server.port')` in `config.ts`. A `setting('json')` leaf is a whole structured subtree: the file writes an object, env is the same JSON string, and its inner keys derive no env names — the owner validates the shape (`@shadecn/server-kit/llm`). Derived names are unique across the whole tree and may not hit a bootstrap variable (`BOOTSTRAP_ENV`: `NODE_ENV` / `DATA_DIR` / `SERVER_CONFIG`) — both checked at resolve. A message naming a variable derives it (`envNameOf`, the module's `agentEnv` & co.); only `packages/agent`, which knows no config layer, spells them out, pinned by `test/config-env-names.test.ts`. An old name left in an `.env` or `envFrom` resource is silently ignored — nothing warns (`docs/28` §3.3).
- **`enabled: false` can only switch off**, and a switched-off module doesn't load at all: its routes don't exist, `/api/features` says false, a hard dependent fails boot. `enabled(config)` is the module's own verdict (storage: S3 incomplete).
- **The kernel derives the lifecycle**: `setup` in dependency order, `shutdown` in reverse under each handle's `shutdownTimeoutMs`. Agent stopping before collab flushes comes from `agent → collab`; declare a dependency instead of editing `boot.ts`. The frontend is not a module: `boot.ts` attaches it after `assemble()` (catch-all must come last), `dev.ts` passes Vite, `index.ts` the static one; `assertNoDevCode` in `build-server.mjs` fails the build if `dev.ts`, `frontend/dev.ts` or `vite` reach the metafile.
- **Tests assemble the real platform**: `test/setup.ts` runs `prepare(modules)` + `assemble({ app, server })` (all roles, no listen) per file, so `app.request` hits the production wiring. Re-wiring under a different env needs a fresh module graph that is prepared and assembled again (`helpers/fresh-app.ts`; `testing.md`); for agent alone use `wireAgent` (`test/agent/sandbox-config.test.ts`). `test.env` configures a fake S3 so storage loads; "storage unavailable" is `replaceAssetStorage(null)`. Tests never read a developer's `server.config.*` (`SERVER_CONFIG=''`).
- **The bus is scatter-gather with a mandatory fallback** (`@shadecn/server-kit/bus`): a request goes to every instance registered for the token and waits for all or the timeout; `missing` / `failures` are normal. Wrappers like `flushFlowContent()` never throw. No responders = immediate empty result. The local handler is called directly.
- **Access revocation is a core signal** (`@shadecn/server-kit/access`): routes `await revokeAccess()`; capabilities subscribe with `onAccessRevoked`. Don't route it through the bus (it already has a cross-instance path: epoch + collab's watcher).
- **`CLUSTER_MODE=single` + a role set that isn't "all roles" is refused at boot** (`assertRolesSupported`). Two processes without Redis each hold their own Y.Doc — the data-loss case of `docs/14` §2. Redis mode also refuses SQLite.
- **Cross-role calls are bus request/reply (or the access signal) — never HTTP between roles.** `SharedChannel` doesn't guarantee delivery (`cluster.md`); a reply that never comes must degrade (e.g. `flushFlowContent` → read the DB), not hang.
- **Starting an agent run has no fast path** (`@shadecn/mod-agent/dispatch`). `POST /messages` always goes `bus.dispatch(AGENT_START_RUN)` → the executing replica's `runtime.start()` → events into `SharedLog agent-dispatch:<dispatchId>` (batched, contiguous `seq`, end marker) → the route reads it from the start. Even in one all-roles process. A "start directly when local" branch would only run in dev and mask dispatch bugs until production. **Never relay the initiator's stream through the orchestrator's replay log** — it only exists once the run is listed, so an immediate subscribe (or a run that ends first) 404s. `dispatch` never retries on timeout (the run may have started). On a process without the `agent` role the module builds a **read-only runtime** (`executesRuns: false` → `NO_DRIVER`, no sandbox driver, no dispatch handler, no reconciler) — reads (view, conversations, reattach, abort) still work through the shared registry.
- **Only the executing agent replica signs the Grant** — "the initiator can enter this canvas right now" is judged at execution time, not at enqueue time (`docs/22` §5).
