# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Language

**Always reply in Chinese (中文).** All user-facing output — answers, explanations, plans, summaries, questions — is written in Chinese. Keep technical terms in their original English form (Vite, MikroORM, OIDC, Hono, …) rather than translating them.

Code identifiers, types, and commit messages stay English. **Source comments in `apps/server/`, `apps/web/src/` and `packages/shared/`, log/error messages shown to a developer or user, and test names are written in Chinese**, matching every existing file. Documentation under `docs/` is Chinese too.

## Project Overview

A Vue 3 learning/experimentation sandbox that combines shadcn-vue UI components, Three.js 3D scenes, and canvas-based mini-games. It serves as a playground for exploring different Vue and web technologies within a single app.

Requirements live in `docs/`, one file per requirement — see `docs/README.md` for the index. This file describes *how the code is built*; `docs/` describes *what it is supposed to do*.

## Monorepo layout

A pnpm workspace (`pnpm-workspace.yaml`) with four packages. The root `package.json` keeps **every command name unchanged** — each one is a `pnpm --filter <pkg>` delegation (`pnpm dev` → `@shadecn/server`, `pnpm build:client` → `@shadecn/web`, …) — so nothing you type changed when the repo was split.

- **`apps/web` (`@shadecn/web`)** — the frontend. `src/` (the `@/` alias target), `vite.config.ts`, `index.html`, `login.html`, `components.json`, `public/`. Its `package.json` has `devDependencies` only: it is bundled into `output/public`, nothing of it is installed at runtime.
- **`apps/server` (`@shadecn/server`)** — the backend, laid out flat: what used to be `server/*` is now `apps/server/*`. The data layer lives in it too — `db.ts` (the MikroORM singleton) and `db/` (entities, ORM factory, schema sync + its CLI) — next to `scripts/` (`build-server.mjs`, `dev-cluster.mjs`, `local-start*.mjs`, `output-image/`). Its `dependencies` is the production runtime set (see the dependency section).
- **`packages/shared` (`@shadecn/shared`)** — source-only TypeScript (no build step, no publish) that both sides import: sub-paths `flow-graph` (graph types, schema version, v1 upgrade, `FlowUserState`), `flow-doc` (the Y.Doc shape and its read/write), `canvas` (project / canvas API shapes), `auth` (identity views, login-done constants), `collab` (close codes, room/path constants). It exists so "two TS projects, so change one and change the other" stops being a rule anyone has to remember.
- **`packages/agent` (`@shadecn/agent`)** — the canvas agent (REQ-AGENT, `docs/20-agent-canvas.md`), source-only like shared (no build, no publish) but **server-only**: its `tsconfig.json` is the server's (Node types + ES2023), because the sandbox spawns processes and touches files. Sub-paths `session` (the run orchestrator over pi's `Agent` — several conversations per flow × user, one run per flow at a time; conversations and the run / tool-call log are **persisted through injected interfaces**, only the "who is running" registry — and each running run's replay buffer — stays in process memory and is therefore not shared across replicas; **a run does not die with the HTTP connection that started it**: a disconnect only drops a subscriber, and `subscribe()` / `GET …/runs/:runId/events` replays everything since RUN_STARTED and then streams on, frame-for-frame identical to the original stream), `store` (those two interfaces — `AgentConversationStore` / `AgentRunLog` — plus in-memory implementations for the package's own tests; the package never sees MikroORM, `apps/server/store/agent.ts` is the real implementation and `createAgentRuntime` has **no default**, so forgetting to wire the database can't silently degrade into "lost on restart"), `tools` (the canvas tools — `read_canvas` / `add_node` / `update_node` / `connect` / `delete_elements`, one Y transaction per call), `canvas` (the `CanvasHandle` abstraction the tools take — they never see Hocuspocus; `createDocCanvasHandle` wraps a bare `Y.Doc` for tests), `events` (**the only place** pi's `AgentEvent`s become wire events — the AG-UI subset declared in `@shadecn/shared/agent`; change protocols here and nowhere else), `model` (picks a pi `Model` from an **explicit options object — the package never reads `process.env`**; env parsing lives in `apps/server/config.ts` + `apps/server/agent/index.ts`), `sandbox` (`SandboxProvider` / `Sandbox` + `LocalSandboxProvider`, a child-process sandbox that is **not** strong isolation — empty env, command whitelist, timeout, output cap, workdir-only file access; production wants a docker / k8s gVisor implementation of the same interface). What stays in `apps/server`: the route (`routes/agent.ts`, SSE + auth), `agent/canvas-access.ts` (direct connection into the live room, re-checks the initiator's access and the quota before **every** read/write), and the env/config. It declares `@mariozechner/pi-agent-core`, `@mariozechner/pi-ai` and `yjs` as **peerDependencies** (plus devDependencies for its own tests), and `apps/server` keeps the two pi packages in its `dependencies` — same reason as shared's yjs: esbuild inlines `@shadecn/*`, the third-party packages they import stay external, and `build-server.mjs` checks those against `apps/server/package.json`. `@shadecn/agent` is a `workspace:*` devDependency of `apps/server` only; the frontend never imports it (the contract it needs is `@shadecn/shared/agent`).
- **What stays at the root:** `docs/`, `k8s/`, `ci/`, `.gitea/`, `Dockerfile`, `.env`, `data/`, `output/`, `eslint.config.ts`, and a `vitest.config.ts` that is *only* a `projects` aggregator (each package owns its own config, project names `server` / `client` / `shared` / `agent`). The root `devDependencies` hold only repo-wide tooling: the eslint family, `typescript`, `vitest`, the coverage plugin, `jsdom`.
- **Two base directories, not one.** `rootDir` / `appRoot` (`apps/server/config.ts`, `runtime.ts`) is the **repo root** and is where `.env`, `data/` and `output/` live; `webRoot` (`config.ts`, the Vite root in dev) and `serverDir` (the build/test scripts) are each package's own directory. Running from source, `runtime.ts` derives the app root as `apps/server/`'s **parent's parent** (two levels up, not one); in the bundle it is still `process.cwd()`. Mixing the two bases is the typical way to read the wrong `.env` or put the database in `apps/server/data`.

Invariants that came out of the split — each is a bug if you undo it:

- **`tsx watch` must carry `--exclude '../web/node_modules/.vite-temp/**'`, in `dev` and in `dev-cluster` alike.** Vite bundles `vite.config.ts` into a temp file under `apps/web/node_modules/.vite-temp/` and deletes it again; tsx's default ignore rule for `node_modules` is relative to *its* cwd (`apps/server`) and never covers `../web`, so every middleware-mode `createServer` triggers a restart, which creates a new Vite, which writes a new temp file — an endless restart loop (measured: 50 restarts in 26 seconds).
- **The schema-sync CLI (`apps/server/db/sync-cli.ts`) goes through `apps/server/env.ts` + `config.ts`, never its own `.env` read.** `pnpm db:push` runs with `apps/server` as cwd, and a bare `process.loadEnvFile()` reads `./.env` — it would quietly find nothing and fall through to the default SQLite file while the server talks to a different database. `env.ts` loads the repo-root `.env` explicitly; keep it that way (this was `prisma.config.ts`'s invariant before the switch to MikroORM).
- **Local `pnpm start` goes through `node --import ./apps/server/scripts/local-start.mjs`.** The bundle is ESM and resolves bare imports by walking up from the *artifact's* location (`output/server` → `output` → repo root), but the runtime dependencies are declared only in `apps/server` — the root `node_modules` has none of them, so a plain `node output/server/index.js` dies with `ERR_MODULE_NOT_FOUND`. The registered hook only catches "bare package name not found" and resolves it once more starting from `apps/server/package.json`, so the dependency list still has exactly one source. In a container the artifact has its own `node_modules` beside it and the hook is never reached.
- **The root `Dockerfile`'s build stage copies each package's `package.json` one by one, then runs `pnpm install --frozen-lockfile`, then `COPY . .`.** That ordering is what keeps the install layer cacheable; the cost is that **a new workspace package needs one more `COPY …/package.json` line**. And `.dockerignore` must say `**/node_modules`, not `node_modules`: each package's `node_modules` is a directory of symlinks into the host's `.pnpm` store, and if one leaks into the context `COPY . .` overwrites the dependencies the image just installed with dangling links.
- **Tailwind's automatic source scan is rooted at `apps/web`** (the Vite root), not the repo root — class names used outside `apps/web` are not detected, and scanning the whole repo would have swept `docs/` and `output/` in.
- **esbuild no longer uses `packages: 'external'`; `scripts/build-server.mjs` has an `externalizePackages` plugin instead.** The criterion is the same (anything not starting with `.` or `/` stays external) with one exception: `@shadecn/*` is **inlined**. `packages: 'external'` has no exception list, and with it `@shadecn/shared` would survive as a runtime `import` of a package that is not installed anywhere in the artifact. Third-party packages that shared itself imports (yjs) still go external and still land in the generated runtime dependency list.
- **`@shadecn/shared` is a `workspace:*` `devDependency` of both `web` and `server`** — it is bundled by Vite / esbuild, so the artifact never needs it installed. It declares `yjs` as a **peerDependency**: there must be exactly one copy of yjs in any bundle, because `instanceof Y.Map` across two copies is always `false` (and shared's whole reading side is `instanceof` checks). One copy is guaranteed by pnpm linking every consumer to the same realpath, plus the frontend's `resolve.dedupe`; `apps/server/test/collab/shared-yjs.test.ts` and `apps/web/src/test/lib/sharedYjs.test.ts` pin the `instanceof` so a dependency drift fails a test instead of blanking a canvas.
- **Rules for writing code in `packages/shared`.** Relative imports inside the package carry the `.ts` extension. No DOM or Node API: its `tsconfig.json` sets `lib: ["ES2020"]` and `types: []` as the guard-rail, because both consumers recompile the source under *their own* config (DOM+ES2020 vs. Node+ES2023) and the intersection is the only safe subset. Tests use a separate `tsconfig.test.json` — vitest's types pull in `@types/node`, and folding them into the main config would silently turn the guard-rail off.
- **The lockfile's dependency version ranges were deliberately kept identical to the pre-monorepo ones.** Letting pnpm re-resolve from scratch drifts `reka-ui` to 2.10.1, so don't `pnpm update` casually and read the lockfile diff of any install.
- **Run the `shadcn-vue` CLI from `apps/web`** (that is where `components.json` is); the packages it adds land in `apps/web/package.json`, which only has `devDependencies` — so the old "move it out of `dependencies`" chore is mostly gone, but check anyway.

## Commands

- `pnpm dev` — (delegates to `@shadecn/server`) Start the whole app (Node/Hono + Vite as middleware, watch mode) on http://127.0.0.1:3000
- `pnpm build` — Build both halves into `output/`: frontend (`vue-tsc -b` + `vite build`) into `output/public`, backend (esbuild bundle) into `output/server`
- `pnpm build:client` / `pnpm build:server` — Just one half. `build:client` no longer type-checks the server as a side effect; `build:server` still runs `typecheck` first
- `pnpm start` — Run the production server locally (`NODE_ENV=production node --import ./apps/server/scripts/local-start.mjs output/server/index.js`, see the monorepo section for why the `--import`)
- `pnpm preview` — `pnpm build && pnpm start`
- `pnpm typecheck:server` / `pnpm typecheck:shared` / `pnpm typecheck:agent` — Type-check the `apps/server` / `packages/shared` / `packages/agent` project (the shared one runs two configs: the source guard-rail config and `tsconfig.test.json`; the frontend is checked by `vue-tsc -b` inside `pnpm build:client`)
- `pnpm test` — Run all three Vitest projects once; `pnpm test:watch` for watch mode
- `pnpm test:server` / `pnpm test:client` / `pnpm test:shared` / `pnpm test:agent` — Run only the backend / frontend / shared / agent project
- `pnpm test:coverage` — v8 coverage into `coverage/`
- `pnpm lint` / `pnpm lint:fix` — ESLint
- `pnpm db:push` — sync the tables to the entity definitions (`tsx db/sync-cli.ts` — **this project keeps no migration files**, see the database section). Additive changes only; anything lossy is refused with the offending statements printed. `pnpm dev` runs it first. There is no `db:generate` (nothing is generated) and no `db:studio` (MikroORM has no equivalent — use `sqlite3` / `psql`)
- `pnpm db:push:force` — the same sync with `--force`, for when a local entity change drops or retypes a column (also drops tables that aren't entities). **Dev only, and deliberately a separate command**: `dev` / `dev:cluster` / both Dockerfiles keep the bare sync, so a destructive change fails loudly instead of quietly dropping a column on every server start

One process, one port: the Node server is the only entry point in both dev and prod — there is no separate Vite dev server and no proxy.

Copy `.env.example` → `.env` (repo root) before the first run; `apps/server/env.ts` loads it via `process.loadEnvFile()` (no dotenv dependency).

## Architecture

**Stack:** Vue 3 + TypeScript + Vite + Tailwind CSS v4 + shadcn-vue (new-york style)

**Path alias:** `@/` maps to `apps/web/src/` (configured in both `apps/web/vite.config.ts` and `apps/web/tsconfig.app.json`). The shared contract is imported as `@shadecn/shared/<subpath>`, not through `@/`

**Routing:** `apps/web/src/router/index.ts` — vue-router 5 (history mode). The route table has exactly two top-level records, one per layout (see below); every page is a *child* of one of them, and the child paths stay flat (`projects/:projectId`, not further nesting). The *views* are grouped into feature folders (see below). It is the only place that imports from `apps/web/src/views/` and from `apps/web/src/layouts/`.

**Layout — `apps/web/src/layouts/`, one component per layout, picked by the route table.** `App.vue` is only `<RouterView />` + the `Toaster` (vue-sonner) mounted once at the root; it contains no layout branch. `SidebarLayout.vue` is `AppSidebar` + a scrolling `<main><RouterView /></main>` and holds almost every route; `BlankLayout.vue` is a bare full-screen `<RouterView />` and holds only `/flows/:flowId`, the canvas editor, which needs the whole screen. Both top-level records use `path: "/"`, so adding a page means putting it under the layout it belongs to — nothing else changes, and there is no `meta.layout` flag anymore. Every SPA route is a logged-in route (the login page is a separate Vite entry, `login.html`, and never enters the SPA) — a bare layout is *not* an auth exception. The app fills the viewport height (`h-screen`).

**Auth (frontend):** the gate is on the server (`apps/server/frontend/guard.ts`) — an anonymous browser can fetch the bundle but never receives `index.html`, so the SPA never boots. `apps/web/src/router/index.ts`'s global `beforeEach` is only the fallback for a session that dies mid-visit: it calls `fetchSession()` (one `GET /api/auth/me`, cached) and, when anonymous, either `goToLoginPage()` — a full-page `location.replace('/login?redirect=<fullPath>')`, because `/login` is the frontend's other Vite entry and not a SPA route — on the *first* navigation (`from === START_LOCATION`, nothing on screen to lose), or `requestReLogin(to.fullPath)` once the user is already inside the app. `apps/web/src/lib/auth.ts` exposes `useAuth()` (`user` / `roles` / `isAuthenticated` / `authEnabled` / `sessionExpired` / `hasRole`) and `apiFetch()`. There is no token in the browser — login/logout are full-page navigations to `/api/auth/login` and `/api/auth/logout`.
- **An expired session is never a silent redirect.** A 401 from `apiFetch` (or the guard, mid-visit) calls `requestReLogin(redirect)`, which clears the local user, remembers the return url, and flips `sessionExpired`; `SessionExpiredDialog.vue` — mounted once in `App.vue` next to the `Toaster` — asks, and offers two ways out plus "close and do nothing" (× / Esc / overlay → `dismissReLogin()`, the next 401 asks again). **退出** is `logoutFromExpired()` → `/api/auth/logout?redirect=<return url>`, which lands back on `/login?redirect=<return url>` so logging in again returns to the same page. **重新登录** never leaves the page: it opens a **second window** on `/api/auth/login?redirect=/auth/login-done`, and the page — with whatever was typed into it — stays put. Yanking the page away on a 401 both destroys unsubmitted input and hides what happened.
- **The re-login is a popup window, not an iframe, and its success signal has two legs because the session is an httpOnly cookie the frontend can't read.** The iframe version needed Keycloak's realm to drop `X-Frame-Options: SAMEORIGIN` (otherwise the modal is simply blank) and, third-party-cookie rules being what they are, Keycloak's own SSO cookie was blocked inside it, so the password had to be retyped every time. A popup is a *top-level* browsing context: neither applies, and no realm configuration is needed. The one cost is the popup blocker — `window.open()` returning `null` is reported in a toast and the button becomes 「重新打开登录窗口」, the dialog itself never closes. `apps/server/frontend/login-done-page.ts` renders `/auth/login-done` (`LOGIN_DONE_PATH` / `LOGIN_DONE_SOURCE` / `LOGIN_DONE_MESSAGE` live in `@shadecn/shared/auth`, so the page and the dialog cannot disagree on them) (registered *after* `pageGuard`, so an unauthenticated landing bounces back to `/login` inside the popup), `postMessage`s a same-origin `app-auth:login-done` to `window.opener` and closes itself; the dialog accepts the message only when `event.origin === location.origin` *and* the marker matches, then calls `finishReLogin()` → `fetchSession(true)` and only closes if `/api/auth/me` really says logged-in. A 3s poll while waiting is the second leg (message blocked, or `opener` severed by an intermediate page); the same tick notices `loginWindow.closed` and drops out of the waiting state so the button comes back.

**UI Components (shadcn-vue):** Located in `apps/web/src/components/ui/`. Added via the `shadcn-vue` CLI (`pnpm exec shadcn-vue add <name>`, configured in `apps/web/components.json`; run the CLI from `apps/web`) — note the CLI drops new packages into `dependencies`, so move them to `devDependencies` afterwards (see the dependency split below). **Icon library is `@lucide/vue` — the only one.** lucide's v1 rename moved the package from `lucide-vue-next` (0.x) to the scoped `@lucide/vue` (1.x), and the shadcn-vue CLI now generates the new specifier, so the two coexisted for a while: 26 CLI-generated `ui/` components on the new one, 36 of ours on the old. They are unified on `@lucide/vue`. Deprecated names still resolve — `Home`, `Loader2`, `MoreHorizontal`, `Grid3X3` are all re-exported as aliases, so the migration was a specifier swap with no renames. **What v1 did drop is the entire brand-icon set** (`Github`, `Gitlab`, `Twitter`, … are simply gone), which is why `apps/web/src/components/icons/GithubMark.vue` exists: an inline SVG of the official mark, used by both the settings card and the login page (which now share it, since the login page moved into `apps/web/src/`). Reach for that pattern for any other brand, not for a new dependency. The `cn()` utility in `apps/web/src/lib/utils.ts` merges Tailwind classes via `clsx` + `tailwind-merge`. Two components are edited beyond what the CLI generates and must not be clobbered by a re-`add`: `button` carries an extra `loading` prop (spinner + auto-`disabled`, the visual half of the one-click-one-request rule below) and extra `size` variants (`xs` / `icon-xs`). **The CLI rewrites `Button.vue` whenever it is pulled in as a dependency of another component** (adding `command` does it) — `git diff apps/web/src/components/ui/button/` after any `add`, and `git checkout` it back.
- **`command` is a filter-it-yourself list.** Its built-in filtering renders *every* item and hides the misses with `v-if`, which is fine for a 20-line command palette and not fine for the 400+ IANA time zones — `TimeZonePicker.vue` therefore drives the list itself (own keyword ref + own matcher + a hard cap) and uses `Command` only for keyboard navigation, feeding the input through reka-ui's `ListboxFilter` directly instead of `CommandInput` (which is hard-wired to the built-in filter state). Two consequences worth remembering: `CommandItem` **must** sit inside a `CommandGroup` (it injects the group context and throws otherwise), and `CommandEmpty` is useless in this mode — it renders off the built-in filter's hit count, which stays 0, so write the empty state by hand.

**Styling:** Tailwind CSS v4 loaded via `@tailwindcss/vite` plugin. CSS variables for theming (light/dark) are defined in `apps/web/src/styles/tailwind.css` (`apps/web/src/style.css` only `@import`s it plus `vue-flow.css`) using oklch colors. Uses `tw-animate-css` for animations.
- **Which of the two variable sets applies is `apps/web/src/lib/theme.ts`'s job — it is the only thing that puts the `.dark` class on `<html>`** (via `useColorMode`, storage key `app:theme`, default "follow the system"). Everything else about theming was already there; nothing reads the preference directly. **Tailwind v4's Preflight stopped giving buttons `cursor: pointer`** (it follows the browser's native `default` now, where v3 forced pointer), so `tailwind.css`'s `@layer base` restores it for `button:not(:disabled), [role="button"]:not(:disabled)` — the upgrade guide's own snippet. Doing it once in `base` covers shadcn's `Button` *and* every reka-ui trigger that renders a `div[role=button]` (dropdown menus, Tabs, Select), and leaves per-element `cursor-*` utilities free to override it since `utilities` cascades after `base`. Without it every button in the app looks unclickable on hover. Three more rules that are easy to miss: **the first frame is `index.html`'s inline script**, not this module (by the time the bundle parses, a dark-mode user has already been flashed a white page — both places read the same key in the same raw-string format); **`color-scheme` must be declared in both blocks** (`light` on `:root`, `dark` on `.dark`) or the browser paints a white scrollbar over a dark page; and **vue-sonner doesn't look at the class** — it has its own `theme` prop, which `App.vue` feeds from `resolvedTheme`. **vue-sonner ≥2.0 also ships its stylesheet separately and its own entry point does not import it**, so `apps/web/src/style.css` has to (`@import "vue-sonner/style.css"`). Forget that line and toasts still *work* — they just render as unstyled elements with no `position: fixed`, so they join the document flow at the end of the page and stretch it into a scrollbar. The failure is easy to miss because most toasts are click-triggered and short-lived; the one that exposed it fired on page load. The `.dark` palette is deliberately **one step lighter than shadcn's default** (background `0.145 → 0.215`, card `0.205 → 0.255`, …); the login page's own inline CSS carries the same numbers, so keep the two in sync.

**Views — `apps/web/src/views/` is grouped by feature, one folder per area.** Only `apps/web/src/router/index.ts` imports from here, so moving a view means touching exactly one other file.
- `views/Home.vue`, `views/Settings.vue` — the shell pages stay at the root (they belong to no feature). `Settings.vue` is the account + login-methods + appearance + display-preference page (theme lives in `apps/web/src/lib/theme.ts`, dates in `apps/web/src/lib/preferences.ts` — both browser-local, both apply with no save button); its only entry point is the sidebar's bottom user menu, which also holds 关于 and 退出登录 — the middle nav list is pages only. **`apps/web/src/components/settings/LinkedAccounts.vue` is the one card on this page that writes to the server**: it lists the user's `UserIdentity` rows, offers 关联 for providers not yet bound (one account per provider, so a bound provider loses its button) and 解绑 behind an `AlertDialog`, disabled at the last row. Linking is a **full-page navigation** to `/api/auth/link/:provider`, not an XHR — it has to pass through a third party's consent page, same as login and logout — and coming back it is still *not linked*: the card sees `pending` in the identities response and opens a confirm dialog naming the account, which is the whole point (see the auth section). Failures come back as `?link_error=`, which the card toasts once and then strips from the URL (leave it and every refresh re-announces it); success has no query param at all, since success is decided in the dialog. Dismissing that dialog is a legitimate third option: the pending row lives on the server, not on the page, so Esc just means "later" — nothing is bound, the question comes back next visit, and it expires in ten minutes. What has to hold is "no write without a confirm", and that is enforced server-side rather than by refusing to close a modal. Because the card reads the route it needs a router installed, which is why `Settings.test.ts` mounts through a memory router and stubs `@/lib/api`. **关于 is a modal, not a page** (`apps/web/src/components/AboutDialog.vue`, no route — it's one paragraph of blurb, not worth a navigation), and **退出登录 asks first** (an `AlertDialog` in `AppSidebar.vue`) because logging out is an irreversible full-page trip through Keycloak sitting one row below 设置.
- `views/canvas/` — REQ-CANVAS, the one non-demo feature: `PersonalFlows.vue`, `ProjectHome.vue`, `InviteAccept.vue`, `FlowEditor.vue` (see below); the in-page workspace sidebar they share is `components/canvas/CanvasWorkspace.vue`.
- `views/three/` — everything 3D: `ThreeEditor.vue` (REQ-3DEDITOR), `3DScene.vue` (REQ-DIRECTOR), `Canvas3D.vue` / `LightScene.vue` (Three.js scaffolds, not implemented), `Emu3DView.vue` (CSS-only 3D cube via `Cube3D.vue`).
- `views/games/` — canvas games: `Demo3.vue` (brick-breaker), `SnakeGame.vue`, `Game2048.vue` (scoped CSS, no shadcn).
- `views/demos/` — single-page capability checks: `FlowChart.vue` (REQ-FLOW, the Vue Flow interaction demo the canvas feature grew out of), `RichEditor.vue` (REQ-PROMPT), `HiC.vue`, `Example.vue`.
- `Example.vue` and `Emu3DView.vue` have **no route** — they're orphaned view files kept around, see `docs/01-app-shell.md` §3.

**Projects & canvases (REQ-CANVAS, `docs/13-flow-canvas-management.md`)** — the one non-demo feature. A **project** owns canvases and is the permission boundary; the only way in is its share link — one per project, unlimited uses, admins open the 分享 dialog and the link is already there (`GET /api/projects/:id/invite` creates it on read). Four views in `apps/web/src/views/canvas/`, the first two wrapped in one workspace shell (**`components/canvas/CanvasWorkspace.vue`**: an in-page second-level sidebar, `w-56`, whose first item is 「个人画布」 and below it a 「项目」 group — a `+` button on the group header opens the new-project dialog, each project row shows a hover `Trash2` (admins only) that goes through an `AlertDialog` with two refs; the app sidebar has a single「画布」 entry → `/personal`, highlighted under `/personal` and `/projects/*` via `NavItem.activePaths`; `/projects` itself is only a `redirect` to `/personal` for old bookmarks, there is no project-list page any more). The project list lives in a **module-level cache**, `composables/useProjectNav.ts` (`projects / loading / error / refresh()`, first use loads, `resetProjectNav()` for tests), because the two pages are separate route components and the shell remounts on every switch — a per-component list would flash a skeleton each time; create / delete / rename call `refresh()`. `PersonalFlows.vue` (`/personal` — see REQ-SOLO below), `ProjectHome.vue` (`/projects/:projectId`, one route, same-page Tabs for 画布 / 成员 — switching tabs never touches the URL), `InviteAccept.vue` (`/invite/:token`, preview-then-confirm; anonymous visitors get bounced through `/login` by the page guard and land back here), and `FlowEditor.vue` (`/flows/:flowId`, the one route under `BlankLayout`).
- **The editor is split into a hooks layer and a component layer — the view itself only builds the context and places components.** `provideFlowEditor(props)` (in `apps/web/src/composables/flow/`) creates the shared payload once and `provide`s it; every child pulls it with `useFlowEditor()`, so there is no prop drilling and adding a panel touches no existing file. The context bundles `store` + `sync` (`useFlowSync`, see below) + three composables: `useFlowDocument` (load / rename / duplicate / delete / save-state text / `flushBeforeLeave`), `useFlowCanvas` (the Vue Flow glue: `nodes`/`edges` bindings, drag→`node.move`, connect→`edge.add`, viewport sync, cursor-anchored ctrl-wheel zoom, `addNode`), and `useFlowSelection` (just `selectedNodeId` + `select` / `clearSelection`). `useFlowShortcuts(ctx)` adds the keybindings and the two don't-lose-work guards. Note `useVueFlow()` is called inside `useFlowCanvas` at the *root* setup, so the later `<VueFlow>` adopts that instance and out-of-canvas components (toolbar, capsule) can still use `screenToFlowCoordinate`.
- **Node types are a registry, not a hardcoded map — `apps/web/src/components/flow/node-types.ts`.** One entry per `type` declares its component, menu label, icon, default `data` and default top-level fields; `FlowCanvas` feeds `:node-types` from it and `useFlowCanvas.addNode(type)` builds the node from it. **Adding a node type touches this one file** and nothing else. The toolbar does *not* render one button per entry anymore — types will keep piling up and a row of icons is neither recognisable nor affordable, so the add entry is a single `+` that creates `NEW_NODE_TYPE` (currently `text`, a card whose body is edited in place on double-click; `data.text` is its own key, so retitling and rewriting merge per key). That constant is separate from `FALLBACK_NODE_TYPE` (`process`, what an unrecognised `type` renders as — it is the **same constant** `fromYNode` falls back to — defined in `@shadecn/shared/flow-graph`, re-exported from `node-constants.ts` — so the two cannot drift and change the shape of old canvases). `group` is the proof that entries need not resemble each other: fixed size, `zIndex: -1` (a background board must paint under every node), `pointer-events-none` on the body so it doesn't swallow rubber-band selection over the area it covers, resized through the official `@vue-flow/node-resizer` (its stylesheet is imported in `apps/web/src/styles/vue-flow.css`, or the handles are invisible — and that stylesheet declares no `pointer-events`, so the same file has to hand `.vue-flow__resize-control` its events back or the handles inherit the body's `none` and resizing is silently dead) and committed to the doc only on `resize-end` — mid-resize frames are intermediates, exactly like drag. **Its chrome is the shared `FlowNodeChrome`, like any other node**: the name sits *outside*, above the top-left corner, and the toolbar floats top-center — a group used to carry its name inside a title bar, which made it read as a different kind of object when it is just a node with a different body. Groups swap the button row through the `#actions` slot (no duplicate, and its one button is **ungroup**, not delete — `Ungroup` icon, plain ghost, no destructive red: removing the frame loses nothing and undo brings it back, so both a bin icon and the red would be claiming otherwise); placement and when-to-show stay in the chrome, since those must not vary by node type. The one thing that can't move out with the label: **dragging**. `NodeToolbar` teleports to the viewport container, so pressing the label never reaches the node's d3-drag — a group therefore keeps a full-width, 24px grab strip inside its own top edge (invisible until hover), which is also why a rubber band can't be *started* from that band. Removing a group **detaches its children instead of deleting them** (which is why the button reads as ungroup) (`store.removeElements` clears `parentNode`/`extent` and converts each child's parent-relative position back to canvas coordinates — leave the dangling `parentNode` and the whole group snaps to the origin). Dragging a node *into* an existing group (auto-reparent) is still not wired; the data path is.
- **The rubber band is full-containment, edges follow their endpoints, and nothing but the highlight moves while it's being dragged.** `:selection-mode="SelectionMode.Full"` (Vue Flow's default, written out because it's a product rule: clip a corner and you'd select every node the band sweeps past). Nodes flip highlight one by one as the band grows — that's live already, since Vue Flow applies selection changes internally on every pointermove. Edges connected to a hit node count as selected, but Vue Flow's own pass **can't be relied on**: it diffs against the previous frame's edge-id set, and `removeSelectedElements()` on pointerdown clears the elements without clearing that cache — so two box selections in a row that hit the same edge leave it unselected the second time. `useFlowCanvas` therefore re-asserts the rule itself (`getConnectedEdges` → `addSelectedElements([...nodes, ...edges])` — pass the nodes too, that action means "the selection is exactly this"), and only **while the band is active**: clicking an edge empties the node selection, so applying the rule outside the gesture would immediately deselect the edge just clicked. Selected edges are styled in `apps/web/src/styles/vue-flow.css` (theme-default's `#555` on a gray line is a state you can't see). **No toolbar is on screen during the drag** — `canvas.boxSelecting` (Vue Flow's `userSelectionActive`) gates both the per-node chrome (the band sweeping over the first node makes it briefly the single selection, so duplicate/delete would flash) and the selection toolbar (which would otherwise chase the moving bounding rect); they appear on release.
- **A group is created by grouping a selection, never from the toolbar** (`canvas.groupSelection()`, reached from `FlowSelectionToolbar`): it grows around nodes that are already selected, so "add an empty group, then drag nodes in" is both backwards and impossible (auto-reparent doesn't exist). The box is the selection's bounding rect (`getRectOfNodes`, i.e. `computedPosition` + measured dimensions) plus padding; nodes already inside another group, and groups themselves, are excluded. Two things it can't be built without. **The group and its children go in one transaction** (`store.groupNodes`, `extent: 'parent'` included) — split them and every child briefly points at a `parentNode` that doesn't exist yet, which is `NODE_MISSING_PARENT` plus a whole group of nodes jumping to the origin, and undo would leave half a group behind. And **`extent: 'parent'` must be withheld from Vue Flow until the parent has been measured** — `extentReady()` in `useFlowCanvas`'s `nodes` adapter, which hands over `extent: undefined` while `findNode(parentNode).dimensions.width` is still 0 (write the key explicitly; a key you stop sending keeps its old value through `Object.assign`). Vue Flow derives that bound from the parent's `dimensions`, so before the group's first render the bound degenerates to a point and every child is clamped to `parent - its own size` — the whole group piles up outside the box's top-left corner. **The gate belongs in the adapter, not in the write path**: delaying the *write* only protects the author, and the bug's real victim is everyone else — a peer reads `extent` straight out of the doc the moment the update lands, long before the new group node has rendered on their side. That is what "打组没同步给别人" actually was: the data arrived intact, the receiver's view mangled it. The doc is correct throughout, which is why a reload "fixes" it and why it is easy to miss.
- **Components live in `apps/web/src/components/flow/`**, each owning one region and reading the context directly: `FlowCanvas.vue` (Vue Flow + background + minimap, plus a `<slot/>` for extra in-canvas overlays), `FlowViewControls.vue` (zoom/fit/lock + undo/redo, top-right), `FlowTitleCapsule.vue` (top-**left**: logo/home + inline-editable name + save state + menu, owns its delete confirm), `FlowToolbar.vue` (bottom, canvas-content actions), `FlowSelectionToolbar.vue` (floats above a **multi-node** selection — `NodeToolbar` takes an id *array* and positions itself over their bounding rect; holds 打组), `ProcessNode.vue` / `TextNode.vue` (the nodes themselves — body only), `FlowNodeChrome.vue` (what every node type shares: the external name label with double-click rename, and the duplicate/delete `NodeToolbar` shown only when this node is the single selected one — so it and the selection toolbar are never on screen together), `FlowSnapGuides.vue` (the drag alignment guides), `FlowConnectionEndedDialog.vue` (the modal for a sync channel the server ended for good — one copy block per reason; the expired-session case is deliberately *not* here, it goes to the app-wide `SessionExpiredDialog`. It is non-dismissible **except for `too-large`**, and that exception is the point: for the other reasons nothing the user does on this page helps, while an over-quota canvas is fixed precisely *by deleting on this page* — a modal you can't close would block the only way out). **There is no property panel**: clicking a node selects it and nothing more. Per-node editing lives on the node (double-click to rename, the toolbar for duplicate/delete), so a selection never steals a third of the canvas.
- **Snapping (`useFlowSnapping` + `apps/web/src/lib/flow-snap.ts`) applies to dragging only — never to nodes already placed.** Both snaps (grid + alignment guides) are **always on: no toggle, no toolbar button, no persisted state** — the grid *is* the visible background dots and the guides only appear when something genuinely lines up, so both are the default feel; a switch would only make you click once to get it and force the docs to explain two states. Grid is `FLOW_GRID_SIZE`, the same constant `<Background :gap>` uses — a grid you snap to but can't see lines up with nothing. The guide tolerance is **6 screen pixels ÷ zoom**, not a flow-coordinate constant, or the magnet grows 4× when you zoom in. **Vue Flow's own `:snap-to-grid` is deliberately unused**: besides dragging it also rounds a node's position at *mount* (`NodeWrapper`'s `clampPosition`), a local-view-only shift that never enters the doc, so someone with snapping on and someone without would see different canvases. Both snaps are computed in one place and produce one delta (guides win over grid — the alignment is the more deliberate intent); multi-select drags snap by the group's bounding box so relative positions survive. The correction runs *in* `onNodeDrag`, after Vue Flow has written the raw pointer position and before the frame paints — it can't accumulate, because every drag event recomputes from the pointer, which is exactly why the magnet releases when your hand moves off the line. Snap first, *then* `publishDrag`, or collaborators watch the unsnapped position. The guide overlay lives in the `#zoom-pane` slot next to the presence cursors (flow coordinates, only stroke width and dash counter-scaled).
- **Canvas behaviour is Vue Flow's job, not CSS's.** Anything that has to live *on* the canvas — a label outside a node, a per-node toolbar, a resize handle, an overlay that must follow zoom/pan — is built from the official packages (`@vue-flow/node-toolbar`, `@vue-flow/node-resizer`, `<Panel>`, `<Handle>`, `<NodeToolbar>`, …), following [the guide](https://vueflow.dev/guide/) and [the examples](https://vueflow.dev/examples/). **Do not hand-roll positioning** (`absolute` + `transform`, viewport math, manual `screenToFlowCoordinate` re-anchoring) when a Vue Flow component already does it — a hand-written overlay silently breaks under zoom, and the transform math it duplicates is exactly what the library maintains. Tailwind classes stay for *appearance* (type scale, color, spacing inside the slot); *placement* comes from the component's props (`position` / `align` / `offset`). Missing package → add it as a `devDependency` (it's frontend, see the dependency split) rather than reimplementing it. `ProcessNode.vue`'s external top-left name label is the reference case: `<NodeToolbar :is-visible="true" :position="Position.Top" align="start">`.
- **State: `apps/web/src/stores/flow/` (Pinia) is a *projection of a Y.Doc*, not a store of record.** The canvas content **is** the Yjs document (shape in `@shadecn/shared/flow-doc` — one implementation that both the browser and the server import; the frontend's incremental projection — `changedTopLevelKeys` / `projectMap` / `readFallbackViewport` — is `apps/web/src/lib/flow-projection.ts` (formerly `flow-doc.ts`), and what is left server-side in `apps/server/collab/flow-doc.ts` is only `readGraphFromDoc` and `pruneDanglingEdges`): `nodes`/`edges` are `Y.Map<id, Y.Map>` and each node's `data` is a nested `Y.Map` again, because Y.Map merges *per key* — one person retitling while another drags merges cleanly, whereas storing a node as one JSON blob would let the later write clobber the earlier one wholesale. **Business fields sit flat on `data`, never wrapped in a `config` object (graph schema v2)** — the same argument one level down: a single `config` key would let one person's edit to `config.prompt` clobber another's to `config.model`. `data.kind` is gone with it: a node's business type **is** its top-level `type`, which is the key of the node-type registry. **A batch of independently-edited elements (3D objects, timeline tracks, a resource list) goes one-element-per-key — `<prefix>.<id>`, flat, plain JSON — never into one `data.scene` blob and never into a nested `Y.Map`** (`apps/web/src/lib/flow-collection.ts`; write and delete land in one transaction via `store.writeNodeData(id, {set, remove})`). The blob is the `config` bug one level down: everyone in the batch shares a merge unit, so two people posing two different characters clobber each other. The nested `Y.Map` fixes merging but puts *structure* into the CRDT layer, and that is the one thing this doc can't version: with no version number in a Y.Doc, an old and a new client write **different types to the same key**, the winner is decided by clientID (i.e. randomly), the loser's whole subtree vanishes, and the losing side's code throws `TypeError` — read-time upgrading (`upgradeNodeData`) rescues a changed *shape*, never a changed *type*. Flat prefixed keys are invisible to the CRDT layer instead (shared has **two write doors**: `toYNode`/`toYEdge` for elements the editor creates, and `writeNode`/`writeEdge`/`applyGraphToDoc` for the server's legacy-`graph` migration; `toYEdge` writes `null` for an absent handle while `writeEdge` writes nothing — they read back identically, and a test pins that): `toYNode`/`fromYNode` (one copy, in shared), `duplicateNode` and the whole server are untouched, and an old client passes the unknown keys through as it already does. Measured on the 43.7KB director-console sample: 26,626 B per element edit and guaranteed clobbering → 3,358 B and both edits surviving, for +5% doc bytes. Three rules: **a key's type is fixed from its first write and can never change** — that is the precise form of the rule, so a brand-new key that is `Y.Text` from day one is fine (an old client `toJSON()`s it to a string and passes it through, never writing plain to it), while *upgrading* an existing plain key is the thing that destroys data; **ids must be stable, never array indices** (an index shifts when someone else inserts, and your write lands on their element — mint one with `createId()` if the source data has none, as the sample's 5 uuid-less objects and its id-less keyframes both do); and **prefixes must not nest** (`dc.obj` + `dc.obj.pose` collide — convention only, nothing enforces it). Granularity stops at one element per key; two people editing *the same* element loses one side, and that gap is **deliberately left open**, exactly as it is for every other element on the canvas (§4.0.1: concurrent editing is allowed, presence only *shows* who else is touching a node — `occupantsOf` is already wired into `FlowNodeChrome`). Narrowing it belongs on the occupancy/notice side rather than in a finer CRDT, and the cheap forms come first — a soft warning, or a conflict check at commit time — not read-only enforcement, whose lease/TTL/leak handling plus Vue Flow's `Object.assign` trap (write the flags explicitly as `true` *and* `false`, or the element stays dead after the lock lifts) costs far more than this one gap is worth. v1 data is upgraded **on read** — pure, idempotent, and deliberately never written back, because a projection that writes produces a Yjs transaction that enters everyone's undo stack and broadcasts. Y.Docs carry no version number, so v1 is recognised by shape (a string `kind` *and* an object `config` together); `Flow.graph` rows do carry one, and **`parseGraph` must keep accepting v1** — every stored projection is v1 and `readGraph()` is the only path old canvases take into Yjs, so rejecting them would blank each one on first open. The projection is **incremental**: `observeDeep`'s events name which top-level keys changed, only those get re-parsed, and everything else keeps its previous object identity — which Vue Flow relies on to skip re-syncing untouched nodes (a `null` from `changedTopLevelKeys` means "can't tell, redo everything"). The one rule: **every content change goes through `store.mutate()`**, which wraps it in a Y transaction tagged `LOCAL_ORIGIN`; components never touch a Y.Map directly, or the change is neither undoable nor synced. Undo is `Y.UndoManager` with `trackedOrigins: [LOCAL_ORIGIN]` — that single option is what makes Ctrl+Z undo only *your* edits and leave a collaborator's alone; `separateUndo()` (`stopCapturing`) splits operations that would otherwise merge inside the 400ms capture window. There is **no save, no revision, no 409, no dirty state** — edits are live and the server persists the same stream. The one exception is a *notice*, not a state: when the server's write queue starts failing it broadcasts a **stateless** message to the room and the status line reads 「服务器暂时无法保存」 (`onStoreStateChange` → `broadcastStateless` → the transport's `onStateless` → `saveFailed`). Four rules there, each of which is a bug if you skip it: broadcast **only on flip** (good→bad, bad→good — stores are 2–10s apart, so per-store notices are pure noise), **re-send to a joining connection** (`connected` reads `isStoreFailing`, or whoever arrives after the flip sees 「已同步」 on a canvas the server cannot store), **clear `saveFailed` when the transport is replaced** (it describes *that* server; keeping it across a reconnect pins the UI at "cannot save" forever), and **parse defensively** — stateless is a general side channel, and a payload you can't read must never throw, because that kills the connection's message loop. It is deliberately not a `fatal`: that tier means "won't fix itself", and this one will. Drag *intermediates* deliberately stay out of the doc (one drag would otherwise emit dozens of updates and audit rows); only the settled position is committed in `onNodeDragStop`, while the in-flight motion rides the feedback layer. **Panning and zooming are not canvas data and take a second, separate path**: `setViewport()` → `setUserState(key, value)`, which never enters the doc and never touches undo (undo must not yank the viewport back). **`setUserState` only buffers — it sends nothing.** The buffer is flushed to `PATCH /api/flows/:id/user-state` by `noteLocalEdit()`, which every local edit (`mutate`, `undo`, `redo`) calls. The shape is **leading send + debounced tail**: the first edit after a quiet period fires immediately (no window), everything after it goes through a `useDebounceFn` (`USER_STATE_FLUSH_DELAY`) that lands the final state once the hand stops, with a `maxWait` (`USER_STATE_FLUSH_MAX_WAIT`, 10s) so nonstop editing still lands periodically. So a view-only visit produces **zero** write traffic, a burst of editing produces one PATCH at its start and one at its end, and **no edit is dropped**. Neither half alone works: a plain debounce lags (it never fires while someone draws continuously, and this PATCH doubles as a heartbeat that can't wait), a plain throttle discards the tail of the window. The tail flush skips itself when nothing happened after the leading send, so a single edit costs exactly one request. **The window always fires a request, even when the view never moved** (it falls back to sending the current viewport), because that PATCH doubles as the session's heartbeat: content rides the WebSocket and produces no HTTP at all, the collab server's minute-by-minute revalidation is deliberately non-renewing (`loadSession(..., { refresh: false })`), and without this one request someone could be idled out *while actively editing*. Net rule: editing = one PATCH per window = session stays alive; looking = no requests = it idles out as it should. Panning without editing is caught by the flush in `saveNow()` / `reset()` on the way out. This is why the viewport rides editing rather than firing on its own: once Yjs took over content, a self-triggering viewport save was the editor's *only* periodic HTTP request — merely looking at a canvas would PATCH. To persist another per-user thing, add a field to `FlowUserState` (in `@shadecn/shared/flow-graph` — one place now), a parser to the server's `FLOW_USER_STATE_PARSERS` (it is a mapped type over the `FlowUserState` keys, so forgetting the parser is a compile error), and call `setUserState` — batching, retry and flush-on-leave are already there. Each viewer gets their own row, so `meta.viewport` in the doc is only the first-open fallback.
- **Continuously-changing values — a dragged slider, a scrubbed timeline, typed text — take one shape: a local draft owns the screen, the draft is throttled onto awareness if peers should see it, and the doc is written *once* when the gesture ends, bracketed by `separateUndo()`** (`docs/13` §3.7.2). **The no-release kind (rename in place, edit body text) is a composable, not a pattern to copy: `useDraftField` (`apps/web/src/composables/flow/useDraftField.ts`)** — `{current, commit, normalize?, equals?, focus?}` in, `{editing, draft, start, commit, cancel}` out. It owns the draft ref, the `editing` flag and **both `separateUndo()` calls**, and it drops the three no-op cases for you: value unchanged, `normalize` returning `null` (an emptied title is a slip, not a rename), and the double submit you get because **Enter and blur routinely both fire** (the second `commit()` sees `editing` already false). `TextNode.vue` and `FlowNodeChrome.vue` are its two consumers. The with-a-release kind is still hand-written — copy `onNodeDragStart/Drag/DragStop` in `useFlowCanvas.ts` — and differs by exactly one step, throttling the draft onto awareness; that step is deliberately not in the composable because it needs a new awareness field (`transform` only carries `{x, y}`) and has no consumer yet, and when it does, `watch(draft, useThrottleFn(publish, throttleMs))` in the component is the whole change. **Throttling doc writes instead is the wrong fix**: the cost isn't doc size (60 dragged frames grow it from 33,411 to 33,438 — Yjs GCs overwritten Map keys well), it's broadcast + persistence (1.59MB for those same frames), and throttling can't fix the two things that matter — a half-dragged value shouldn't survive a refresh or be undoable, and the doc's guaranteed-ordered-merged delivery is the wrong channel for data that is *fine to drop*. **One undo item comes from committing once, not from `captureTimeout`** — a >400ms pause mid-gesture splits the window. Four rules for the awareness half: it's a *new* feedback field, not a reuse of `transform` (whose value type is `PresencePoint`); send only the numbers that changed, never the whole element (awareness is a *broadcast* — at 25fps a `{x,y}` packet is 45KB/s in a 10-person room, a 4.8KB object packet is 2.16MB/s, so **shrink the packet before lowering the frame rate**, which costs nothing while a lower rate costs responsiveness); clear it when the gesture ends (y-protocols replays local state every 15s, so a stale draft is rebroadcast forever); and keep **both** throttle edges (`useThrottleFn(fn, ms, trailing, leading)` — awareness is last-writer-wins *state*, not an event stream, so dropping middle packets is free but dropping the last one is a bug; the same property is why lowering the rate costs only smoothness, which is what makes the **adaptive window** safe: `ms` is a getter, `feedbackThrottle(roomSize)` in `apps/web/src/lib/presence.ts`, re-read on every call because VueUse's filter does `toValue(ms)` per invocation. It returns the plain `FEEDBACK_THROTTLE` (60ms — one window, one buffer for every feedback field: cursor, selection, drag geometry and connecting all go through `publish()` in `useFlowPresence`, so however many changed, one window sends at most one packet, and an unchanged value sends nothing) up to `FEEDBACK_THROTTLE_ROOM` people — i.e. unchanged for every realistic room — and widens stepwise beyond that, capped at `FEEDBACK_THROTTLE_MAX` (below ~6fps a peer cursor reads as frozen and you may as well stop publishing). **That curve is a judgement, not a measurement, and it is second-order** — shrink the packet first). Text splits by field: short/atomic commits on blur; long-form wants a debounced commit (accepting that >400ms debounce means finer undo — durability and undo granularity trade off, pick one); character-level co-editing needs `Y.Text`, which must be a brand-new key **and** requires fixing `duplicateNode`, whose projection→`structuredClone`→`toYNode` path silently flattens it back to a plain string. And while dragging locally the panel must read its own draft, never the projection — same reason `useFlowCanvas` freezes the `:nodes` array.
- **Personal canvases are a different *kind* of canvas, not a different transport (REQ-SOLO, `docs/16-personal-flow.md`).** A **personal space** is a `Project` with `kind='personal'` and a unique `personalOwner` (lazily created by `GET /api/projects/personal`, which creates on read); canvases inside it have `mode: 'solo'` — **derived from the owning project, never stored on `Flow`**. Nothing about content forks: same Y.Doc, same `Flow.ydoc` bytes, same projection, **and the same transport** — `apps/web/src/composables/flow/sync/` has exactly one, `collab.ts` (Hocuspocus WebSocket), and a personal canvas opens its room the moment the metadata arrives. (It used to ride HTTP push/pull and switch to the WebSocket only when an agent run started; that switch, the `solo.ts` transport and its client API are gone — the agent writes into the server's live room, so a canvas that isn't in the room can't see what the agent does, and "switch on first send" was a whole hand-off protocol for no remaining benefit. The server's `GET/POST /api/flows/:id/doc` route and `flow-writer.ts`'s `applyFlowUpdate()` still exist but no longer have a frontend caller.) Three rules hold it together. **`mode` now only says what the canvas *is*** — where leaving it lands (`/personal`), the wording of the terminal dialogs and the status line (nothing on a personal canvas may mention 协作 / 协作者), and whether the presence layer runs (`useFlowPresence(sync, mode)`: off for `solo`, so neither your own other tab nor yourself shows up as a collaborator). **The doc and its IndexedDB cache are created immediately; the transport still waits for the metadata** — which is why `context.ts` computes `mode` only when `store.meta.id === flowId` (connecting first would work, but a canvas you can't open would then report itself twice: the page's load error *and* the room's handshake refusal). **The room is owner-only and presence-free on the server too** — `authorizeCollab` lets only the `personalOwner` into a personal room (the client-side split is not an access control; a hand-rolled provider would otherwise put someone else's cursor on your private canvas) and `beforeHandleAwareness` empties every awareness frame for it. The client still has to *send* awareness: on a personal canvas presence resets the local state to `{}`, **never `null`** — y-protocols' 15s local-state replay is the connection's only client→server heartbeat (the server's `timeout` is "time since last message", it sends no ping), and a `null` state stops the replay, so an idle personal canvas would be timed out and reconnected every 30s. Because it is a normal collab room, **every collab rule applies, including one-window-per-user** (`exclusive.ts`): opening the same personal canvas in a second tab knocks the first one offline, and `FlowConnectionEndedDialog` / `syncTextOf` word that as 「这张画布已在另一个窗口打开」 rather than 「协作会话已过期」. Personal spaces reject invites / member changes / delete / rename with **403** and are filtered out of `GET /api/projects`; `PROJECT_LIMITS.flows` does not apply to them. **On the UI side the two share one workspace screen but are separate routes, not two Tabs of one page** (`/personal` vs `/projects/:id`, switched from the in-page sidebar of `CanvasWorkspace`): a Tab bar says "two views of one thing", but a project has a second level under it (members, sharing, roles) and a personal canvas has none — no header button, empty state, or available action is shared between the two sides. Both lists are the same `FlowList` component (a personal space *is* a project to the API, so it only needs a `projectId`), and keeping them separate routes is what lets *both* own their URL query (`syncQuery`) — side-by-side Tabs had to share one `?page=`, so only the project side could keep it. Deleting a project is only offered from the sidebar row (not the project header); deleting the one currently open goes to `/personal`. **Anywhere the UI leaves a canvas, the destination is keyed on `mode`, never on `projectId`** — `useFlowDocument`'s `backPath()` (the capsule's home button, its menu item, and where a delete lands) sends solo to `/personal` (and the collab fallback without a `projectId` too), and its icon/label follow the same check. A personal space *is* a project in the database and `meta.projectId` really does point at it, but following that lands a private canvas on a project home offering members and sharing — three things the server 403s for personal spaces. The reverse door is shut too: `ProjectHome.vue` `replace`s to `/personal` when the loaded project has `kind === 'personal'` (old bookmarks are the only way in).
- **Collaboration splits into two layers with one question deciding which (`docs/04-realtime-collab.md` §4.0): *should it still be there after a refresh?*** Yes → **data layer**: a Yjs shared type, which means CRDT merge, undo, and persistence. No → **feedback layer**: an awareness field, ephemeral, dropped frames are fine. `useFlowSync(flowId, mode)` owns the doc and its transport; the collab transport (`sync/collab.ts`) owns the one Yjs connection under both — a `HocuspocusProvider` (room `flow:<flowId>` passed as `name`, not in the URL; identity is the httpOnly `sid` cookie the handshake carries, gated server-side in `apps/server/auth/ws.ts`). The same doc also carries a **`y-indexeddb`** cache (db name = room name), which is what makes edits survive going offline and closing the tab — they re-send on reconnect. Loading is therefore gated on *server-synced **or** local cache has content*, and the offline banner ORs in `navigator.onLine` because the provider needs a heartbeat timeout (tens of seconds) to notice a pulled cable. Teardown order matters: provider → indexeddb → doc. **`vite.config.ts` must keep `resolve.dedupe: ['yjs', 'y-protocols']`**: we and the provider each `import * as Y from 'yjs'`, and Vite's prebundling otherwise ships two copies — `instanceof` across them is always false, which would silently turn `@shadecn/shared/flow-doc`'s `value instanceof Y.Map` checks into an empty canvas. and hands out a `session` that changes on reconnect/route-change; the store takes its `doc` and the presence layer takes its `awareness`. Dependency order is a straight line — `selection`/`sync` → `presence` → `canvas` — and `useFlowCanvas` is the **only** thing that knows all three: `useFlowPresence` doesn't import selection or Vue Flow, it just offers "publish" and "read others", which is why a new feedback signal costs one setter plus one computed and touches nothing else.
- **Data layer — the Y.Doc is the source of truth, and the server subscribes to it.** `apps/server/collab/persistence.ts` implements Hocuspocus's `onLoadDocument`/`onStoreDocument`: first joiner loads `Flow.ydoc`, writes are debounced by the framework (2s, 10s ceiling) and skipped entirely when the state vector is unchanged, the derived `graph` projection is written **only in `beforeUnloadDocument`** — not under `onStoreDocument`'s `clientsCount === 0`, because Hocuspocus only re-stores on last-leave if a debounced store is still pending, so "edit, wait two seconds, close the tab" never fires it (verified) — and SIGTERM does `closeConnections()` + a direct per-room store (`flushAllRoomsToDatabase` — **not** `flushPendingStores()`, whose triggered store only reaches our queue after a microtask chain, so a synchronous sample sees an empty queue and the last debounce window is lost) + drains our own write queue. **A store is read → merge → CAS write, and the *merge* is the part that matters.** Writing `Y.encodeStateAsUpdate(doc)` straight into the `ydoc` column is a full overwrite; that is only safe while this process is the sole writer. Under `CLUSTER_MODE=redis` a pub/sub hiccup forks the two instances' documents and the later writer wins outright. **Adding CAS alone does not fix it** — `where: { revision }` proves nobody interleaved between *your* read and *your* write, not that your document is a superset of what is stored: an instance that wrote before you read gives you a fresh `revision`, your CAS passes, and you overwrite it anyway. So each store re-reads `ydoc`, `Y.applyUpdate`s it into the in-memory doc under the `'persistence'` origin (never `local` — it must not enter anyone's undo stack), and *then* CAS-writes; `count === 0` re-reads and retries, up to `MAX_STORE_ATTEMPTS`, after which it throws to the retry table below. The merge is idempotent, so on a single replica it reads back a subset, produces no update event, and costs nothing but the read. Redlock (`lockTimeout: 10_000`, raised from the 1s default that a large doc blows straight through) is now only an optimization — correctness lives in the CAS, which also covers Redis being down entirely. **A failed store MUST propagate — never swallow it, and this is the one rule in this file most likely to get re-broken by a well-meaning `catch`.** Hocuspocus's two data-loss protections are both *triggered by the hook throwing*: `onStoreDocument` throwing makes `storeDocumentHooks` keep the document in memory ("Document stays in memory to avoid data loss"), and `beforeUnloadDocument` throwing makes `unloadDocument` `return` before `documents.delete()`/`destroy()`. The write queue used to `.catch()` the error into a `console.error` and resolve — which silently disarmed both, so one database hiccup during "close the tab" lost that round of edits for good (docs/19 §4.1). Propagating is only two-thirds of it: the doc stays in memory but **nothing ever retries** (`onStoreDocument` is debounce-driven and by then nobody is editing), so failures are registered in `failedStores` and `retryFailedStores()` sweeps them every 30s, serially, clearing each on success — `GET /api/collab/health`'s `owed` is that table's size. The inverse rule holds for the **shared layer**: `sameAsStored` (read) and `rememberStoredVersion` (write) are *cache* operations, so they fail open — worst case is one redundant write, whereas failing the store would stall persistence whenever Redis twitches (§4.2 a). `rememberStoredVersion` must stay `async` even though its body is one line: the shared-layer lazy proxy resolves its implementation on first call and **throws synchronously** when Redis is down, and a synchronous throw sails straight past the caller's `.catch()`. **No y-leveldb** (native module) and no `@hocuspocus/extension-database` (a thin wrapper over the same two hooks): persistence is only load/store, so it writes the app's own `flow` table. **Legacy migration is `onLoadDocument` itself** — a canvas whose `ydoc` is NULL gets its old `graph` JSON poured into the doc on first open, so there is no migration script and no downtime. `Flow.graph` survives as a **read-only projection** the server derives on write (list counts, thumbnails, future read-only previews); the editor never reads it. There is **no per-update audit log** — the old `FlowOperation` table is gone, and with it any notion of history or rollback; `Flow.ydoc` is a converging snapshot (Yjs gc reclaims overwritten content), so nothing accumulates per edit. Since content no longer passes through any REST route, validation moved here too: the quota (`apps/server/collab/quota.ts` — **bytes only**: 1MB/message, 20MB/doc; node and edge counts deliberately have no ceiling, they were a product judgement rather than a guardrail and the byte line already covers the resource side) is measured in `onChange` and enforced in `beforeHandleMessage`, and it **can only refuse before applying**, because an applied-and-broadcast Yjs update is unrecallable. Refusal **never throws** — Hocuspocus closes the connection on a thrown message and the reconnecting provider resends the same message forever; it flips the connection `readOnly` instead (writes get NACKed, reads and awareness keep working). The quota is two-tier: over the *soft* limit only marks the room and still accepts writes (deleting is the only way to shrink back, and deletes are writes too — the mark clears at the next byte re-measure, ≤1s, since measuring means serializing the whole doc and can't run per message), the *hard* ceiling (soft × 1.25) locks the room read-only until it unloads. **The doc limit and the projection limit are two different numbers on purpose** (`COLLAB_LIMITS.document` 20MB ≥ `GRAPH_LIMITS.bytes` 2MB, never the other way round): the projection is JSON that ships inside `GET /api/flows/:id`, the content is binary that only rides the WebSocket, so a doc between the two simply stops refreshing its projection (`deriveProjection` returns null and keeps the previous one — stale list counts, content untouched, and duplicate copies `ydoc` anyway). `onStoreDocument` prunes dangling edges (the legitimate product of one peer deleting a node while another connects to it) under a `'gc'` origin so the cleanup never enters anyone's undo stack. **Anything that mutates the graph must go through the store** — Vue Flow's own defaults will happily bypass it (`deleteKeyCode` under `applyDefault: true` edits its internal nodes/edges directly, so a deleted edge never synced or persisted). `FlowCanvas` passes `:delete-key-code="null"` and `canvas.deleteSelection()` is the single delete path.
- **Feedback layer — awareness carries who's here, where their cursor is, what they're dragging, and what line they're pulling.** `apps/web/src/lib/presence.ts` is the pure, socket-free half (color hashing, defensive parsing of peer state, occupancy arbitration) and keys elements as `node:<id>` / `edge:<id>` so a third kind costs one `ElementKind` value. **The server rewrites the identity in every awareness update** (`beforeHandleAwareness` → `enforceIdentity`): clients may report any cursor/selection they like, but `user.id`/`name`/`avatarUrl` are replaced with what `onConnect` authenticated, so nobody can impersonate a teammate. Two more guards live on the same path: awareness entries are bound to the socket that first published their `clientID` (`dropForeignClients` — forged entries carrying a teammate's `clientID` are dropped, claims released on disconnect), and membership + session are **re-validated every minute** for live connections (`revalidateConnections`) — being removed from a project kicks an open WebSocket too, not just future handshakes. That sweep passes `{ refresh: false }`: it may only *read* the session, never renew it, or an open tab would keep its own session alive forever and idle timeout would stop meaning anything (renewal is the job of real requests — the handshake itself, then the edit-triggered user-state PATCH). **Occupancy arbitration exists and is tested but is deliberately not wired into the canvas right now** — anyone may edit anything concurrently and the CRDT merges it; the node label only *shows* who else is touching it. To reinstate the restriction, feed `presence.lockedKeys` back into the nodes'/edges' `draggable`/`selectable`/`updatable` in `useFlowCanvas`, and write those flags **explicitly as `true` as well as `false`** — Vue Flow merges node props with `Object.assign(existing, incoming)`, so a key you stop sending keeps its old `false` and the element stays dead after the lock lifts. See `docs/04-realtime-collab.md` §4.0.1.
- **One user, one canvas, one connection — and the newest window wins** (`apps/server/collab/exclusive.ts`). Opening the same canvas in a second browser/tab kicks that user's older connections offline — personal canvases included, since they are collab rooms too; the old window gets a non-dismissible 「协作会话已过期，请刷新页面」 (「这张画布已在另一个窗口打开」 on a personal canvas) (`FlowConnectionEndedDialog.vue`) and **stops reconnecting**. The rule is per *room × user*, not per user — having canvas A and canvas B open at once is normal work. Three things it can't be built without. **The holder registry lives in the shared layer** (`SharedMap`), because the two windows are very likely on different replicas and a local-only check kicks nobody; `connected` handles the local half on the spot, a 3s sweep converges the cross-instance half and renews the holder's TTL. **Kicking must close the socket, not just the connection** — Hocuspocus's `connection.close()` detaches the doc connection and sends a CLOSE message but leaves the socket open, and the client's next message (awareness heartbeat, ~30s) is re-authenticated as a *fresh* document connection: the old window resurrects itself and kicks the new one, forever. So it sends both the CLOSE message and a real close frame (`4409` / `session-superseded`), and the client accepts either signal. **The client must stop reconnecting itself** (the collab transport's `onClose` → `provider.disconnect()`), or the retry handshake reads as yet another new window and knocks out the tab the user is actually in; `disconnect()` leaves the doc and awareness intact, so the canvas stays on screen — just unsynced until a refresh takes it back. It is a UX rule, not an access gate (that one is `onConnect` / `revalidateConnections`), so a failing shared layer **fails open**, and with login disabled there is no identity to key on and exclusivity is simply off.
- **Four refusals are terminal, and the client must tell them apart** (the close codes and reasons — `CLOSE_SUPERSEDED` / `CLOSE_UNAUTHORIZED` / `CLOSE_REVOKED` / `CLOSE_QUOTA_LOCKED` and the `CloseReason` type — live in `@shadecn/shared/collab` alongside `COLLAB_PATH`, `FLOW_ROOM_PREFIX`, `STORE_STATE_MESSAGE` and `FLOW_STATE_VECTOR_HEADER`; `apps/server/collab/close.ts` re-exports them and adds the server-side closing helpers; client side `sync/collab.ts`'s `classifyClose`; `docs/04-realtime-collab.md` §4.4): `4409`/`session-superseded` (a newer window took over → refresh), `4401`/`Unauthorized` (session gone → the app-wide `SessionExpiredDialog`, then reconnect in place), `4403`/`permission-revoked` (still logged in, just not allowed in this room — not a project member, canvas deleted → leave), `4413`/`quota-exceeded` (the canvas hit the hard content ceiling and the room was locked and cleared — **the only one that is not about this person**: everyone in the room gets it, and it maps to `too-large` on both kinds of canvas). Two things the copy has to get right: `forbidden` must cover *both* "deleted" and "not a member" in one sentence (the server deliberately doesn't distinguish them) and land on `/projects`, not the project home the second half can't open — **except on a personal canvas**, where `forbidden` can only mean "this canvas is gone" and both the wording and the destination (`/personal`) change; and **the person doing the deleting gets kicked too** (the route revokes before answering 204, so the close often beats the response), which is why `remove()` calls `sync.leave()` *before* the request — otherwise deleting your own canvas reports itself as an accident — and `sync.stay()` if the delete fails, or a later genuine kick would be silent. `authorizeCollab` returns which one (`CollabDenialReason`); collapsing the two is not cosmetic — a viewer whose session idled out *by design* would be told 「你已不是这个项目的成员」. Lumping any of them in with "offline" is worse still: the provider retries forever (`maxAttempts: 0`), the status line keeps promising 「恢复连接后自动同步」, and everything drawn from then on lands in IndexedDB and never leaves.
- **The server signals this over two different paths, and the client must handle both.** ① A connection that was already established gets closed — that goes out **on two legs**, because `connection.close()` detaches the doc connection and sends a CLOSE *message* but leaves the socket open, so the client's next message (awareness heartbeat, 15s) is re-authenticated as a fresh connection and the window resurrects itself; the real close frame is the second leg. ② **The handshake is refused (`onConnect` throws) — no socket close and no close code at all.** Hocuspocus only replies with a `PermissionDenied` message carrying `error.reason ?? 'permission-denied'`, which the provider surfaces as `onAuthenticationFailed({reason})` — **`onClose` never fires**. So the server must throw an error carrying `reason` (`denialError`), and the client must handle `onAuthenticationFailed` and `disconnect()` itself, or an authenticated-but-refused socket spins until the 30s server timeout, reconnects, and spins again — forever, while the UI says 「同步中…」. Path ② is the common one: reopening a canvas after being removed from the project, or reconnecting after the session expired. **Hence `reason` is the discriminator, not `code`** — it is the only thing both paths carry — and both paths funnel into one `endConnection()`. `4401` deliberately does *not* navigate to `/login`: `requestReLogin()` re-logs in inside an iframe so the canvas and its unsynced edits stay on screen, and a watch reconnects once the session is really back (gated on actually-authenticated, since dismissing the dialog also clears `sessionExpired`).
- **Revoking access kicks the live connection on the spot; the periodic sweep is only the backstop** (`apps/server/collab/revocation.ts` + `revokeCollabAccess()`, called by remove-member / delete-project / delete-canvas; `docs/04-realtime-collab.md` §4.2.1). Waiting out a sweep is not merely "late": a removed member can still write for the whole window, those writes merge and persist, and **the people who remain cannot undo them** — `Y.UndoManager`'s `trackedOrigins` only tracks their own `LOCAL_ORIGIN`, so anything arriving over the wire never enters their undo stack, and one `deleteSelection()` empties the canvas. There is no audit log and no restore path — whatever a revoked member destroys is simply gone. So: the writing instance revalidates immediately, and **cross-instance is covered by one shared key** — a fresh token written on every revocation, polled by each instance every `REVOCATION_POLL_INTERVAL` (3s), and a change triggers a full revalidation. One global key + full sweep beats per-project/per-user delivery because revocations are rare while precise routing would need a room→project cache and a read count that scales with rooms. The route **awaits** it, so a 204 from `DELETE …/members/:userId` means the person is genuinely off the canvas. Broadcast failures never block — they degrade to the `REAUTH_INTERVAL` sweep, so a broken shared layer is slower, not leakier. The sweep itself must **fan out across documents and guard against re-entry**; the old serial `await` made `REAUTH_INTERVAL` a lower bound rather than the guarantee it is quoted as.
- **Kicking a connection is not the same as refusing a frame — the write gate is the second, message-level half** (`apps/server/collab/write-gate.ts`, hooked on `beforeSync`; `docs/04-realtime-collab.md` §4.2 ④). Between "the verdict went bad" and "the socket is actually closed" sits the sweep interval, the 3s cross-instance poll, and whatever is already queued behind `closeForGood` — Hocuspocus's `Connection` carries no closed flag and `processMessages` never checks whether the connection is still attached, so those frames apply, broadcast and persist. **`beforeSync`, not `beforeHandleMessage`**: the latter runs on every frame including awareness (a cursor per pointermove), while `beforeSync` fires only inside a sync message *after* the type is read — so only writes pay for auth (`type` separates SyncStep1/read from SyncStep2+Update/write; never gate SyncStep1 or reconnect's own sync handshake breaks), and it runs *before* Hocuspocus's own `readOnly` check, so setting `readOnly` there NACKs the frame in flight. **Never `throw`** (same reason as the quota). **Refusing is only half — the connection must also be closed**: the provider does nothing with `syncStatus=false` (`applySyncStatusMessage` only decrements when `applied`), it never resends, so the rejected edits sit in the local Y.Doc + y-indexeddb until a *reconnect*'s SyncStep1/2 exchange carries them up — which is exactly the existing `classifyClose` → `SessionExpiredDialog` → re-login → `useFlowSync` watch → rebuilt provider path. Don't close and the user logs back in with the edits still stranded in the browser. **Cache the verdict; never batch-delay the frames** — message handling is one serial queue, so awaiting a timer in this hook stalls that connection's awareness heartbeat too and the 30s `timeout` kills it. The cached value is the *Promise*, which doubles as in-flight dedup. **TTL is long (10s) because the urgent half is event-driven**: `revalidateConnections` clears the table at its top, and it is the confluence of all three revocation paths, so a revoked member's next write frame always re-queries (window ≈0) at zero polling cost; the TTL only backstops session expiry, whose detection floor is the access-token lifetime anyway. Net: fewer queries than the 20s sweep, shorter window, and enforced before the Y.Doc rather than by close timing. `prime()` on `connected` (the handshake just authenticated), `forget()` on `onDisconnect`, and **an authorize that throws means allow** — no evidence, no refusal, same as the sweep and session refresh. **What it checks is injected and mandatory** (`createWriteGate({ authorize })`, no default): both project and personal canvases get `collabWriteAuthorize` — it goes through `authorizeCollab`, which for a personal room checks session + canvas still alive + **is the owner**, strictly stronger than the session-only `sessionWriteAuthorize` that was once planned for personal rooms (that helper still has no caller; personal canvases now ride the WebSocket too, see docs/20 §3.3.2). An `if (personal)` inside the gate would make it know what a project is; the channel's shape belongs to whoever mounts the gate.
- **The WebSocket upgrade is outside Hono, so `Origin` is checked by hand** (`isAllowedCollabOrigin` in `apps/server/auth/ws.ts`, called from the `upgrade` listener). WebSocket is not covered by the same-origin policy — any page can open `wss://us/ws/collaboration` and the browser attaches the `sid` cookie, which is CSWSH; `app.ts`'s `cors` only guards `/api/*` and a raw `server.on('upgrade')` sees none of the middleware chain. `SameSite=Lax` on `sid` already stops this in current browsers, but that is the browser covering for us, not a decision in our code. Allow on three grounds: **no `Origin` at all** (non-browser clients — browsers always send one, so this opens nothing), **on the `APP_ORIGINS` whitelist** (`APP_ORIGIN` is always in it; a multi-domain deployment has to let every one of its domains open a collab socket), or **`Origin`'s host equals the request `Host`** (same-origin with a mis-set `APP_ORIGIN`, e.g. dev defaults to `127.0.0.1` while you browse `localhost`; a cross-site attacker can't reach this branch since its `Origin` is its own domain).
- **Never rebuild the `:nodes` array while the local user is dragging.** Vue Flow decides whether to re-sync nodes by array *reference*, and a re-sync runs `Object.assign(existing, incoming)` — since drag intermediates deliberately never reach the Y.Doc, `incoming.position` is the pre-drag position and the node snaps back mid-gesture. Something always changes during a drag (this client is publishing its drag position to awareness, which recomputes every presence-derived value), so `useFlowCanvas` keeps a `localDragging` flag and returns `store.nodes` untouched while it's set. Mapping over the array is only safe when a *remote* peer is dragging.
- **Types are shared, with a deliberately small server-only remainder.** Graph structure types, `GRAPH_SCHEMA_VERSION` and the v1 upgrade live in `@shadecn/shared/flow-graph`; project / canvas API shapes in `@shadecn/shared/canvas`. What stays in `apps/server/store/flow-types.ts` is only what the server alone uses (and it uses `Buffer`, which shared must not): `parseGraph` / `parseTransactions` / `parseUserStatePatch`, `GRAPH_LIMITS` and the Op types. **One known drift is kept on purpose:** the v1 upgrade's `createdAt` test is lenient on the frontend (`typeof === 'number'`) and strict on the server (`isTimestamp`); `UpgradeOptions` / `STRICT_UPGRADE` carry that difference explicitly and both server call sites pass `STRICT_UPGRADE`. Unifying them would change what an old canvas reads as, i.e. a behaviour change, not a cleanup.
- **`apps/web/src/lib/api.ts`** wraps every endpoint over `apiFetch` and throws `ApiError` (carries `status`) on non-2xx — the store needs to tell 409 apart.

**3D:** Three.js is a dependency with types (`@types/three`). The `Cube3D.vue` component is pure CSS 3D transforms (not Three.js). The Three.js views (`Canvas3D`, `LightScene`) are placeholders.

**Backend (`apps/server/`) — the single entry point:** Node + [Hono](https://hono.dev) + `@hono/node-server`, run through `tsx` (no build step). It serves the API, the Yjs WebSocket, *and* the frontend. Layout:
- `apps/server/index.ts` — entry. Loads `.env`, `assertAuthConfig()`, builds the http server with `createAdaptorServer` (no `listen` yet), attaches collab + frontend, starts the hourly expired-session sweep, then listens. Handles SIGINT/SIGTERM cleanup, and `shutdown()` carries a re-entry guard because the two signals can arrive back to back
  - **In dev, the process that actually holds the port is a grandchild, so it also has to notice when it has been orphaned.** `pnpm dev` is four layers — `pnpm` → `sh -c` → `tsx watch` → `node apps/server/index.ts` — and only the last one listens (since the monorepo split the root `pnpm dev` is itself a `--filter` delegation, so there is at least one more `pnpm` layer above these; the argument only gets stronger). Ctrl+C in a terminal signals the whole foreground process *group*, so all of them get it; stopping the task from an IDE, killing the top-level pid, or closing the terminal tab reaches only the top layer or two, and the listener survives with the port still bound. It gets reparented to init and nothing ever kills it, so the *next* `pnpm dev` dies with `EADDRINUSE` — and since each failure leaves another one behind, they accumulate (found 29 of them once, the oldest three days old, plus one still holding live browser connections). `watchForOrphan()` therefore samples `process.ppid` every 2s and runs the normal `shutdown()` once it changes, so the Y.Doc still gets flushed on the way out. The timer is `unref()`'d — it is a sentinel, not a reason for the process to stay alive — and the check is dev-only (under an init system the server is PID-1-adjacent by design). This is *not* a bug in the shutdown path: a plain SIGTERM to the listener has always exited cleanly in about a second; the signal simply never reached it.

**Logging (`apps/server/logger/`) — winston, and the rule is *keep writing `console.*`*.** The whole layer is injected at four wiring points; there is **no `logger.info()` anywhere in business code**, and adding one is the thing not to do. Write `console.warn('[collab] …')` exactly as the existing 49 call sites do — `console.ts` intercepts `console.*`, parses the `[prefix]` into a structured `module` field, attaches the request context, and hands it to winston. That interception is the load-bearing piece: it is what let the whole codebase become structured logging with zero diffs, and it is why third-party output (ioredis) is collected too. The four mount points, one line each: `index.ts` imports `./logger/install.ts` **second, right after `./env.ts`** (a side-effect module, not a function call — ESM hoists imports, so a call in the module body would run *after* every other module has already initialised and logged); `app.ts` uses `httpLogger()` in place of `hono/logger` (it also opens the `AsyncLocalStorage` that gives every downstream log a `requestId`); `db/orm.ts` passes `loggerFactory: ormLoggerFactory` (`logger/db.ts`; MikroORM calls `logQuery()` for every statement with the SQL, timing and row count — **it logs SQL text but never parameter values**: the `query-params` namespace is permanently off, which is what makes MikroORM hand over the `?`-placeholder SQL instead of the interpolated one, and `logQuery` only reads `query`/`took`/`results`/`affected`, never the `params`/`formatted` that also ride in the context; the ORM's own `debug` and `slowQueryThreshold` stay unused so `LOG_SLOW_QUERY_MS` is the one threshold); `collab/hocuspocus.ts` puts `collabLogging()` in the extensions array. That last one is the interesting one: Hocuspocus pushes the `new Hocuspocus({...})` hooks onto the *end* of the extension list, so a `priority`-tagged logging extension brackets the business hooks — `onStoreDocument` (start) and `afterStoreDocument` (only reached if the whole chain succeeded) mean **`started - completed` is the failed-persist count, derived purely by observation**, which is what REQ-RESILIENCE §4.5 asks for. Noise control is a design constraint, not an afterthought: per-update and per-frame events are *counted*, never printed (one node drag is dozens of updates), and summarised once a minute; `LOG_HTTP` defaults to `api` so dev's few-hundred Vite module requests stay out; nothing in a hook may throw (the hook chain is serial — an observer that throws kills the quota/auth hooks behind it) and nothing may call `Y.encodeStateAsUpdate()` just to print a byte count (it serializes up to 20MB). Config is `LOG_LEVEL` / `LOG_FORMAT` / `LOG_DIR` / `LOG_HTTP` / `LOG_SLOW_MS` / `LOG_SLOW_QUERY_MS`; winston is silent under `NODE_ENV=test`, and since tests never import `apps/server/index.ts`, the console interception never touches them.

**Frontend hosting (`apps/server/frontend/`):** `attachFrontend(app, server)` registers a catch-all *after* the `/api` routes, so API routes always win and everything else falls through to the UI.
- **`frontend/guard.ts` — the page gate, and what it guards is "you can't *see* the UI", not "you can't fetch the bytes".** Mounted by `app.ts` right after the `/api` routes, so before the frontend catch-all. An anonymous **document request** (`Sec-Fetch-Mode: navigate` or `Accept: text/html`) for anything other than `/login`, `/favicon.ico`, `/vite.svg` gets a 302 to `/login?redirect=<path>`; **every non-navigation request passes through** — `/assets/*.js`, `/assets/*.css`, dev's `/src/**` and `/@vite/*`. Assets have to be public because **the login page is itself an entry of the frontend bundle** (below); gating them would leave the login page staring at a blank screen. Serving them costs nothing, because booting the SPA needs `index.html`, and *that* is a navigation the first rule already turned away. `GET /login` still lives here but now does exactly one thing: 302 the already-logged-in away (`safeRedirect` on `?redirect=`), then `next()` to let the frontend layer serve the page
- **The login page is the frontend's *second Vite entry*, not a server-rendered string and not a SPA route.** `login.html` + `apps/web/src/login/` sit alongside `index.html` in `vite.config.ts`'s `rollupOptions.input` (MPA). It cannot be a SPA route — anonymous browsers never receive `index.html`, so a login screen that needs the SPA to boot could never render. It reads what it needs itself: providers from `GET /api/auth/config` (public), `?redirect=` and `?error=` from `location.search`. `?redirect=` is passed straight through to `/api/auth/login`, where `safeRedirect` validates it — the in-site check is **not** reimplemented on the client. This replaced a hand-written HTML string whose palette and GitHub icon had to be kept in sync by hand, and had already drifted (`--primary` was `0.985` on one side and `0.922` on the other); both entries now share the same chunks, so the duplication is gone. The cost, stated plainly: the page went from a 5.3KB self-contained zero-JS document to ~62KB gzip that needs JS to render, most of it the Tailwind CSS chunk shared with the app (~20KB gzip, already cached once you're inside). Serving it is a one-line branch in both `frontend/dev.ts` (through `transformIndexHtml`) and `frontend/static.ts`
- **`login.html` carries the same inline theme script as `index.html`** — reading `app:theme` before first paint. Both copies must change together; it is the one thing a second entry cannot share, because it has to run before any module loads. It also fixed a real mismatch: the old server-rendered page only knew `prefers-color-scheme`, so anyone whose app theme disagreed with their OS saw the login page in the wrong one
- `frontend/dev.ts` (dev only, dynamically imported so Vite never loads in prod) — `createServer({ root, appType: 'custom', server: { middlewareMode: true, hmr: { server } } })`. Vite's connect middleware chain is run against `c.env.incoming/outgoing` and the handler returns `RESPONSE_ALREADY_SENT`; if the chain calls `next()`, the SPA fallback renders `index.html` through `vite.transformIndexHtml`. `hmr.server` is what makes HMR ride the same port — with only `middlewareMode: {server}` Vite would still open port 24678
- `frontend/static.ts` (prod) — `serveStatic({ root: <staticDir relative to cwd> })` + `index.html` fallback for unknown paths
- `vite.config.ts` is still the config of record (plugins, `@/` alias) — it's read both by `vite build` and by the middleware-mode `createServer`. `build.outDir` is `output/public`, i.e. the frontend builds straight into the backend's static directory. It has no `server.proxy` anymore because there is nothing to proxy to

**Build (`apps/server/scripts/build-server.mjs`) — `output/` is a self-contained, runnable app directory.** `pnpm build` (`pnpm build:client` then `pnpm build:server`) fills it with `public/` (frontend, from `vite build`), `server/index.js` (backend, esbuild bundle, ESM/node22), `server/db-sync.js` (the schema-sync entry, `apps/server/db/sync-cli.ts` — a second esbuild entry point in the same build, sharing chunks with the first), and — copied verbatim from `apps/server/scripts/output-image/` — `Dockerfile`, `.dockerignore`, `README.md`. Copy `output/` anywhere and `npm install --omit=dev && npm run db:push && npm start` runs it; `docker build ./output` images it. No repo source needed.
- `output/package.json` is generated: its `dependencies` are derived from esbuild's *external* list (metafile) — the packages the bundle actually imports, read against `apps/server/package.json` — each pinned to the version installed at build time. That includes **both** `@mikro-orm/sqlite` and `@mikro-orm/postgresql` (their drivers, better-sqlite3 and pg, come in as their pinned dependencies — the bundle never imports them directly). `vite` is filtered out (`DEV_ONLY`) because it only appears in the never-loaded dev chunk. Its scripts are `start`, `db:push` (`node server/db-sync.js`) and `db:push:force`. `node_modules` is deliberately not shipped: better-sqlite3 is native and its binary must match the target platform.
- Relative imports are inlined, **and so are workspace packages (`@shadecn/*`, via the `externalizePackages` plugin)**, so there is no `tsx` and no CLI tool at runtime.
- **One artifact serves both databases.** Nothing is provider-specific at build time any more: `pnpm build` ignores `DB_PROVIDER`, and the same artifact / image connects to SQLite or PostgreSQL depending on the runtime env. Don't reintroduce a per-provider build.
- Two non-negotiables in the esbuild call: `splitting: true`, so `frontend/index.ts`'s `await import('./dev.ts')` stays a real dynamic import and `vite` never becomes a top-level static import (it is not installed in prod); and `define: { __APP_BUNDLE__: true }`, which is how `apps/server/runtime.ts` tells bundle from source.

**Yjs 协同 (`apps/server/collab/`):** the same HTTP server also serves a Yjs sync endpoint at `ws://host:3000/ws/collaboration` (room name travels in the message, not the path); one room = one `Y.Doc`, held in memory only.
- `collab/hocuspocus.ts` — the collaboration server: [Hocuspocus](https://tiptap.dev/docs/hocuspocus) (`@hocuspocus/server`, MIT) mounted on our own HTTP server. We never call `listen()` (that would open a second port); instead we own the `upgrade` listener, take **only `/ws/collaboration`**, and hand it to crossws, which calls `handleConnection()`. Everything else — notably Vite's HMR socket (`vite-hmr`, path `/`) — we simply don't touch, and Node's multi-listener `upgrade` event delivers it to Vite's own listener; crossws registers no listener of its own, so "don't touch" really means untouched. This replaced a 282-line port of y-websocket's `bin/utils.js` that existed only because upstream `@y/websocket-server` statically imports `y-leveldb` → `leveldown` (no node 22/arm64 prebuild). **The room name travels in the message, not the URL** — that's also why the wire protocol is incompatible with y-websocket and the frontend must use `@hocuspocus/provider`.
- `collab/index.ts` — `attachCollabServer(server, { destroyUnmatchedUpgrades, authorize })`: a `ws` server in `noServer` mode; only `/ws/collaboration` upgrades are accepted. In dev `destroyUnmatchedUpgrades` is `false` — Vite's HMR socket rides the same `upgrade` event (protocol `vite-hmr`, path `/`) and killing unmatched sockets would break hot reload. `authorize` (wired to `auth/ws.ts`) checks the session cookie on the handshake and answers `401` + destroy when anonymous
- **Timings are constants in `hocuspocus.ts`, not env vars, because they are all derived from one fact: the server sends no heartbeat.** `timeout` is *not* a ping interval — Hocuspocus only compares "when did I last hear from this client". What actually holds the connection open is y-protocols' awareness replay: the client re-announces its local state every `outdatedTimeout / 2` = **15s** (`useFlowPresence` publishes on connect, so it always runs), and the server's awareness broadcast does **not** exclude the sender — so there is a 15s round-trip in both directions and a 60s reverse-proxy idle timeout (nginx / k8s Ingress defaults) is already covered without us sending anything. `timeout: 30_000` = two missed beats, matching the provider's own `messageReconnectTimeout` so both ends give up together; tighter than the 60s default because a dead connection still holds the exclusive-holder slot and a ghost cursor, and staying under the proxy's 60s means *we* notice first and run `onDisconnect` instead of the middlebox quietly cutting the tunnel. `REAUTH_INTERVAL: 20_000` is the **backstop** sweep, not the main path — see the revocation bullet below.
- `GET /api/collab/rooms` reports live rooms/connections; `GET /api/collab/health` is the **persistence health** endpoint alerting hangs off (REQ-RESILIENCE §4.5) — failed-store count, how long since the last successful store, write-queue depth, shared-layer status, and **the HTTP status code is the verdict** (200/503) so a `curl`-checks-the-code alert works without parsing JSON. Two judgement calls in it: `failed` is *observed*, not reported (see the logging section — the extension brackets the business hooks, so started-minus-completed is the failure count), and "hasn't stored in a while" is only unhealthy **together with a non-empty write queue**, because stores only happen when someone is editing — the time alone would fire every quiet night. Both endpoints sit behind the auth gate; opening `/health` up for Prometheus is a security-boundary change and deliberately not done here
- Frontend: `new HocuspocusProvider({ url: '/ws/collaboration' as absolute ws:// URL, name: room, document: doc })` — docs stay in memory, so a server restart drops all content

**单副本 / 多副本 (`apps/server/cluster/`) — one image, two modes, picked by env.** Full write-up in `docs/14-clustering.md`. `CLUSTER_MODE` (`single` | `redis`) resolves exactly like `dbProvider`: explicit variable wins, else infer from whether `REDIS_URL` is set, else the zero-dependency default. **Database and Redis are configured independently** — neither infers the other; `assertClusterConfig()` rejects `redis` without a `REDIS_URL` everywhere (contradictory config), but `redis` + SQLite only *warns* in dev, because SQLite + Redis in one process is a legitimate way to exercise the Redis path locally. Production refuses it.
- The state that used to be module-level `Map`s — audit `seq`, quota marks, awareness clientID ownership, session-refresh mutex — is now three abstract classes in `cluster/shared.ts`: `SharedMap<V>` (`get`/`set`/`claim`/`entries`, TTL), `SharedCounter` (`next(key, seed)`), `SharedLock` (`run(key, task, {fallback})`). Two implementations, `memory.ts` (literally the old `Map`s) and `redis.ts` (`SET NX` / `INCR` / lock+Lua-release), run the same contract test suite (`apps/server/test/cluster/shared.test.ts` — memory always, Redis when `TEST_REDIS_URL` is set). The backend also answers `health()` (surfaced as `clusterHealth()`), which is **synchronous and sends no network request** — it reads ioredis's own `status` field, because a health check must not hang when the thing it checks is slow; only `ready` counts as usable, since during `connecting`/`reconnecting` commands silently pile into the offline queue.
- **Every method is async even in the memory implementation** — otherwise wiring in Redis later would have meant changing every call site's signature. And **the factories return lazy proxies**: modules declare their tables at module top level (the way they used to write `new Map()`), but picking an implementation needs `await import('ioredis')`, which happens later in `initCluster()`. The proxy resolves against the current backend on first use, so swapping backends just bumps a generation counter.
- **`redis.ts` is dynamically imported**, like the two database drivers in `db/orm.ts` — a single-replica process never loads ioredis. Like the drivers, both packages stay in the built artifact: the image supports either mode, and nothing about the database is baked in at build time either.
- Multi-replica collab is `@hocuspocus/extension-redis` (pub/sub for updates + awareness, redlock around `onStoreDocument` so only one instance actually writes, `afterLoadDocument` waits for a peer's in-memory state). **socketId gets an `instanceId:` prefix** — Hocuspocus's socketId is only unique within a process, and awareness ownership uses it to tell "is this clientID yours", so a collision would drop the rightful owner's updates as impersonation. No sticky session needed anywhere.
- **The same update fires `onChange` on *every* instance holding the room.** Nothing writes per-update rows today, but anything that starts to (webhooks, notifications, metrics) must filter on `transactionOrigin` and skip `source === 'redis'` — otherwise the side effect fires a multiple of the replica count (measured back when the audit table existed: two instances, 11 edits, 22 rows), and the forwarded copy carries no author `context` anyway. Unknown origin shapes should count as "act" — better one too many than losing the author's.
- **Quota is deliberately eventually-consistent**: `quotaLocked()` is called *synchronously* on every message, so it reads a local `Map`; the verdict is pushed to the shared layer fire-and-forget and pulled back on the byte-remeasure tick (1–5s). That matches what the quota already was — after-the-fact accounting, effective on the *next* message — not a synchronous gate.
- Local: bring up Redis/PostgreSQL yourself (commands are in `.env.example`; the scripts deliberately don't), then `pnpm dev` (single) or `pnpm dev:cluster` (`apps/server/scripts/dev-cluster.mjs` spawns one `tsx watch` per port from `DEV_CLUSTER_PORTS`, overriding only `PORT` and `INSTANCE_ID` — **it contains no configuration**, everything else comes from `.env`). k8s: `k8s/deployment.yaml` (single, PVC, `Recreate`) or `k8s/variants/deployment.cluster.yaml` (`replicas: 3`, `RollingUpdate`, no PVC) — the two are one Deployment identity in two shapes, and **the variant deliberately lives outside `k8s/`**: ArgoCD syncs that directory non-recursively, so two manifests for `dev/shadecn-learning` sitting in it is a `RepeatedResourceWarning` with no guarantee which one wins. Switching is a git operation (copy the variant over `k8s/deployment.yaml` and commit) — applying it by hand gets reverted by `selfHeal` within seconds.

Frontend, `/api/*` and `/ws/collaboration` are same-origin in every mode, so frontend code should always use relative paths.

**Auth (`apps/server/auth/`) — Keycloak OIDC + GitHub OAuth2, BFF style.** Full write-up in `docs/02-auth-keycloak.md`. The browser never sees a token: the authorization-code exchange happens server-side, tokens live in the database, and the client only holds an httpOnly `sid` cookie.
- **`auth/providers/` — the registry that keeps everything else provider-blind.** `types.ts` declares one interface (`authorizationUrl` / `exchange` / `refresh`), `index.ts` holds a `REGISTRY` array whose **order is the login page's button order**, and `keycloak.ts` / `github.ts` are the two implementations. Routes, the session layer and the login page all speak `AuthProvider`, so **adding a login method is one new file plus one array entry** — nothing else is touched. `refresh: null` is a first-class answer, not an oversight: GitHub OAuth App tokens never expire and there is no refresh token, so `Session.provider` exists purely so renewal knows who to ask, and a github session's `expiresAt` is set to `SESSION_TTL` (it can never reach the renewal branch, and the session-age cap is what ends it).
- **There is exactly one callback *path*** (`/api/auth/callback`) for every provider; `AuthRequest.provider` dispatches. Registering a second redirect URI in Keycloak for each new provider would be pure config drift, and GitHub only allows one per OAuth App anyway.
- **But the callback's *host* follows the domain the browser actually used — `apps/server/auth/origin.ts`'s `originOf(c)`, gated by the `APP_ORIGINS` whitelist.** One deployment routinely answers on several domains (external, internal, an old one, a bare IP), and `redirect_uri` is an absolute URL: with a single hard-coded `APP_ORIGIN`, clicking 登录 on domain B finishes the callback on domain A, the session cookie lands on A, and B is still anonymous — while every step of the flow 302s without an error, so it reads as success. `redirect_uri`, the CORS echo, the WebSocket `Origin` check, the invite link and the cookie's `Secure` flag all take their origin from that helper. **What it must not do is follow `Host` blindly**: behind a proxy `Host` / `X-Forwarded-Host` are attacker-controllable, and building `redirect_uri` from them mails the authorization code to someone else's domain. So it takes the first of `X-Forwarded-Proto`+`X-Forwarded-Host` → `Host` → `Origin` that is **on the whitelist** (`Origin` last: a full-page navigation carries none, but it is the only header left when a proxy rewrites `Host` to an internal name), and falls back to `APP_ORIGIN` otherwise — i.e. behaviour without the list is exactly what it was. `APP_ORIGIN` is always a member (it is the fallback target), comparison is normalized (lowercase, no trailing slash, default port dropped, http/https only), and **there are no wildcards** — every domain's `/api/auth/callback` has to be registered in Keycloak's *Valid redirect URIs*, so a wildcard would only mint addresses nobody can register. Two details are load-bearing: **`AuthRequest.origin` is stored**, because OAuth2 requires the token exchange's `redirect_uri` to match the authorization step character for character and recomputing it on the callback leg is not safe (a changed header or a changed list yields a different value and the provider refuses it); and **the cookie's `Secure` flag is per-request** (`secureCookieFor`), because the list can mix https and http domains — miss it on https and you drop a layer of protection, set it on http and the browser silently *discards* the cookie, which looks like "login succeeded but I'm still logged out" with a completely clean server log.
- `auth/oidc.ts` — everything that talks to Keycloak: cached `.well-known/openid-configuration` discovery (endpoints are never hard-coded), PKCE `S256` helpers, `exchangeCode` / `refreshTokens` / `revokeRefreshToken`, RP-initiated `buildLogoutUrl`, and `verifyIdToken` — JWKS fetch (kid miss → one refetch) + `crypto.createPublicKey({format:'jwk'})` signature check for RS/PS/ES, then `iss` / `aud` / `azp` / `exp` / `iat` / `nonce`. No `jose`/`openid-client` dependency. `revokeRefreshToken` / `buildLogoutUrl` are **no longer called by the logout route** (see below) but stay as part of the OIDC client. `OidcError` is deliberately shared with the GitHub path — `session.ts`'s retry logic keys on `retryable` alone, and two error types would fork that judgement for no reason
- **`auth/providers/github.ts` — four things that make GitHub *not* an OIDC client.** No discovery (endpoints are hard-coded — GitHub publishes no well-known document); no `id_token`, so identity costs a second call to `/user`, plus `/user/emails` when the user has made their address private (unreachable → the account simply has no email, it is not a login failure); **the token endpoint answers HTTP 200 on failure** with `{error, error_description}` in the body, so checking only the status code reads "this code was already used" as success; and no PKCE support (a `code_challenge` is silently ignored — replay protection is the one-shot `AuthRequest`). Roles are always `[]`: GitHub has no notion of this app's roles
- `auth/session.ts` — session lifecycle. The cookie holds a 32-byte random token; the DB row id is `HMAC-SHA256(SESSION_SECRET, token)`, so a database dump alone can't forge a cookie. `loadSession()` transparently refreshes an access token that is within 30s of expiry (concurrent refreshes for one session are deduped through an in-process promise map), so **the session is kept alive by traffic** — it only really expires once nothing has hit the server for long enough that the refresh token passes Keycloak's SSO Session Idle. `loadSession(token, { refresh: false })` is the read-only variant for callers that are *not* user traffic — currently just the collab server's periodic connection revalidation: it answers "still valid right now?" (a live refresh token counts) without renewing anything, and never deletes a row. A long-lived WebSocket must not be able to keep its own session alive. A failed refresh is **not** uniformly fatal: only a 4xx rejection from Keycloak (`invalid_grant` — logged out, idled out, kicked) destroys the session. Anything that proves nothing — connection refused, timeout, a 5xx, even a local DB write failure — keeps the session and retries on the next request, with a 15s per-session cooldown so a dead Keycloak doesn't make every request eat a timeout. `OidcError` carries `code` + `retryable` to make that call, and every outbound OIDC request has an 8s timeout (node's fetch has none by default). Deleting the session in the network-failure case is the bug this replaced: with a 60s access-token lifespan the refresh runs constantly, so one blip logged the user out. `sweepExpired()` drops timed-out sessions and unused auth requests
- `auth/middleware.ts` — `withSession` (parse, refresh, expose `c.get('user')`, clear a stale cookie; mounted on `*`, not just `/api/*`, because the page gate needs it too), `requireAuth` (401), `requireRole(...)` (403). Keycloak realm roles land in `User.roles` as-is, client roles as `clientId:role`
- `auth/ws.ts` — the same session check for WebSocket handshakes
- `auth/redirect.ts` — `safeRedirect()`, the shared in-site-only check for every `?redirect=`
- `routes/auth.ts` — `GET /api/auth/{config,me,login,link/:provider,callback,identities,logout}` + `DELETE /api/auth/identities/:id`. `/me` always answers 200 (`{enabled, authenticated, user}`) so the router guard has no error branch. `state`/`nonce`/`code_verifier` live in the `AuthRequest` table keyed by a short-lived `oidc_tx` cookie and are consumed exactly once, so a replayed callback fails. `?redirect=` is restricted to in-site paths (`//evil.com` and `/\evil.com` fall back to `/`). **`/api/auth` is in `PUBLIC_API`, so the four logged-in-only endpoints check `c.get('user')` themselves** — there is no `requireAuth` above them
- **Login and "link another account" are the same flow**; the only difference is `AuthRequest.linkUserId`, which makes the callback stash a pending link instead of minting a session. Two consequences worth keeping: the callback **reads the `AuthRequest` before it looks at `?error=`**, because "user cancelled" has to land back on `/settings` rather than `/login` and only that row knows which; and it re-checks `c.get('user')?.id === linkUserId`, so a session swapped in another tab mid-flow can't graft an identity onto the wrong person
- **A link is never written until the user confirms which account it is (`PendingLink` + `POST /api/auth/link/confirm`).** The settings-page session proves *you* are you, but it says nothing about the trip out to the provider: the browser may still be signed into someone else's GitHub (a shared machine), and because an OAuth App that has been authorized once never shows its consent screen again, the whole round-trip is invisible — click 关联, and you are back with a code, having been asked nothing. Writing straight to `UserIdentity` there binds *that person's* account, and they can then sign into yours. GitHub also has **no account chooser** (no `prompt=select_account`; `login=` is only a hint, switching means logging out of github.com), so nobody else is going to ask the question — we have to. Hence: the callback only pre-checks (`identities.checkLink`, read-only, so a doomed attempt doesn't get a pointless dialog) and stashes; the dialog shows the resolved username/email; confirming re-runs the real check, because the identity can be taken during the time the user spends reading. Four details that are load-bearing: **one pending row per user** (`userId` unique, a new attempt replaces the old — otherwise "which attempt is this dialog about" needs explaining); **no access token is stored** for an unconfirmed binding; the pending state rides **`GET /api/auth/identities`, not the URL**, so closing the tab and coming back still surfaces it; and confirm is **POST**, never reachable by following a link
- **Logout only ends the local session** — no `revokeRefreshToken`, no RP-initiated logout. This app is one client on a Keycloak realm; signing out here must not sign the user out of every other app behind the same SSO. The accepted cost is that Keycloak's SSO cookie survives, so clicking 使用 Keycloak 登录 right after logging out silently returns the same account and looks like the logout did nothing. Keycloak's *Valid post logout redirect URIs* is therefore no longer configuration this app needs
- When neither Keycloak (`KEYCLOAK_ISSUER` + `KEYCLOAK_CLIENT_ID`) nor GitHub (`GITHUB_CLIENT_ID` + `GITHUB_CLIENT_SECRET`) is configured, `authEnabled` is `false`: dev warns and lets everything through (so the demo pages still run without an IdP), production refuses to boot. Half a provider (issuer but no client id) is reported as a missing variable rather than treated as "not using it"
- **`apps/server/store/identities.ts` — one user, several login methods.** Each binding is a `UserIdentity` row and `@@unique([provider, subject])` *is* the whole conflict check — a third-party account can belong to exactly one local user, so `link()` never has to guess. One of the rows is the **primary identity**, and it has no boolean column: it is the row whose `(issuer, subject)` equals `User.issuer` / `User.subject`. Storing an `isPrimary` flag would just add a second place that can disagree with those two columns. Three rules the login path depends on: every login refreshes *that identity's* display fields, **`User`'s profile fields only follow the primary identity** (otherwise one GitHub login quietly renames a Keycloak-named user), and **`User.roles` is only written on a Keycloak login** — GitHub always reports `[]`, so writing it unconditionally wipes the user's roles on every GitHub sign-in. Unbinding the last identity is refused (409): there is no email-recovery path here, so it would orphan the account and everything it owns. Unbinding the primary promotes another row and rewrites those two columns but leaves name and avatar alone. Users that predate this table get their primary row **backfilled on use** (the login path adopts them, `listFor` writes it on read) — this repo has no migrations, so a lazy backfill is the migration.
- **Identity is `(provider, subject)` and never email — there is deliberately no "same email means same person" shortcut**, not even for an address the provider swears is verified. The default position is *different people*; a merge only happens when someone has proved themselves with the target account's own credential, i.e. signed in and then hit 关联 in settings. Three reasons, in order: that session **is** the strongest possible proof and needs no third party trusted; email is an attribute, not an identifier (it changes, it gets reassigned after an account is closed, and Sign in with Apple hands out a different private-relay address per app — every major IdP's docs say key on `sub`, not `email`); and auto-merging is the textbook account-takeover entry point, because the load-bearing claim "the person signing in really controls this mailbox" can only come from the source IdP and we cannot re-check it — one lax IdP, or an admin who can flip `email_verified` by hand (Keycloak can), turns it into a way into someone else's account. One implementation consequence: **GitHub only calls `/user/emails` when `/user` returned no address** — email is a display field here, not worth a round-trip on every login. The accepted cost is that one person signing in via Keycloak and then via GitHub ends up with **two** accounts; the supported path is sign in with the main account first, *then* link — never the other way round. Merging two accounts that already exist is still absent
- **`auth/profile.ts` — what a user gets *after* login, kept outside the login path.** `identities.resolveLogin()` does one thing: turn a provider profile into a `User` row. "And now give this person a default avatar / display name / timezone" is a different, ever-growing concern, so it hangs off the side: `registerProfileHook({name, fill})` adds a rule, `completeUserProfile(user)` runs them all in the callback (and in `auth/project.ts`'s dev-user path, so the no-Keycloak local mode gets the same treatment). Each hook only answers "what's missing" and the mechanism merges the answers into **one** update; a hook that throws is logged and skipped — it must never block a login. **It runs on every login**, which is what backfills existing users: no migration script, and no fallback logic scattered across the read paths. Adding a rule = one new file + one `registerProfileHook`; login code stays untouched.
- **`apps/server/avatar/` — the one hook there is today: no avatar → an identicon.** GitHub-style pixel blocks, generated by [minidenticons](https://github.com/laurentpayot/minidenticons) (MIT, dependency-free). Keycloak's `picture` always wins; the hook only fills the empty ones. **No image is stored**: the DB holds `/api/avatars/<seed>.svg` and `routes/avatars.ts` renders it on demand — no DB read, no notion of who's asking, so it's served `immutable` for a year. The seed is `sha256(issuer + "\n" + subject)` truncated to 16 hex — keyed on `(issuer, subject)` rather than `user.id` so the picture survives a rebuilt database, hashed so a subject never rides in an image URL. The route module is also what *installs* the hook (it imports `avatar/index.ts`), so mounting the route and having default avatars are the same one line in `app.ts`. Wherever a stored avatar is displayed, put a round background under it (`bg-muted` / `bg-sidebar-accent`) — the identicon is transparent-backed, and without it the blocks float on the page instead of sitting in the same circle the no-avatar fallback draws

**Database (`apps/server/db/entities/*.ts`, MikroORM 7, SQLite *or* PostgreSQL):** `User` (unique on `(issuer, subject)` — now the *primary identity*'s redundant copy rather than the only identity; roles as a JSON string), `UserIdentity` (one login method, unique on `(provider, subject)` — its `email` is display-only and joins nothing), `Session` (`provider` says which implementation renews it; its `id` is the cookie token's HMAC and is **set by the caller**, never auto-generated), `AuthRequest` (`provider` dispatches the single callback, `linkUserId` turns the flow from login into account-linking), `PendingLink` (a link waiting for the user to confirm *which* third-party account it is; `user` unique, so a retry replaces it); plus `Project`, `ProjectMember` (unique on `(project, user)` — the creator's admin row is written for real, never inferred from `createdBy`), `ProjectInvite` (the project's one share link — `project` is unique; token stored in the clear: it *is* the credential you hand out; unlimited uses, `expiresAt` is the only gate, and "reset" just swaps the token in place), `Flow` (`ydoc` = the Yjs state as bytes and **the source of truth for content**; `graph` = a JSON projection the server derives from it for list counts and previews — both are **lazy** columns, so a list query never loads them and code that needs them says `populate: ['ydoc']` / `fields: [...]`; `revision` = a monotonic write counter, *not* a client lock — it is the server's own CAS), and `FlowUserState` (per-user view state, unique on `(flow, user, key)` — one row per state partition, value is a JSON string; `viewport` is the first partition and adding another one is a new key, not a schema change); plus the canvas agent's three (`db/entities/agent.ts`, REQ-AGENT): `AgentConversation` (one conversation of one user on one canvas — real FKs to `flow` and `user` with cascade; `messages` / `llmMessages` are **lazy** JSON-string columns, the list reads only title / summary / `messageCount`), and the audit log `AgentRun` (id = the runId the SSE stream carries) + `AgentToolCall` (one row per tool call; `args` is `digestArgs` output — ids and string *lengths*, never content), whose `conversationId` / `flowId` / `userId` / `runId` are **plain text with no FK on purpose**: an audit trail must survive deleting the conversation or the canvas it describes. Tables and columns follow MikroORM's default `UnderscoreNamingStrategy` (`user_identity`, `avatar_url`), and **foreign keys are relation properties** (`user`, `project`, `flow`, `createdBy`, `personalOwner` → `user_id`, …): filter with `{ user: userId }`, read with `row.user.id`, `populate` when you need the other side's fields. Only the owning side is defined — there are no inverse collections (`defineEntity`'s type inference degrades to `any` on mutual references, and every query starts from the table holding the FK, e.g. "my projects" is a `ProjectMember` query). `Flow.createdById`, `ProjectInvite.createdById`, `ProjectMember.invitedById` and `AuthRequest.linkUserId` are plain text columns with no FK, as before. The DB lives at `$DATA_DIR/app.db` (`DATA_DIR` defaults to `<repo>/data`, gitignored), `DATABASE_URL` overrides it outright, and relative `file:` paths resolve against the repo root — not the cwd; `mkdir -p` of the parent happens before opening, since better-sqlite3 won't create it.

**Two databases, one entity definition, one artifact (`docs/05-data-persistence.md`).** Which one you get is `DB_PROVIDER` (`sqlite` | `postgresql`), or — when unset — the scheme of `DATABASE_URL` (`file:` vs `postgres(ql)://`), defaulting to sqlite. A `DB_PROVIDER` that contradicts the URL's scheme, an unknown value, or `postgresql` with no `DATABASE_URL` all **throw at startup** rather than guessing. That resolution exists **once**, in `apps/server/config.ts` (`dbProvider` / `databaseUrl`) — the server and the schema-sync CLI both read it. It only decides which driver `db/orm.ts` **dynamically imports** (`@mikro-orm/sqlite` drags in the native better-sqlite3, `@mikro-orm/postgresql` drags in pg — a static import would make every process load both). A Prisma-style `?schema=public` on the PG URL is still accepted: `orm.ts` strips it and passes it as MikroORM's `schema` option (pg itself doesn't understand it).
- **Entity rules — each one is a measured difference between the two databases, not a style choice** (`db/entities/columns.ts` has them in the header): **strings are always `p.text()`, never `p.string()`** (that is `varchar(255)` on PG and unbounded on SQLite — tokens and avatar URLs fit on one and fail on the other); **only five types**: text / integer / boolean / datetime / blob — no json, enum, array or native `columnType`, JSON stays a string; **nullable scalars use `strictNullable()`** (plain `nullable()` types as `T | null | undefined` and leaks `undefined` into the API types) — and since `em.create` doesn't fill unset nullable props, **write `null` explicitly in any `create` whose entity you map straight into a response**; **timestamps get their defaults in the app** (`onCreate`/`onUpdate`), never a DB default — `current_timestamp` stores differently on the two sides; ids are app-generated UUID text (`idColumn()` / `newId()`).
- **Prisma habits that are now bugs.** `nativeUpdate` / `em.insert` / `em.upsert` **don't run `onCreate`/`onUpdate`**: every `nativeUpdate` that changes content must write `updatedAt: new Date()` itself (Prisma's `@updatedAt` did it in `updateMany`; the CAS writes in `collab/persistence.ts` and `collab/flow-writer.ts` are the ones that matter — miss it and edited canvases never move in "recently modified"), and every `upsert` must pass its own `id` + `createdAt` and restrict `onConflictMergeFields`, or the conflict branch rewrites the id too. CAS is `nativeUpdate(Flow, { id, revision: read }, { revision: read + 1, … })` and its return value is the affected-row count. Nested writes and `$transaction([...])` became `em.transactional(async (em) => …)`. Unique conflicts throw `UniqueConstraintViolationException` on both databases (was P2002) — catch **only** that one in the "lost the race, re-read" branches. There is no P2025: `nativeUpdate`/`nativeDelete` on a missing row return 0, so the old `.catch(() => undefined)` around deletes is gone, and the OAuth callback's one-shot consume now means "the request that deleted the row" (`nativeDelete` returned 1) — a concurrent replay of the same `oidc_tx` loses.
- **There are no migration files, and schema sync has its own lossy-change guard (`apps/server/db/schema-sync.ts`).** `pnpm db:push` (`tsx db/sync-cli.ts`), the container's `node server/db-sync.js` and the test global-setup all run the same code: `getUpdateSchemaSQL()` → classify every statement → `schema.execute()` the very same text. **MikroORM's `schema.update({ safe: true })` is not a guard** (measured): on SQLite any column change (type, nullability, default) is a `__temp_alter` table rebuild that `safe` doesn't see, and on PG `safe` only skips `drop column` while `alter column … type` goes through. So the guard refuses drop table / drop column / `alter column … type` / any `__temp_alter` rebuild / renames (MikroORM guesses renames heuristically) / truncate-delete, prints each statement with its category and exits 1 without executing anything; create table, add column, create/drop index, add constraint and PG nullability/default changes pass. `--force` (= `pnpm db:push:force`, the old `--accept-data-loss`) lets everything through. **Tables that aren't entities are ignored** in normal mode (`dropTables: false`) and only listed as a warning — e.g. the old Prisma tables (`"User"`, `"Session"`…) still sitting in a dev PostgreSQL; they differ in case from the new ones and don't collide — while `--force` drops them along with everything else. The reason there are no migrations is unchanged: they'd be written twice in two dialects, and SQLite can't alter a column, for no existing data. **The costs**: no history, no rollback, and a lossy change makes the bare sync refuse; both Dockerfiles and the artifact's `db:push` deliberately omit `--force` (better a failed container start than silent data loss), so assess whether an entity change is lossy *before* shipping it — on SQLite even making a column nullable is a rebuild. `db:push:force` stays a *separate command* rather than a flag on `pnpm dev`, because the point of the refusal is that a human sees it once. The guard's matcher is unit-tested against SQL that MikroORM 7.2.5 *actually emitted* on both databases, plus plan-only cases against the real test DB (`apps/server/test/db/schema-sync.test.ts`) — one of which pins "the entities and a freshly synced DB produce an empty diff", because an entity MikroORM can't diff stably would make every startup trip the guard.
- **The one behavioural difference that needed code**: case-insensitive search. SQLite's `LIKE` is case-insensitive for ASCII, PostgreSQL's isn't, and MikroORM's `$ilike` is PG-only (a syntax error on SQLite). `apps/server/db/query.ts`'s `containsIgnoreCase(column, keyword)` emits `lower(col) like lower(?) escape '\'` through a `raw()` key (the alias callback makes it work inside nested relation filters too) and escapes `%`/`_`/`\` in the keyword. Any new keyword search goes through it — never `$like`/`$ilike` inline. Note it takes the **column** name, not the property name.

**Deploy:** two paths to the same image. `pnpm build && docker build ./output` uses the Dockerfile the build drops into `output/` (deps stage: `npm install --omit=dev` off `output/package.json` — no compiler toolchain, better-sqlite3 13 ships prebuilt binaries for every platform incl. `linuxmusl-x64/arm64` and declares `gypfile: false`; runtime stage: those `node_modules` + the artifact, `WORKDIR /app`, `CMD sh -c "node server/db-sync.js && exec node server/index.js"` — the `exec` makes node PID 1 so SIGTERM actually reaches the shutdown flush). The repo-root `Dockerfile` is the from-source variant: a build stage that copies each package's `package.json` (web, shared, server — one `COPY` per package, add a line for any new workspace package), runs `pnpm install --frozen-lockfile`, copies the source (`.dockerignore` excludes `**/node_modules`, see the monorepo section) and runs `pnpm build`, then the exact same deps + runtime stages over `/app/output` — keep the two in sync (edit `apps/server/scripts/output-image/Dockerfile`, not `output/`). Only the deps stage runs on the target platform; better-sqlite3 picks its prebuilt binary by the *runtime* platform + arch, so a correct base image means the correct binary. `NODE_ENV=production`, `HOST=0.0.0.0`, port 3000; no source, no pnpm, no tsx in the runtime image. nginx is gone — the Node server serves `public/` itself. No stage installs `python3 make g++` any more. **pnpm 9 ignores `gypfile: false`** and runs `node-gyp rebuild` for any package with a `binding.gyp` and no install script, which fails on machines without node-gyp — hence the root `package.json`'s `pnpm.neverBuiltDependencies: ["better-sqlite3"]` (npm honours `gypfile: false`, so the deps stage needs nothing).
- **Both runtime stages end with a native-module load check, and both must keep it.** A native module of the wrong architecture does not stop the container from booting: Node dlopens it only on the first `require`, and `/api/health` never touches the database — so readiness stays 200, the Deployment reports `1/1 Available`, and only real requests 500 with `Error relocating …/better_sqlite3.node: unsupported relocation type 1026`. That is exactly what shipped once, and the cause is the one to remember: **a single-arch base-image tag plus QEMU binfmt makes pulling the wrong architecture completely silent.** Harbor's `library/node:22-alpine` is an arm64-only image someone pushed by hand; `buildah bud --platform linux/amd64` can only fall back to the arm64 manifest, binfmt runs every `RUN` without complaint, and that round installs an aarch64 `.node` into an image labelled amd64. Never read "the build succeeded" as "the architecture is right" — verify a base image with `uname -m` on an amd64 node before adopting its tag. Three independent guards, all in the Dockerfiles: one **multi-arch** reference shared by all stages (`192.168.68.95:31443/docker.io/library/node:22-alpine` — *not* `harbor-core.harbor.svc/library/node`), `ARG TARGETARCH` compared against `process.arch` in the deps and runtime stages, and the load check as the catch-all. The check is two steps now: `require('better-sqlite3')` opens a `:memory:` database and runs a query (its `prebuilds/` holds `.node` files for *every* platform, so dlopen-ing them all would always fail — that directory is excluded from the loop and verified through the package's own selection logic instead; every artifact ships better-sqlite3 now), then every other `*.node` is `process.dlopen`ed as before. `docs/12-deployment.md` §2.5.1 has the full write-up.

SQLite lives on a volume at `/app/data` (`DATA_DIR=/app/data`); `k8s/deployment.yaml` adds a PVC + auth Secret, targets container port 3000, and stays at `replicas: 1` with `strategy: Recreate`. **Two probe paths, and the split is load-bearing**: liveness/startup hit `/api/health` (shallow — touches no dependency), readiness hits `/api/health/ready` (checks database + shared layer). They fail in opposite directions — a failed readiness drains the Pod from the Service, a failed liveness *restarts the container*, and restarting fixes nothing about a database outage while killing a process that is still holding unstored Y.Doc content. So liveness must stay shallow; a test pins that `/api/health` never touches the database. `terminationGracePeriodSeconds: 60` plus a `preStop: sleep 5` (k8s removes the endpoint and sends SIGTERM **in parallel**, so without the sleep a dying Pod still accepts new WebSocket handshakes), matched on the app side by `SHUTDOWN_FLUSH_TIMEOUT` (20s) around the flush — an unbounded flush against a black-holed database means SIGKILL at the grace deadline, which loses both the write *and* the clean exit. A PostgreSQL deployment is the **same image** with `DB_PROVIDER=postgresql` + `DATABASE_URL` in the environment (the artifact is provider-agnostic); on the k8s side that drops the PVC and moves `DATABASE_URL` into the Secret. Going past one replica additionally needs `CLUSTER_MODE=redis` + `REDIS_URL` — that's `k8s/variants/deployment.cluster.yaml` (`replicas: 3`, `RollingUpdate`), see the cluster section above. The *image* is mode-agnostic and database-agnostic.

- **Component tests** (`apps/web/src/test/views/`, `@vue/test-utils` + jsdom) mount the real view with only `@/lib/api` stubbed — shadcn-vue and reka-ui run for real, because that's where "clicked it, nothing happened" bugs live. `ProjectHome.test.ts` pins the confirm dialogs: **`AlertDialogAction` closes the dialog *before* the forwarded `@click` runs**, so a confirm dialog needs two refs — one for `open`, one for "which item" — or the handler reads a target that close already cleared and the request is silently never sent. **`@click.prevent` does not stop it**: `DialogClose` calls `onOpenChange(false)` unconditionally and never looks at `event.defaultPrevented`, so reaching for `.prevent` only hides the fact that the two refs are still missing (`ProgressDialog.vue` shipped exactly that and deleted nothing). **A confirm that must stay open — anything multi-step — cannot use `AlertDialogAction` at all**: use a plain `Button` and close the dialog from code. `ModelConfig.vue`'s delete is two-stage (the first call omits `force`; the engine answers 409 *naming who still points at it*, and that sentence has to stay on screen for the "delete anyway" decision) — with `AlertDialogAction` the dialog is already gone by the time the 409 comes back, so there is nowhere left to show it. `GalStoryModelConfig.test.ts` and `GalStoryProgressDialog.test.ts` pin both halves. In jsdom: menus/dialogs teleport into `document.body` (not the wrapper), `DropdownMenuTrigger` opens on `click` while `TabsTrigger` switches on `mousedown`, and `PointerEvent` + pointer-capture need stubbing.

**Dependencies — each package declares only what it needs; the runtime set is `apps/server/package.json`'s `dependencies`, everything else is `devDependencies`.** The frontend is bundled into `output/public` and the backend into `output/server/index.js`, so `apps/web` has **only `devDependencies`** (vue/three/tailwind/reka-ui/`@hocuspocus/provider`/`y-protocols`/`lib0`, `vite`, `vue-tsc`, …) and `@shadecn/shared` is a `workspace:*` devDependency of both web and server (it is inlined into both bundles). `apps/server`'s `dependencies` holds just the packages the server bundle still needs at runtime: `hono` + `@hono/node-server`, `@hocuspocus/server` + `crossws` + `yjs` (collab server — crossws vendors its own `ws`, so we no longer depend on it directly), `@mikro-orm/core` + both drivers (`@mikro-orm/sqlite`, `@mikro-orm/postgresql` — pinned to exactly `7.2.5`, and *every* artifact keeps both, since the database is a runtime choice), `ioredis` + `@hocuspocus/extension-redis` (multi-replica mode; both stay in the artifact because the mode is an env switch, not a build flag), `minidenticons` (default avatars are rendered per request, so it is runtime, not build-time), and `winston` (the logging layer, see above — it is imported by `apps/server/index.ts`'s very first side-effect import); `esbuild`, `tsx` and `vite` (dev middleware) are server `devDependencies`. The **root** `package.json` holds only repo-wide tooling: the eslint family, `typescript`, `vitest` + the coverage plugin, `jsdom` — plus the `pnpm.neverBuiltDependencies: ["better-sqlite3"]` setting (see the deploy section). `apps/server/scripts/build-server.mjs` enforces the runtime set: it reads `apps/server/package.json`, and if a package the bundle imports is only in `devDependencies` (or missing), the build fails. So a package the *server* imports goes into `apps/server`'s `dependencies`; a frontend package goes into `apps/web`'s `devDependencies` (the `shadcn-vue` CLI, run from `apps/web`, already writes there); don't hoist either to the root.

**Key libraries:** `reka-ui` (headless UI primitives behind shadcn-vue), `@vueuse/core`, `class-variance-authority`, `vue-router` 5, `pinia` (only the flow editor's store) and `vue-sonner` (toasts) on the frontend; `hono` on the backend; `vite` for dev middleware + the frontend build; `tsx` only for `pnpm dev`.

## Conventions

- TypeScript strict mode with `noUnusedLocals`, `noUnusedParameters`, `erasableSyntaxOnly`
- All Vue components use `<script setup lang="ts">`
- Package manager: pnpm workspace. Add a package with `pnpm --filter <pkg> add -D <name>` (or `-P` for a server runtime dependency — see the dependency split above); never to the root unless it is repo-wide tooling
- Tests live in `apps/server/test/` and `apps/web/src/test/`, mirroring the directory they cover (`apps/server/test/routes/auth.test.ts` ↔ `apps/server/routes/auth.ts`). Imports inside `apps/server/test/` keep the explicit `.ts` extension like the rest of `apps/server/`. Tests for shared contract code live in `packages/shared/test/`.
- Vitest globals are **not** enabled — import `describe`/`it`/`expect`/`vi` from `vitest` explicitly.
- Test names are written as the behaviour being constrained ("未登录 → 401"), not as the function being called.
- **Time is UTC everywhere except on screen.** The database stores `datetime` as an absolute instant (`timestamptz` on PG; MikroORM maps SQLite's the same way), entities hand back `Date` objects, and every store maps rows out through `toISOString()`, so the wire format is always an ISO string with `Z` — never a pre-formatted, timezone-less string. The frontend never formats a date inline: `apps/web/src/lib/format.ts` is the only place that builds an `Intl.DateTimeFormat`, and by default it follows the browser (`navigator.languages` for the locale, the runtime default for the timezone) rather than a hard-coded `zh-CN`. Use `formatDateTime` / `formatDate` / `formatTime`, or `formatWith(value, options)` for another granularity; all four take a string/number/`Date`/null and render `-` for anything unparseable.
  - **What "follows the browser" means is now a preference, not a constant** — `apps/web/src/lib/preferences.ts` (a `useStorage` under `app:display-preferences`, browser-local, never sent to the server) holds locale / timeZone / dateStyle / timeStyle / hourCycle, every one of them defaulting to `AUTO` = follow the browser, which is why turning the setting page on changed nothing about existing output. `format.ts` reads the **reactive** `resolvedDisplayPreferences`, so changing a setting re-renders every already-displayed date with no reload and no per-page wiring. Two rules: a **caller-supplied option always wins** (`formatWith(v, { timeZone: "UTC" })` stays UTC no matter the preference — the preference only fills in what the caller didn't say), and the stored value is **validated on read** against a whitelist (localStorage is user-editable, and a misspelled `dateStyle` makes `Intl` throw `RangeError` and takes the page down). The UI is `apps/web/src/views/Settings.vue`.
- **On the canvas's own path, time is a *number* — UTC epoch milliseconds, not an ISO string** (`FlowNodeData.createdAt`, `FlowEdgeData.createdAt`). Numbers compare directly with no timezone, format, or parse step in between, and they ride inside the Y.Doc where a formatted string would be dead weight. Don't build ordering on them across clients: these are stamped by whichever browser created the element, so two clients' clocks are two clocks.
- **One click, one request — every write-side interaction goes through `apps/web/src/composables/useAsyncAction.ts`.** `const { run, pending } = useAsyncAction(fn, { errorMessage })`: `run()` records the action as pending **synchronously**, before the request is even sent, so a second click in the same event-loop turn is dropped on the spot; the template binds `pending` for the visual half (`<Button :loading="pending">`). The guard has to live in the handler, not in the markup — `:disabled` only takes effect on the next render, and half the entry points (`@keydown.enter`, `DropdownMenuItem @select`, an `@blur` that fires alongside an Enter-submit, `AlertDialogAction`) have no button to disable at all. `run` never rejects, so `@click="submit()"` leaves no unhandled rejection; errors go to `toast.error(err.message ?? errorMessage)` unless `onError` is given, which is why the wrapped action bodies carry no `try/catch`. Lists pass `key: (item) => item.id` so each row locks on its own. **Write `@click="submit()"`, not `@click="submit"`** — the latter hands the MouseEvent to the action as its first argument. Reads are deliberately *not* in scope: dropping a duplicate list load would strand the list on stale parameters.
- **Client-generated ids go through `apps/web/src/lib/id.ts`'s `createId(prefix)`** — `<prefix>_<base36 timestamp>_<random>`. The timestamp prefix keeps ids roughly sortable by creation; the random tail is the part that matters: two clients can add a node in the same millisecond, and a counter-based suffix (`nodes.length`) would hand both the same id and merge them into one object on sync.
