# Canvas agent — `packages/agent` (`@shadecn/agent`, REQ-AGENT, `docs/20-agent-canvas.md`)

Source-only, server-only (Node types + ES2023 tsconfig — the sandbox spawns processes and touches files). A `workspace:*` devDependency of `apps/server` only; the frontend's contract is `@shadecn/shared/agent`.

**Two sides since phase 2 (`docs/22` §4).** The pi loop runs in a per-run **sandbox** (`runner/`), which talks to the server only through the **gateway** (`gateway.ts`, mounted at `/api/agent-gateway`) with a run-scoped token. Everything else — Y.Doc, tool execution, canvas watch / digests, run registry / replay / SSE / broadcast, DB writes, authority, the real LLM key — stays server-side (`session.ts`). Runner-side modules must never import server-side ones (`session`, `gateway`, `store`, `canvas-changes`): the runner bundle (`output/server/agent-runner.js`) would drag them into the sandbox.

**Server-side model calls (`docs/22` §4.3): steps 1–5 are implemented (protocol 7; step 5 = usage on `agent_run`, no protocol change).** The runner's `streamFn` is pi's `streamProxy` with an **empty context**; the server calls the upstream itself (`model-stream.ts`), steps are counted per model request, **the LLM context is the server's own transcript** (`transcript.ts`, below) — the request body is only size-checked (`MODEL_BODY_LIMIT`, 64 KiB) and must be a JSON object, nothing in it is used — and **the UI events are server-made** (`events` / `session` below): nothing a person sees in the chat comes from what the runner reports. The wire carries only what the server actually needs: `RunnerInput` has no system prompt / prompt / history, `SubagentInput` none either, `RunnerEvent` is tool start / end only, `/agent/finish` is `{ agentId }`, there is no notice route. Don't add a field back "for the runner's context" — the runner's pi transcript only drives its loop and never leaves the sandbox.

## Sub-paths

- `session` — run orchestrator (server side; **no pi `Agent` here any more**): several conversations per flow × user, **one run per conversation at a time** (different conversations / users on one flow run concurrently; the slot is claimed synchronously in `start()`). **Every per-run limit lives on that run** (`RunState` / the `execute` closure: delete budget via a fresh `createCanvasTools` `runState`, tool-call count, replay buffer, abort, timer) — never add a per-flow counter there. Conversations and the run / tool-call log persist through injected interfaces; the `RunState` itself lives only on the replica holding it, everything other replicas need goes through the injected `RunRegistry` (below). **A run outlives the HTTP connection that started it**: a disconnect drops one subscriber; `subscribe()` / `GET …/runs/:runId/events` replays from RUN_STARTED and streams on, frame-for-frame identical — on any replica.
  - **Read vs write ownership** (`store.ts` header): display reads (`list` / `get`) are flow-scoped — project members see others' conversations read-only, flow access is the host's `requireFlowMember`; writes and the model context (`latest` / `getWithContext` / `save` / `remove`) keep `user` in the `where`. The route's 403 is the first gate, the `where` the second — don't collapse them.
  - A run enters the run list only after RUN_STARTED and leaves when removed from the registry; both moments call `onRunsChange` with the **full** list, which `apps/server/agent/runs-broadcast.ts` sends as stateless `agent:runs` (`@shadecn/shared/agent` `AgentRunsMessage`). The broadcast never carries `mine` (each client computes it).
  - **Multi-replica state (`docs/20` §3.10.10, `run-registry.ts`) goes only through the injected `RunRegistry`** (`runRegistry`, required — no default, like `leases`; host: `apps/server/agent/runs.ts` over `SharedMap` / `SharedLog` / `SharedChannel`). Never answer "which runs exist / is this conversation running / can I reattach" from the local `runs` map alone — other replicas' runs only exist in the registry; the local map is the fast path for runs this replica holds and the same-tick guard.
    - **Run record** `<flowId>:<runId>` = the `AgentRunEntry` + `instanceId`, written (overwrite, TTL) only by the holder, serialized per run (`registryChain`), renewed in the heartbeat directly (never only via the throttled push), released with `deleteIfEquals` after the replay log chain has drained. `activeRuns` / `view` / every broadcast read the **full** list from the registry (local runs overlay their fresher entry); pushes are serialized per flow so a later broadcast is never older.
    - **Conversation slot** `<flowId>:<conversationId>`: `start()` keeps the synchronous local placeholder first (same-tick guard), then `claimSlot` (atomic) — lost = `busy` (409), registry down = `unavailable` (503). Renew = compare-and-set, release = `deleteIfEquals`, like leases. `start()` / `subscribe()` / `abort()` / `activeRuns()` are therefore async — the status code is still decided before the stream opens.
    - **Replay log**: one record per `send` batch (`emitBatch`: one `TEXT_BATCH_MS` window of streamed text frames, one tool start / end, one sub-task change, one closing, …), never one per frame, with a contiguous `seq` from 1. Appends are chained in order and the run's `done` waits for them before deleting the record. A remote subscriber needs the record (else 404), a gap-free, overflow-free log from seq 1 (else 410), then blocks for more and closes on the terminal frame, a seq gap, or the record disappearing (holder crashed). Overflow is decided by the local buffer's limits on the same batch, so 404/410 don't depend on which replica you hit; post-overflow records keep flowing (flagged, trimmed to the last `REPLAY_TAIL_RECORDS`) for subscribers already attached. The log gets a TTL on each append + heartbeat and is left to expire after the run.
    - **Stop on another replica**: authorization (initiator / project admin) happens on the replica that got the request, from the record's `owner`; then `sendStop(record.instanceId, …)`. No record = already over (`not-running`). The holder's `onStop` only checks "is this run mine" — it never re-judges permission.
    - **Watch attribution**: `nameOf` stays synchronous; the watch resolves names at notice time after `resolveActors` (registry lookup of unknown run ids, started already when the transaction is observed — the other run may be gone by then). Finished local runs are remembered too.
  - **`openCanvas` is called once per run and `close()`d in step 5 on every outcome** (success / abort / error / shutdown) — never per tool call; the canvas watch and its baseline live on that one handle. The host's connection (`canvas-access.ts`) pins the room until `close()`; if it is gone mid-run the call fails with `CONNECTION_CLOSED` — never reopen silently (a new doc breaks the watch baseline).
  - **Others' edits (`docs/20` §3.10.2) are inserted server-side, into the parent's transcript, in `modelRequest`** (`insertNotice`): only when the parent's request arrives while its transcript stops after a tool batch (`transcript.pending` existed — never the first request), right after that batch's results (+ `toolsAdded`): flush the merge window, merge the queue into **one** user message, emit `agent.canvas-change` at that moment (the request carries it = the model sees it). "No notice while the model writes its final answer" stays structural: after a tool-less answer pi makes no further request. It is still a *pull* (timed by the next request), never a push; the runner has no part in it (no notice route on the wire), so a compromised runner can't withhold notices. Sub-agents never get notices. Undelivered (still queued) changes go into the closing digest (`closingDigest` rolls their elements back so the next run reports them). Chat order is fixed on both sides: `[user, since-last-run?, assistant, live…]` — the frontend fold appends, the final save writes the same order.
  - **The server-owned transcript (`transcript.ts`, `docs/22` §4.3 step 2, problem C)**: one per agent (`RunAgent.transcript`), the **only** source of the upstream request (`modelRequest` → `requestContext`) and of the stored LLM context. Every segment has a server source: leading system message = server system prompt + the agent's tools (`createInitialSystemMessage`, tools from `definitionsOf`: `load_skill` [+ `request_confirmation` for subs] + the agent's loaded skills, same order as the runner's pi); history = DB `llmMessages` (parent only; non-user/assistant/toolResult roles dropped); this run's user message = the server-built prompt (sub: the `/agent/delegate` prompt); assistant = the server's own model result (`ModelTurnResult` from `proxyFramesOf`, recorded via the decision's `release` **before** the terminal frame is written — the runner may call tools the moment it sees it); tool results filled in call order at the agent's next request (`closeBatch`). Invariants:
    - **Runner input never enters it**: not the model request body (whatever it sends). The **only** runner-sourced results are runner-executed tools (`execution: 'runner'` except `delegate_task`, plus `request_confirmation`) from `tool_execution_end` (`noteLocalResult`: the call must be in the server's reply with that name, no result recorded yet (a server-set limit refusal wins), text only, clipped to `TOOL_RESULT_CONTENT_LIMIT`).
    - **Gateway tool calls are bound to the server's reply** (`bindCall` in `executeTool`, after the not-found / not-loaded checks, before counting): same id as an unanswered call of *this agent's latest reply*, same name, args equal (key-order-insensitive) to the server-validated ones; execution uses the server's args; one execution per call (`claimed`). A bound call's gateway reply (success, refusal, thrown error) **is** its transcript result (`gatewayResultRecord`). Unbound / mismatched requests are refused and recorded nowhere. `/agent/delegate` binds the same way (brief / nodeIds are the server's); its result is the server's `finishSubagent` text (refusals after binding are recorded too).
    - **Only what pi refuses inside the runner (never reaching the gateway) is recomputed server-side, in pi's check order** (`recordReply` at reply time): `stopReason: 'length'` (pi's `failToolCallsFromTruncatedMessage` text) → cut for too-long arguments → `Tool X not found` against the tools declared in that request → pi-ai's `validateToolArguments` → `request_confirmation` not alone (`REQUEST_CONFIRMATION_ALONE_REASON`; runner-local, so the runner's `beforeToolCall` blocks it too — the rule reads only the reply, so both sides agree). A pre-refused call is also refused at the gateway with the same text. No record and no refusal → `TOOL_NOT_EXECUTED` (`TOOL_INTERRUPTED` if the gateway had started it).
    - **The tool-call limit and the `load_skill` alone rule are decided by the gateway, not predicted** (`executeBound`, after binding: count first, then alone — the runner's old order; the refusal is the call's execution record, same text as before: `toolCallLimitReason` / `LOAD_SKILL_ALONE_REASON`). There is **one run-wide count** (`toolCallCount`): bound gateway calls, `delegate_task` at `/agent/delegate` binding, and runner-executed commands (`run_media_command`) when their `tool_execution_start` is reported (`countLocalCall`; over the limit → that call's transcript result is the limit text). `request_confirmation` is not counted (`docs/20` §3.10.11). The runner keeps a count only to block runner-executed commands before running them (`limits.maxToolCalls` stays in `RunnerInput` for that); gateway tools it always sends — never re-add a runner-side block for them (a blocked call never reaches the gateway, so the model would see `TOOL_NOT_EXECUTED` instead of the limit text).
    - **Request legality**: one in flight per agent; allowed only at the start or after a reply that called tools (`transcript.open`) — after a final / errored / aborted reply it's 409. A reply arriving after the run was stopped is dropped (the half answer never enters the context, as before).
    - **`toolsAdded` is inserted by the server** (`declareTools`, pi-ai's `getToolStateChanges` over `getCurrentTools`) after a batch, before the notice — pi's `declareToolChanges` position. Memory-only, like every system message.
    - **Persisting** (`persistedMessages`, then `completeToolResults` + `trimLlmHistory`): this run's slice of the parent transcript after `closeBatch(…, 'final')` (unknown results = `TOOL_INTERRUPTED`), system messages dropped, `partialJson` / `partialArgs` stripped, images → placeholder (`slimMessage`). Nothing from this run is stored if the parent never made a model request. Sub-agent transcripts are never stored. Contexts stored before step 2 were runner-reported and are not cleaned.
    - Images from `view_node_media` live in the in-memory transcript (that is how the model sees them this run, bounded by the run's image budget).
  - **The runner is untrusted and killable at any step.** So: every per-run limit is enforced server-side (**steps = model requests, counted per agent in `modelRequest`**; tool calls counted by the server (`toolCallCount`, above), timeout, delete budget in the server's tool instances); the outcome is decided server-side (`stopped` › protocol mismatch = `runner_protocol_mismatch` › no `/run/finish` = `runner_failed` › runner error › aborted / model error (the server's own reply) › parent transcript still open (`model_error` if its last request was refused pre-stream, else `run_failed`) / success; "aborted" is read from the server transcript's last message); the LLM context is the server transcript (above), with a killed batch's missing tool results filled in as `TOOL_INTERRUPTED` (`closeBatch(…, 'final')`, `completeToolResults` as the backstop — keep both even though pi-ai's `transformMessages` also patches orphaned calls at request time: ours carries the canvas wording and makes the stored context the one actually sent); canvas tool-call audit rows come from the gateway's execution record, not from what the runner reports (only the runner-local media tool is logged from its report).
  - **Stop = close the gateway registration, then kill the sandbox** (`run.interrupt`): tokens 401 and in-flight upstream model requests abort before the kill lands. A stop before the sandbox exists means it is never started.
  - **Node occupancy (`docs/20` §3.10.8, `occupancy.ts`) is written only server-side, only here**: the injected `NodeLeaseRegistry` (`leases`, required — no default, like `store`; host: `apps/server/agent/leases.ts` over `SharedMap`). Never put a lease in the Y.Doc, never give the model a release tool, never trust the runner for it. Claim = `claim`; renew / transfer = `compareAndSet`; **release only ever via `deleteIfEquals`** (never `delete` — an expired key re-claimed by another run must survive the old holder's cleanup). Comparison is on the serialized value, so the run keeps the exact `NodeLease` object it wrote (`RunState.held`) and hands that same object back.
    - **The holder is an agent of the run, not the run** (`NodeLease.agentId`: `MAIN_AGENT_ID` or a sub-agent id; old entries without it read as main via `leaseAgentOf`). Agents of the same run count as "someone else" to each other — check `held` by `agentId`, never just "is it in `run.held`". `delegate` transfers the parent's leases on `nodeIds` (`transferNodes`, CAS, building the new object from the held one); a sub-agent's leases are released when it finishes (`releaseAgentNodes`), never handed back to the parent.
  - **The occupancy / "changed since read" guard (`guardDataWrites` in `executeTool`) runs after the capability check and is a separate step — never merge it into `authorize` or into a tool.** Which calls count is policy in `occupancy.ts` (`dataWriteTargets` / `createdNodeIds`): only writes to a node's `data` (incl. delete and director `nodeId`, new nodes claimed after execution); edges, layout, `metadata`, `ungroup` don't. Both refusals are model-facing tool errors, never a run stop. A call that throws releases what it just claimed (tools validate before their first write). Claims are serialized per run (`run.claiming`) so one call's rollback can't release a lease another concurrent call already counted as its own. Released on every outcome (after the gateway closes, and again in `run.done` as a backstop); renewed every TTL/3, dropping leases that were lost.
  - **"Changed since read" is per agent** (`RunAgent.stale`): watch marks go to every live agent; a successful data write by one agent of the run marks those nodes in every *other* agent's set (`noteWrite` → `markStale(…, except)`) — the watch can't see it (same run origin). A read clears only the reading agent's set; a sub-agent's set starts empty when it is delegated (its mention expansion is its read).
  - **"Changed since read" is structural, from the watch, not from diffs**: `CanvasTransaction.dataNodeIds` (`touchedElements`: a change under the node's `data` group, the group replaced, node added / removed) feeds `onDataTouched` synchronously; diffs only supply the summary text (`onDataChange`). A read clears only marks with `seq <=` the mark taken before it executed. Read tools report `details.readNodeIds`, which `session.ts` strips before replying to the runner (keeps the wire and the stored LLM context unchanged — no protocol bump).
  - **Idle limit** (`limits.idleTimeoutMs`, host: `AGENT_RUN_IDLE_TIMEOUT_MS`) reads `GatewayRun.activity()`: enforced only after the runner's first request; a model request stays in flight from arrival until the server's own stream ends (terminal frame written) or the runner disconnects (the SSE body is cancelled) — upstream retries count as in flight; a pre-stream refusal ends immediately. Sub-agents' gateway requests are this run's activity like any other.
  - **Sub-agents (`docs/20` §3.10.11) are not runs**: the runner builds another pi `Agent` in-process; same token, conversation, Grant, sandbox, run-list entry. Server side they are `RunAgent`s inside `execute` — registered only by `/agent/delegate` (`delegateTask`), closed by `/agent/finish` (`finishSubagent`). Invariants:
    - **One level, judged server-side**: `delegate` refuses any caller that isn't `MAIN_AGENT_ID`; the sub-agent's plan excludes the `delegate` skill (`plan({ exclude })`), so `load_skill('delegate')` and `delegate_task` over `/canvas/tool` are refused too. Limits (`maxSubagents` concurrent, `maxSubagentsPerRun` total) and the shared tool-call count are decided in `delegateTask`, reserved **synchronously** before its first await (a parallel batch arrives together). A delegate must match an unanswered `delegate_task` of the parent's latest server reply (`brief` / `nodeIds` taken from it, the runner's only compared); on binding the server opens that call's entry itself (`openCall` — no reported `tool_execution_start` needed), so `subtaskStart` always finds the view. Each sub-agent gets its own transcript at delegation (its system prompt + tools + the expanded brief), dropped when it finishes.
    - **`delegatedCalls` holds in-flight calls only** (removed at that call's parent `tool_execution_end`, cleared at the parent's **next model request**): upstreams reuse call ids across replies (`call_0` every time), so "one sub-agent per call id per run" refuses honest delegations. Never key it run-wide.
    - **A delegation that didn't succeed is rolled back completely** — `delegatedCalls` entry, `delegatedTotal`, `activeSubagents` + clock, the registered `RunAgent` (deleted, marked finished) and leases already transferred to it (released, not handed back) — everything after the reservation sits in one `try`. Only the tool-call count stays (the model did call it; the runner counted it too). `transferNodes` **throws** on a registry error so this path runs; don't go back to swallowing it (the sub would start without a node it was promised and get "the parent is editing it").
    - **The reply handed to the parent is the server's `mapper.subtaskReply`** (last server-made sub `message_end` with text = the server's own model result), never anything the runner sends; the entry and the parent show the same text. **The sub-task's status / question / error are judged server-side too** (`subagentVerdict`, from the sub's transcript: stopped › `exhausted` › an unrefused `request_confirmation` in its latest reply — question from that call's args › latest reply errored / aborted › transcript still open (turns ≥ `maxTurns` = step limit, else "didn't finish") › done); `SubagentFinishRequest` is just `{ agentId }` — the runner doesn't judge it at all.
    - **Agent ids only distinguish agents inside this run**: the server assigns them; a request / event with an id it didn't assign, or of a finished sub-agent, is refused / dropped. Never key anything cross-run on them, and key per-call maps by `callKey(agentId, toolCallId)` (two models can mint the same call id).
    - **Per agent**: steps (= model requests, `RunAgent.turns`, counted in `modelRequest` on arrival — stopped / failed / disconnected requests count too; one in flight at a time per agent, `RunAgent.requesting`, a second is 409; the parent's `maxTurns + 1`-th request stops the run without calling the upstream; a sub's is answered with one `error` frame and marks it `exhausted` → its tool calls refused. The runner ends a sub's loop at the limit with pi's `finishTurn` → `{ action: 'end' }`, but the server never relies on that), loaded skills + load count, stale set, leases. **Run-wide**: tool calls, delete budget, image bytes (same `runState` / tool instances).
    - **Sub-agent events never touch the parent's context or assistant text**: `display` routes a sub's server-made events to `mapper.subtaskEvent` (its text is not streamed — only the server-made `message_end` of its reply updates the entry); the parent's context is its own transcript, which only ever gets the sub's final `finishSubagent` result. Notices go to the parent's transcript only.
    - **Time**: the single-run timer pauses while `run.activeSubagents > 0` (server's own delegate / finish bookkeeping, never the runner's word) and resumes when it drops to 0; `totalTimeoutMs` (`AGENT_RUN_TOTAL_TIMEOUT_MS`) is wall-clock and never pauses. The sandbox `deadlineMs` and the Grant's `timeoutMs` (absolute expiry) are derived from **`totalTimeoutMs`**, not `timeoutMs` — at start nobody knows whether the run will delegate.
    - A parent model request while sub-agents are still registered can't come from an honest runner (the parent is blocked in `delegate_task`): they're closed as failed (`abandonSubagents`, in `modelRequest`). Unfinished sub-agents at run end are failed by `mapper.finish`.
  - **Context trimming (`trimLlmHistory`) caps by count and by estimated tokens** (`llmHistoryTokenBudget`: window − output reserve − system prompt and offered tool definitions, then half) and still cuts only on a user message. Estimate per message with pi-ai's `estimateMessageTokens` (`@earendil-works/pi-ai/utils/estimate` — not in the root entry), never `estimateContextTokens`: it anchors on the last assistant `usage`, which includes that request's system prompt + tools and covers the whole prefix, so it can't price a suffix. A model-reported overflow is recognised with pi-ai's `isContextOverflow` and ends the run as `context_overflow` with the raw upstream text appended (the panel's `modelError.ts` shows it as-is).
  - Run-list pushes for occupancy changes / renewals go through `scheduleRunsChange` (≤ 1 per `runsThrottleMs` per flow, trailing); enter / leave stay immediate. Entries carry `occupies` + `expiresAt` (= last heartbeat + TTL); the payload and `view()` carry the server clock `now` so clients convert `expiresAt` without trusting their own clock.
- `store` — `AgentConversationStore` / `AgentRunLog` + in-memory implementations for the package's tests. The package never sees MikroORM; `apps/server/store/agent.ts` is the real one, and **`createAgentRuntime` has no default**, so a missing DB wiring can't silently become "lost on restart".
- `tools` — the atomic tool set of `docs/20` §3.10.1 (read, content, connect, delete, layout), one Y transaction per call; read-only tools (`get_node`, `check_connection`) go through `canvas.read` and never write. **Writes only through `@shadecn/shared/flow-ops`** inside `canvas.write(doc => ops.x(opContext(doc), …))` — never a hand-written Y.Map op; the editor's store calls the same ops, so the two can't diverge (`docs/13` §3.7). The tool keeps only argument validation (`TOOL_LIMITS`, delete caps, ids), `add_node`'s `type` check against shared's `CREATABLE_NODE_TYPES` (never a local list), and turning `FlowOpError` into a model-facing message (`runOps`). `update_node` touching two groups asserts both (`assertNodeFieldsWritable`) before writing either — transactions don't roll back. `connect` passes only the logic gate (it may connect into an `asset` node, which flips it to `generate`). `data.src` / `data.form` are managed: `update_node` refuses both; `add_node` accepts `src` only to hand it to `ops.attachAsset` after create/connect (same form rule as a human upload) and refuses `form`. **`dc.*` keys belong to the `director` skill**: `update_node` / `add_node` refuse them on any node (they'd bypass the director ops' validation and limits), and `read_canvas` / `get_node` show a director node's scene only as one summary under `data['dc.*']` (a scene is up to ~2600 keys); `duplicate_node` copies them on purpose. **Sizes without a DOM come only from shared's `nodeSizeOf`** (stored width/height, else the type's `defaultSize` — an estimate); placement, `group_nodes` (`ops.groupFrameFor`) and `auto_layout` (`ops.autoLayout`) never keep a local size table, or agent and editor geometry drift. **`ungroup` spends 1 from the per-run delete budget** — it is `delete_elements` on a group by another name, so not charging it would be a bypass. Batch tools (`move_nodes`, `group_nodes`) reject the whole call if one id is missing, like `delete_elements`.
  - **`view_node_media` (`docs/20` §3.10.7) never fetches the URL in a node.** Bytes come only from the injected `MediaReader` (`media.ts`; host: `apps/server/agent/media.ts` reverses the URL to an own-bucket asset key with `assetKeyOfUrl` and reads by key — a foreign URL is refused before any request, that is the SSRF guard; don't "fall back" to fetching it). The image type is sniffed from the bytes, never taken from the stored content-type (non-image bytes labelled `image/png` make the upstream reject the whole model call). The run's image-byte budget lives on `ToolRunState` like the delete budget. **Offered only when the host passed `mediaReader` and `model.input` includes `image`** (skill `media-view`'s `available`): for a text-only model pi silently swaps images for a placeholder and the model believes it looked.
  - **Message attachments (`docs/20` §3.10.12)**: ownership is checked by the host route against `FlowAsset` *before* `start()` (`resolveAttachments` in `routes/agent.ts`); `contentType` comes from that record and `url` from `storage.objectUrl(key)` — never from the request (it carries only `key` + `name`). `view_attachment` resolves keys **only** against `SkillContext.attachments`, which `session.ts` builds from the conversation's stored user messages — never read a key / URL the model names (that would let it view other canvases' assets). Attachments reach the model inside the server-built prompt (the server transcript), never over the wire.
- `skills` — built-in skills (`docs/23`): `registry.ts` (`defineSkill`, `createSkillRegistry`, `plan`, `load_skill`) + one dir per skill; `BUILTIN_SKILLS` in `skills/index.ts`. **Shared by both sides** — runner and server build tools from the same registry (server: real canvas; runner: `definitionContext`), so nothing under `skills/` may import `session` / `gateway` / `store` / `canvas-changes`. A test registry must be passed to **both** `createAgentRuntime({ skills })` and `createInlineDriver({ skills })`.
  - `createSkillRegistry` throws on: duplicate tool names (incl. the platform names `load_skill` / `request_confirmation`), `requires` not covering a tool's `capability`, `offeredWith` not a subset of `requires`, a `spawnsProcess` tool that isn't `execution: 'runner'` or whose skill lacks `sandbox:exec`. **`execution: 'runner'` alone does not require `sandbox:exec`**: `delegate_task` runs in the runner but spawns nothing — every step of the sub-agent is a normal, authorized gateway request; only tools that start a child process in the workdir (`run_media_command`) set `spawnsProcess`. `requires` (or `offeredWith` when given) only decides *offering*; every gateway tool still authorizes its own capability. **`canvas` is offered on `flow:read` alone (`offeredWith`)** — a grant without write / delete still gets all 13 tools and the gateway denies the write ones one by one (`docs/23` §4); don't narrow `requires` (the coverage check) or drop write tools to get there.
  - **No session scope** (`docs/20` §3.10.9): `SkillContext` / `SkillAvailability` / `RunnerInput` carry nothing about the conversation's `nodeId` — it only records the entry point (stored, echoed as `AgentRunEntry.nodeId`). Never restrict which node a tool may name by it, and never load a skill from it: `auto` skills load only from `@` mentions in this message (plus the conversation's remembered skills).
  - **Stored skill ids are read through `canonicalSkillIds`** (`@shadecn/shared/agent`; `apps/server/store/agent.ts` on every row, `session.ts` again on `previous` / views): a merged or renamed skill (`canvas-edit` → `canvas`) gets an entry in `AGENT_SKILL_ID_ALIASES`, never removed — old rows keep the old id until their next final save rewrites the union.
  - **The gateway refuses tools of skills not loaded this run** (`session.ts` `executeTool`, separate from the capability check — never merge them). Not-offered skills' tools are never built server-side, so they're "not found".
  - **The sub-agent prompt is `subagentPrompt({ maxTurns, replyChars })`** (`prompt.ts`), built from the run's actual `limits` — never hard-code a number into it (the budget the model is told must be the one the server enforces).
  - **`delegate` (`skills/delegate/`)**: `always`, `flow:read`, one tool `delegate_task` (`execution: 'runner'`, executed through `SkillContext.delegate`, which only the runner's parent context has). It is the only `executionMode: 'parallel'` tool; the runner forces every other tool to `'sequential'` and runs pi with `toolExecution: 'parallel'` — pi (still in 1.4) runs a batch sequentially as soon as one call is sequential, so only an all-`delegate_task` batch is parallel. `request_confirmation` (sub-agents only, runner-local, `terminate`) is how a sub-agent ends with "needs confirmation"; like `load_skill` it must be alone in its batch (runner-blocked + server-recomputed, above).
  - **`load_skill` runs alone** (`docs/23` S4): the gateway refuses a `load_skill` whose reply has another tool call (`executeBound`); the runner doesn't block it. A successful load returns `details.loadedSkill` and no `terminate` (the batch doesn't end). Runner side, new tools enter in `prepareNextTurnWithContext` (pi snapshots `state.tools` per `prompt` / `continue`, so a mid-loop `state.tools` write alone does nothing): return `context` with the merged `tools` **and** write the same list back to `agent.state.tools` — otherwise a later `continue()` diffs against the stale snapshot and pi declares the new tools removed (pi must execute calls against the new table). What the *model* sees is the server's `toolsAdded` (`declareTools`, from `agent.loadedSkills`), not the runner's. Sub-agents load the same way.
  - **`director` (`skills/director/`)**: every tool takes `nodeId` (any director node on the canvas; existence / type is the ops' check); writes only through the director ops in `flow-ops` (one `canvas.write` each), measurements only through `director-eval` — model-facing time is seconds, converted to ms at the tool, never inside eval. `delete_director_elements` spends the shared `runState.deleted` budget: explicitly named elements that exist, counted inside the write transaction before the op runs (cascaded tracks / keyframes are free, same as edges under `delete_elements`).
  - The per-run load cap (`limits.maxSkillLoads`) and the loaded set live on the run; the conversation's `skills` only grow (union written at the final save). `load_skill` is hidden from the tool-call list (`events.ts`); a load shows as CUSTOM `agent.skill-loaded`, stored in the chat like `canvas-change`.
- `canvas` — the `CanvasHandle` abstraction tools take (never Hocuspocus); `createDocCanvasHandle` wraps a bare `Y.Doc` for tests. `observe` (both implementations go through `observeDocTransactions`) runs **inside other people's transactions** (Hocuspocus applying a client update): the callback only records actor + element ids, never reads content, and every throw is swallowed. Content is read later in `canvas-changes.ts`'s watch via `canvas.read`, so the host's per-read access check still gates what the model is told. `observeDocTransactions` must instantiate `nodes` / `edges` with `getMap` first — before that, a remote update creates a placeholder root type and `transaction.changed` keys won't match by reference. Who an origin belongs to is the host's `OriginClassifier` (`classifyCollabOrigin` in `canvas-access.ts`: `{source:'connection'}` → `connection.context.identity`, `'gc'` / `'migrate'` → ignored, anything else → unknown).
- `events` — **the only place** pi `AgentEvent`s become wire events (the AG-UI subset in `@shadecn/shared/agent`), **run server-side on server-made events** (`ServerAgentEvent`: same names and shapes as pi's, `docs/22` §4.3 step 3). Protocol changes happen here only; the runner only trims its tool start / end events (`runnerEventOf` in `protocol.ts`), never maps them.
  - **Where `session.ts` gets each input (`display`)** — never from the runner's report: text deltas from the server's own model stream (`ModelRequestDecision.frame`, called by the gateway before each frame is written to the runner; batched for `TEXT_BATCH_MS` via `sendText` and merged in front of the next `send`, so it still streams per delta without one replay record per delta); the reply's `message_end` (closes text, sets `mapper.modelError`, a sub's reply text) from the server's `ModelTurnResult` in `onReply`; a tool entry's start (name, args = `entry.call.arguments`) from the server's reply — gateway tools at binding, **before** execution (watchers see the entry before the canvas change), `delegate_task` at `/agent/delegate` binding; ends from the gateway's execution record, the `finishSubagent` result (sent right after the sub-task's closing frame), or the server's pre-refusal text (`batchResult` = what the model sees). After a stop nothing new is produced (`mapper.finish` settles what's still running).
  - **What the reports are used for** (protocol 7: only `tool_execution_start` / `_end`; a batch with anything else is rejected whole): *timing only* for calls the server can't see happen — runner-executed ones (`entry.local`) and ones pi refuses locally (`entry.refused`) are shown at their reported start / end, content still the server's; counting runner-executed commands (`countLocalCall`); the runner-executed tool's result (the same record `noteLocalResult` puts into the transcript; its `summary` clipped); audit rows for non-gateway calls; `delegatedCalls` cleanup. A parent loop failure's reason is only in the runner's own log (the driver forwards runner output to the server log). Never derive chat text, a tool result, a sub-task's content or a model error from a report.
  - **Order is call order**: `openCall` first shows every earlier unshown call of the same reply (refused ones with their end); whatever is still unshown is completed by `revealBatch` at that agent's next model request (a sub: at `/agent/finish`), with the record `closeBatch` puts into the transcript. Display state lives in a `WeakMap<TranscriptCall, …>`, not in the transcript.
  - **A runner that finishes while the parent's transcript is still open** (called tools and never requested again, or never requested at all — pi's `handleRunFailure`, or a request that never reached us) is judged server-side, never from the runner's error message: the agent's last request refused pre-stream (`modelRefused`, e.g. `llm:invoke` denied) → `model_error` "模型请求被拒绝：<server reason>", else `run_failed` (`runUnfinishedMessage`).
  - Sub-agent events never become TOOL_CALL_* (those are the parent's): `subtaskStart` sends one CUSTOM `agent.subtask` with the whole `AgentSubtaskView`, every later change is a CUSTOM `agent.subtask-update` carrying **only what changed** (the one tool call, the new reply, the closing status), merged with shared's `applyAgentSubtaskUpdate` on the frontend. Never go back to whole-entry frames: the brief (≤ 8000 chars) and every tool call repeated per frame make replay grow with calls × entry size and a few long sub-tasks overflow `replayChars` (410). The stored `subtasks` stay whole entries, equal to the folded frames.
  - **Wire tool-call ids are display ids**, unique within one assistant message / one sub-task entry (`uniqueCallId`: a reused raw id gets `#2`, `#3`…; an `end` goes to the latest `start` of that raw id). The LLM context, `startedCalls` / `executed` and audit rows keep the raw id. Server code looking up "the view of this call" uses `mapper.toolCall(rawId, subagentId?)`, never `toolCalls.find(id === rawId)` (finds the older call); `subtaskStart` takes the raw id and stores the display id.
- `protocol` — the one definition of the runner ↔ gateway wire: routes, `RUNNER_ENV`, token claims, `RunnerInput`, `RunnerEvent`, request parsers (the server validates every body — the runner is in the untrusted zone).
  - **Image blocks travel downstream only** (`/canvas/tool` → runner → pi's in-memory context; the model sees them through the server's in-memory transcript, which records the same `/canvas/tool` reply). Every upstream `tool_execution_end` has them replaced by a text placeholder **twice** — in the runner (`runnerEventOf`, or one image overflows the 4MB events body and kills the uplink) and in `parseEventsRequest` (an untrusted runner must not put base64 into the replay buffer). The stored context goes through `slimMessage` (`transcript.ts`) in `persistedMessages`. So the persisted LLM context, replay buffer and frontend never hold image bytes, and a later run doesn't see earlier images — by design; don't "fix" it by persisting them.
- `token` — HS256 run tokens (`docs/22` §3 claims, 10 min) + one-time bootstrap tokens (only the SHA-256 is kept). Header must be `HS256`, signatures compared with `timingSafeEqual`.
- `gateway` — STS, token → run lookup, body limits, event batch `seq`, and the model route; it delegates every capability check to the run's handlers. **It never reads the token's `scope`**: every call goes through the run's `authorize` (renewal probes `flow:read`). Any failure is 401 with one generic message (reasons only in logs); a cookie is never a credential here, and neither is `x-api-key` (bearer only).
  - **Model route `POST /model/<agentId>/api/stream`** (pi's `streamProxy` appends `/api/stream` and allows no extra headers, so the agent is in the path; `metadata` is an upstream field, never our channel). Order: token → body (size ≤ `MODEL_BODY_LIMIT` + `isModelStreamRequest`) → `authorizeLlm` → the run's `modelRequest(agentId)` (agent known & unfinished, not already in flight, transcript open, step count; returns the server transcript as `context`) → `streamUpstream(decision.context)`. **Nothing of the body is used** (size + "is a JSON object" only; the runner sends an empty context): the model is the server's resolved one; `maxTokens` (`outputTokenLimit`: min(model, `AGENT_MAX_OUTPUT_TOKENS` ?? 16384)), retries, `sessionId` (parent: conversation id, sub: `<runId>:<agentId>`), `identity` (`AGENT_CLIENT_IDENTITY`: own UA, no attribution) and headers (only the model config's) are set server-side — never forward anything from the runner's `model` / `options`. Tests use `ProviderRequestOptions.fetch`.
  - **Two hooks into the session**: `decision.frame` gets every non-terminal frame before it is written (the chat's text stream comes from here — a throw is logged, the stream goes on), and `handlers.modelRefused(agentId, status, message)` hears every pre-stream refusal of a known run (size / shape / `llm:invoke` / the session's own) so the session can say why an agent stopped in its own words.
  - **Pre-stream refusals are `{ error: string }`** (`streamProxy` reads only a string `error`; an object becomes `[object Object]`). After the stream opens every failure is an `error` frame: upstream errors carry pi's formatted text verbatim; a stop / runner disconnect aborts the upstream (signal = run `signal` ∪ request `signal` ∪ local cutoff) and the stream still ends with `error { reason: 'aborted' }` — never an HTTP stream error (`@hono/node-server` would log that as a server fault).
  - **`proxyFramesOf` (`model-stream.ts`) never forwards `toolcall_delta`** (`toolcall_end` carries the whole call; forwarding would make the runner's `streamProxy` re-parse per delta, pi #9265), **mints missing / duplicate call ids at `toolcall_end`** (the wire rejects empty ids; ids are minted here now, not in the runner), and **cuts a request whose tool arguments exceed `MAX_TOOL_ARGUMENT_CHARS`** (2 × `TOOL_LIMITS.dataBytes`) — pi-ai 1.4.0 re-parses the whole argument text on every delta on the server's main thread. The cut reply is closed as a **tool-use reply**, not an error: open blocks get their end frames, still-open calls go down with `arguments: {}` and are listed in `ModelTurnResult.cut`, later blocks are dropped, the stream ends `done { reason: 'toolUse' }`. The runner's pi "executes" them (local schema error, or the gateway refuses with the cut text) and keeps looping; the model gets "arguments too long" as that call's tool error at the next request — never back to a whole-run `model_error`. `onResult` must fire before the terminal frame is yielded. Usage is logged once per request (`[agent-gateway] run=… agent=… step=…`) and **persisted from the same number: the `usage` of the result the stream decision's `release` gets** (`addRunUsage` in `modelRequest`, before `onReply` — a reply dropped after a stop still counts; runner-reported usage is never read). One run-wide total, parent + every sub-agent (`AgentRunFinish.usage`); `release` is called exactly once per opened stream, and step 5 waits (≤ `USAGE_SETTLE_MS`) for still-unsettled requests before `finishRun` — keep both, or a stop loses the aborted request's partial usage. Cost is pi-ai's `usage.cost.total`; a model whose price table is all zero (custom endpoints) records `costUsd: null`, never 0 (`modelHasPricing`).
  - An API the server can't call (`SERVED_MODEL_APIS`) makes `createAgentRuntime` disabled, not a per-run failure.
- `runner` — the sandbox side: redeem → input → pi with tool **proxies** (`runLoop` serves both the parent and each sub-agent; sub-agents' tool calls / events carry their `agentId`, the parent's carry none) (definitions from the same skill registry, `execute` = `/canvas/tool`; `execution: 'runner'` tools run locally; the workdir sandbox opens only if an offered skill requires `sandbox:exec`), flush events before each gateway tool call and **before each model request** (`streamFn`: the server closes the previous batch at that request, and runner-executed results must already be there). **`streamFn` wraps pi's `streamProxy`** with an empty context (`normalizeContext({ messages: [] })`) and only `authToken` (the run token, renewed first via `client.token()`), `proxyUrl` (`client.modelProxyUrl(agentId)`) and the abort signal — the runner holds no upstream address or key, no system prompt / prompt / history (pi starts from `prompt('')`), and has nothing to say about model parameters; `streamProxy` uses the global `fetch`. The runner imports no `@earendil-works/pi-ai/api/*` (those are server-side, `model-stream.ts`). Call ids arrive already minted in `toolcall_end` (server-side); the server's id validation stays strict. **No message of the runner's pi transcript leaves the runner** (`runnerEventOf` reports tool start / end only). pi 1.x's `handleRunFailure` — a loop failure (a throwing listener, `streamFn` before its request, or `prepareNextTurnWithContext`) — makes no model request, so it is **not** a step server-side (a model-stream error is: the request was sent); the runner logs its reason itself (`[agent-runner]`). `runner/main.ts` is the process entry: reads `RUNNER_ENV`, logs only env **names**, deletes the bootstrap token from `process.env`, kills its own process group when the parent changes.
- `model` — picks a pi `Model` from an **explicit options object; the package never reads `process.env`** (env parsing: `apps/server/config.ts` + `apps/server/agent/index.ts`). Registry lookup is `getBuiltinModel` (`@earendil-works/pi-ai/providers/all`). **A custom `baseUrl` forces `CUSTOM_ENDPOINT_COMPAT`** (`supportsMidConvoSystemMessages` / `supportsMidConvoToolChanges` = `false`) on top of the registry / preset compat: with them on, the SDK sends mid-conversation system / `tool_addition` blocks (+ beta headers) after `load_skill`, which self-hosted Anthropic / OpenAI-compatible endpoints don't understand. The registry branch (official URL) keeps the registry's values. **The `AGENT_API_KEY` fallback is our own table** (`AGENT_PROVIDER_KEY_ENV` / `agentProviderApiKey` in `apps/server/config.ts`), not pi's `getEnvApiKey` (only in `/compat` since 1.x); it deliberately omits ADC / AWS credential chains — the server calls the upstream with a plain `apiKey` (Bedrock / Vertex are out of scope, `docs/22` §4.3).
- `sandbox` — `Sandbox` + `LocalSandbox` (`openLocalSandbox(workdir)`): command whitelist, no shell, timeout, output cap, workdir-only files. **The media tool runs it inside the runner's own workdir** (the runner *is* the sandbox); the server only keeps the media tool's definition for `describe`, and the gateway refuses to execute it. **`exec`'s `signal` SIGKILLs the child; `dispose()` kills running children before removing the workdir.**
- `sandbox/drivers` — `SandboxDriver` / `SandboxSpec` / `SandboxHandle` (`docs/22` §7) + the `process` driver: spawns `node` on the host-given command, **env built from scratch (`runnerEnv`: PATH + `RUNNER_ENV` only)**, `detached` so `kill` SIGKILLs the whole process group (runner + ffmpeg), workdir removed before `wait()` resolves, `deadlineMs` as a backstop. **It throws when `production` unless `allowInProduction`** — the package never reads `NODE_ENV`; the host passes it. `reap` is a no-op (the runner kills its group when its parent dies).
  - **`oci` driver** (`oci.ts` + `engine.ts`, `docs/22` §7.2): Docker Engine API over the unix socket with `node:http` — **no client library, and no `/v1.xx` prefix** (unversioned paths work on Docker and Podman; Docker 29 raised the minimum API to 1.44). The container config (`ociContainerConfig`) is the isolation boundary: **`Env` is exactly the three `RUNNER_ENV` vars** (PATH comes from the image, which is `FROM scratch` so it carries no base-image env — never add a var to the container or an `ENV` to the image); read-only rootfs, `noexec` tmpfs at `/work` + `/tmp`, `User` 10001, `CapDrop: ALL`, `no-new-privileges`, **no seccomp option** (= engine default), no binds/mounts, `host` / `none` networks refused. The runner's workdir is `/work/run`, not the mount point (`rm` of a mount point is EBUSY).
  - **No `AutoRemove`**: `wait()` = long-poll exit → inspect (OOM) → drain logs → delete, and only then resolves; auto-removal would race all three. `kill` only SIGKILLs; deletion happens on the exit path. Every wait is bounded (`killConfirmMs` after a kill when the engine is unreachable) so a run can't hang on a dead engine.
  - **`reap` deletes only containers labelled with this host's `instance`** (apps/server: hash of the gateway URL — a run can only reach the instance that issued it, so same-URL containers after a restart are orphans; other instances on the same engine are untouched) **and skips containers the driver itself is still managing**, so a reap racing a fresh `start()` can't kill it. The host runs it at startup and every 10 min (`startAgentSandboxReaper`).
  - **Socket discovery is filesystem-only** (`findEngineSocket` / `engineSocketCandidates`, env values passed in by the host): the server never shells out to `podman` / `docker`.
  - In a container the runner is **PID 1**: `runner/main.ts` skips the parent watch there (`ppid` is 0, and `kill(-1)` would mean "every process").
  - **Changing the runner ↔ gateway wire (`protocol.ts`: routes, bodies, `RunnerEvent`, `RUNNER_ENV`, parser rules — v4 added `/agent/delegate`, `/agent/finish` and `agentId`; v7 is the step-4 cleanup) means bumping `RUNNER_PROTOCOL_VERSION`** and the recorded hash in `packages/agent/test/protocol-version.test.ts` (comments / whitespace don't count; types imported *into* `protocol.ts` aren't hashed — remember those yourself). The runner reports the version in the bootstrap redeem; a mismatch or a missing field (old image) is **409 `protocol_mismatch`, never 401**, voids the bootstrap anyway (delete-then-judge), and goes through the gateway's `protocolMismatch` handler so `session.ts` ends the run as `runner_protocol_mismatch` (ahead of `runner_failed`) — don't infer it from the runner's exit code (4). The build id (`__AGENT_BUILD_ID__`, `'source'` when unbuilt) is advisory only: warn, never reject.
  - The image runs the runner from `output/agent-sandbox/` (the runner's chunk closure + only its external packages, `build-server.mjs`) — **rebuild the image after changing runner-side code or the protocol**; a stale image talks an old protocol to the gateway.
  - **`k8s` driver** (`k8s.ts` + `kube.ts`, `docs/22` §7.5): one **bare Pod** per run, not a Job (a retry would re-redeem the one-time bootstrap token; the outcome is server-side). Kubernetes API over `node:https` — **no client library, no kubeconfig parsing**; the host passes URL / token file / CA file (in-cluster defaults: `KUBERNETES_SERVICE_*` + the ServiceAccount files). **The token file is re-read on every request** (projected tokens rotate ~hourly — caching it 401s after an hour); the CA is read once; `http://` only to loopback (`kubectl proxy`, tests).
    - `k8sPodSpec` is the isolation boundary and must keep satisfying Pod Security `restricted` **and** the `dev` VAP (`k8s/variants/agent-sandbox-vap.yaml`; one of them enforces it, the self-check dry-runs it): env exactly the three `RUNNER_ENV` vars, `automountServiceAccountToken: false` (else the namespace's default SA token lands in the sandbox), `enableServiceLinks: false`, memory-medium `emptyDir` at `/work` + `/tmp`, requests = limits. kubelet still injects `KUBERNETES_SERVICE_*` unconditionally — not a secret, don't fight it. There is no Pod-level PIDs field (`AGENT_SANDBOX_PIDS` is a no-op here) and emptyDir can't be `noexec`.
    - `wait()`: GET → watch from that `resourceVersion` → **re-GET after any watch end / 410** (so nothing is missed) → terminal → log drain → DELETE `gracePeriodSeconds: 0` + uid precondition → **resolve only after the Pod is confirmed gone**. The Pending limit (`K8S_START_TIMEOUT_MS`) must stay **below the bootstrap token TTL** (a Pod that starts later can't redeem). Deadline, Pending limit and stop all go through one kill path, and every kill is bounded by `killConfirmMs`.
    - **`reap`**: own-instance Pods like `oci`, **plus any instance's Pod past its own `activeDeadlineSeconds` + grace** — the instance is the hash of `http://$POD_IP:…`, so a replaced server Pod gets a new IP and its orphans would otherwise never match anyone. Never widen that to "other instances' Pods" in general: they may be live runs.
    - **The self-check gates enabling** (host, `apps/server/agent/index.ts`): failed (unreachable, 401, missing RBAC verb, namespace missing, dry-run rejected, **privileged counter-probe `k8sPrivilegedPodSpec` admitted** = no admission guard) → runtime built as disabled and the driver's `start` refuses. **Re-run before every reap tick, passing or not** (a removed VAP / Role must disable a running server, not wait for a restart); ticks never overlap, details are logged only on the first check and on a verdict change. The counter-probe must differ from `k8sPodSpec` only in `privileged` (+ `allowPrivilegeEscalation: true`, else the API's own validation 422s it and the probe proves nothing).
    - `nodeSelector` comes from `AGENT_SANDBOX_K8S_NODE_SELECTOR`, parsed by `parseK8sNodeSelector` at the host's assembly point (bad format = disabled with the reason), like the pull policy. F14: the gateway URL defaults to `http://$POD_IP:$PORT` (Downward API) — **never a Service address** (another replica has no registration → 401).
- `testing` — test-only: `registerScriptedModel` (an OpenAI-compatible scripted upstream, faux-style steps; called by the **server's** `streamSimple` through `ProviderRequestOptions.fetch` = `upstreamFetch`, so `requests` are what the server actually sent — the adversarial transcript tests in `test/transcript.test.ts` assert on them directly; only accepts the server's key), `gatewayFetch` (route test-gateway requests to `runtime.gateway.handle` / `app.fetch` — the runner's `streamProxy` uses the global fetch), `createInlineDriver` (runner in-process, same protocol). **Production code never imports it; no `AGENT_SANDBOX` value selects the inline driver.**
- `authority` — a run's execution identity (`docs/22`): `RunAuthorityProvider.issue()` → `RunAuthority` (Grant id, scopes, `authorize(capability)`, `release`). **The package never sees the DB or sessions**; the host (`apps/server/agent/authority.ts`) implements it, and phase 2's gateway reuses the same `authorize`.
  - **Every capability is authorized before use, in one of three fixed places**: each canvas tool's required `capability` at the gateway (wrapped in `session.ts`, never inside the tool), `llm:invoke` in the gateway's model route (before every upstream request), and `flow:read` / `flow:write` inside the host's canvas handle (`canvas-access.ts` gets the run's authority and has no access check of its own — don't add a second one). `sandbox:exec` only decides whether skills that need it (`media-exec`) are offered; it runs inside the sandbox without a gateway check (`docs/22` §3). A tool without a `capability` doesn't compile.
  - **A `revoked` / `expired` failure stops the whole run** (`stopRun` → cancelled / expired with the reason), never just a model-facing tool error; `denied` (scope not granted, check unavailable) refuses one call. The host's reconciler also stops runs proactively via `GrantRequest.stop`. First stop reason wins.
  - **The run is decoupled from the session**: nothing after `start()` may look at the initiator's login state (logout / expiry must not stop a run, `docs/22` §6). Only `revokeAllGrantsForUser` (account security events) stops all of a user's runs.
  - Host side: effective = Grant row not revoked / expired ∩ `currentFlowAccess` ∩ same project / personal owner as the issue-time snapshot; verdicts cached ≤ 3s as a Promise. Reconcile = `collab/revocation.ts`'s agent-agnostic `onAccessRevoked` (fired by `revokeCollabAccess` locally, by the epoch watcher cross-instance) + `startAgentReconciler` (10 min, also expires due grants). `agent_grant` / `agent_grant_scope` have **no FKs** (audit outlives flows and users).

## What stays in `apps/server`

The route (`routes/agent.ts`, SSE + auth + the permission matrix in its header; admin abort reads `projectRole` from this request's `requireFlowMember`), the gateway mount (`routes/agent-gateway.ts`, in `PUBLIC_API` — outside the session gate, bearer-only), `agent/index.ts`'s `agentHostOptions` (the wiring tests reuse) and driver / gateway wiring (`AGENT_SANDBOX`, production refusal, token secret; the driver is built once and shared by the lazy runtime and the startup reaper), `agent/runner-command.ts` (how the runner is spawned: tsx loader from source, `agent-runner.js` + forwarded `--import`s from the bundle), `agent/runs-broadcast.ts` (the room broadcast — agent-side, the collab layer stays agent-agnostic), `agent/canvas-access.ts` (direct connection into the live room, **authorizes through the run's authority and checks the quota before every read/write**), `agent/authority.ts` (Grant issue / authorize / reconcile, above), `agent/media.ts` (the `MediaReader` over `storage/`, wired only when S3 is configured), `agent/leases.ts` (the node-occupancy registry: `SharedMap` `agent-node-lease`, `stringCodec` + own `JSON.stringify` so CAS compares exact strings, TTL `AGENT_LEASE_TTL_MS`, value carries `INSTANCE_ID`), `agent/runs.ts` (the run registry: `SharedMap` `agent-run` / `agent-conversation`, `SharedLog` `agent-replay`, `SharedChannel` `agent-stop` on channel = `INSTANCE_ID`; same codec rule and TTL), and env/config (`AGENT_IMAGE_INPUT` overrides the model's image input).

## Tests

Agent tests run the real path: `registerScriptedModel()` + inline driver + `vi.stubGlobal('fetch', gatewayFetch(...))` (server tests: `test/helpers/agent.ts`'s `useScripted`, routed through `app.fetch`) — the runner's real `streamProxy` against our server half, which calls the scripted upstream through the real OpenAI SDK. Upstream errors are formatted server-side by pi 1.x as `<status>: <upstream JSON body>` (`formatProviderError`), forwarded verbatim in the `error` frame — the chat panel parses it for display only (`components/flow/agent/modelError.ts`). The `k8s` driver likewise against a fake API over loopback http (`k8s-driver.test.ts`); `apps/server/test/agent/k8s-manifests.test.ts` parses `k8s/` with a dependency-free YAML subset parser (`test/helpers/yaml.ts` — keep manifests inside that subset; it throws on block scalars / anchors) and pins RBAC / NetworkPolicy / Pod Security / the VAP (through a rule-by-rule TS twin of its CEL, plus the allow / deny sample Pods) against `k8sPodSpec`; `sandbox-k8s.test.ts` (real cluster) is **skipped unless `AGENT_SANDBOX_K8S_IT=1` plus explicit `AGENT_SANDBOX_K8S_IT_API_URL` / `_NAMESPACE`** — it has no default that could reach a cluster.
