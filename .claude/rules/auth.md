**Auth (`apps/server/auth/`) — Keycloak OIDC + GitHub OAuth2, BFF style.** Full write-up in `docs/02-auth-keycloak.md`. The browser never sees a token: the authorization-code exchange happens server-side, tokens live in the database, and the client only holds an httpOnly `sid` cookie.
- **`auth/providers/` — the registry that keeps everything else provider-blind.** `types.ts` declares one interface (`authorizationUrl` / `exchange` / `refresh`), `index.ts` holds a `REGISTRY` array whose **order is the login page's button order**, and `keycloak.ts` / `github.ts` are the two implementations. Routes, the session layer and the login page all speak `AuthProvider`, so **adding a login method is one new file plus one array entry** — nothing else is touched. `refresh: null` is a first-class answer, not an oversight: GitHub OAuth App tokens never expire and there is no refresh token, so `Session.provider` exists purely so renewal knows who to ask, and a github session's `expiresAt` is set to `SESSION_TTL` (it can never reach the renewal branch, and the session-age cap is what ends it).
- **There is exactly one callback *path*** (`/api/auth/callback`) for every provider; `AuthRequest.provider` dispatches. Registering a second redirect URI in Keycloak for each new provider would be pure config drift, and GitHub only allows one per OAuth App anyway.
- **But the callback's *host* follows the domain the browser actually used — `apps/server/auth/origin.ts`'s `originOf(c)`, gated by the `APP_ORIGINS` whitelist.** One deployment routinely answers on several domains (external, internal, an old one, a bare IP), and `redirect_uri` is an absolute URL: with a single hard-coded `APP_ORIGIN`, clicking 登录 on domain B finishes the callback on domain A, the session cookie lands on A, and B is still anonymous — while every step of the flow 302s without an error, so it reads as success. `redirect_uri`, the CORS echo, the WebSocket `Origin` check, the invite link and the cookie's `Secure` flag all take their origin from that helper. **What it must not do is follow `Host` blindly**: behind a proxy `Host` / `X-Forwarded-Host` are attacker-controllable, and building `redirect_uri` from them mails the authorization code to someone else's domain. So it takes the first of `X-Forwarded-Proto`+`X-Forwarded-Host` → `Host` → `Origin` that is **on the whitelist** (`Origin` last: a full-page navigation carries none, but it is the only header left when a proxy rewrites `Host` to an internal name), and falls back to `APP_ORIGIN` otherwise — i.e. behaviour without the list is exactly what it was. `APP_ORIGIN` is always a member (it is the fallback target), comparison is normalized (lowercase, no trailing slash, default port dropped, http/https only), and **there are no wildcards** — every domain's `/api/auth/callback` has to be registered in Keycloak's *Valid redirect URIs*, so a wildcard would only mint addresses nobody can register. Two details are load-bearing: **`AuthRequest.origin` is stored**, because OAuth2 requires the token exchange's `redirect_uri` to match the authorization step character for character and recomputing it on the callback leg is not safe (a changed header or a changed list yields a different value and the provider refuses it); and **the cookie's `Secure` flag is per-request** (`secureCookieFor`), because the list can mix https and http domains — miss it on https and you drop a layer of protection, set it on http and the browser silently *discards* the cookie, which looks like "login succeeded but I'm still logged out" with a completely clean server log.
- `auth/oidc.ts` — everything that talks to Keycloak: cached `.well-known/openid-configuration` discovery (endpoints are never hard-coded), PKCE `S256` helpers, `exchangeCode` / `refreshTokens` / `revokeRefreshToken`, RP-initiated `buildLogoutUrl`, and `verifyIdToken` — JWKS fetch (kid miss → one refetch) + `crypto.createPublicKey({format:'jwk'})` signature check for RS/PS/ES, then `iss` / `aud` / `azp` / `exp` / `iat` / `nonce`. No `jose`/`openid-client` dependency. `revokeRefreshToken` / `buildLogoutUrl` are **no longer called by the logout route** (see below) but stay as part of the OIDC client. `OidcError` is deliberately shared with the GitHub path — `session.ts`'s retry logic keys on `retryable` alone, and two error types would fork that judgement for no reason
- **`auth/providers/github.ts` — four things that make GitHub *not* an OIDC client.** No discovery (endpoints are hard-coded — GitHub publishes no well-known document); no `id_token`, so identity costs a second call to `/user`, plus `/user/emails` when the user has made their address private (unreachable → the account simply has no email, it is not a login failure); **the token endpoint answers HTTP 200 on failure** with `{error, error_description}` in the body, so checking only the status code reads "this code was already used" as success; and no PKCE support (a `code_challenge` is silently ignored — replay protection is the one-shot `AuthRequest`). Roles are always `[]`: GitHub has no notion of this app's roles
- `auth/session.ts` — session lifecycle. The cookie holds a 32-byte random token; the DB row id is `HMAC-SHA256(SESSION_SECRET, token)`, so a database dump alone can't forge a cookie. `loadSession()` transparently refreshes an access token that is within 30s of expiry (concurrent refreshes for one session are deduped through an in-process promise map), so **the session is kept alive by traffic** — it only really expires once nothing has hit the server for long enough that the refresh token passes Keycloak's SSO Session Idle. `loadSession(token, { refresh: false })` is the read-only variant for callers that are *not* user traffic — currently just the collab server's periodic connection revalidation: it answers "still valid right now?" (a live refresh token counts) without renewing anything, and never deletes a row. A long-lived WebSocket must not be able to keep its own session alive. A failed refresh is **not** uniformly fatal: only a 4xx rejection from Keycloak (`invalid_grant` — logged out, idled out, kicked) destroys the session. Anything that proves nothing — connection refused, timeout, a 5xx, even a local DB write failure — keeps the session and retries on the next request, with a 15s per-session cooldown so a dead Keycloak doesn't make every request eat a timeout. `OidcError` carries `code` + `retryable` to make that call, and every outbound OIDC request has an 8s timeout (node's fetch has none by default). Deleting the session in the network-failure case is the bug this replaced: with a 60s access-token lifespan the refresh runs constantly, so one blip logged the user out. `sweepExpired()` drops timed-out sessions and unused auth requests
- `auth/middleware.ts` — `withSession` (parse, refresh, expose `c.get('user')`, clear a stale cookie; mounted on `*`, not just `/api/*`, because the page gate needs it too), `requireAuth` (401), `requireRole(...)` (403). Keycloak realm roles land in `User.roles` as-is, client roles as `clientId:role`
- `auth/ws.ts` — the same session check for WebSocket handshakes
- `auth/redirect.ts` — `safeRedirect()`, the shared in-site-only check for every `?redirect=`
- `routes/auth.ts` — `GET /api/auth/{config,me,login,link/:provider,callback,identities,logout}` + `DELETE /api/auth/identities/:id`. `/me` always answers 200 (`{enabled, authenticated, user}`) so the router guard has no error branch. `state`/`nonce`/`code_verifier` live in the `AuthRequest` table keyed by a short-lived `oidc_tx` cookie and are consumed exactly once, so a replayed callback fails. `?redirect=` is restricted to in-site paths (`//evil.com` and `/\evil.com` fall back to `/`). **`/api/auth` is in `PUBLIC_API`, so the four logged-in-only endpoints check `c.get('user')` themselves** — there is no `requireAuth` above them
- **Login and "link another account" are the same flow**; the only difference is `AuthRequest.linkUserId`, which makes the callback stash a pending link instead of minting a session. Two consequences worth keeping: the callback **reads the `AuthRequest` before it looks at `?error=`**, because "user cancelled" has to land back on `/settings` rather than `/login` and only that row knows which; and it re-checks `c.get('user')?.id === linkUserId`, so a session swapped in another tab mid-flow can't graft an identity onto the wrong person
- **A link is never written until the user confirms which account it is (`PendingLink` + `POST /api/auth/link/confirm`).** The settings-page session proves *you* are you, but it says nothing about the trip out to the provider: the browser may still be signed into someone else's GitHub (a shared machine), and because an OAuth App that has been authorized once never shows its consent screen again, the whole round-trip is invisible — click 关联, and you are back with a code, having been asked nothing. Writing straight to `UserIdentity` there binds *that person's* account, and they can then sign into yours. GitHub also has **no account chooser** (no `prompt=select_account`; `login=` is only a hint, switching means logging out of github.com), so nobody else is going to ask the question — we have to. Hence: the callback only pre-checks (`identities.checkLink`, read-only, so a doomed attempt doesn't get a pointless dialog) and stashes; the dialog shows the resolved username/email; confirming re-runs the real check, because the identity can be taken during the time the user spends reading. Four details that are load-bearing: **one pending row per user** (`userId` unique, a new attempt replaces the old — otherwise "which attempt is this dialog about" needs explaining); **no access token is stored** for an unconfirmed binding; the pending state rides **`GET /api/auth/identities`, not the URL**, so closing the tab and coming back still surfaces it; and confirm is **POST**, never reachable by following a link
- **Logout only ends the local session** — no `revokeRefreshToken`, no RP-initiated logout. This app is one client on a Keycloak realm; signing out here must not sign the user out of every other app behind the same SSO. The accepted cost is that Keycloak's SSO cookie survives, so clicking 使用 Keycloak 登录 right after logging out silently returns the same account and looks like the logout did nothing. Keycloak's *Valid post logout redirect URIs* is therefore no longer configuration this app needs
- When neither Keycloak (`KEYCLOAK_ISSUER` + `KEYCLOAK_CLIENT_ID`) nor GitHub (`GITHUB_CLIENT_ID` + `GITHUB_CLIENT_SECRET`) is configured, `authEnabled` is `false`: dev warns and lets everything through (so the demo pages still run without an IdP), production refuses to boot. Half a provider (issuer but no client id) is reported as a missing variable rather than treated as "not using it"
- **`apps/server/store/identities.ts` — one user, several login methods.** Each binding is a `UserIdentity` row and `@@unique([provider, subject])` *is* the whole conflict check — a third-party account can belong to exactly one local user, so `link()` never has to guess. One of the rows is the **primary identity**, and it has no boolean column: it is the row whose `(issuer, subject)` equals `User.issuer` / `User.subject`. Storing an `isPrimary` flag would just add a second place that can disagree with those two columns. Three rules the login path depends on: every login refreshes *that identity's* display fields, **`User`'s profile fields only follow the primary identity** (otherwise one GitHub login quietly renames a Keycloak-named user), and **`User.roles` is only written on a Keycloak login** — GitHub always reports `[]`, so writing it unconditionally wipes the user's roles on every GitHub sign-in. Unbinding the last identity is refused (409): there is no email-recovery path here, so it would orphan the account and everything it owns. Unbinding the primary promotes another row and rewrites those two columns but leaves name and avatar alone. Users that predate this table get their primary row **backfilled on use** (the login path adopts them, `listFor` writes it on read) — this repo has no migrations, so a lazy backfill is the migration.
- **Identity is `(provider, subject)` and never email — there is deliberately no "same email means same person" shortcut**, not even for an address the provider swears is verified. The default position is *different people*; a merge only happens when someone has proved themselves with the target account's own credential, i.e. signed in and then hit 关联 in settings. Three reasons, in order: that session **is** the strongest possible proof and needs no third party trusted; email is an attribute, not an identifier (it changes, it gets reassigned after an account is closed, and Sign in with Apple hands out a different private-relay address per app — every major IdP's docs say key on `sub`, not `email`); and auto-merging is the textbook account-takeover entry point, because the load-bearing claim "the person signing in really controls this mailbox" can only come from the source IdP and we cannot re-check it — one lax IdP, or an admin who can flip `email_verified` by hand (Keycloak can), turns it into a way into someone else's account. One implementation consequence: **GitHub only calls `/user/emails` when `/user` returned no address** — email is a display field here, not worth a round-trip on every login. The accepted cost is that one person signing in via Keycloak and then via GitHub ends up with **two** accounts; the supported path is sign in with the main account first, *then* link — never the other way round. Merging two accounts that already exist is still absent
- **`auth/profile.ts` — what a user gets *after* login, kept outside the login path.** `identities.resolveLogin()` does one thing: turn a provider profile into a `User` row. "And now give this person a default avatar / display name / timezone" is a different, ever-growing concern, so it hangs off the side: `registerProfileHook({name, fill})` adds a rule, `completeUserProfile(user)` runs them all in the callback (and in `auth/project.ts`'s dev-user path, so the no-Keycloak local mode gets the same treatment). Each hook only answers "what's missing" and the mechanism merges the answers into **one** update; a hook that throws is logged and skipped — it must never block a login. **It runs on every login**, which is what backfills existing users: no migration script, and no fallback logic scattered across the read paths. Adding a rule = one new file + one `registerProfileHook`; login code stays untouched.
- **`apps/server/avatar/` — the one hook there is today: no avatar → an identicon.** GitHub-style pixel blocks, generated by [minidenticons](https://github.com/laurentpayot/minidenticons) (MIT, dependency-free). Keycloak's `picture` always wins; the hook only fills the empty ones. **No image is stored**: the DB holds `/api/avatars/<seed>.svg` and `routes/avatars.ts` renders it on demand — no DB read, no notion of who's asking, so it's served `immutable` for a year. The seed is `sha256(issuer + "\n" + subject)` truncated to 16 hex — keyed on `(issuer, subject)` rather than `user.id` so the picture survives a rebuilt database, hashed so a subject never rides in an image URL. The route module is also what *installs* the hook (it imports `avatar/index.ts`), so mounting the route and having default avatars are the same one line in `app.ts`. Wherever a stored avatar is displayed, put a round background under it (`bg-muted` / `bg-sidebar-accent`) — the identicon is transparent-backed, and without it the blocks float on the page instead of sitting in the same circle the no-avatar fallback draws
