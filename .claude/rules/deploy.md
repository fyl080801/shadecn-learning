**Deploy:** two paths to the same image. `pnpm build && docker build ./output` uses the Dockerfile the build drops into `output/` (deps stage: `npm install --omit=dev` off `output/package.json` — no compiler toolchain, better-sqlite3 13 ships prebuilt binaries for every platform incl. `linuxmusl-x64/arm64` and declares `gypfile: false`; runtime stage: those `node_modules` + the artifact, `WORKDIR /app`, `CMD sh -c "node server/db-sync.js && exec node server/index.js"` — the `exec` makes node PID 1 so SIGTERM actually reaches the shutdown flush). The repo-root `Dockerfile` is the from-source variant: a build stage that copies each package's `package.json` (web, shared, server — one `COPY` per package, add a line for any new workspace package), runs `pnpm install --frozen-lockfile`, copies the source (`.dockerignore` excludes `**/node_modules`, see the monorepo section) and runs `pnpm build`, then the exact same deps + runtime stages over `/app/output` — keep the two in sync (edit `apps/server/scripts/output-image/Dockerfile`, not `output/`). Only the deps stage runs on the target platform; better-sqlite3 picks its prebuilt binary by the *runtime* platform + arch, so a correct base image means the correct binary. `NODE_ENV=production`, `HOST=0.0.0.0`, port 3000; no source, no pnpm, no tsx in the runtime image. nginx is gone — the Node server serves `public/` itself. No stage installs `python3 make g++` any more. **pnpm 9 ignores `gypfile: false`** and runs `node-gyp rebuild` for any package with a `binding.gyp` and no install script, which fails on machines without node-gyp — hence the root `package.json`'s `pnpm.neverBuiltDependencies: ["better-sqlite3"]` (npm honours `gypfile: false`, so the deps stage needs nothing).
- **Both runtime stages end with a native-module load check, and both must keep it.** A native module of the wrong architecture does not stop the container from booting: Node dlopens it only on the first `require`, and `/api/health` never touches the database — so readiness stays 200, the Deployment reports `1/1 Available`, and only real requests 500 with `Error relocating …/better_sqlite3.node: unsupported relocation type 1026`. That is exactly what shipped once, and the cause is the one to remember: **a single-arch base-image tag plus QEMU binfmt makes pulling the wrong architecture completely silent.** Harbor's `library/node:22-alpine` is an arm64-only image someone pushed by hand; `buildah bud --platform linux/amd64` can only fall back to the arm64 manifest, binfmt runs every `RUN` without complaint, and that round installs an aarch64 `.node` into an image labelled amd64. Never read "the build succeeded" as "the architecture is right" — verify a base image with `uname -m` on an amd64 node before adopting its tag. Three independent guards, all in the Dockerfiles: one **multi-arch** reference shared by all stages (`192.168.68.95:31443/docker.io/library/node:22-alpine` — *not* `harbor-core.harbor.svc/library/node`), `ARG TARGETARCH` compared against `process.arch` in the deps and runtime stages, and the load check as the catch-all. The check is two steps now: `require('better-sqlite3')` opens a `:memory:` database and runs a query (its `prebuilds/` holds `.node` files for *every* platform, so dlopen-ing them all would always fail — that directory is excluded from the loop and verified through the package's own selection logic instead; every artifact ships better-sqlite3 now), then every other `*.node` is `process.dlopen`ed as before. `docs/12-deployment.md` §2.5.1 has the full write-up.

SQLite lives on a volume at `/app/data` (`DATA_DIR=/app/data`); `k8s/deployment.yaml` adds a PVC + auth Secret, targets container port 3000, and stays at `replicas: 1` with `strategy: Recreate`. **Two probe paths, and the split is load-bearing**: liveness/startup hit `/api/health` (shallow — touches no dependency), readiness hits `/api/health/ready` (checks database + shared layer). They fail in opposite directions — a failed readiness drains the Pod from the Service, a failed liveness *restarts the container*, and restarting fixes nothing about a database outage while killing a process that is still holding unstored Y.Doc content. So liveness must stay shallow; a test pins that `/api/health` never touches the database. `terminationGracePeriodSeconds: 60` plus a `preStop: sleep 5` (k8s removes the endpoint and sends SIGTERM **in parallel**, so without the sleep a dying Pod still accepts new WebSocket handshakes), matched on the app side by `SHUTDOWN_FLUSH_TIMEOUT` (20s) around the flush — an unbounded flush against a black-holed database means SIGKILL at the grace deadline, which loses both the write *and* the clean exit. A PostgreSQL deployment is the **same image** with `DB_PROVIDER=postgresql` + `DATABASE_URL` in the environment (the artifact is provider-agnostic); on the k8s side that drops the PVC and moves `DATABASE_URL` into the Secret. Going past one replica additionally needs `CLUSTER_MODE=redis` + `REDIS_URL` — that's `k8s/variants/deployment.cluster.yaml` (`replicas: 3`, `RollingUpdate`), see the cluster section above. The *image* is mode-agnostic and database-agnostic.
