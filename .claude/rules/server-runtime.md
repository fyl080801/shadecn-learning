# Backend runtime (`packages/server-core` + `apps/server`)

Node + Hono + `@hono/node-server`, run through `tsx` in dev. One process serves the API, the Yjs WebSocket and the frontend.
The core is the package **`@shadecn/server-core`** and knows no module; `apps/server` assembles one product: entries + module list + build/dev scripts + integration tests (`docs/28` §3.1).

## File map

- **`apps/server`** — `index.ts` (production; the server's esbuild entry) and `dev.ts` (`tsx watch`, `pnpm dev` / `dev:cluster`) both import `@shadecn/server-core/env` then `@shadecn/server-core/logger/install`, then `boot({ modules, frontend })`; the only difference is the frontend host (`frontend/static` vs `frontend/dev` = Vite). `modules.ts` is the module list; `db-sync.ts` is the `db:push` entry (`runSchemaSyncCli(modules)`). **`index.ts` must never reference `@shadecn/server-core/frontend/dev`**, statically or dynamically — `build-server.mjs`'s `assertNoDevCode` fails the build if `dev.ts` / `frontend/dev.ts` or the `vite` package appear in the metafile (`docs/28` §3.8).
- **Core never imports a module package, modules never import the core** — they meet only in `apps/server`'s entries. Anything a module needs from the core is a `@shadecn/server-kit` contract (`server-modules.md`).
- `boot.ts` — `prepare(modules)` → `assertClusterConfig()` / `assertRolesSupported()` → `initCluster` + `configureBus({ instanceId })` → `createAdaptorServer` (no `listen` yet) → `assemble()` → `attachUpgrades(server)` → the frontend host (web role only, after all API routes) → `ready` → listen. SIGINT/SIGTERM → `shutdown()` (re-entry guard): modules in reverse setup order, each under its own `shutdownTimeoutMs` (`withDeadline`: log and move on, never hang — k8s SIGKILLs at 60s), then the frontend, `bus().close()`, `closeCluster()`, `disconnectDb()`, `server.close()`. Returns `shutdown` for `dev.ts`'s orphan watch.
  - **Dev orphan watch** (`dev.ts` only): `pnpm dev` is several process layers and only the innermost listens; stopping from an IDE or closing a terminal tab often reaches only the top, leaving the listener holding the port (next `pnpm dev` → `EADDRINUSE`, and they accumulate). It samples `process.ppid` every 2s and runs the normal `shutdown()` when it changes (so the Y.Doc still flushes). The timer is `unref()`'d.
- `server.ts` — `prepare(modules)`: re-validate the whole config file with the full schema (`resolveFullConfig`), parse every module's section, `initDatabase(serverEntities(modules))`, build the route table; once per module graph. `assemble({ app, server })`: select + order + `setup` every module (modules mount their own routes), `onProvide` hooks a module's `auth` service into the platform.
- `platform.ts` — the platform contract's implementation, `configurePlatform` at import: `runtime`, `origins` (SERVER_ORIGIN(S)), `log` (winston), and an `auth` that **forwards to whichever module provides `AUTH_SERVICE`** (`@shadecn/mod-auth`); none = disabled, gates pass.
- `routes-table.ts` — `coreRoutes` (health, features) + `buildServerRouteTable(modules)`; no config import (`dev:cluster` uses it). A new core entry must be declared in `coreRoutes`.
- `env.ts` — side effect: `process.loadEnvFile()` on the repo-root `.env` (real env wins). Imported first by `config-source.ts` and by every entry.
- `runtime.ts` — `isBundle` / `moduleDir` / `appRoot`. `__APP_BUNDLE__` (esbuild `define`) → app root = `process.cwd()`; from source = **three levels above `packages/server-core/src/`** (the repo root).
- `config-source.ts` — the config layer (`docs/28` §3.3): the core schema is resolved at import with `modules` **deferred**; `resolveFullConfig(modules)` validates everything once the list is known (`prepare`). Files from `SERVER_CONFIG` or `server.config.{yaml,yml,json}` + `server.config.<NODE_ENV>.*` in the data dir, merged with `process.env` (env wins). Imports `./env.ts` first, so `.env` (always in the app root) counts as env. `dataDir` is defined here, before the files are read, from `process.env.DATA_DIR` only: it locates the file, so it can never be a schema key.
- `config.ts` — every core config constant, each read through `cfg('<path>')` (`cfg('server.port')`) (paths, `isDev`, port/host, `serverRoles`, `isApiPath()`, DB provider/URL, origins + `isAllowedOrigin()` / `resolveOrigin()`, cluster config + asserts, `llmProviders` — parsed here so a bad `llm.providers` means no listening port). Login settings are `modules.auth` (`@shadecn/mod-auth`'s `config.ts`). `staticDir` defaults to `output/public`, `SERVER_STATIC_DIR` overrides.
- `app.ts` — `Hono<{ Bindings: HttpBindings }>` (frontend middleware needs raw `req`/`res` via `c.env`). Logger + CORS, the role gate, `platform.auth.session`, the login gate (`platform.auth.requireUser` on `/api/*` unless the route table says `access: 'public'`), the page guard (`platform.auth.pageGuard` on non-`/api`), core routes, 404/error handlers. **Module routes are not here** — `assemble()` mounts them, so a test must prepare + assemble before `app.request` (`apps/server/test/setup.ts` does). Hono builds its matcher on the first request: nothing may be mounted after that.
  - `GET /api/features` returns the kernel's feature table (which modules are loaded / why not) — behind the login gate; it says what to *show*, never what is allowed.
  - **`/api/agent-gateway/*` (declared `access: 'public'` by mod-agent) is deliberately outside the login gate**: the agent's sandboxed runner has no cookie, only a run token, and the gateway (`@shadecn/agent/gateway`) authenticates every call itself. Never put it behind `requireUser`, and never let it read the session — a browser cookie must buy nothing there (`agent.md`). The mount passes the raw `Request` through; nothing before it may consume the body.
- `db.ts` — MikroORM singleton, **built by `initDatabase(entities)`** (from `prepare`; `orm()` / `db()` throw before), cached on `globalThis` for `tsx watch` (reused only for the identical entity list), handed to the platform (`configureDatabase`) so modules' `db()` (`@shadecn/server-kit/db`) works; `db()` = `orm().em.fork()`. **Fork once per operation** (or per group sharing a transaction); `allowGlobalContext` is off and there's no RequestContext middleware, so stores work outside requests. `init` connects on first query, so a dead DB doesn't block boot.
- `db/` — `orm.ts`, `schema-sync.ts`, `sync-cli.ts` (`runSchemaSyncCli(modules)`; see `database.md`).
- `logger/`, `frontend/` — below. `tsconfig.json` of each package is a separate TS project (Node types, no DOM); imports use explicit `.ts` extensions.

## Logging (`logger/`) — keep writing `console.*`

- **There is no `logger.info()` in business code; don't add one.** Write `console.warn('[collab] …')` like every existing call site — `console.ts` intercepts `console.*`, parses `[prefix]` into `module`, attaches request context, and hands it to winston (third-party output like ioredis is caught too).
- Four mount points:
  - Each entry imports `@shadecn/server-core/logger/install` **second, right after `@shadecn/server-core/env`** — a side-effect import, because ESM hoisting would run a body call after everything else has logged.
  - `app.ts` uses `httpLogger()` instead of `hono/logger` (also opens the `AsyncLocalStorage` giving every log a `requestId`).
  - `db/orm.ts` passes `loggerFactory: ormLoggerFactory` (`logger/db.ts`). **SQL text only, never parameter values**: `query-params` stays off (so MikroORM hands over `?`-placeholder SQL) and `logQuery` reads only `query` / `took` / `results` / `affected`. The ORM's own `debug` / `slowQueryThreshold` stay unused; `LOG_SLOW_QUERY_MS` is the one threshold.
  - mod-collab adds `collabLogging()` (`packages/mod-collab/src/logging.ts`, structured fields through `ctx.platform.log`) to the extensions. A `priority`-tagged extension brackets the business hooks, so `onStoreDocument` (start) vs `afterStoreDocument` (whole chain succeeded) gives **`started − completed` = failed persists** by observation (REQ-RESILIENCE §4.5).
- Noise rules: per-update / per-frame events are **counted** and summarised once a minute, never printed; `LOG_HTTP` defaults to `api`; **nothing in a hook may throw** (the chain is serial); never call `Y.encodeStateAsUpdate()` just to log a size. The agent runner's per-batch uploads (`/api/agent-gateway/events`) are the same kind of noise — `logger/http.ts`'s `QUIET_API_PATHS` skips them on success; server-side model calls (`/api/agent-gateway/model/*`) are exempt from the slow-request warning (that latency is the upstream model's).
- Config: `LOG_LEVEL` / `LOG_FORMAT` / `LOG_DIR` / `LOG_HTTP` / `LOG_SLOW_MS` / `LOG_SLOW_QUERY_MS`. Silent under `NODE_ENV=test`; tests never import `index.ts`, so interception never touches them.

## Frontend hosting (`frontend/`)

- The frontend host (`frontend/static.ts` / `frontend/dev.ts`) registers a catch-all; `boot.ts` attaches it **after** `assemble()` mounted every module's routes, so they win. It's core, not a module, and only on the web role. It picks `login.html` for `LOGIN_PATH` (`@shadecn/shared/auth`), everything else gets `index.html`.
- **The page guard (`@shadecn/mod-auth`'s `guard.ts`, reached as `platform.auth.pageGuard`) guards "you can't *see* the UI", not "you can't fetch the bytes".** `app.ts` calls it for non-`/api` paths before any module route. An anonymous **document request** (`Sec-Fetch-Mode: navigate` or `Accept: text/html`) for anything but `/login`, `/favicon.ico`, `/vite.svg` → 302 `/login?redirect=<path>`. **Every non-navigation request passes** (`/assets/*`, dev's `/src/**`, `/@vite/*`) because the login page is itself a bundle entry; booting the SPA needs `index.html`, which is already gated. `GET /login` 302s the logged-in away (`safeRedirect`), else `next()`.
- **The login page is the frontend's second Vite entry**: `login.html` + `apps/web/src/login/` in `rollupOptions.input`. It can't be a SPA route (anonymous browsers never get `index.html`). It reads providers from `GET /api/auth/config` and `?redirect=` / `?error=` from `location.search`; `?redirect=` is passed straight to `/api/auth/login` where `safeRedirect` validates it — **don't reimplement the check client-side**. Served by a one-line branch in `frontend/dev.ts` (through `transformIndexHtml`) and `frontend/static.ts`.
- **`login.html` carries the same inline theme script as `index.html`** (reads `app:theme` before first paint); change both together.
- `frontend/dev.ts` (dev only — reachable only from `dev.ts`, never from `index.ts`) — `createServer({ root, appType: 'custom', server: { middlewareMode: true, hmr: { server } } })`; runs Vite's connect chain against `c.env.incoming/outgoing` and returns `RESPONSE_ALREADY_SENT`; on `next()` it renders `index.html` via `transformIndexHtml`. **`hmr.server` keeps HMR on the same port** (otherwise Vite opens 24678).
- `frontend/static.ts` (prod) — `serveStatic({ root: <staticDir relative to cwd> })` + `index.html` fallback.
- `vite.config.ts` is the config of record for both `vite build` and middleware mode; `build.outDir` is `output/public`; no `server.proxy`.

## Build (`scripts/build-server.mjs`) — `output/` is self-contained

- `pnpm build` fills `output/` with `public/` (vite), `server/index.js` (esbuild, ESM/node22), `server/db-sync.js` (`apps/server/db-sync.ts`, a second entry sharing chunks), `server/agent-runner.js` (`packages/agent/src/runner/main.ts`, the sandboxed agent runner the `process` driver spawns — a third entry; its boundary is enforced by the sandbox build, `agent.md`), `server/agents/*.md` (copied from `packages/agent/agents/` — agent definitions, read next to `index.js` via mod-agent's `config.ts` (`paths.definitionsDir`); never bundled, never in the sandbox context), `server/skills/` (text skills: `*.md` copied from `packages/agent/skills/` keeping subdirs — `<name>/SKILL.md` —, skipped if the source dir is missing; read via `paths.textSkillsDir`, same rules as `agents/`), and — copied from `scripts/output-image/` — `Dockerfile`, `.dockerignore`, `README.md`. `npm install --omit=dev && npm run db:push && npm start` runs it anywhere; `docker build ./output` images it.
- `output/agent-sandbox/` is the `oci` sandbox image's build context, **built by `apps/agent-sandbox`, not here** (`pnpm build:sandbox`; `pnpm build` runs both, ownership in `deploy.md`): the runner as one file in `runner/` and a `package.json` with **only its external packages** (pinned like the main one). Never copy `output/server/` or the server's dependency list into it — the sandbox must not carry the DB drivers or hono. It is excluded from the main image by `output/.dockerignore`.
- `scripts/bundle-common.mjs` is what the two esbuild builds share (`externalizePackages`, `nodeBundleOptions`, `externalPackagesOf`, `installedVersion`, `resolveBuildId`). It stays Node-builtins-only so it needs no package of its own.
- **Build id**: `AGENT_BUILD_ID` if set, else generated per build. `pnpm build` (`scripts/build-all.mjs`) fixes one and passes it to both builds, which is what makes "one build, one id" true across two processes; a build run alone gets its own id and the gateway's soft warning fires, as it should.
- The runner is spawned with mod-agent's `runner-command.ts`: from source `node --import <tsx loader> …/runner/main.ts`; from the bundle `node <moduleDir>/agent-runner.js` plus this process's `--import` flags made absolute (so local `pnpm start`'s `local-start.mjs` resolve hook reaches the runner too — its cwd is its own workdir).
- `output/package.json` is generated: `dependencies` = esbuild's external list (metafile) read against `apps/server/package.json`, pinned to installed versions. Both `@mikro-orm/sqlite` and `@mikro-orm/postgresql` are included; `vite` is filtered (`DEV_ONLY`). Scripts: `start`, `db:push`, `db:push:force`. `node_modules` is not shipped (better-sqlite3 is native).
- Relative imports and `@shadecn/*` are inlined (`externalizePackages`, `scripts/bundle-common.mjs`); no `tsx` at runtime.
- **One artifact serves both databases** — the build ignores `DATABASE_PROVIDER`; never reintroduce a per-provider build.
- Two non-negotiables: `splitting: true` (the three entries share chunks) and `define: { __APP_BUNDLE__: true }`. `vite` is kept out of the artifact by `assertNoDevCode` (above), not by a runtime branch — there is no `DEV_ONLY` filter any more.
