# Canvas editor (REQ-CANVAS `docs/13`, REQ-SOLO `docs/16`, REQ-NODEKIT `docs/21`)

Collaboration (sync transport, persistence, presence, close codes) is in `collab.md`.

## Projects, pages, workspace

- A **project** owns canvases and is the permission boundary (`docs/13` §3.2–3.3). `GET /api/projects/:id/invite` writes on read (creates the link, or renews an expired one) — it is not a pure GET.
- Views in `apps/web/src/views/canvas/`: `PersonalFlows.vue` (`/canvas`), `ProjectHome.vue` (`/projects/:projectId`), `InviteAccept.vue` (`/invite/:token`), `FlowEditor.vue` (`/flows/:flowId`, the one `BlankLayout` route).
- The first two share `components/canvas/CanvasWorkspace.vue` (layout: `docs/16` §4.8); its delete confirm uses two refs (`testing.md`). The app sidebar's multi-path highlight goes through `NavItem.activePaths`, not a route-name check.
- The project list is a **module-level cache**, `composables/useProjectNav.ts` (`projects / loading / error / refresh()`, `resetProjectNav()` for tests), because the shell remounts on every route switch; create / delete / rename call `refresh()`.

## Editor structure

- **Hooks layer + component layer; the view only builds the context and places components.** `provideFlowEditor(props)` (`composables/flow/`) creates the context once; children call `useFlowEditor()` — no prop drilling, a new panel touches no existing file. The context bundles `store` + `sync` (`useFlowSync`) + `useFlowDocument` (load / rename / duplicate / delete / save-state text / `flushBeforeLeave`), `useFlowCanvas` (Vue Flow glue: bindings, drag→`node.move`, connect→`edge.add`, viewport sync, cursor-anchored ctrl-wheel zoom, `addNode`), `useFlowSelection` (`selectedNodeId` + `select` / `clearSelection`). `useFlowShortcuts(ctx)` adds keybindings and the two don't-lose-work guards.
- `useVueFlow()` is called inside `useFlowCanvas` at the *root* setup, so `<VueFlow>` adopts that instance and out-of-canvas components (toolbar, capsule) can use `screenToFlowCoordinate`.
- Components in `components/flow/` each own one region and read the context directly (inventory and placement: `docs/13` §4.4.1–4.4.2).
  - Programmatic zoom emits no `move-end`: `canvas.zoomInView` / `zoomOutView` / `zoomToLevel` / `fitAll` call `syncViewport()` after the transition.
  - `canvas.autoLayout()` calls shared's pure `planAutoLayout` (`@shadecn/shared/flow-layout`, dagre — the agent's `ops.autoLayout` runs the same function with estimated sizes) with Vue Flow's measured `dimensions`, over top-level nodes only (a group is one box; edges into its children count as the group's) and commits with **one** `moveNodes` — one undo item. `groupSelection`'s padding is shared's `groupFrameAround` for the same reason.
  - `agent/FlowAgentChat.vue` and `agent/FlowAgentQuickPrompt.vue` share one `useFlowAgent` via `composables/flow/agent-panel.ts` (`provideFlowAgentPanel(editor)` in `FlowEditor.vue`) — two calls mean two streams. The director overlay reuses both components by calling `provideFlowAgentPanel(editor, { nodeId, adoptLatest: false, copy, selection })` once more in `FlowDirectorWorkspace.vue`, shadowing the canvas panel for its subtree only (`docs/07` §7.5) — never pass an agent in as a prop. A panel's `selection` is what new-conversation auto-mentions read (`docs/20` §3.10.9): the canvas passes `canvas.selectedNodeIds`, which `useFlowCanvas` keeps **in selection order** with a sync watch (Vue Flow's `getSelectedNodes` is canvas order; a lazy computed would skip unread changes) — don't swap it back to a plain map of `getSelectedNodes`. **The run list has no polling**: it is one `GET` on open + one per reconnect (`sync.connected` rising edge), then only `sync.onStateless('agent:runs', …)` pushes (full list, replace; a `GET` that was in flight during a push must not overwrite it). `mine` is computed client-side (`withMine`), and only the *current* conversation being in the list blocks sending — switching away only detaches the local stream, never aborts. An entry is dropped locally at its `expiresAt`, **converted with the payload's server clock `now`** (`expiresAt - now` added to the receive time — never compared against the local clock directly). Node occupancy tags (`NodePresence.vue`) and the director's "正在编辑这个场景" read only `AgentRunEntry.occupies` — never the entry-point `nodeId`.
  - **Upload state has one home: `composables/useAssetUpload.ts`** (`startUpload` handle: status / progress — `null` for a one-shot upload, % only for multipart / cancel; `useAssetUploadList` for attachments). `node-upload.ts`'s module-level registry and the agent composer's attachment list both build on it — never a second state machine. Any code that puts a file into a node (body button, the pane context menu's upload in `file-nodes.ts`, the composer's input-preview plus in `composer/ComposerInputs.vue`) enters through `node-upload.ts`'s component-free `runNodeUpload(flowId, nodeId, task)` + the shared `uploadImageToNode` / `uploadVideoToNode` tasks — create the node first, then start the upload, so the body picks the progress up from the registry. The list clears itself on `flowId` change: an asset belongs to the canvas it was uploaded to and the server refuses it as another canvas's attachment.
  - `FlowSelectionToolbar.vue` is a `NodeToolbar` with an id array; `FlowGrowMenu.vue` is mounted once, in `FlowEditor.vue`.
- `apps/web/src/lib/api.ts` wraps every endpoint over `apiFetch` and throws `ApiError` (carries `status`).

## Node types — `components/flow/node-types.ts`

- A registry: `defineNodeType(type, {label, icon, view, features?, parts?, modes?})`. The render half is `view` (`body` component, `shell: 'card' | 'frame'`, size `class`, `selectedClass` / `idleClass`, `style(ctx)`, `fallbackLabel`) and `features` *by name* (default `STANDARD_NODE_FEATURES` = rename / duplicate / delete / connectable / status). The data half — default `data`, default layout, **port declarations** (`inputs` / `outputs: PortDef[]`) — lives in `@shadecn/shared/flow-node-types`, shared with the agent.
- **No per-type component**: `flowNodeComponents` maps every type to `node-kit/NodeHost.vue`. `useFlowCanvas.addNode(type)` builds from the registry (`buildFlowNode`). **Adding a type = this file + the shared entry**, nothing else.
- **The creatable set is shared's `CREATABLE_NODE_TYPES`** (which types, and what each renders: `docs/13` §3.7). The toolbar menu (`ADDABLE_NODE_TYPES`), the grow menu and the agent's `add_node` all read it — never a local list. Per-type composers go through `definePromptComposerPart` (`composer/composer-part.ts`). `edit-prompt` is a **feature** (`composer/prompt.ts`), not a per-type mode — mode ids are global in the registry, so several types can't each register it.
- "Has content" is asked only through shared's `hasNodeResource(type, data)` — never by reading `data` fields directly (fields: `docs/13` §3.7). It means "has material" only: it decides neither the image/video composer nor connectability.
- **Image/video form (`generate` / `asset`) is stored in `data.form`, never derived from `src`**, and read only through shared's `nodeFormOf(type, data)` (missing ⇒ `generate`; old data is never migrated or inferred). It changes only inside `flow-ops`, in the same transaction as its cause: `attachAsset` (upload; `asset` iff no incoming edge) and `insertEdge` (an edge into an `asset` node flips it back). An upload therefore goes through `store.attachAsset` / `useFlowNode().attachAsset`, **never `setData({ src })`** — that would bypass the form rule. Known concurrent-upload race: `docs/13` §3.7.
- `NEW_NODE_TYPE` is only `addNode()`'s default. `FALLBACK_NODE_TYPE` is what an unknown `type` renders as — the **same constant** `fromYNode` falls back to, defined in `@shadecn/shared/flow-graph` and re-exported from `node-constants.ts`, so old canvases can't change shape.
- **Ports are declared, never rendered as extra handles** — at most one unnamed handle per side. Whether a side shows is `hasSide(type, side, data)`: form-aware (an `asset` image/video has no left handle) and the predicate under shared's `interactionGate`; never decide it from `type` alone (rules: `docs/13` §3.7). Never prune existing edges when a side closes — the read side doesn't write.
- **Direction is enforced with Vue Flow's own switches** — left handle `:connectable-start="false"`, right `:connectable-end="false"` — not with event handlers or CSS alone (behaviour: `docs/13` §3.7). The grow menu (`canvas.openGrowMenu` → `FlowGrowMenu.vue`) is a `DropdownMenuContent :reference` anchored at the handle element / a virtual element at the drop point — no trigger, no hand-rolled coordinates — and lists only shared's `connectableNodeTypes(sourceId, ctx)`. `growFromMenu` → `addConnectedNode(source, type, at)` puts node + edge in one transaction (`store.addConnectedNode` → `ops.createConnectedNode`) and merges the post-measure move into the same undo item. A drop on a node's **body** goes through the same `connectNodes` path as `onConnect` (`dropTargetAt` reads the node root's `data-id` under the pointer).
- **`group` — every difference is in its declaration, none in the host** (the one outside exception: `FlowPaneContextMenu` lets a right-click on a group frame's blank area through, so "添加" there creates into the group): `shell: 'frame'`, fixed size, `zIndex: -1`, `pointer-events-none` in `view.class` (so it doesn't swallow rubber-band selection), background from `data.background` via `view.style`, features `rename` / `status` / `ungroup` / `resizable` / `drag-strip` (no `connectable` / `duplicate` / `delete`).
  - Resizing is the `resizable` feature (`NodeResizerPart.vue`, any type that enables it; constraints from `view.resize`). Its stylesheet is imported in `styles/vue-flow.css`, which must also give `.vue-flow__resize-control` its `pointer-events` back (it inherits `none` from the body otherwise). Commit to the doc only on `resize-end`.
  - **`NodeResizeControl` needs an explicit `:node-id`** — unlike `NodeResizer` it doesn't inject it, and without one it never attaches its drag (handle visible, nothing happens).
  - **After committing, set the Vue Flow node's `style` width/height back to `undefined`** — the resizer writes them into `node.style`, which outranks `node.width`, so undo / a peer's resize would never reach the screen. Not `{}`: Vue Flow's style computed writes `node.width` *into* an existing style object, refilling it.
  - `NodeToolbar` teleports, so pressing the label never reaches d3-drag: the group keeps a full-width 24px **`drag-strip`** inside its top edge (invisible until hover; a rubber band can't start there).
  - Removing a group **detaches its children** (`ops.removeElements` clears `parentNode` / `extent` and converts positions back to canvas coordinates — a dangling `parentNode` snaps the whole group to the origin).

## Node-kit — `components/flow/node-kit/` (`docs/21`)

- Node UI is flat registrations: **parts** (component in a slot), **actions** (icon + label + `run` + `when`/`enabled` + optional `shortcut`), **modes** (edit states that `reveal` / `conceal` slots), **event handlers** — bundled into **features** (`node-kit/features/`) that a type enables by name.
- **Slots are a closed set owned by the host** (`label` `label-end` `toolbar` `badge` `header` `body` `footer` `composer` `side` `overlay` `handles`). Placement and when a slot may show is `NodeHost`'s call; a part's `when` can only narrow it. Matching is static per type (`match: {types, features, not}`), so `kit.partsFor(type, slot)` is cached; `replaces` / `hides` name what they displace — no implicit priority. **A slot with nothing registered doesn't exist on that node** (no `NodeToolbar` mounted).
- Rules that are bugs to break:
  - **Features never import each other**; they cooperate through events and the shared context (composer emits `composer:submit`, `runnable` turns it into `node:run`).
  - **`protocol.ts` is a type-only leaf; only `install.ts` lists features** (it imports node components, so nothing a node imports may import it — same cycle rule as `editor-context.ts`).
  - **The host knows no concrete type or feature** (no `if (type === 'group')`, no `has('runnable')`).
  - Parts take **no props** — they call `useNodePart()` (`id` / `type` / `node` = `useFlowNode` / `label` / `editor` / `selected` / `mode` / `slots` / `emit`), because half are teleported.
- Events: a typed editor-level bus (`FlowNodeEventMap`, extended by module augmentation in each feature's file). Synchronous broadcast, each handler try/catch'd, depth-capped; **never a write channel** — handlers write via `ctx.node.write` / `store.mutate`.
- **Edit mode is one editor-level value** (`node-kit/modes.ts`; rule: `docs/21` §4.6). Entering a mode or selecting another node preempts; `'preempted'` commits the draft (like blur), only `'cancel'` (Esc) drops it. A part whose overlay unmounts mid-edit must commit on unmount.
- Actions run through one runner (`node-kit/actions.ts`, `useAsyncAction` keyed by node × action, emitting `action:invoke` / `action:done`) for buttons and keyboard alike. `useFlowShortcuts` handles global keys first, then the **single-selected** node's visible actions (`Mod` = Meta or Ctrl, exact modifier match; a disabled match is swallowed).
- Presence avatars are built into the host, not a feature (`docs/21` §10.4).
- The registry is not a singleton: `createNodeKit()` / `createNodeKitRuntime()` for tests; `apps/web/src/test/components/node-kit/with-kit.ts` provides the default kit for mounting `NodeHost`.

## Selection, groups, snapping

- **Box selection is written out as `:selection-mode="SelectionMode.Full"`** (rule: `docs/13` §4.4). Edges touching a hit node must count as selected, but Vue Flow's own pass is unreliable (its edge-id cache isn't cleared by `removeSelectedElements()`, so a second identical box selection misses the edge). `useFlowCanvas` re-asserts it with `getConnectedEdges` → `addSelectedElements([...nodes, ...edges])`, **only while the band is active** (outside it, clicking an edge would get deselected). Selected-edge styling is in `styles/vue-flow.css`.
- Per-node chrome and the selection toolbar both gate on `canvas.boxSelecting` (`userSelectionActive`) — one flag, not two.
- Grouping enters only through `canvas.groupSelection()` (eligibility and box: `docs/13` §4.4). Membership afterwards changes only through `ops.settleLayout` (drag in / out, `docs/13` §4.4 "拖动决定归属") or by creating into a group (`layout.parentNode` on the new record — `addNode` / `addConnectedNode` pick the group under the drop point with `groupAt`).
  - **Group + children in one transaction** (`ops.groupNodes`, `extent: 'parent'` included) — split it and children briefly point at a missing parent (`NODE_MISSING_PARENT`, nodes jump to origin, undo leaves half a group).
  - **Membership and frame-fitting are `ops.settleLayout`'s job, never the editor's** (geometry: shared `flow-layout`'s `groupUnderNode` / `fitGroupFrame`). `moveNodes` / `resizeNode` / `createNode` all go through it, so join / leave, growing the frame and shifting siblings land in the same transaction as the move — never a second write after it (that would be two undo items and a moment where a peer sees a dangling child). User drags pass `{ sizeOf: measuredSizeOf, reparent: true }`; programmatic placement (centering, auto layout) passes no `reparent`. The agent runs the same op with `nodeSizeOf`.
  - **`extent: 'parent'` stays in the doc but is never handed to Vue Flow** — the `nodes` adapter sends `extent: undefined` for every node that has one (explicitly — an omitted key keeps its old value via `Object.assign`). Handing it over clamps children so they can neither leave nor grow the frame, and Vue Flow computes the clamp from the parent's `dimensions`, which are 0 until measured (children land outside the box, worst on peers who read `extent` before the group renders). Don't use Vue Flow's `expandParent` either: it writes the parent's `style` (outranks `width`) and doesn't compensate siblings when growing left / up.
- **Snapping (`useFlowSnapping` + pure `lib/flow-snap.ts`; behaviour: `docs/13` §4.4.3) applies to dragging only, never to placed nodes.** Grid is `FLOW_GRID_SIZE`, the same constant as `<Background :gap>`; guide tolerance is in **screen** px, divided by zoom.
  - **Vue Flow's `:snap-to-grid` is deliberately unused**: it also rounds positions at mount, a view-only shift that makes peers see different canvases.
  - One delta from both snaps (`lib/flow-snap.ts`). The correction runs in `onNodeDrag` after Vue Flow writes the raw position and recomputes from the pointer each event (so it never accumulates). **Snap first, then `publishDrag`.** Guides render in the `#zoom-pane` slot next to presence cursors.
- **Canvas UI drawn at screen size (behaviour: `docs/13` §3.7) goes through one conversion, `components/flow/flow-screen.ts`**: `FlowCanvas.vue` writes `--flow-zoom-inv` / `--flow-px` on the canvas root; CSS uses `calc(N * var(--flow-px))` or `transform: scale(var(--flow-zoom-inv))` (`.flow-node*`, `.flow-screen-fixed` in `styles/vue-flow.css`), TS geometry uses `screenToCanvas`. A new element declares the trait (table in `flow-screen.ts`'s header — e.g. a part in the `badge` slot gets it from the host for free) instead of doing the math. Never a second per-component `1 / zoom`, and:
  - **No `transition` on anything that carries these values** — they change every zoom frame (the handle splits hover `scale` (transitioned) from the zoom `transform` (not)).
  - **A card's border is an outer `box-shadow` ring, not `border`**: browsers round a sub-1px `border-width` up to 1px *before* the zoom transform, so it thickens when zoomed in. Only the group's dashed frame keeps a real border.
  - Change box sizes never — only transform / shadow / stroke — so Vue Flow's measured node and handle bounds stay valid. Edge endpoints compensate with `flowHandleShift`.
- **Canvas behaviour is Vue Flow's job, not CSS's.** Anything on the canvas — external labels, per-node toolbars, resize handles, zoom-following overlays — uses the official packages (`@vue-flow/node-toolbar`, `@vue-flow/node-resizer`, `<Panel>`, `<Handle>`, `<NodeToolbar>`; see [guide](https://vueflow.dev/guide/) / [examples](https://vueflow.dev/examples/)). Placement comes from component props (`position` / `align` / `offset`); Tailwind is for appearance only. Never hand-roll `absolute` + `transform` / viewport math. Missing package → add it as a `devDependency`. Reference case: `NodeHost.vue`'s label is `<NodeToolbar :is-visible="true" :position="Position.Top" align="start">`.

## State — `stores/flow/` is a projection of a Y.Doc

- The canvas content **is** the Yjs doc (shape in `@shadecn/shared/flow-doc`, shared by browser and server). The frontend's incremental projection (`changedTopLevelKeys` / `projectMap` / `createNodeProjector` / `readFallbackViewport`) is `lib/flow-projection.ts`; server-side `apps/server/collab/flow-doc.ts` keeps only `readGraphFromDoc` and `pruneDanglingEdges`.
- `nodes` / `edges` are `Y.Map<id, Y.Map>` because Y.Map merges **per key** — a node as one JSON blob would let the later write clobber the earlier wholesale.
- **Node = five groups (schema v3): `type` / `layout` / `metadata` / `data` / `runtime`, plus derived, never-stored `inputs`** (`docs/13` §3.7).
  - `layout` (position, size, zIndex, parentNode, extent, handle positions) is **flat on the node's top level** (drag hot path, Vue Flow's shape). `metadata` (label, description, icon, createdAt, createdBy, ui), `data`, `runtime` (status, error, taskId, `outputs.<portId>` flat keys) are nested `Y.Map`s.
  - **Business fields sit flat on `data`, never in a `config` object; `data` has no reserved keys** (a single `config` key would let two people's edits to different fields clobber each other).
  - A node's business type **is** its top-level `type` = the registry key.
- **Edges are the only source of truth for wiring; ports live on `edge.data`, not on handles.** At most one unnamed handle per side; `sourceHandle` / `targetHandle` are always `null`; `edge.data.sourcePort` / `targetPort` / `index` say which pair is wired (multi-input `index` = max + 1 on connect, never renumbered; port-less edges carry none). The pair is chosen only by shared's `resolveConnection` (algorithm: `docs/13` §3.7). **Two gates, not mutually exclusive**: `resolveConnection` (logic gate) only matches ports — it never rejects for resource or form, so the agent and `flow-ops` can connect into an `asset` node; a human drag must first pass `interactionGate` (target's form). `useFlowCanvas`'s `resolve` (`is-valid-connection`), `connectNodes` (incl. a drop on a node body) and `connectableNodeTypes` (grow menu) check the interaction gate first; every actual edge is created by `ops.connect` / `ops.createConnectedNode` on the doc (`docConnectionContext`). The context **requires `dataOf`** so no caller can skip the form. Both matrices (logic, interaction) are pinned in `packages/shared/test/flow-node-types.test.ts`.
- **Writes go by group: `store.writeNode(id, 'metadata' | 'data' | 'runtime', {set, remove})`** (via `useFlowNode(id)`) → `ops.writeNodeFields`; layout has its own write paths.
- **Collections (3D objects, timeline tracks, resource lists) go one element per key — `<prefix>.<id>`, flat, plain JSON** (`@shadecn/shared/flow-collection`; write + delete in one `writeNode(id, 'data', {set, remove})`). Never one `data.scene` blob (everyone in the batch clobbers each other) and never a nested `Y.Map` (structure in the CRDT can't be versioned: old and new clients write *different types* to the same key, clientID picks a random winner, the loser's subtree vanishes and its code throws). Shared has two write doors — `toYNode`/`toYEdge` (editor-created elements) and `writeNode`/`writeEdge`/`applyGraphToDoc` (server legacy migration); `toYEdge` writes `null` for an absent handle, `writeEdge` writes nothing, and a test pins that they read back identically. Rules:
  - **A key's type is fixed from its first write and never changes.** A brand-new `Y.Text` key is fine; upgrading an existing plain key destroys data.
  - **Ids are stable, never array indices** — mint with `createId()` if the source has none.
  - **Prefixes must not nest** (`dc.obj` + `dc.obj.pose` collide; convention only).
  - Same-element concurrent edits are left open (`docs/04` §4.0.1). If you narrow them, use soft warnings or commit-time conflict checks, never read-only locks.
- **v1/v2 data is never migrated, but reading it must never throw.** The Y.Doc reader and `parseGraph` both go through shared's `nodeRecordFromParts`, which only falls back (missing `metadata`/`runtime` → empty label / `idle`; old `label`/`status`/`kind`/`config` stay in `data`; no valid `position` → skipped). **`parseGraph` must keep accepting v1/v2 rows** (layout fields flat on the node) — `readGraph()` is the only path old canvases take into Yjs.
- **Never write back from the read side** — a projection that writes creates a transaction that enters everyone's undo stack and broadcasts.
- **The projection is incremental**: `observeDeep` events name changed top-level keys; only those re-parse, the rest keep object identity (Vue Flow relies on it). `changedTopLevelKeys` returning `null` = redo everything. `createNodeProjector` gives a node a new object only if its record, its incoming-edge bucket (by edge identity), or an upstream's `runtime.outputs` (by value) changed. `toVueFlowNode` is WeakMap-cached, flattens layout writing every key explicitly, and puts the other four groups in Vue Flow's `data`.
- **Every content change goes through `store.mutate()`** (a Y transaction tagged `LOCAL_ORIGIN`). Components never touch a Y.Map directly. Undo is `Y.UndoManager` with `trackedOrigins: [LOCAL_ORIGIN]` — that is what makes Ctrl+Z skip collaborators' edits; `separateUndo()` (`stopCapturing`) splits operations inside the 400ms capture window.
- **The director (`docs/07` §7.6) writes through `store.mutateDirector()` (`DIRECTOR_ORIGIN`), never `mutate()`**: the canvas `UndoManager` must not track it, and the director's own stack (`store.createNodeHistory(nodeId)`, scope = that node's Y.Map, tracks only `DIRECTOR_ORIGIN`) is created on open and destroyed on close (`composables/flow/useDirectorNode.ts`). The 3D scene is a projection (`components/director/directorProjection.ts`): reconcile by object id on non-transform fields, then every transform comes from shared's `objectStateAt` — never `AnimationMixer`, never a doc write during playback; a gizmo drag commits once on `mouseUp` (`directorGizmoCommit.ts`). `store.onNodeDataChange` is feedback-only (remote highlight), not a data channel.
- **Taking a node out of the canvas to edit it is one of two hosts, never a hand-rolled `Teleport`** (`docs/21` §4.10): full-screen takeover = `FlowDirectorOverlay.vue` (director only); backdrop popup = `components/flow/popup/FlowNodePopupHost.vue` + an entry in `popup/popups.ts` (`defineNodePopup`) + a `popupOpenPart` on the type. The node only emits the open event. Close = unmount the content component, which commits its draft on unmount (and skips the commit if the node is gone) — no separate close hook.
- **An overlay that owns the keyboard calls `suspendCanvasShortcuts()`** (`composables/flow/shortcut-layer.ts`; `useFlowShortcuts` checks it) — never `stopPropagation` on window capture (the overlay's own inputs stop receiving keydown) or on document (reka-ui's `onKeyStroke` Esc on window breaks).
- **Canvas rules live in `@shadecn/shared/flow-ops`, not in the store.** Each store write method is `mutate(ctx => ops.x(ctx, …))`; an op runs inside the caller's transaction, never calls `transact`, validates before its first write and throws `FlowOpError` (nothing written). The store swallows it where it always silently no-op'd (missing target); `connect` / `addConnectedNode` / `addUpstreamNode` rethrow so `useFlowCanvas` can toast the reason. UI concerns (`separateUndo`, selection, `nextTick`, toasts) stay in `useFlowCanvas`; DOM-measured inputs (group rect, rendered size) are op arguments.
- **No save, revision, 409 or dirty state** — edits are live. The one exception is a *notice*: when the server's write queue fails it broadcasts a stateless message (server rules in `collab.md`; wording `docs/16` §4.6). Client side: **clear `saveFailed` when the transport is replaced**, and **parse stateless payloads defensively** (a throw kills the message loop).
- **Drag intermediates stay out of the doc**; only `onNodeDragStop` commits; in-flight motion rides awareness.
- **Never rebuild the `:nodes` array while the local user drags.** Vue Flow re-syncs on a new array reference via `Object.assign(existing, incoming)`, and `incoming.position` is the pre-drag one, so the node snaps back. `useFlowCanvas` keeps a `localDragging` flag and returns the `computed`'s `previous` array while set. Mapping is only safe when a *remote* peer drags.

## Per-user view state (viewport)

- **Pan/zoom is not canvas data**: `setViewport()` → `setUserState(key, value)`, never the doc, never undo. `meta.viewport` in the doc is only the first-open fallback; each viewer has their own row.
- **`setUserState` only buffers.** `noteLocalEdit()` (called by `mutate` / `undo` / `redo`) flushes to `PATCH /api/flows/:id/user-state` as **leading send + debounced tail** (`useDebounceFn`, `USER_STATE_FLUSH_DELAY`, `maxWait` `USER_STATE_FLUSH_MAX_WAIT` 10s). The tail skips itself if nothing happened after the leading send. Viewing only = zero requests.
- **The window always sends, even if the view never moved** — that PATCH is the session heartbeat (content rides the WebSocket, and collab revalidation never renews the session). Editing keeps the session alive; looking lets it idle out (`docs/13` §3.5.1). Pan-without-edit is flushed by `saveNow()` / `reset()` on leave.
- To persist another per-user thing: add a field to `FlowUserState` (`@shadecn/shared/flow-graph`), a parser to the server's `FLOW_USER_STATE_PARSERS` (a mapped type, so a missing parser is a compile error), and call `setUserState`.

## Continuously-changing values (`docs/13` §3.7.2)

- One shape: **a local draft owns the screen, the draft is throttled onto awareness if peers should see it, the doc is written once when the gesture ends, bracketed by `separateUndo()`.** One undo item comes from committing once, not from `captureTimeout`.
- **No-release kind (rename, body text) = `useDraftField`** (`composables/flow/useDraftField.ts`): `{current, commit, normalize?, equals?, focus?}` → `{editing, draft, start, commit, cancel}`. It owns the draft, `editing`, both `separateUndo()` calls, and drops no-ops (unchanged value, `normalize` → `null`, the double submit from Enter + blur). Consumers: `TextBody.vue`, `node-kit/features/RenameTitle.vue`, `composer/PromptComposer.vue`, via `useFlowNode(id).draft(group, key, …)`.
- **With-release kind** is hand-written — copy `onNodeDragStart/Drag/DragStop` in `useFlowCanvas.ts`. Awareness publishing isn't in the composable (needs a new field; add `watch(draft, useThrottleFn(publish, throttleMs))` when there's a consumer).
- **Don't throttle doc writes instead** — the cost is broadcast + persistence, a half-dragged value mustn't survive refresh or be undoable, and the doc is the wrong channel for droppable data.
- Awareness rules: a *new* field, not `transform` (typed `PresencePoint`); send only changed numbers, never the whole element (shrink the packet before lowering the frame rate); clear it when the gesture ends (y-protocols replays local state every 15s); keep **both** throttle edges (`useThrottleFn(fn, ms, trailing, leading)` — dropping the last packet is a bug).
- The window is adaptive: `ms` is a getter, `feedbackThrottle(roomSize)` in `lib/presence.ts` — `FEEDBACK_THROTTLE` (60ms, one window/buffer for every feedback field via `useFlowPresence`'s `publish()`) up to `FEEDBACK_THROTTLE_ROOM` people, then widening stepwise to `FEEDBACK_THROTTLE_MAX`. The curve is a judgement, not a measurement.
- Text: short/atomic commits on blur; long-form wants a debounced commit (>400ms debounce = finer undo). Character-level co-editing needs `Y.Text` as a brand-new key **and** a fix to `ops.duplicateNode` (its `fromYNode` → deep clone → `toYNode` path flattens `Y.Text` to a string).
- While dragging locally, a panel reads its own draft, never the projection.

## Personal canvases (REQ-SOLO)

- A personal space is a `Project` with `kind='personal'` and a unique `personalOwner` (created on read by `GET /api/projects/personal`); its canvases have `mode: 'solo'`, **derived from the project, never stored on `Flow`**. Content, doc, projection and **transport are identical** — `composables/flow/sync/` has exactly one transport, `collab.ts`. (`GET/POST /api/flows/:id/doc` and `flow-writer.ts`'s `applyFlowUpdate()` remain server-side with no frontend caller.)
- **`mode` only decides presentation**: where leaving lands, terminal-dialog / status-line wording (`docs/16` §4.6) and whether presence runs (`useFlowPresence(sync, mode)`). Never branch content, doc or transport on it.
- **The doc and its IndexedDB cache are created immediately; the transport waits for metadata** (`context.ts` computes `mode` only when `store.meta.id === flowId`), or an unopenable canvas reports its failure twice.
- Server side the room is owner-only and presence-free (see `collab.md`). The client must still *send* awareness: reset local state to `{}`, **never `null`** — the 15s replay is the only client→server heartbeat.
- All collab rules apply, including one-window-per-user (`collab.md`).
- Every project-level mutation must refuse a personal space with **403** (list: `docs/16` §4.5) — a new project route needs the same check.
- Both canvas lists are the same `FlowList` (it only needs a `projectId`); each page owns its URL query (`syncQuery`) (`docs/16` §4.8).
- **Wherever the UI leaves a canvas, key the destination on `mode`, never `projectId`** — `useFlowDocument`'s `backPath()` sends solo (and collab without a `projectId`) to `/canvas`; icon/label follow the same check. `ProjectHome.vue` `replace`s to `/canvas` for `kind === 'personal'`.

## Types

Graph types, `GRAPH_SCHEMA_VERSION`, `nodeRecordFromParts` and `inputs` derivation are in `@shadecn/shared/flow-graph`; ports and `resolveConnection` in `@shadecn/shared/flow-node-types`; project/canvas API shapes in `@shadecn/shared/canvas`. `apps/server/store/flow-types.ts` keeps only server-only code (it uses `Buffer`): `parseGraph` / `parseTransactions` / `parseUserStatePatch`, `GRAPH_LIMITS`, Op types. `metadata.createdAt` is validated with `isTimestamp` everywhere.
