# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Language

**Always reply in Chinese (中文).** All user-facing output — answers, explanations, plans, summaries, questions — is written in Chinese. Keep technical terms in their original English form (Vite, MikroORM, OIDC, Hono, …) rather than translating them.

Code identifiers, types, and commit messages stay English. **Source comments in `apps/server/`, `apps/web/src/` and `packages/shared/`, log/error messages shown to a developer or user, and test names are written in Chinese**, matching every existing file. Documentation under `docs/` is Chinese too.

## Project Overview

A Vue 3 learning/experimentation sandbox that combines shadcn-vue UI components, Three.js 3D scenes, and canvas-based mini-games. It serves as a playground for exploring different Vue and web technologies within a single app.

Requirements live in `docs/`, one file per requirement — see `docs/README.md` for the index. This file describes *how the code is built*; `docs/` describes *what it is supposed to do*.

## Monorepo layout

A pnpm workspace (`pnpm-workspace.yaml`) with four packages. The root `package.json` keeps **every command name unchanged** — each one is a `pnpm --filter <pkg>` delegation (`pnpm dev` → `@shadecn/server`, `pnpm build:client` → `@shadecn/web`, …) — so nothing you type changed when the repo was split.

- **`apps/web` (`@shadecn/web`)** — the frontend. `src/` (the `@/` alias target), `vite.config.ts`, `index.html`, `login.html`, `components.json`, `public/`. Its `package.json` has `devDependencies` only: it is bundled into `output/public`, nothing of it is installed at runtime.
- **`apps/server` (`@shadecn/server`)** — the backend, laid out flat: what used to be `server/*` is now `apps/server/*`. The data layer lives in it too — `db.ts` (the MikroORM singleton) and `db/` (entities, ORM factory, schema sync + its CLI) — next to `scripts/` (`build-server.mjs`, `dev-cluster.mjs`, `local-start*.mjs`, `output-image/`). Its `dependencies` is the production runtime set (see the dependency section).
- **`packages/shared` (`@shadecn/shared`)** — source-only TypeScript (no build step, no publish) that both sides import: sub-paths `flow-graph` (graph types, schema version, v1 upgrade, `FlowUserState`), `flow-doc` (the Y.Doc shape and its read/write), `canvas` (project / canvas API shapes), `auth` (identity views, login-done constants), `collab` (close codes, room/path constants). It exists so "two TS projects, so change one and change the other" stops being a rule anyone has to remember.
- **`packages/agent` (`@shadecn/agent`)** — the canvas agent (REQ-AGENT, `docs/20-agent-canvas.md`), source-only, **server-only** (its `tsconfig.json` is the server's). Peer-depends on `@mariozechner/pi-agent-core`, `@mariozechner/pi-ai` and `yjs`, which `apps/server` keeps in `dependencies`; the frontend never imports it (its contract is `@shadecn/shared/agent`). Sub-paths and their rules: `.claude/rules/agent.md`.
- **What stays at the root:** `docs/`, `k8s/`, `ci/`, `.gitea/`, `Dockerfile`, `.env`, `data/`, `output/`, `eslint.config.ts`, and a `vitest.config.ts` that is *only* a `projects` aggregator (each package owns its own config, project names `server` / `client` / `shared` / `agent`). The root `devDependencies` hold only repo-wide tooling: the eslint family, `typescript`, `vitest`, the coverage plugin, `jsdom`.
- **Two base directories, not one.** `rootDir` / `appRoot` (`apps/server/config.ts`, `runtime.ts`) is the **repo root** and is where `.env`, `data/` and `output/` live; `webRoot` (`config.ts`, the Vite root in dev) and `serverDir` (the build/test scripts) are each package's own directory. Running from source, `runtime.ts` derives the app root as `apps/server/`'s **parent's parent** (two levels up, not one); in the bundle it is still `process.cwd()`. Mixing the two bases is the typical way to read the wrong `.env` or put the database in `apps/server/data`.

Invariants that came out of the split — each is a bug if you undo it:

- **`tsx watch` must carry `--exclude '../web/node_modules/.vite-temp/**'`, in `dev` and in `dev-cluster` alike.** Vite bundles `vite.config.ts` into a temp file under `apps/web/node_modules/.vite-temp/` and deletes it again; tsx's default ignore rule for `node_modules` is relative to *its* cwd (`apps/server`) and never covers `../web`, so every middleware-mode `createServer` triggers a restart, which creates a new Vite, which writes a new temp file — an endless restart loop (measured: 50 restarts in 26 seconds).
- **The schema-sync CLI (`apps/server/db/sync-cli.ts`) goes through `apps/server/env.ts` + `config.ts`, never its own `.env` read.** `pnpm db:push` runs with `apps/server` as cwd, and a bare `process.loadEnvFile()` reads `./.env` — it would quietly find nothing and fall through to the default SQLite file while the server talks to a different database. `env.ts` loads the repo-root `.env` explicitly; keep it that way (this was `prisma.config.ts`'s invariant before the switch to MikroORM).
- **Local `pnpm start` goes through `node --import ./apps/server/scripts/local-start.mjs`.** The bundle is ESM and resolves bare imports by walking up from the *artifact's* location (`output/server` → `output` → repo root), but the runtime dependencies are declared only in `apps/server` — the root `node_modules` has none of them, so a plain `node output/server/index.js` dies with `ERR_MODULE_NOT_FOUND`. The registered hook only catches "bare package name not found" and resolves it once more starting from `apps/server/package.json`, so the dependency list still has exactly one source. In a container the artifact has its own `node_modules` beside it and the hook is never reached.
- **The root `Dockerfile`'s build stage copies each package's `package.json` one by one, then runs `pnpm install --frozen-lockfile`, then `COPY . .`.** That ordering is what keeps the install layer cacheable; the cost is that **a new workspace package needs one more `COPY …/package.json` line**. And `.dockerignore` must say `**/node_modules`, not `node_modules`: each package's `node_modules` is a directory of symlinks into the host's `.pnpm` store, and if one leaks into the context `COPY . .` overwrites the dependencies the image just installed with dangling links.
- **Tailwind's automatic source scan is rooted at `apps/web`** (the Vite root), not the repo root — class names used outside `apps/web` are not detected, and scanning the whole repo would have swept `docs/` and `output/` in.
- **esbuild no longer uses `packages: 'external'`; `scripts/build-server.mjs` has an `externalizePackages` plugin instead.** The criterion is the same (anything not starting with `.` or `/` stays external) with one exception: `@shadecn/*` is **inlined**. `packages: 'external'` has no exception list, and with it `@shadecn/shared` would survive as a runtime `import` of a package that is not installed anywhere in the artifact. Third-party packages that shared itself imports (yjs) still go external and still land in the generated runtime dependency list.
- **`@shadecn/shared` is a `workspace:*` `devDependency` of both `web` and `server`** — it is bundled by Vite / esbuild, so the artifact never needs it installed. It declares `yjs` as a **peerDependency**: there must be exactly one copy of yjs in any bundle, because `instanceof Y.Map` across two copies is always `false` (and shared's whole reading side is `instanceof` checks). One copy is guaranteed by pnpm linking every consumer to the same realpath, plus the frontend's `resolve.dedupe`; `apps/server/test/collab/shared-yjs.test.ts` and `apps/web/src/test/lib/sharedYjs.test.ts` pin the `instanceof` so a dependency drift fails a test instead of blanking a canvas.
- **Rules for writing code in `packages/shared`.** Relative imports inside the package carry the `.ts` extension. No DOM or Node API: its `tsconfig.json` sets `lib: ["ES2020"]` and `types: []` as the guard-rail, because both consumers recompile the source under *their own* config (DOM+ES2020 vs. Node+ES2023) and the intersection is the only safe subset. Tests use a separate `tsconfig.test.json` — vitest's types pull in `@types/node`, and folding them into the main config would silently turn the guard-rail off.
- **The lockfile's dependency version ranges were deliberately kept identical to the pre-monorepo ones.** Letting pnpm re-resolve from scratch drifts `reka-ui` to 2.10.1, so don't `pnpm update` casually and read the lockfile diff of any install.
- **Run the `shadcn-vue` CLI from `apps/web`** (that is where `components.json` is); the packages it adds land in `apps/web/package.json`, which only has `devDependencies` — so the old "move it out of `dependencies`" chore is mostly gone, but check anyway.

## Commands

- `pnpm dev` — (delegates to `@shadecn/server`) Start the whole app (Node/Hono + Vite as middleware, watch mode) on http://127.0.0.1:3000
- `pnpm build` — Build both halves into `output/`: frontend (`vue-tsc -b` + `vite build`) into `output/public`, backend (esbuild bundle) into `output/server`
- `pnpm build:client` / `pnpm build:server` — Just one half. `build:client` no longer type-checks the server as a side effect; `build:server` still runs `typecheck` first
- `pnpm start` — Run the production server locally (`NODE_ENV=production node --import ./apps/server/scripts/local-start.mjs output/server/index.js`, see the monorepo section for why the `--import`)
- `pnpm preview` — `pnpm build && pnpm start`
- `pnpm typecheck:server` / `pnpm typecheck:shared` / `pnpm typecheck:agent` — Type-check the `apps/server` / `packages/shared` / `packages/agent` project (the shared one runs two configs: the source guard-rail config and `tsconfig.test.json`; the frontend is checked by `vue-tsc -b` inside `pnpm build:client`)
- `pnpm test` — Run all three Vitest projects once; `pnpm test:watch` for watch mode
- `pnpm test:server` / `pnpm test:client` / `pnpm test:shared` / `pnpm test:agent` — Run only the backend / frontend / shared / agent project
- `pnpm test:coverage` — v8 coverage into `coverage/`
- `pnpm lint` / `pnpm lint:fix` — ESLint
- `pnpm db:push` — sync the tables to the entity definitions (`tsx db/sync-cli.ts` — **this project keeps no migration files**, see the database section). Additive changes only; anything lossy is refused with the offending statements printed. `pnpm dev` runs it first. There is no `db:generate` (nothing is generated) and no `db:studio` (MikroORM has no equivalent — use `sqlite3` / `psql`)
- `pnpm db:push:force` — the same sync with `--force`, for when a local entity change drops or retypes a column (also drops tables that aren't entities). **Dev only, and deliberately a separate command**: `dev` / `dev:cluster` / both Dockerfiles keep the bare sync, so a destructive change fails loudly instead of quietly dropping a column on every server start

One process, one port: the Node server is the only entry point in both dev and prod — there is no separate Vite dev server and no proxy.

Copy `.env.example` → `.env` (repo root) before the first run; `apps/server/env.ts` loads it via `process.loadEnvFile()` (no dotenv dependency).

## Architecture

**Stack:** Vue 3 + TypeScript + Vite + Tailwind CSS v4 + shadcn-vue (new-york style). **Path alias:** `@/` → `apps/web/src/` (in `apps/web/vite.config.ts` and `apps/web/tsconfig.app.json`); the shared contract is imported as `@shadecn/shared/<subpath>`, never through `@/`. Frontend, `/api/*` and `/ws/collaboration` are same-origin in every mode, so frontend code always uses relative paths.

The detailed architecture lives in `.claude/rules/`, one file per area. Each file loads automatically when you touch a path it lists; **read the matching file before changing code in that area** — each one is a set of invariants where the obvious change is a known bug:

- **Canvas editor** — `.claude/rules/flow-editor.md`: project/canvas views, the hooks-vs-components editor split, node-type registry and node-kit, rubber band / groups / snapping, the Pinia store as a *projection of a Y.Doc* (`store.mutate()` is the only write path), five-group node schema, flat prefixed keys for collections, drafts (`useDraftField`), personal canvases (REQ-SOLO).
- **Collaboration** — `.claude/rules/collab.md`: data layer vs feedback layer, Hocuspocus mount and timings, persistence (read → merge → CAS; **a failed store must propagate**), awareness identity rewrite, one-window-per-user, the four terminal close codes, revocation and the write gate, WebSocket `Origin` check.
- **Frontend shell** — `.claude/rules/web-shell.md`: router + two layouts, frontend auth and the popup re-login, shadcn-vue components (`Button.vue` is hand-edited — the CLI clobbers it), `@lucide/vue` only, theme/Tailwind gotchas, views by feature folder.
- **Backend runtime** — `.claude/rules/server-runtime.md`: `apps/server/` file map, dev orphan watch, logging (keep writing `console.*` with a `[prefix]`), frontend hosting and the login page as a second Vite entry, the esbuild build and `output/`.
- **Auth** — `.claude/rules/auth.md`: Keycloak OIDC + GitHub OAuth2 BFF, provider registry, per-request callback origin (`APP_ORIGINS`), sessions kept alive by traffic, account linking with confirmation, identity is `(provider, subject)` never email, profile hooks, avatars.
- **Database** — `.claude/rules/database.md`: entities, SQLite *or* PostgreSQL from one artifact, entity-writing rules, Prisma habits that are now bugs (`nativeUpdate` skips `onUpdate`), no migrations + the lossy-change guard, `containsIgnoreCase()`.
- **Clustering** — `.claude/rules/cluster.md`: `CLUSTER_MODE`, `SharedMap`/`SharedCounter`/`SharedLock`, extension-redis, eventual-consistent quota, `dev:cluster`, k8s variants.
- **Deploy** — `.claude/rules/deploy.md`: the two Dockerfiles, native-module architecture checks, probes and shutdown timing.
- **Tests** — `.claude/rules/testing.md`: Vitest projects, hermetic setup, `TEST_*` env, module caches, component-test gotchas (`AlertDialogAction` closes before `@click`).
- **Canvas agent** — `.claude/rules/agent.md`.

Requirements (*what* each feature should do) stay in `docs/`; the rule files describe *how* it is built. When a section here or in a rule file goes stale, edit it where it lives — each fact has one home.

**Dependencies — each package declares only what it needs; the runtime set is `apps/server/package.json`'s `dependencies`, everything else is `devDependencies`.** The frontend is bundled into `output/public` and the backend into `output/server/index.js`, so `apps/web` has **only `devDependencies`** (vue/three/tailwind/reka-ui/`@hocuspocus/provider`/`y-protocols`/`lib0`, `vite`, `vue-tsc`, …) and `@shadecn/shared` is a `workspace:*` devDependency of both web and server (it is inlined into both bundles). `apps/server`'s `dependencies` holds just the packages the server bundle still needs at runtime: `hono` + `@hono/node-server`, `@hocuspocus/server` + `crossws` + `yjs` (collab server — crossws vendors its own `ws`, so we no longer depend on it directly), `@mikro-orm/core` + both drivers (`@mikro-orm/sqlite`, `@mikro-orm/postgresql` — pinned to exactly `7.2.5`, and *every* artifact keeps both, since the database is a runtime choice), `ioredis` + `@hocuspocus/extension-redis` (multi-replica mode; both stay in the artifact because the mode is an env switch, not a build flag), `minidenticons` (default avatars are rendered per request, so it is runtime, not build-time), and `winston` (the logging layer, see above — it is imported by `apps/server/index.ts`'s very first side-effect import); `esbuild`, `tsx` and `vite` (dev middleware) are server `devDependencies`. The **root** `package.json` holds only repo-wide tooling: the eslint family, `typescript`, `vitest` + the coverage plugin, `jsdom` — plus the `pnpm.neverBuiltDependencies: ["better-sqlite3"]` setting (see the deploy section). `apps/server/scripts/build-server.mjs` enforces the runtime set: it reads `apps/server/package.json`, and if a package the bundle imports is only in `devDependencies` (or missing), the build fails. So a package the *server* imports goes into `apps/server`'s `dependencies`; a frontend package goes into `apps/web`'s `devDependencies` (the `shadcn-vue` CLI, run from `apps/web`, already writes there); don't hoist either to the root.

**Key libraries:** `reka-ui` (headless UI primitives behind shadcn-vue), `@vueuse/core`, `class-variance-authority`, `vue-router` 5, `pinia` (only the flow editor's store) and `vue-sonner` (toasts) on the frontend; `hono` on the backend; `vite` for dev middleware + the frontend build; `tsx` only for `pnpm dev`.

## Conventions

- TypeScript strict mode with `noUnusedLocals`, `noUnusedParameters`, `erasableSyntaxOnly`
- All Vue components use `<script setup lang="ts">`
- Package manager: pnpm workspace. Add a package with `pnpm --filter <pkg> add -D <name>` (or `-P` for a server runtime dependency — see the dependency split above); never to the root unless it is repo-wide tooling
- Tests live in `apps/server/test/` and `apps/web/src/test/`, mirroring the directory they cover (`apps/server/test/routes/auth.test.ts` ↔ `apps/server/routes/auth.ts`). Imports inside `apps/server/test/` keep the explicit `.ts` extension like the rest of `apps/server/`. Tests for shared contract code live in `packages/shared/test/`.
- Vitest globals are **not** enabled — import `describe`/`it`/`expect`/`vi` from `vitest` explicitly.
- Test names are written as the behaviour being constrained ("未登录 → 401"), not as the function being called.
- **Time is UTC everywhere except on screen.** The database stores `datetime` as an absolute instant (`timestamptz` on PG; MikroORM maps SQLite's the same way), entities hand back `Date` objects, and every store maps rows out through `toISOString()`, so the wire format is always an ISO string with `Z` — never a pre-formatted, timezone-less string. The frontend never formats a date inline: `apps/web/src/lib/format.ts` is the only place that builds an `Intl.DateTimeFormat`, and by default it follows the browser (`navigator.languages` for the locale, the runtime default for the timezone) rather than a hard-coded `zh-CN`. Use `formatDateTime` / `formatDate` / `formatTime`, or `formatWith(value, options)` for another granularity; all four take a string/number/`Date`/null and render `-` for anything unparseable.
  - **What "follows the browser" means is now a preference, not a constant** — `apps/web/src/lib/preferences.ts` (a `useStorage` under `app:display-preferences`, browser-local, never sent to the server) holds locale / timeZone / dateStyle / timeStyle / hourCycle, every one of them defaulting to `AUTO` = follow the browser, which is why turning the setting page on changed nothing about existing output. `format.ts` reads the **reactive** `resolvedDisplayPreferences`, so changing a setting re-renders every already-displayed date with no reload and no per-page wiring. Two rules: a **caller-supplied option always wins** (`formatWith(v, { timeZone: "UTC" })` stays UTC no matter the preference — the preference only fills in what the caller didn't say), and the stored value is **validated on read** against a whitelist (localStorage is user-editable, and a misspelled `dateStyle` makes `Intl` throw `RangeError` and takes the page down). The UI is `apps/web/src/views/Settings.vue`.
- **On the canvas's own path, time is a *number* — UTC epoch milliseconds, not an ISO string** (`FlowNodeData.createdAt`, `FlowEdgeData.createdAt`). Numbers compare directly with no timezone, format, or parse step in between, and they ride inside the Y.Doc where a formatted string would be dead weight. Don't build ordering on them across clients: these are stamped by whichever browser created the element, so two clients' clocks are two clocks.
- **One click, one request — every write-side interaction goes through `apps/web/src/composables/useAsyncAction.ts`.** `const { run, pending } = useAsyncAction(fn, { errorMessage })`: `run()` records the action as pending **synchronously**, before the request is even sent, so a second click in the same event-loop turn is dropped on the spot; the template binds `pending` for the visual half (`<Button :loading="pending">`). The guard has to live in the handler, not in the markup — `:disabled` only takes effect on the next render, and half the entry points (`@keydown.enter`, `DropdownMenuItem @select`, an `@blur` that fires alongside an Enter-submit, `AlertDialogAction`) have no button to disable at all. `run` never rejects, so `@click="submit()"` leaves no unhandled rejection; errors go to `toast.error(err.message ?? errorMessage)` unless `onError` is given, which is why the wrapped action bodies carry no `try/catch`. Lists pass `key: (item) => item.id` so each row locks on its own. **Write `@click="submit()"`, not `@click="submit"`** — the latter hands the MouseEvent to the action as its first argument. Reads are deliberately *not* in scope: dropping a duplicate list load would strand the list on stale parameters.
- **Client-generated ids go through `apps/web/src/lib/id.ts`'s `createId(prefix)`** — `<prefix>_<base36 timestamp>_<random>`. The timestamp prefix keeps ids roughly sortable by creation; the random tail is the part that matters: two clients can add a node in the same millisecond, and a counter-based suffix (`nodes.length`) would hand both the same id and merge them into one object on sync.
