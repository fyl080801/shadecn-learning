## Language

## Project Overview

A Vue 3 learning/experimentation sandbox that combines shadcn-vue UI components, Three.js 3D scenes, and canvas-based mini-games. It serves as a playground for exploring different Vue and web technologies within a single app.

Requirements live in `docs/`, one file per requirement — see `docs/README.md` for the index. This file describes *how the code is built*; `docs/` describes *what it is supposed to do*.

## Commands

- `pnpm dev` — Start the whole app (Node/Hono + Vite as middleware, watch mode) on http://127.0.0.1:3000
- `pnpm build` — Build both halves into `output/`: frontend (`vue-tsc -b` + `vite build`) into `output/public`, backend (esbuild bundle) into `output/server`
- `pnpm build:client` / `pnpm build:server` — Just one half
- `pnpm start` — Run the production server (`NODE_ENV=production node output/server/index.js`)
- `pnpm preview` — `pnpm build && pnpm start`
- `pnpm typecheck:server` — Type-check the `server/` project
- `pnpm test` — Run both Vitest projects once; `pnpm test:watch` for watch mode
- `pnpm test:server` / `pnpm test:client` — Run only the backend / frontend project
- `pnpm test:coverage` — v8 coverage into `coverage/`
- `pnpm lint` / `pnpm lint:fix` — ESLint
- `pnpm db:generate` — Regenerate the Prisma client into `server/generated/prisma` for the *current* provider (also runs on `postinstall`). There is no schema-generation step: the two per-provider schema dirs are hand-written and share one physical copy of the models through a symlink (see below)
- `pnpm db:push` / `pnpm db:studio` — sync the schema into the database (`prisma db push` — **this project keeps no migration files**, see the database section) and the data browser. `pnpm dev` runs `db:push` first
- `pnpm db:push:force` — the same push with `--accept-data-loss`, for when a local schema change drops or retypes a column. **Dev only, and deliberately a separate command**: `dev` / `dev:cluster` / both Dockerfiles keep the bare `db:push`, so a destructive change fails loudly instead of quietly dropping a column on every server start

One process, one port: the Node server is the only entry point in both dev and prod — there is no separate Vite dev server and no proxy.

Copy `.env.example` → `.env` before the first run; `server/env.ts` loads it via `process.loadEnvFile()` (no dotenv dependency).

## Architecture

**Stack:** Vue 3 + TypeScript + Vite + Tailwind CSS v4 + shadcn-vue (new-york style)

**Path alias:** `@/` maps to `src/` (configured in both `vite.config.ts` and `tsconfig.app.json`)

**Routing:** `src/router/index.ts` — vue-router 5 (history mode). The route table has exactly two top-level records, one per layout (see below); every page is a *child* of one of them, and the child paths stay flat (`projects/:projectId`, not further nesting). The *views* are grouped into feature folders (see below). It is the only place that imports from `src/views/` and from `src/layouts/`.

**Layout — `src/layouts/`, one component per layout, picked by the route table.** `App.vue` is only `<RouterView />` + the `Toaster` (vue-sonner) mounted once at the root; it contains no layout branch. `SidebarLayout.vue` is `AppSidebar` + a scrolling `<main><RouterView /></main>` and holds almost every route; `BlankLayout.vue` is a bare full-screen `<RouterView />` and holds only `/flows/:flowId`, the canvas editor, which needs the whole screen. Both top-level records use `path: "/"`, so adding a page means putting it under the layout it belongs to — nothing else changes, and there is no `meta.layout` flag anymore. Every SPA route is a logged-in route (the login page is server-rendered and never enters the SPA) — a bare layout is *not* an auth exception. The app fills the viewport height (`h-screen`).

**Auth (frontend):** the gate is on the server (`server/frontend/guard.ts`) — an anonymous browser never receives this bundle in the first place. `src/router/index.ts`'s global `beforeEach` is only the fallback for a session that dies mid-visit: it calls `fetchSession()` (one `GET /api/auth/me`, cached) and, when anonymous, either `goToLoginPage()` — a full-page `location.replace('/login?redirect=<fullPath>')`, because `/login` is server-rendered HTML and not a SPA route — on the *first* navigation (`from === START_LOCATION`, nothing on screen to lose), or `requestReLogin(to.fullPath)` once the user is already inside the app. `src/lib/auth.ts` exposes `useAuth()` (`user` / `roles` / `isAuthenticated` / `authEnabled` / `sessionExpired` / `hasRole`) and `apiFetch()`. There is no token in the browser — login/logout are full-page navigations to `/api/auth/login` and `/api/auth/logout`.
- **An expired session is never a silent redirect.** A 401 from `apiFetch` (or the guard, mid-visit) calls `requestReLogin(redirect)`, which clears the local user, remembers the return url, and flips `sessionExpired`; `SessionExpiredDialog.vue` — mounted once in `App.vue` next to the `Toaster` — asks, and offers two ways out plus "close and do nothing" (× / Esc / overlay → `dismissReLogin()`, the next 401 asks again). **退出** is `logoutFromExpired()` → `/api/auth/logout?redirect=<return url>`, which lands back on `/login?redirect=<return url>` so logging in again returns to the same page. **重新登录** never leaves the page: it opens a **second window** on `/api/auth/login?redirect=/auth/login-done`, and the page — with whatever was typed into it — stays put. Yanking the page away on a 401 both destroys unsubmitted input and hides what happened.
- **The re-login is a popup window, not an iframe, and its success signal has two legs because the session is an httpOnly cookie the frontend can't read.** The iframe version needed Keycloak's realm to drop `X-Frame-Options: SAMEORIGIN` (otherwise the modal is simply blank) and, third-party-cookie rules being what they are, Keycloak's own SSO cookie was blocked inside it, so the password had to be retyped every time. A popup is a *top-level* browsing context: neither applies, and no realm configuration is needed. The one cost is the popup blocker — `window.open()` returning `null` is reported in a toast and the button becomes 「重新打开登录窗口」, the dialog itself never closes. `server/frontend/login-done-page.ts` renders `/auth/login-done` (registered *after* `pageGuard`, so an unauthenticated landing bounces back to `/login` inside the popup), `postMessage`s a same-origin `app-auth:login-done` to `window.opener` and closes itself; the dialog accepts the message only when `event.origin === location.origin` *and* the marker matches, then calls `finishReLogin()` → `fetchSession(true)` and only closes if `/api/auth/me` really says logged-in. A 3s poll while waiting is the second leg (message blocked, or `opener` severed by an intermediate page); the same tick notices `loginWindow.closed` and drops out of the waiting state so the button comes back.

**UI Components (shadcn-vue):** Located in `src/components/ui/`. Added via the `shadcn-vue` CLI (`pnpm exec shadcn-vue add <name>`, configured in `components.json`) — note the CLI drops new packages into `dependencies`, so move them to `devDependencies` afterwards (see the dependency split below). Icon library is `lucide-vue-next`. The `cn()` utility in `src/lib/utils.ts` merges Tailwind classes via `clsx` + `tailwind-merge`. Two components are edited beyond what the CLI generates and must not be clobbered by a re-`add`: `button` carries an extra `loading` prop (spinner + auto-`disabled`, the visual half of the one-click-one-request rule below) and extra `size` variants (`xs` / `icon-xs`). **The CLI rewrites `Button.vue` whenever it is pulled in as a dependency of another component** (adding `command` does it) — `git diff src/components/ui/button/` after any `add`, and `git checkout` it back.
- **`command` is a filter-it-yourself list.** Its built-in filtering renders *every* item and hides the misses with `v-if`, which is fine for a 20-line command palette and not fine for the 400+ IANA time zones — `TimeZonePicker.vue` therefore drives the list itself (own keyword ref + own matcher + a hard cap) and uses `Command` only for keyboard navigation, feeding the input through reka-ui's `ListboxFilter` directly instead of `CommandInput` (which is hard-wired to the built-in filter state). Two consequences worth remembering: `CommandItem` **must** sit inside a `CommandGroup` (it injects the group context and throws otherwise), and `CommandEmpty` is useless in this mode — it renders off the built-in filter's hit count, which stays 0, so write the empty state by hand.

**Styling:** Tailwind CSS v4 loaded via `@tailwindcss/vite` plugin. CSS variables for theming (light/dark) are defined in `src/styles/tailwind.css` (`src/style.css` only `@import`s it plus `vue-flow.css`) using oklch colors. Uses `tw-animate-css` for animations.
- **Which of the two variable sets applies is `src/lib/theme.ts`'s job — it is the only thing that puts the `.dark` class on `<html>`** (via `useColorMode`, storage key `app:theme`, default "follow the system"). Everything else about theming was already there; nothing reads the preference directly. Three rules that are easy to miss: **the first frame is `index.html`'s inline script**, not this module (by the time the bundle parses, a dark-mode user has already been flashed a white page — both places read the same key in the same raw-string format); **`color-scheme` must be declared in both blocks** (`light` on `:root`, `dark` on `.dark`) or the browser paints a white scrollbar over a dark page; and **vue-sonner doesn't look at the class** — it has its own `theme` prop, which `App.vue` feeds from `resolvedTheme`. The `.dark` palette is deliberately **one step lighter than shadcn's default** (background `0.145 → 0.215`, card `0.205 → 0.255`, …); the login page's own inline CSS carries the same numbers, so keep the two in sync.

**Views — `src/views/` is grouped by feature, one folder per area.** Only `src/router/index.ts` imports from here, so moving a view means touching exactly one other file.
- `views/Home.vue`, `views/Settings.vue` — the shell pages stay at the root (they belong to no feature). `Settings.vue` is the account + appearance + display-preference page (theme lives in `src/lib/theme.ts`, dates in `src/lib/preferences.ts` — both browser-local, both apply with no save button); its only entry point is the sidebar's bottom user menu, which also holds 关于 and 退出登录 — the middle nav list is pages only. **关于 is a modal, not a page** (`src/components/AboutDialog.vue`, no route — it's one paragraph of blurb, not worth a navigation), and **退出登录 asks first** (an `AlertDialog` in `AppSidebar.vue`) because logging out is an irreversible full-page trip through Keycloak sitting one row below 设置.
- `views/canvas/` — REQ-CANVAS, the one non-demo feature: `Projects.vue`, `PersonalFlows.vue`, `ProjectHome.vue`, `InviteAccept.vue`, `FlowEditor.vue` (see below).
- `views/three/` — everything 3D: `ThreeEditor.vue` (REQ-3DEDITOR), `3DScene.vue` (REQ-DIRECTOR), `Canvas3D.vue` / `LightScene.vue` (Three.js scaffolds, not implemented), `Emu3DView.vue` (CSS-only 3D cube via `Cube3D.vue`).
- `views/games/` — canvas games: `Demo3.vue` (brick-breaker), `SnakeGame.vue`, `Game2048.vue` (scoped CSS, no shadcn).
- `views/demos/` — single-page capability checks: `FlowChart.vue` (REQ-FLOW, the Vue Flow interaction demo the canvas feature grew out of), `RichEditor.vue` (REQ-PROMPT), `HiC.vue`, `Example.vue`.
- `Example.vue` and `Emu3DView.vue` have **no route** — they're orphaned view files kept around, see `docs/01-app-shell.md` §3.

**Projects & canvases (REQ-CANVAS, `docs/13-flow-canvas-management.md`)** — the one non-demo feature. A **project** owns canvases and is the permission boundary; the only way in is its share link — one per project, unlimited uses, admins open the 分享 dialog and the link is already there (`GET /api/projects/:id/invite` creates it on read). Five views in `src/views/canvas/`: `Projects.vue` (`/projects`, sidebar entry「画布项目」 — **the project list and nothing else**), `PersonalFlows.vue` (`/personal`, its own sidebar entry「个人画布」 — see REQ-SOLO below), `ProjectHome.vue` (`/projects/:projectId`, one route, same-page Tabs for 画布 / 成员 — switching tabs never touches the URL), `InviteAccept.vue` (`/invite/:token`, preview-then-confirm; anonymous visitors get bounced through `/login` by the page guard and land back here), and `FlowEditor.vue` (`/flows/:flowId`, the one route under `BlankLayout`).
- **The editor is split into a hooks layer and a component layer — the view itself only builds the context and places components.** `provideFlowEditor(props)` (in `src/composables/flow/`) creates the shared payload once and `provide`s it; every child pulls it with `useFlowEditor()`, so there is no prop drilling and adding a panel touches no existing file. The context bundles `store` + `sync` (`useFlowSync`, see below) + three composables: `useFlowDocument` (load / rename / duplicate / delete / save-state text / `flushBeforeLeave`), `useFlowCanvas` (the Vue Flow glue: `nodes`/`edges` bindings, drag→`node.move`, connect→`edge.add`, viewport sync, cursor-anchored ctrl-wheel zoom, `addNode`), and `useFlowSelection` (just `selectedNodeId` + `select` / `clearSelection`). `useFlowShortcuts(ctx)` adds the keybindings and the two don't-lose-work guards. Note `useVueFlow()` is called inside `useFlowCanvas` at the *root* setup, so the later `<VueFlow>` adopts that instance and out-of-canvas components (toolbar, capsule) can still use `screenToFlowCoordinate`.
- **Node types are a registry, not a hardcoded map — `src/components/flow/node-types.ts`.** One entry per `type` declares its component, menu label, icon, default `data` and default top-level fields; `FlowCanvas` feeds `:node-types` from it and `useFlowCanvas.addNode(type)` builds the node from it. **Adding a node type touches this one file** and nothing else. The toolbar does *not* render one button per entry anymore — types will keep piling up and a row of icons is neither recognisable nor affordable, so the add entry is a single `+` that creates `NEW_NODE_TYPE` (currently `text`, a card whose body is edited in place on double-click; `data.text` is its own key, so retitling and rewriting merge per key). That constant is separate from `FALLBACK_NODE_TYPE` (`process`, what an unrecognised `type` renders as — it must match `fromYNode`'s own fallback or old canvases change shape). `group` is the proof that entries need not resemble each other: fixed size, `zIndex: -1` (a background board must paint under every node), `pointer-events-none` on the body so it doesn't swallow rubber-band selection over the area it covers, resized through the official `@vue-flow/node-resizer` (its stylesheet is imported in `src/styles/vue-flow.css`, or the handles are invisible — and that stylesheet declares no `pointer-events`, so the same file has to hand `.vue-flow__resize-control` its events back or the handles inherit the body's `none` and resizing is silently dead) and committed to the doc only on `resize-end` — mid-resize frames are intermediates, exactly like drag. **Its chrome is the shared `FlowNodeChrome`, like any other node**: the name sits *outside*, above the top-left corner, and the toolbar floats top-center — a group used to carry its name inside a title bar, which made it read as a different kind of object when it is just a node with a different body. Groups swap the button row through the `#actions` slot (no duplicate, and its one button is **ungroup**, not delete — `Ungroup` icon, plain ghost, no destructive red: removing the frame loses nothing and undo brings it back, so both a bin icon and the red would be claiming otherwise); placement and when-to-show stay in the chrome, since those must not vary by node type. The one thing that can't move out with the label: **dragging**. `NodeToolbar` teleports to the viewport container, so pressing the label never reaches the node's d3-drag — a group therefore keeps a full-width, 24px grab strip inside its own top edge (invisible until hover), which is also why a rubber band can't be *started* from that band. Removing a group **detaches its children instead of deleting them** (which is why the button reads as ungroup) (`store.removeElements` clears `parentNode`/`extent` and converts each child's parent-relative position back to canvas coordinates — leave the dangling `parentNode` and the whole group snaps to the origin). Dragging a node *into* an existing group (auto-reparent) is still not wired; the data path is.
- **The rubber band is full-containment, edges follow their endpoints, and nothing but the highlight moves while it's being dragged.** `:selection-mode="SelectionMode.Full"` (Vue Flow's default, written out because it's a product rule: clip a corner and you'd select every node the band sweeps past). Nodes flip highlight one by one as the band grows — that's live already, since Vue Flow applies selection changes internally on every pointermove. Edges connected to a hit node count as selected, but Vue Flow's own pass **can't be relied on**: it diffs against the previous frame's edge-id set, and `removeSelectedElements()` on pointerdown clears the elements without clearing that cache — so two box selections in a row that hit the same edge leave it unselected the second time. `useFlowCanvas` therefore re-asserts the rule itself (`getConnectedEdges` → `addSelectedElements([...nodes, ...edges])` — pass the nodes too, that action means "the selection is exactly this"), and only **while the band is active**: clicking an edge empties the node selection, so applying the rule outside the gesture would immediately deselect the edge just clicked. Selected edges are styled in `src/styles/vue-flow.css` (theme-default's `#555` on a gray line is a state you can't see). **No toolbar is on screen during the drag** — `canvas.boxSelecting` (Vue Flow's `userSelectionActive`) gates both the per-node chrome (the band sweeping over the first node makes it briefly the single selection, so duplicate/delete would flash) and the selection toolbar (which would otherwise chase the moving bounding rect); they appear on release.
- **A group is created by grouping a selection, never from the toolbar** (`canvas.groupSelection()`, reached from `FlowSelectionToolbar`): it grows around nodes that are already selected, so "add an empty group, then drag nodes in" is both backwards and impossible (auto-reparent doesn't exist). The box is the selection's bounding rect (`getRectOfNodes`, i.e. `computedPosition` + measured dimensions) plus padding; nodes already inside another group, and groups themselves, are excluded. Two things it can't be built without. **The group and its children go in one transaction** (`store.groupNodes`, `extent: 'parent'` included) — split them and every child briefly points at a `parentNode` that doesn't exist yet, which is `NODE_MISSING_PARENT` plus a whole group of nodes jumping to the origin, and undo would leave half a group behind. And **`extent: 'parent'` must be withheld from Vue Flow until the parent has been measured** — `extentReady()` in `useFlowCanvas`'s `nodes` adapter, which hands over `extent: undefined` while `findNode(parentNode).dimensions.width` is still 0 (write the key explicitly; a key you stop sending keeps its old value through `Object.assign`). Vue Flow derives that bound from the parent's `dimensions`, so before the group's first render the bound degenerates to a point and every child is clamped to `parent - its own size` — the whole group piles up outside the box's top-left corner. **The gate belongs in the adapter, not in the write path**: delaying the *write* only protects the author, and the bug's real victim is everyone else — a peer reads `extent` straight out of the doc the moment the update lands, long before the new group node has rendered on their side. That is what "打组没同步给别人" actually was: the data arrived intact, the receiver's view mangled it. The doc is correct throughout, which is why a reload "fixes" it and why it is easy to miss.
- **Components live in `src/components/flow/`**, each owning one region and reading the context directly: `FlowCanvas.vue` (Vue Flow + background + minimap, plus a `<slot/>` for extra in-canvas overlays), `FlowViewControls.vue` (zoom/fit/lock + undo/redo, top-right), `FlowTitleCapsule.vue` (top-**left**: logo/home + inline-editable name + save state + menu, owns its delete confirm), `FlowToolbar.vue` (bottom, canvas-content actions), `FlowSelectionToolbar.vue` (floats above a **multi-node** selection — `NodeToolbar` takes an id *array* and positions itself over their bounding rect; holds 打组), `ProcessNode.vue` / `TextNode.vue` (the nodes themselves — body only), `FlowNodeChrome.vue` (what every node type shares: the external name label with double-click rename, and the duplicate/delete `NodeToolbar` shown only when this node is the single selected one — so it and the selection toolbar are never on screen together), `FlowSnapGuides.vue` (the drag alignment guides), `FlowConnectionEndedDialog.vue` (the modal for a sync channel the server ended for good — one copy block per reason; the expired-session case is deliberately *not* here, it goes to the app-wide `SessionExpiredDialog`. It is non-dismissible **except for `too-large`**, and that exception is the point: for the other reasons nothing the user does on this page helps, while an over-quota canvas is fixed precisely *by deleting on this page* — a modal you can't close would block the only way out). **There is no property panel**: clicking a node selects it and nothing more. Per-node editing lives on the node (double-click to rename, the toolbar for duplicate/delete), so a selection never steals a third of the canvas.
- **Snapping (`useFlowSnapping` + `src/lib/flow-snap.ts`) applies to dragging only — never to nodes already placed.** Both snaps (grid + alignment guides) are **always on: no toggle, no toolbar button, no persisted state** — the grid *is* the visible background dots and the guides only appear when something genuinely lines up, so both are the default feel; a switch would only make you click once to get it and force the docs to explain two states. Grid is `FLOW_GRID_SIZE`, the same constant `<Background :gap>` uses — a grid you snap to but can't see lines up with nothing. The guide tolerance is **6 screen pixels ÷ zoom**, not a flow-coordinate constant, or the magnet grows 4× when you zoom in. **Vue Flow's own `:snap-to-grid` is deliberately unused**: besides dragging it also rounds a node's position at *mount* (`NodeWrapper`'s `clampPosition`), a local-view-only shift that never enters the doc, so someone with snapping on and someone without would see different canvases. Both snaps are computed in one place and produce one delta (guides win over grid — the alignment is the more deliberate intent); multi-select drags snap by the group's bounding box so relative positions survive. The correction runs *in* `onNodeDrag`, after Vue Flow has written the raw pointer position and before the frame paints — it can't accumulate, because every drag event recomputes from the pointer, which is exactly why the magnet releases when your hand moves off the line. Snap first, *then* `publishDrag`, or collaborators watch the unsnapped position. The guide overlay lives in the `#zoom-pane` slot next to the presence cursors (flow coordinates, only stroke width and dash counter-scaled).
- **Canvas behaviour is Vue Flow's job, not CSS's.** Anything that has to live *on* the canvas — a label outside a node, a per-node toolbar, a resize handle, an overlay that must follow zoom/pan — is built from the official packages (`@vue-flow/node-toolbar`, `@vue-flow/node-resizer`, `<Panel>`, `<Handle>`, `<NodeToolbar>`, …), following [the guide](https://vueflow.dev/guide/) and [the examples](https://vueflow.dev/examples/). **Do not hand-roll positioning** (`absolute` + `transform`, viewport math, manual `screenToFlowCoordinate` re-anchoring) when a Vue Flow component already does it — a hand-written overlay silently breaks under zoom, and the transform math it duplicates is exactly what the library maintains. Tailwind classes stay for *appearance* (type scale, color, spacing inside the slot); *placement* comes from the component's props (`position` / `align` / `offset`). Missing package → add it as a `devDependency` (it's frontend, see the dependency split) rather than reimplementing it. `ProcessNode.vue`'s external top-left name label is the reference case: `<NodeToolbar :is-visible="true" :position="Position.Top" align="start">`.
- **State: `src/stores/flow/` (Pinia) is a *projection of a Y.Doc*, not a store of record.** The canvas content **is** the Yjs document (shape in `src/lib/flow-doc.ts`, mirrored server-side in `server/collab/flow-doc.ts` — two TS projects, so change one and change the other): `nodes`/`edges` are `Y.Map<id, Y.Map>` and each node's `data` is a nested `Y.Map` again, because Y.Map merges *per key* — one person retitling while another drags merges cleanly, whereas storing a node as one JSON blob would let the later write clobber the earlier one wholesale. **Business fields sit flat on `data`, never wrapped in a `config` object (graph schema v2)** — the same argument one level down: a single `config` key would let one person's edit to `config.prompt` clobber another's to `config.model`. `data.kind` is gone with it: a node's business type **is** its top-level `type`, which is the key of the node-type registry. **A batch of independently-edited elements (3D objects, timeline tracks, a resource list) goes one-element-per-key — `<prefix>.<id>`, flat, plain JSON — never into one `data.scene` blob and never into a nested `Y.Map`** (`src/lib/flow-collection.ts`; write and delete land in one transaction via `store.writeNodeData(id, {set, remove})`). The blob is the `config` bug one level down: everyone in the batch shares a merge unit, so two people posing two different characters clobber each other. The nested `Y.Map` fixes merging but puts *structure* into the CRDT layer, and that is the one thing this doc can't version: with no version number in a Y.Doc, an old and a new client write **different types to the same key**, the winner is decided by clientID (i.e. randomly), the loser's whole subtree vanishes, and the losing side's code throws `TypeError` — read-time upgrading (`upgradeNodeData`) rescues a changed *shape*, never a changed *type*. Flat prefixed keys are invisible to the CRDT layer instead: `toYNode`/`fromYNode` (both copies), `duplicateNode` and the whole server are untouched, and an old client passes the unknown keys through as it already does. Measured on the 43.7KB director-console sample: 26,626 B per element edit and guaranteed clobbering → 3,358 B and both edits surviving, for +5% doc bytes. Three rules: **a key's type is fixed from its first write and can never change** — that is the precise form of the rule, so a brand-new key that is `Y.Text` from day one is fine (an old client `toJSON()`s it to a string and passes it through, never writing plain to it), while *upgrading* an existing plain key is the thing that destroys data; **ids must be stable, never array indices** (an index shifts when someone else inserts, and your write lands on their element — mint one with `createId()` if the source data has none, as the sample's 5 uuid-less objects and its id-less keyframes both do); and **prefixes must not nest** (`dc.obj` + `dc.obj.pose` collide — convention only, nothing enforces it). Granularity stops at one element per key; two people editing *the same* element loses one side, and that gap is **deliberately left open**, exactly as it is for every other element on the canvas (§4.0.1: concurrent editing is allowed, presence only *shows* who else is touching a node — `occupantsOf` is already wired into `FlowNodeChrome`). Narrowing it belongs on the occupancy/notice side rather than in a finer CRDT, and the cheap forms come first — a soft warning, or a conflict check at commit time — not read-only enforcement, whose lease/TTL/leak handling plus Vue Flow's `Object.assign` trap (write the flags explicitly as `true` *and* `false`, or the element stays dead after the lock lifts) costs far more than this one gap is worth. v1 data is upgraded **on read** — pure, idempotent, and deliberately never written back, because a projection that writes produces a Yjs transaction that enters everyone's undo stack and broadcasts. Y.Docs carry no version number, so v1 is recognised by shape (a string `kind` *and* an object `config` together); `Flow.graph` rows do carry one, and **`parseGraph` must keep accepting v1** — every stored projection is v1 and `readGraph()` is the only path old canvases take into Yjs, so rejecting them would blank each one on first open. The projection is **incremental**: `observeDeep`'s events name which top-level keys changed, only those get re-parsed, and everything else keeps its previous object identity — which Vue Flow relies on to skip re-syncing untouched nodes (a `null` from `changedTopLevelKeys` means "can't tell, redo everything"). The one rule: **every content change goes through `store.mutate()`**, which wraps it in a Y transaction tagged `LOCAL_ORIGIN`; components never touch a Y.Map directly, or the change is neither undoable nor synced. Undo is `Y.UndoManager` with `trackedOrigins: [LOCAL_ORIGIN]` — that single option is what makes Ctrl+Z undo only *your* edits and leave a collaborator's alone; `separateUndo()` (`stopCapturing`) splits operations that would otherwise merge inside the 400ms capture window. There is **no save, no revision, no 409, no dirty state** — edits are live and the server persists the same stream. The one exception is a *notice*, not a state: when the server's write queue starts failing it broadcasts a **stateless** message to the room and the status line reads 「服务器暂时无法保存」 (`onStoreStateChange` → `broadcastStateless` → the transport's `onStateless` → `saveFailed`). Four rules there, each of which is a bug if you skip it: broadcast **only on flip** (good→bad, bad→good — stores are 2–10s apart, so per-store notices are pure noise), **re-send to a joining connection** (`connected` reads `isStoreFailing`, or whoever arrives after the flip sees 「已同步」 on a canvas the server cannot store), **clear `saveFailed` when the transport is replaced** (it describes *that* server; keeping it across a reconnect pins the UI at "cannot save" forever), and **parse defensively** — stateless is a general side channel, and a payload you can't read must never throw, because that kills the connection's message loop. It is deliberately not a `fatal`: that tier means "won't fix itself", and this one will. Drag *intermediates* deliberately stay out of the doc (one drag would otherwise emit dozens of updates and audit rows); only the settled position is committed in `onNodeDragStop`, while the in-flight motion rides the feedback layer. **Panning and zooming are not canvas data and take a second, separate path**: `setViewport()` → `setUserState(key, value)`, which never enters the doc and never touches undo (undo must not yank the viewport back). **`setUserState` only buffers — it sends nothing.** The buffer is flushed to `PATCH /api/flows/:id/user-state` by `noteLocalEdit()`, which every local edit (`mutate`, `undo`, `redo`) calls. The shape is **leading send + debounced tail**: the first edit after a quiet period fires immediately (no window), everything after it goes through a `useDebounceFn` (`USER_STATE_FLUSH_DELAY`) that lands the final state once the hand stops, with a `maxWait` (`USER_STATE_FLUSH_MAX_WAIT`, 10s) so nonstop editing still lands periodically. So a view-only visit produces **zero** write traffic, a burst of editing produces one PATCH at its start and one at its end, and **no edit is dropped**. Neither half alone works: a plain debounce lags (it never fires while someone draws continuously, and this PATCH doubles as a heartbeat that can't wait), a plain throttle discards the tail of the window. The tail flush skips itself when nothing happened after the leading send, so a single edit costs exactly one request. **The window always fires a request, even when the view never moved** (it falls back to sending the current viewport), because that PATCH doubles as the session's heartbeat: content rides the WebSocket and produces no HTTP at all, the collab server's minute-by-minute revalidation is deliberately non-renewing (`loadSession(..., { refresh: false })`), and without this one request someone could be idled out *while actively editing*. Net rule: editing = one PATCH per window = session stays alive; looking = no requests = it idles out as it should. Panning without editing is caught by the flush in `saveNow()` / `reset()` on the way out. This is why the viewport rides editing rather than firing on its own: once Yjs took over content, a self-triggering viewport save was the editor's *only* periodic HTTP request — merely looking at a canvas would PATCH. To persist another per-user thing, add a field to `FlowUserState` (both copies), a parser to the server's `FLOW_USER_STATE_PARSERS`, and call `setUserState` — batching, retry and flush-on-leave are already there. Each viewer gets their own row, so `meta.viewport` in the doc is only the first-open fallback.
- **Continuously-changing values — a dragged slider, a scrubbed timeline, typed text — take one shape: a local draft owns the screen, the draft is throttled onto awareness if peers should see it, and the doc is written *once* when the gesture ends, bracketed by `separateUndo()`** (`docs/13` §3.7.2). **The no-release kind (rename in place, edit body text) is a composable, not a pattern to copy: `useDraftField` (`src/composables/flow/useDraftField.ts`)** — `{current, commit, normalize?, equals?, focus?}` in, `{editing, draft, start, commit, cancel}` out. It owns the draft ref, the `editing` flag and **both `separateUndo()` calls**, and it drops the three no-op cases for you: value unchanged, `normalize` returning `null` (an emptied title is a slip, not a rename), and the double submit you get because **Enter and blur routinely both fire** (the second `commit()` sees `editing` already false). `TextNode.vue` and `FlowNodeChrome.vue` are its two consumers. The with-a-release kind is still hand-written — copy `onNodeDragStart/Drag/DragStop` in `useFlowCanvas.ts` — and differs by exactly one step, throttling the draft onto awareness; that step is deliberately not in the composable because it needs a new awareness field (`transform` only carries `{x, y}`) and has no consumer yet, and when it does, `watch(draft, useThrottleFn(publish, throttleMs))` in the component is the whole change. **Throttling doc writes instead is the wrong fix**: the cost isn't doc size (60 dragged frames grow it from 33,411 to 33,438 — Yjs GCs overwritten Map keys well), it's broadcast + persistence (1.59MB for those same frames), and throttling can't fix the two things that matter — a half-dragged value shouldn't survive a refresh or be undoable, and the doc's guaranteed-ordered-merged delivery is the wrong channel for data that is *fine to drop*. **One undo item comes from committing once, not from `captureTimeout`** — a >400ms pause mid-gesture splits the window. Four rules for the awareness half: it's a *new* feedback field, not a reuse of `transform` (whose value type is `PresencePoint`); send only the numbers that changed, never the whole element (awareness is a *broadcast* — at 25fps a `{x,y}` packet is 45KB/s in a 10-person room, a 4.8KB object packet is 2.16MB/s, so **shrink the packet before lowering the frame rate**, which costs nothing while a lower rate costs responsiveness); clear it when the gesture ends (y-protocols replays local state every 15s, so a stale draft is rebroadcast forever); and keep **both** throttle edges (`useThrottleFn(fn, ms, trailing, leading)` — awareness is last-writer-wins *state*, not an event stream, so dropping middle packets is free but dropping the last one is a bug; the same property is why lowering the rate costs only smoothness, which is what makes the **adaptive window** safe: `ms` is a getter, `feedbackThrottle(roomSize)` in `src/lib/presence.ts`, re-read on every call because VueUse's filter does `toValue(ms)` per invocation. It returns the plain 40ms up to `FEEDBACK_THROTTLE_ROOM` people — i.e. unchanged for every realistic room — and widens stepwise beyond that, capped at `FEEDBACK_THROTTLE_MAX` (below ~6fps a peer cursor reads as frozen and you may as well stop publishing). **That curve is a judgement, not a measurement, and it is second-order** — shrink the packet first). Text splits by field: short/atomic commits on blur; long-form wants a debounced commit (accepting that >400ms debounce means finer undo — durability and undo granularity trade off, pick one); character-level co-editing needs `Y.Text`, which must be a brand-new key **and** requires fixing `duplicateNode`, whose projection→`structuredClone`→`toYNode` path silently flattens it back to a plain string. And while dragging locally the panel must read its own draft, never the projection — same reason `useFlowCanvas` freezes the `:nodes` array.
- **Not every canvas goes through the collab layer (REQ-SOLO, `docs/16-personal-flow.md`).** A **personal space** is a `Project` with `kind='personal'` and a unique `personalOwnerId` (lazily created by `GET /api/projects/personal`, which creates on read); canvases inside it have `mode: 'solo'` — **derived from the owning project, never stored on `Flow`**. The content model does *not* fork: solo canvases are the same Y.Doc, stored in the same `Flow.ydoc` bytes, with the same projection. Only the **transport** forks, and only in `src/composables/flow/sync/`: `collab.ts` (Hocuspocus WebSocket + awareness) vs `solo.ts` (HTTP push/pull over `GET/POST /api/flows/:id/doc`). Three rules hold it together. **The doc and its IndexedDB cache are created immediately; the transport waits for `mode`** to arrive with the metadata — which is why `context.ts` computes `mode` only when `store.meta.id === flowId` (a stale mode would connect the new canvas over the old canvas's channel). **Both channels refuse the other's traffic** — `authorizeCollab` denies a solo room (`forbidden`), the REST route 409s a collab canvas — because the client-side split is not an access control, and a hand-rolled provider would otherwise put someone else's cursor on your private canvas. **The sync protocol is keyed on the server's own state vector** (`x-flow-state-vector` on the GET, `stateVector` in the POST reply): the client pushes `Y.encodeStateAsUpdate(doc, lastAck)`, so resends are idempotent and no pending-update queue is needed — but taking the *merged local* state as the baseline instead would compute an empty diff and strand every edit made offline, forever, while the UI says 「已保存」. Server-side, `server/collab/flow-writer.ts`'s `applyFlowUpdate()` is the single write entry (quota → merge → projection), sharing `persistence.ts`'s per-flow queue and projection with the collab path; cross-replica concurrency is a CAS on `revision` (**not** a client-visible optimistic lock, and *not* `SharedLock` — its memory implementation reuses one in-flight promise, which would silently drop the loser's update). Personal spaces reject invites / member changes / delete / rename with **403** and are filtered out of `GET /api/projects`; `PROJECT_LIMITS.flows` does not apply to them. **On the UI side the two are separate pages under separate sidebar entries, not two Tabs of one page** (`/personal` vs `/projects`): a Tab bar says "two views of one thing", but a project has a second level under it (members, sharing, roles) and a personal canvas has none — no header button, empty state, or available action is shared between the two sides. Both lists are the same `FlowList` component (a personal space *is* a project to the API, so it only needs a `projectId`), and splitting the pages is what lets *both* own their URL query (`syncQuery`) — side-by-side Tabs had to share one `?page=`, so only the project side could keep it. **Anywhere the UI leaves a canvas, the destination is keyed on `mode`, never on `projectId`** — `useFlowDocument`'s `backPath()` (the capsule's home button, its menu item, and where a delete lands) sends solo to `/personal`, and its icon/label follow the same check. A personal space *is* a project in the database and `meta.projectId` really does point at it, but following that lands a private canvas on a project home offering members, sharing and 「全部项目」 — three things the server 403s for personal spaces. The reverse door is shut too: `ProjectHome.vue` `replace`s to `/personal` when the loaded project has `kind === 'personal'` (old bookmarks are the only way in).
- **Collaboration splits into two layers with one question deciding which (`docs/04-realtime-collab.md` §4.0): *should it still be there after a refresh?*** Yes → **data layer**: a Yjs shared type, which means CRDT merge, undo, and persistence. No → **feedback layer**: an awareness field, ephemeral, dropped frames are fine. `useFlowSync(flowId, mode)` owns the doc and its transport; the collab transport (`sync/collab.ts`) owns the one Yjs connection under both — a `HocuspocusProvider` (room `flow:<flowId>` passed as `name`, not in the URL; identity is the httpOnly `sid` cookie the handshake carries, gated server-side in `server/auth/ws.ts`). The same doc also carries a **`y-indexeddb`** cache (db name = room name), which is what makes edits survive going offline and closing the tab — they re-send on reconnect. Loading is therefore gated on *server-synced **or** local cache has content*, and the offline banner ORs in `navigator.onLine` because the provider needs a heartbeat timeout (tens of seconds) to notice a pulled cable. Teardown order matters: provider → indexeddb → doc. **`vite.config.ts` must keep `resolve.dedupe: ['yjs', 'y-protocols']`**: we and the provider each `import * as Y from 'yjs'`, and Vite's prebundling otherwise ships two copies — `instanceof` across them is always false, which would silently turn `src/lib/flow-doc.ts`'s `value instanceof Y.Map` checks into an empty canvas. and hands out a `session` that changes on reconnect/route-change; the store takes its `doc` and the presence layer takes its `awareness`. Dependency order is a straight line — `selection`/`sync` → `presence` → `canvas` — and `useFlowCanvas` is the **only** thing that knows all three: `useFlowPresence` doesn't import selection or Vue Flow, it just offers "publish" and "read others", which is why a new feedback signal costs one setter plus one computed and touches nothing else.
- **Data layer — the Y.Doc is the source of truth, and the server subscribes to it.** `server/collab/persistence.ts` implements Hocuspocus's `onLoadDocument`/`onStoreDocument`: first joiner loads `Flow.ydoc`, writes are debounced by the framework (2s, 10s ceiling) and skipped entirely when the state vector is unchanged, the derived `graph` projection is written **only in `beforeUnloadDocument`** — not under `onStoreDocument`'s `clientsCount === 0`, because Hocuspocus only re-stores on last-leave if a debounced store is still pending, so "edit, wait two seconds, close the tab" never fires it (verified) — and SIGTERM does `closeConnections()` + a direct per-room store (`flushAllRoomsToDatabase` — **not** `flushPendingStores()`, whose triggered store only reaches our queue after a microtask chain, so a synchronous sample sees an empty queue and the last debounce window is lost) + drains our own write queue. **A store is read → merge → CAS write, and the *merge* is the part that matters.** Writing `Y.encodeStateAsUpdate(doc)` straight into the `ydoc` column is a full overwrite; that is only safe while this process is the sole writer. Under `CLUSTER_MODE=redis` a pub/sub hiccup forks the two instances' documents and the later writer wins outright. **Adding CAS alone does not fix it** — `where: { revision }` proves nobody interleaved between *your* read and *your* write, not that your document is a superset of what is stored: an instance that wrote before you read gives you a fresh `revision`, your CAS passes, and you overwrite it anyway. So each store re-reads `ydoc`, `Y.applyUpdate`s it into the in-memory doc under the `'persistence'` origin (never `local` — it must not enter anyone's undo stack), and *then* CAS-writes; `count === 0` re-reads and retries, up to `MAX_STORE_ATTEMPTS`, after which it throws to the retry table below. The merge is idempotent, so on a single replica it reads back a subset, produces no update event, and costs nothing but the read. Redlock (`lockTimeout: 10_000`, raised from the 1s default that a large doc blows straight through) is now only an optimization — correctness lives in the CAS, which also covers Redis being down entirely. **A failed store MUST propagate — never swallow it, and this is the one rule in this file most likely to get re-broken by a well-meaning `catch`.** Hocuspocus's two data-loss protections are both *triggered by the hook throwing*: `onStoreDocument` throwing makes `storeDocumentHooks` keep the document in memory ("Document stays in memory to avoid data loss"), and `beforeUnloadDocument` throwing makes `unloadDocument` `return` before `documents.delete()`/`destroy()`. The write queue used to `.catch()` the error into a `console.error` and resolve — which silently disarmed both, so one database hiccup during "close the tab" lost that round of edits for good (docs/19 §4.1). Propagating is only two-thirds of it: the doc stays in memory but **nothing ever retries** (`onStoreDocument` is debounce-driven and by then nobody is editing), so failures are registered in `failedStores` and `retryFailedStores()` sweeps them every 30s, serially, clearing each on success — `GET /api/collab/health`'s `owed` is that table's size. The inverse rule holds for the **shared layer**: `sameAsStored` (read) and `rememberStoredVersion` (write) are *cache* operations, so they fail open — worst case is one redundant write, whereas failing the store would stall persistence whenever Redis twitches (§4.2 a). `rememberStoredVersion` must stay `async` even though its body is one line: the shared-layer lazy proxy resolves its implementation on first call and **throws synchronously** when Redis is down, and a synchronous throw sails straight past the caller's `.catch()`. **No y-leveldb** (native module) and no `@hocuspocus/extension-database` (a thin wrapper over the same two hooks): persistence is only load/store, so it writes the existing Prisma tables. **Legacy migration is `onLoadDocument` itself** — a canvas whose `ydoc` is NULL gets its old `graph` JSON poured into the doc on first open, so there is no migration script and no downtime. `Flow.graph` survives as a **read-only projection** the server derives on write (list counts, thumbnails, future read-only previews); the editor never reads it. There is **no per-update audit log** — the old `FlowOperation` table is gone, and with it any notion of history or rollback; `Flow.ydoc` is a converging snapshot (Yjs gc reclaims overwritten content), so nothing accumulates per edit. Since content no longer passes through any REST route, validation moved here too: the quota (`server/collab/quota.ts` — **bytes only**: 1MB/message, 20MB/doc; node and edge counts deliberately have no ceiling, they were a product judgement rather than a guardrail and the byte line already covers the resource side) is measured in `onChange` and enforced in `beforeHandleMessage`, and it **can only refuse before applying**, because an applied-and-broadcast Yjs update is unrecallable. Refusal **never throws** — Hocuspocus closes the connection on a thrown message and the reconnecting provider resends the same message forever; it flips the connection `readOnly` instead (writes get NACKed, reads and awareness keep working). The quota is two-tier: over the *soft* limit only marks the room and still accepts writes (deleting is the only way to shrink back, and deletes are writes too — the mark clears at the next byte re-measure, ≤1s, since measuring means serializing the whole doc and can't run per message), the *hard* ceiling (soft × 1.25) locks the room read-only until it unloads. **The doc limit and the projection limit are two different numbers on purpose** (`COLLAB_LIMITS.document` 20MB ≥ `GRAPH_LIMITS.bytes` 2MB, never the other way round): the projection is JSON that ships inside `GET /api/flows/:id`, the content is binary that only rides the WebSocket, so a doc between the two simply stops refreshing its projection (`deriveProjection` returns null and keeps the previous one — stale list counts, content untouched, and duplicate copies `ydoc` anyway). `onStoreDocument` prunes dangling edges (the legitimate product of one peer deleting a node while another connects to it) under a `'gc'` origin so the cleanup never enters anyone's undo stack. **Anything that mutates the graph must go through the store** — Vue Flow's own defaults will happily bypass it (`deleteKeyCode` under `applyDefault: true` edits its internal nodes/edges directly, so a deleted edge never synced or persisted). `FlowCanvas` passes `:delete-key-code="null"` and `canvas.deleteSelection()` is the single delete path.
- **Feedback layer — awareness carries who's here, where their cursor is, what they're dragging, and what line they're pulling.** `src/lib/presence.ts` is the pure, socket-free half (color hashing, defensive parsing of peer state, occupancy arbitration) and keys elements as `node:<id>` / `edge:<id>` so a third kind costs one `ElementKind` value. **The server rewrites the identity in every awareness update** (`beforeHandleAwareness` → `enforceIdentity`): clients may report any cursor/selection they like, but `user.id`/`name`/`avatarUrl` are replaced with what `onConnect` authenticated, so nobody can impersonate a teammate. Two more guards live on the same path: awareness entries are bound to the socket that first published their `clientID` (`dropForeignClients` — forged entries carrying a teammate's `clientID` are dropped, claims released on disconnect), and membership + session are **re-validated every minute** for live connections (`revalidateConnections`) — being removed from a project kicks an open WebSocket too, not just future handshakes. That sweep passes `{ refresh: false }`: it may only *read* the session, never renew it, or an open tab would keep its own session alive forever and idle timeout would stop meaning anything (renewal is the job of real requests — the handshake itself, then the edit-triggered user-state PATCH). **Occupancy arbitration exists and is tested but is deliberately not wired into the canvas right now** — anyone may edit anything concurrently and the CRDT merges it; the node label only *shows* who else is touching it. To reinstate the restriction, feed `presence.lockedKeys` back into the nodes'/edges' `draggable`/`selectable`/`updatable` in `useFlowCanvas`, and write those flags **explicitly as `true` as well as `false`** — Vue Flow merges node props with `Object.assign(existing, incoming)`, so a key you stop sending keeps its old `false` and the element stays dead after the lock lifts. See `docs/04-realtime-collab.md` §4.0.1.
- **One user, one canvas, one connection — and the newest window wins** (`server/collab/exclusive.ts`). Opening the same canvas in a second browser/tab kicks that user's older connections offline; the old window gets a non-dismissible 「协作会话已过期，请刷新页面」 (`FlowConnectionEndedDialog.vue`) and **stops reconnecting**. The rule is per *room × user*, not per user — having canvas A and canvas B open at once is normal work. Three things it can't be built without. **The holder registry lives in the shared layer** (`SharedMap`), because the two windows are very likely on different replicas and a local-only check kicks nobody; `connected` handles the local half on the spot, a 3s sweep converges the cross-instance half and renews the holder's TTL. **Kicking must close the socket, not just the connection** — Hocuspocus's `connection.close()` detaches the doc connection and sends a CLOSE message but leaves the socket open, and the client's next message (awareness heartbeat, ~30s) is re-authenticated as a *fresh* document connection: the old window resurrects itself and kicks the new one, forever. So it sends both the CLOSE message and a real close frame (`4409` / `session-superseded`), and the client accepts either signal. **The client must stop reconnecting itself** (the collab transport's `onClose` → `provider.disconnect()`), or the retry handshake reads as yet another new window and knocks out the tab the user is actually in; `disconnect()` leaves the doc and awareness intact, so the canvas stays on screen — just unsynced until a refresh takes it back. It is a UX rule, not an access gate (that one is `onConnect` / `revalidateConnections`), so a failing shared layer **fails open**, and with login disabled there is no identity to key on and exclusivity is simply off.
- **Four refusals are terminal, and the client must tell them apart** (`server/collab/close.ts` + `sync/collab.ts`'s `classifyClose`; `docs/04-realtime-collab.md` §4.4): `4409`/`session-superseded` (a newer window took over → refresh), `4401`/`Unauthorized` (session gone → the app-wide `SessionExpiredDialog`, then reconnect in place), `4403`/`permission-revoked` (still logged in, just not allowed in this room — not a project member, canvas deleted → leave), `4413`/`quota-exceeded` (the canvas hit the hard content ceiling and the room was locked and cleared — **the only one that is not about this person**: everyone in the room gets it, and it maps to the same `too-large` state a personal canvas reaches through a 413). Two things the copy has to get right: `forbidden` must cover *both* "deleted" and "not a member" in one sentence (the server deliberately doesn't distinguish them) and land on `/projects`, not the project home the second half can't open — **except on a personal canvas**, where `forbidden` can only mean "this canvas is gone" and both the wording and the destination (`/personal`) change; and **the person doing the deleting gets kicked too** (the route revokes before answering 204, so the close often beats the response), which is why `remove()` calls `sync.leave()` *before* the request — otherwise deleting your own canvas reports itself as an accident — and `sync.stay()` if the delete fails, or a later genuine kick would be silent. `authorizeCollab` returns which one (`CollabDenialReason`); collapsing the two is not cosmetic — a viewer whose session idled out *by design* would be told 「你已不是这个项目的成员」. Lumping any of them in with "offline" is worse still: the provider retries forever (`maxAttempts: 0`), the status line keeps promising 「恢复连接后自动同步」, and everything drawn from then on lands in IndexedDB and never leaves.
- **The server signals this over two different paths, and the client must handle both.** ① A connection that was already established gets closed — that goes out **on two legs**, because `connection.close()` detaches the doc connection and sends a CLOSE *message* but leaves the socket open, so the client's next message (awareness heartbeat, 15s) is re-authenticated as a fresh connection and the window resurrects itself; the real close frame is the second leg. ② **The handshake is refused (`onConnect` throws) — no socket close and no close code at all.** Hocuspocus only replies with a `PermissionDenied` message carrying `error.reason ?? 'permission-denied'`, which the provider surfaces as `onAuthenticationFailed({reason})` — **`onClose` never fires**. So the server must throw an error carrying `reason` (`denialError`), and the client must handle `onAuthenticationFailed` and `disconnect()` itself, or an authenticated-but-refused socket spins until the 30s server timeout, reconnects, and spins again — forever, while the UI says 「同步中…」. Path ② is the common one: reopening a canvas after being removed from the project, or reconnecting after the session expired. **Hence `reason` is the discriminator, not `code`** — it is the only thing both paths carry — and both paths funnel into one `endConnection()`. `4401` deliberately does *not* navigate to `/login`: `requestReLogin()` re-logs in inside an iframe so the canvas and its unsynced edits stay on screen, and a watch reconnects once the session is really back (gated on actually-authenticated, since dismissing the dialog also clears `sessionExpired`).
- **Revoking access kicks the live connection on the spot; the periodic sweep is only the backstop** (`server/collab/revocation.ts` + `revokeCollabAccess()`, called by remove-member / delete-project / delete-canvas; `docs/04-realtime-collab.md` §4.2.1). Waiting out a sweep is not merely "late": a removed member can still write for the whole window, those writes merge and persist, and **the people who remain cannot undo them** — `Y.UndoManager`'s `trackedOrigins` only tracks their own `LOCAL_ORIGIN`, so anything arriving over the wire never enters their undo stack, and one `deleteSelection()` empties the canvas. There is no audit log and no restore path — whatever a revoked member destroys is simply gone. So: the writing instance revalidates immediately, and **cross-instance is covered by one shared key** — a fresh token written on every revocation, polled by each instance every `REVOCATION_POLL_INTERVAL` (3s), and a change triggers a full revalidation. One global key + full sweep beats per-project/per-user delivery because revocations are rare while precise routing would need a room→project cache and a read count that scales with rooms. The route **awaits** it, so a 204 from `DELETE …/members/:userId` means the person is genuinely off the canvas. Broadcast failures never block — they degrade to the `REAUTH_INTERVAL` sweep, so a broken shared layer is slower, not leakier. The sweep itself must **fan out across documents and guard against re-entry**; the old serial `await` made `REAUTH_INTERVAL` a lower bound rather than the guarantee it is quoted as.
- **Kicking a connection is not the same as refusing a frame — the write gate is the second, message-level half** (`server/collab/write-gate.ts`, hooked on `beforeSync`; `docs/04-realtime-collab.md` §4.2 ④). Between "the verdict went bad" and "the socket is actually closed" sits the sweep interval, the 3s cross-instance poll, and whatever is already queued behind `closeForGood` — Hocuspocus's `Connection` carries no closed flag and `processMessages` never checks whether the connection is still attached, so those frames apply, broadcast and persist. **`beforeSync`, not `beforeHandleMessage`**: the latter runs on every frame including awareness (a cursor per pointermove), while `beforeSync` fires only inside a sync message *after* the type is read — so only writes pay for auth (`type` separates SyncStep1/read from SyncStep2+Update/write; never gate SyncStep1 or reconnect's own sync handshake breaks), and it runs *before* Hocuspocus's own `readOnly` check, so setting `readOnly` there NACKs the frame in flight. **Never `throw`** (same reason as the quota). **Refusing is only half — the connection must also be closed**: the provider does nothing with `syncStatus=false` (`applySyncStatusMessage` only decrements when `applied`), it never resends, so the rejected edits sit in the local Y.Doc + y-indexeddb until a *reconnect*'s SyncStep1/2 exchange carries them up — which is exactly the existing `classifyClose` → `SessionExpiredDialog` → re-login → `useFlowSync` watch → rebuilt provider path. Don't close and the user logs back in with the edits still stranded in the browser. **Cache the verdict; never batch-delay the frames** — message handling is one serial queue, so awaiting a timer in this hook stalls that connection's awareness heartbeat too and the 30s `timeout` kills it. The cached value is the *Promise*, which doubles as in-flight dedup. **TTL is long (10s) because the urgent half is event-driven**: `revalidateConnections` clears the table at its top, and it is the confluence of all three revocation paths, so a revoked member's next write frame always re-queries (window ≈0) at zero polling cost; the TTL only backstops session expiry, whose detection floor is the access-token lifetime anyway. Net: fewer queries than the 20s sweep, shorter window, and enforced before the Y.Doc rather than by close timing. `prime()` on `connected` (the handshake just authenticated), `forget()` on `onDisconnect`, and **an authorize that throws means allow** — no evidence, no refusal, same as the sweep and session refresh. **What it checks is injected and mandatory** (`createWriteGate({ authorize })`, no default): project canvases get `collabWriteAuthorize` (session + room + membership), personal ones would get `sessionWriteAuthorize` (**session only** — they have no members, and their writes go over REST where every request already runs the full `withSession` → `requireAuth` → `requireFlowMember` chain, so the middleware chain *is* their gate and the helper currently has no caller). An `if (personal)` inside the gate would make it know what a project is; the channel's shape belongs to whoever mounts the gate.
- **The WebSocket upgrade is outside Hono, so `Origin` is checked by hand** (`isAllowedCollabOrigin` in `server/auth/ws.ts`, called from the `upgrade` listener). WebSocket is not covered by the same-origin policy — any page can open `wss://us/ws/collaboration` and the browser attaches the `sid` cookie, which is CSWSH; `app.ts`'s `cors` only guards `/api/*` and a raw `server.on('upgrade')` sees none of the middleware chain. `SameSite=Lax` on `sid` already stops this in current browsers, but that is the browser covering for us, not a decision in our code. Allow on three grounds: **no `Origin` at all** (non-browser clients — browsers always send one, so this opens nothing), **equals `APP_ORIGIN`**, or **`Origin`'s host equals the request `Host`** (same-origin with a mis-set `APP_ORIGIN`, e.g. dev defaults to `127.0.0.1` while you browse `localhost`; a cross-site attacker can't reach this branch since its `Origin` is its own domain).
- **Never rebuild the `:nodes` array while the local user is dragging.** Vue Flow decides whether to re-sync nodes by array *reference*, and a re-sync runs `Object.assign(existing, incoming)` — since drag intermediates deliberately never reach the Y.Doc, `incoming.position` is the pre-drag position and the node snaps back mid-gesture. Something always changes during a drag (this client is publishing its drag position to awareness, which recomputes every presence-derived value), so `useFlowCanvas` keeps a `localDragging` flag and returns `store.nodes` untouched while it's set. Mapping over the array is only safe when a *remote* peer is dragging.
- **Types are duplicated on purpose:** `server/store/flow-types.ts` (with `parseGraph`/`parseTransactions` validation) and `src/types/flow.ts` mirror each other, because `server/` and `src/` are separate TS projects. Change one, change the other.
- **`src/lib/api.ts`** wraps every endpoint over `apiFetch` and throws `ApiError` (carries `status`) on non-2xx — the store needs to tell 409 apart.

**3D:** Three.js is a dependency with types (`@types/three`). The `Cube3D.vue` component is pure CSS 3D transforms (not Three.js). The Three.js views (`Canvas3D`, `LightScene`) are placeholders.

**Backend (`server/`) — the single entry point:** Node + [Hono](https://hono.dev) + `@hono/node-server`, run through `tsx` (no build step). It serves the API, the Yjs WebSocket, *and* the frontend. Layout:
- `server/index.ts` — entry. Loads `.env`, `assertAuthConfig()`, builds the http server with `createAdaptorServer` (no `listen` yet), attaches collab + frontend, starts the hourly expired-session sweep, then listens. Handles SIGINT/SIGTERM cleanup, and `shutdown()` carries a re-entry guard because the two signals can arrive back to back
  - **In dev, the process that actually holds the port is a grandchild, so it also has to notice when it has been orphaned.** `pnpm dev` is four layers — `pnpm` → `sh -c` → `tsx watch` → `node server/index.ts` — and only the last one listens. Ctrl+C in a terminal signals the whole foreground process *group*, so all four get it; stopping the task from an IDE, killing the top-level pid, or closing the terminal tab reaches only the top layer or two, and the listener survives with the port still bound. It gets reparented to init and nothing ever kills it, so the *next* `pnpm dev` dies with `EADDRINUSE` — and since each failure leaves another one behind, they accumulate (found 29 of them once, the oldest three days old, plus one still holding live browser connections). `watchForOrphan()` therefore samples `process.ppid` every 2s and runs the normal `shutdown()` once it changes, so the Y.Doc still gets flushed on the way out. The timer is `unref()`'d — it is a sentinel, not a reason for the process to stay alive — and the check is dev-only (under an init system the server is PID-1-adjacent by design). This is *not* a bug in the shutdown path: a plain SIGTERM to the listener has always exited cleanly in about a second; the signal simply never reached it.
- `server/env.ts` — side-effect module: `process.loadEnvFile()` on the repo-root `.env` (real env vars win). Imported first by `config.ts` and `index.ts`; no dotenv dependency
- `server/runtime.ts` — `isBundle` / `moduleDir` / `appRoot`. `__APP_BUNDLE__` is defined by the esbuild build, so the bundle knows it is a bundle: the app root is then `process.cwd()` (the repo root locally, `/app` in the container) instead of `server/`'s parent
- `server/config.ts` — `rootDir` / `outputDir` / `staticDir` / `isDev` / `port` / `host` / `isApiPath()` / `dataDir` / `dbProvider` / `databaseUrl` / `ensureDatabaseDir()` / `appOrigin` / `authConfig` / `authEnabled` / `assertAuthConfig()` / `clusterMode` / `isClustered` / `redisUrl` / `redisKeyPrefix` / `instanceId` / `assertClusterConfig()`. `isDev` is `NODE_ENV !== 'production'`; `staticDir` defaults to `output/public` (next to the bundle when bundled) and `STATIC_DIR` overrides it

Exports `AppType` for optional `hc<AppType>()` RPC typing on the frontend

**Logging (`server/logger/`) — winston, and the rule is *keep writing `console.*`*.** The whole layer is injected at four wiring points; there is **no `logger.info()` anywhere in business code**, and adding one is the thing not to do. Write `console.warn('[collab] …')` exactly as the existing 49 call sites do — `console.ts` intercepts `console.*`, parses the `[prefix]` into a structured `module` field, attaches the request context, and hands it to winston. That interception is the load-bearing piece: it is what let the whole codebase become structured logging with zero diffs, and it is why third-party output (Prisma, ioredis) is collected too. The four mount points, one line each: `index.ts` imports `./logger/install.ts` **second, right after `./env.ts`** (a side-effect module, not a function call — ESM hoists imports, so a call in the module body would run *after* every other module has already initialised and logged); `app.ts` uses `httpLogger()` in place of `hono/logger` (it also opens the `AsyncLocalStorage` that gives every downstream log a `requestId`); `db.ts` wraps the driver adapter in `instrumentAdapter()` (a Proxy — chosen over `$extends`/`log` events because it is type-identity, keeps `export const prisma: PrismaClient` intact, and sees the real SQL and real timings; **it logs SQL text but never parameter values**); `collab/hocuspocus.ts` puts `collabLogging()` in the extensions array. That last one is the interesting one: Hocuspocus pushes the `new Hocuspocus({...})` hooks onto the *end* of the extension list, so a `priority`-tagged logging extension brackets the business hooks — `onStoreDocument` (start) and `afterStoreDocument` (only reached if the whole chain succeeded) mean **`started - completed` is the failed-persist count, derived purely by observation**, which is what REQ-RESILIENCE §4.5 asks for. Noise control is a design constraint, not an afterthought: per-update and per-frame events are *counted*, never printed (one node drag is dozens of updates), and summarised once a minute; `LOG_HTTP` defaults to `api` so dev's few-hundred Vite module requests stay out; nothing in a hook may throw (the hook chain is serial — an observer that throws kills the quota/auth hooks behind it) and nothing may call `Y.encodeStateAsUpdate()` just to print a byte count (it serializes up to 20MB). Config is `LOG_LEVEL` / `LOG_FORMAT` / `LOG_DIR` / `LOG_HTTP` / `LOG_SLOW_MS` / `LOG_SLOW_QUERY_MS`; winston is silent under `NODE_ENV=test`, and since tests never import `server/index.ts`, the console interception never touches them.

**Frontend hosting (`server/frontend/`):** `attachFrontend(app, server)` registers a catch-all *after* the `/api` routes, so API routes always win and everything else falls through to the UI.
- `frontend/guard.ts` — the page gate, mounted by `app.ts` right after the `/api` routes and therefore *before* the frontend catch-all. Anything non-`/api` other than `/login`, `/favicon.ico` and `/vite.svg` needs a session: a document request (`Sec-Fetch-Mode: navigate` or `Accept: text/html`) gets a 302 to `/login?redirect=<path>`, everything else (`/assets/*.js`, dev's `/src/**` and `/@vite/*`, XHR) gets a bare 401 — never HTML in place of a script. It also owns `GET /login`

- `frontend/dev.ts` (dev only, dynamically imported so Vite never loads in prod) — `createServer({ root, appType: 'custom', server: { middlewareMode: true, hmr: { server } } })`. Vite's connect middleware chain is run against `c.env.incoming/outgoing` and the handler returns `RESPONSE_ALREADY_SENT`; if the chain calls `next()`, the SPA fallback renders `index.html` through `vite.transformIndexHtml`. `hmr.server` is what makes HMR ride the same port — with only `middlewareMode: {server}` Vite would still open port 24678
- `frontend/static.ts` (prod) — `serveStatic({ root: <staticDir relative to cwd> })` + `index.html` fallback for unknown paths

It has no `server.proxy` anymore because there is nothing to proxy to

**Build (`scripts/build-server.mjs`) — `output/` is a self-contained, runnable app directory.** `pnpm build` fills it with `public/` (frontend, from `vite build`), `server/index.js` (backend, esbuild bundle, ESM/node22), `prisma/` (schema only — no migrations), and — copied verbatim from `scripts/output-image/` — `prisma.config.js`, `Dockerfile`, `.dockerignore`, `README.md`. Copy `output/` anywhere and `npm install --omit=dev && npm run db:push && npm start` runs it; `docker build ./output` images it. No repo source needed.

**Yjs 协同 (`server/collab/`):** the same HTTP server also serves a Yjs sync endpoint at `ws://host:3000/ws/collaboration` (room name travels in the message, not the path); one room = one `Y.Doc`, held in memory only.
- `collab/hocuspocus.ts` — the collaboration server: [Hocuspocus](https://tiptap.dev/docs/hocuspocus) (`@hocuspocus/server`, MIT) mounted on our own HTTP server. We never call `listen()` (that would open a second port); instead we own the `upgrade` listener, take **only `/ws/collaboration`**, and hand it to crossws, which calls `handleConnection()`. Everything else — notably Vite's HMR socket (`vite-hmr`, path `/`) — we simply don't touch, and Node's multi-listener `upgrade` event delivers it to Vite's own listener; crossws registers no listener of its own, so "don't touch" really means untouched. This replaced a 282-line port of y-websocket's `bin/utils.js` that existed only because upstream `@y/websocket-server` statically imports `y-leveldb` → `leveldown` (no node 22/arm64 prebuild). **The room name travels in the message, not the URL** — that's also why the wire protocol is incompatible with y-websocket and the frontend must use `@hocuspocus/provider`.
- `collab/index.ts` — `attachCollabServer(server, { destroyUnmatchedUpgrades, authorize })`: a `ws` server in `noServer` mode; only `/ws/collaboration` upgrades are accepted. In dev `destroyUnmatchedUpgrades` is `false` — Vite's HMR socket rides the same `upgrade` event (protocol `vite-hmr`, path `/`) and killing unmatched sockets would break hot reload. `authorize` (wired to `auth/ws.ts`) checks the session cookie on the handshake and answers `401` + destroy when anonymous
- **Timings are constants in `hocuspocus.ts`, not env vars, because they are all derived from one fact: the server sends no heartbeat.** `timeout` is *not* a ping interval — Hocuspocus only compares "when did I last hear from this client". What actually holds the connection open is y-protocols' awareness replay: the client re-announces its local state every `outdatedTimeout / 2` = **15s** (`useFlowPresence` publishes on connect, so it always runs), and the server's awareness broadcast does **not** exclude the sender — so there is a 15s round-trip in both directions and a 60s reverse-proxy idle timeout (nginx / k8s Ingress defaults) is already covered without us sending anything. `timeout: 30_000` = two missed beats, matching the provider's own `messageReconnectTimeout` so both ends give up together; tighter than the 60s default because a dead connection still holds the exclusive-holder slot and a ghost cursor, and staying under the proxy's 60s means *we* notice first and run `onDisconnect` instead of the middlebox quietly cutting the tunnel. `REAUTH_INTERVAL: 20_000` is the **backstop** sweep, not the main path — see the revocation bullet below.
- `GET /api/collab/rooms` reports live rooms/connections; `GET /api/collab/health` is the **persistence health** endpoint alerting hangs off (REQ-RESILIENCE §4.5) — failed-store count, how long since the last successful store, write-queue depth, shared-layer status, and **the HTTP status code is the verdict** (200/503) so a `curl`-checks-the-code alert works without parsing JSON. Two judgement calls in it: `failed` is *observed*, not reported (see the logging section — the extension brackets the business hooks, so started-minus-completed is the failure count), and "hasn't stored in a while" is only unhealthy **together with a non-empty write queue**, because stores only happen when someone is editing — the time alone would fire every quiet night. Both endpoints sit behind the auth gate; opening `/health` up for Prometheus is a security-boundary change and deliberately not done here
- Frontend: `new HocuspocusProvider({ url: '/ws/collaboration' as absolute ws:// URL, name: room, document: doc })` — docs stay in memory, so a server restart drops all content

**单副本 / 多副本 (`server/cluster/`) — one image, two modes, picked by env.** Full write-up in `docs/14-clustering.md`. `CLUSTER_MODE` (`single` | `redis`) resolves exactly like `dbProvider`: explicit variable wins, else infer from whether `REDIS_URL` is set, else the zero-dependency default. **Database and Redis are configured independently** — neither infers the other; `assertClusterConfig()` rejects `redis` without a `REDIS_URL` everywhere (contradictory config), but `redis` + SQLite only *warns* in dev, because SQLite + Redis in one process is a legitimate way to exercise the Redis path locally. Production refuses it.
- The state that used to be module-level `Map`s — audit `seq`, quota marks, awareness clientID ownership, session-refresh mutex — is now three abstract classes in `cluster/shared.ts`: `SharedMap<V>` (`get`/`set`/`claim`/`entries`, TTL), `SharedCounter` (`next(key, seed)`), `SharedLock` (`run(key, task, {fallback})`). Two implementations, `memory.ts` (literally the old `Map`s) and `redis.ts` (`SET NX` / `INCR` / lock+Lua-release), run the same contract test suite (`server/test/cluster/shared.test.ts` — memory always, Redis when `TEST_REDIS_URL` is set). The backend also answers `health()` (surfaced as `clusterHealth()`), which is **synchronous and sends no network request** — it reads ioredis's own `status` field, because a health check must not hang when the thing it checks is slow; only `ready` counts as usable, since during `connecting`/`reconnecting` commands silently pile into the offline queue.
- **Every method is async even in the memory implementation** — otherwise wiring in Redis later would have meant changing every call site's signature. And **the factories return lazy proxies**: modules declare their tables at module top level (the way they used to write `new Map()`), but picking an implementation needs `await import('ioredis')`, which happens later in `initCluster()`. The proxy resolves against the current backend on first use, so swapping backends just bumps a generation counter.
- **`redis.ts` is dynamically imported**, like the two Prisma adapters in `db.ts` — a single-replica process never loads ioredis. Unlike the adapters, both packages stay in the built artifact: the image supports either mode, only the *database provider* is baked in at build time.
- Multi-replica collab is `@hocuspocus/extension-redis` (pub/sub for updates + awareness, redlock around `onStoreDocument` so only one instance actually writes, `afterLoadDocument` waits for a peer's in-memory state). **socketId gets an `instanceId:` prefix** — Hocuspocus's socketId is only unique within a process, and awareness ownership uses it to tell "is this clientID yours", so a collision would drop the rightful owner's updates as impersonation. No sticky session needed anywhere.
- **The same update fires `onChange` on *every* instance holding the room.** Nothing writes per-update rows today, but anything that starts to (webhooks, notifications, metrics) must filter on `transactionOrigin` and skip `source === 'redis'` — otherwise the side effect fires a multiple of the replica count (measured back when the audit table existed: two instances, 11 edits, 22 rows), and the forwarded copy carries no author `context` anyway. Unknown origin shapes should count as "act" — better one too many than losing the author's.
- **Quota is deliberately eventually-consistent**: `quotaLocked()` is called *synchronously* on every message, so it reads a local `Map`; the verdict is pushed to the shared layer fire-and-forget and pulled back on the byte-remeasure tick (1–5s). That matches what the quota already was — after-the-fact accounting, effective on the *next* message — not a synchronous gate.
- Local: bring up Redis/PostgreSQL yourself (commands are in `.env.example`; the scripts deliberately don't), then `pnpm dev` (single) or `pnpm dev:cluster` (`scripts/dev-cluster.mjs` spawns one `tsx watch` per port from `DEV_CLUSTER_PORTS`, overriding only `PORT` and `INSTANCE_ID` — **it contains no configuration**, everything else comes from `.env`). k8s: `k8s/deployment.yaml` (single, PVC, `Recreate`) or `k8s/variants/deployment.cluster.yaml` (`replicas: 3`, `RollingUpdate`, no PVC) — the two are one Deployment identity in two shapes, and **the variant deliberately lives outside `k8s/`**: ArgoCD syncs that directory non-recursively, so two manifests for `dev/shadecn-learning` sitting in it is a `RepeatedResourceWarning` with no guarantee which one wins. Switching is a git operation (copy the variant over `k8s/deployment.yaml` and commit) — applying it by hand gets reverted by `selfHeal` within seconds.

Frontend, `/api/*` and `/ws/collaboration` are same-origin in every mode, so frontend code should always use relative paths.

**Auth (`server/auth/`) — Keycloak OIDC, BFF style.** Full write-up in `docs/02-auth-keycloak.md`. The browser never sees a token: the authorization-code + PKCE exchange happens server-side, tokens live in SQLite, and the client only holds an httpOnly `sid` cookie.
- `auth/oidc.ts` — everything that talks to Keycloak: cached `.well-known/openid-configuration` discovery (endpoints are never hard-coded), PKCE `S256` helpers, `exchangeCode` / `refreshTokens` / `revokeRefreshToken`, RP-initiated `buildLogoutUrl`, and `verifyIdToken` — JWKS fetch (kid miss → one refetch) + `crypto.createPublicKey({format:'jwk'})` signature check for RS/PS/ES, then `iss` / `aud` / `azp` / `exp` / `iat` / `nonce`. No `jose`/`openid-client` dependency
- `auth/session.ts` — session lifecycle. The cookie holds a 32-byte random token; the DB row id is `HMAC-SHA256(SESSION_SECRET, token)`, so a database dump alone can't forge a cookie. `loadSession()` transparently refreshes an access token that is within 30s of expiry (concurrent refreshes for one session are deduped through an in-process promise map), so **the session is kept alive by traffic** — it only really expires once nothing has hit the server for long enough that the refresh token passes Keycloak's SSO Session Idle. `loadSession(token, { refresh: false })` is the read-only variant for callers that are *not* user traffic — currently just the collab server's periodic connection revalidation: it answers "still valid right now?" (a live refresh token counts) without renewing anything, and never deletes a row. A long-lived WebSocket must not be able to keep its own session alive. A failed refresh is **not** uniformly fatal: only a 4xx rejection from Keycloak (`invalid_grant` — logged out, idled out, kicked) destroys the session. Anything that proves nothing — connection refused, timeout, a 5xx, even a local DB write failure — keeps the session and retries on the next request, with a 15s per-session cooldown so a dead Keycloak doesn't make every request eat a timeout. `OidcError` carries `code` + `retryable` to make that call, and every outbound OIDC request has an 8s timeout (node's fetch has none by default). Deleting the session in the network-failure case is the bug this replaced: with a 60s access-token lifespan the refresh runs constantly, so one blip logged the user out. `sweepExpired()` drops timed-out sessions and unused auth requests
- `auth/middleware.ts` — `withSession` (parse, refresh, expose `c.get('user')`, clear a stale cookie; mounted on `*`, not just `/api/*`, because the page gate needs it too), `requireAuth` (401), `requireRole(...)` (403). Keycloak realm roles land in `User.roles` as-is, client roles as `clientId:role`
- `auth/ws.ts` — the same session check for WebSocket handshakes
- `auth/redirect.ts` — `safeRedirect()`, the shared in-site-only check for every `?redirect=`
- `routes/auth.ts` — `GET /api/auth/{config,me,login,callback,logout}`. `/me` always answers 200 (`{enabled, authenticated, user}`) so the router guard has no error branch. `state`/`nonce`/`code_verifier` live in the `AuthRequest` table keyed by a short-lived `oidc_tx` cookie and are consumed exactly once, so a replayed callback fails. `?redirect=` is restricted to in-site paths (`//evil.com` and `/\evil.com` fall back to `/`)
- When `KEYCLOAK_ISSUER`/`KEYCLOAK_CLIENT_ID` are unset, `authEnabled` is `false`: dev warns and lets everything through (so the demo pages still run without a Keycloak), production refuses to boot
- **`auth/profile.ts` — what a user gets *after* login, kept outside the login path.** `upsertUser` does one thing: pour the id_token claims into a `User` row. "And now give this person a default avatar / display name / timezone" is a different, ever-growing concern, so it hangs off the side: `registerProfileHook({name, fill})` adds a rule, `completeUserProfile(user)` runs them all in the callback (and in `auth/project.ts`'s dev-user path, so the no-Keycloak local mode gets the same treatment). Each hook only answers "what's missing" and the mechanism merges the answers into **one** update; a hook that throws is logged and skipped — it must never block a login. **It runs on every login**, which is what backfills existing users: no migration script, and no fallback logic scattered across the read paths. Adding a rule = one new file + one `registerProfileHook`; login code stays untouched.
- **`server/avatar/` — the one hook there is today: no avatar → an identicon.** GitHub-style pixel blocks, generated by [minidenticons](https://github.com/laurentpayot/minidenticons) (MIT, dependency-free). Keycloak's `picture` always wins; the hook only fills the empty ones. **No image is stored**: the DB holds `/api/avatars/<seed>.svg` and `routes/avatars.ts` renders it on demand — no DB read, no notion of who's asking, so it's served `immutable` for a year. The seed is `sha256(issuer + "\n" + subject)` truncated to 16 hex — keyed on `(issuer, subject)` rather than `user.id` so the picture survives a rebuilt database, hashed so a subject never rides in an image URL. The route module is also what *installs* the hook (it imports `avatar/index.ts`), so mounting the route and having default avatars are the same one line in `app.ts`. Wherever a stored avatar is displayed, put a round background under it (`bg-muted` / `bg-sidebar-accent`) — the identicon is transparent-backed, and without it the blocks float on the page instead of sitting in the same circle the no-avatar fallback draws

**Database (`prisma/models.prisma`, SQLite *or* PostgreSQL):** `User` (unique on `(issuer, subject)`, roles as a JSON string), `Session`, `AuthRequest`; plus `Project`, `ProjectMember` (unique on `(projectId, userId)` — the creator's admin row is written for real, never inferred from `createdById`), `ProjectInvite` (the project's one share link — `projectId` is unique; token stored in the clear: it *is* the credential you hand out; unlimited uses, `expiresAt` is the only gate, and "reset" just swaps the token in place), `Flow` (`ydoc` = the Yjs state as bytes and **the source of truth for content**; `graph` = a JSON projection the server derives from it for list counts and previews; `revision` = a monotonic write counter, *not* a lock), and `FlowUserState` (per-user view state, unique on `(flowId, userId, key)` — one row per state partition, value is a JSON string; `viewport` is the first partition and adding another one is a new key, not a migration). Prisma 7 requires a driver adapter — `@prisma/adapter-better-sqlite3` or `@prisma/adapter-pg`, picked in `server/db.ts` — and the client is generated as TypeScript into `server/generated/prisma` (gitignored, `@ts-nocheck`'d, eslint-ignored) rather than into `node_modules`, so it survives `pnpm prune --prod` and gets inlined into the server bundle. `prisma.config.ts` is the CLI config and delegates to `prisma/db-provider.mjs` so the CLI and the server always open the same database: the DB lives at `$DATA_DIR/app.db` (`DATA_DIR` defaults to `<repo>/data`, gitignored), `DATABASE_URL` overrides it outright, and relative `file:` paths in either resolve against the repo root — not the cwd. Both sides `mkdir -p` the parent directory, since better-sqlite3 won't create it.

**Two databases, one model file (`docs/05-data-persistence.md`).** Which one you get is `DB_PROVIDER` (`sqlite` | `postgresql`), or — when unset — the scheme of `DATABASE_URL` (`file:` vs `postgres(ql)://`), defaulting to sqlite. A `DB_PROVIDER` that contradicts the URL's scheme, an unknown value, or `postgresql` with no `DATABASE_URL` all **throw at startup** rather than guessing. That resolution exists twice on purpose: `prisma/db-provider.mjs` (CLI side — `prisma.config.ts`, `scripts/*.mjs`) and `server/config.ts` (`dbProvider` / `databaseUrl`), because `server/` is a separate TS project that can't import a repo-root `.mjs`. Change one, change the other.
- **One copy of the models, two provider dirs — via multi-file schema + a symlink.** Two schemas are unavoidable: `datasource.provider` takes only a literal (`env()` is rejected, the 2.2-era `provider = [...]` array was deprecated, and "make it dynamic" is closed upstream), and one schema can hold only one datasource. But the *models* live once: `prisma/models/{auth,canvas}.prisma` are the only hand-written model files, and `prisma/sqlite/` + `prisma/postgresql/` each contain a 10-line `schema.prisma` (generator + datasource) plus a **`models` symlink pointing at `../models`**. `prisma.config.ts` points `schema` at the *directory*, and Prisma's multi-file schema merges everything in it — so the only difference between the two providers is one `provider = "…"` line. No generated schema files, therefore no drift and no guard script. Notes: Prisma 7 forbids `url` inside a datasource (it lives in `prisma.config.ts`), which is why the block is down to one line; the `generator` must sit in the directory's own `schema.prisma`, so those 4 lines are duplicated; **keep the models provider-agnostic** (no `@db.*` native types, arrays, `Json`, enums) so the two generated clients stay type-identical and business code never forks. **This depends on symlinks** — no native Windows (use a dev container / WSL); `COPY prisma ./prisma` preserves the relative link (verified inside a container), but `scripts/build-server.mjs` copies with `dereference: true` so the *artifact* gets real files, and `scripts/output-image/prisma.config.js` must point `schema` at the **directory** too — pointing it at `prisma/schema.prisma` makes Prisma read that one file, see zero models, and conclude "schema empty, database empty, already in sync", producing a **0-byte database with no tables** (hit this once).
- **There are no migration files.** Schema changes go in via `prisma db push` — no `prisma/migrations/`, no `_prisma_migrations` table, no `migrations` key in `prisma.config.ts`. Dev, tests and the container all take the same path: `pnpm dev` runs `db:push` first, and the image's `CMD` is `npx prisma db push && node server/index.js`. The reason migrations were dropped: they would have to be written **twice**, and not as a wording difference — `migration.sql` is plain DDL generated per provider with no runtime translation, each directory's `migration_lock.toml` pins its provider so the two histories can never merge, and the dialects genuinely differ (`BLOB`/`BYTEA`, `DATETIME`/`TIMESTAMP(3)`, inline foreign keys vs a separate `ALTER TABLE ADD CONSTRAINT`). Worst of all, **SQLite cannot alter or drop a column**: a "drop 5 columns, add 1" change is one `ALTER TABLE` on PG but a full table rebuild on SQLite (`new_` table → copy → `DROP` → `RENAME`). That double bookkeeping only pays for itself when there is production data to carry forward, and there isn't. **The costs, which are real**: no history of schema changes and no rollback scripts; and a destructive change (rename/retype/drop) makes `db push` refuse unless `--accept-data-loss` is passed. Both Dockerfiles and the artifact's `db:push` script deliberately omit that flag — better a failed container start than silent data loss — so assess whether a model change is destructive *before* shipping it. Locally that refusal is just friction (the data is throwaway), so there is one escape hatch: **`pnpm db:push:force`**. It stays a *separate command* rather than a flag on `pnpm dev`, because the whole point of the refusal is that a human sees it once — wiring it into the dev server's startup would drop a column on every save-and-restart and nobody would ever read the line. Prisma 7's `db push` does not generate the client (and has no `--skip-generate`), so `db:generate` stays a separate step.
- **The one behavioural difference that needed code**: SQLite's `LIKE` is case-insensitive for ASCII, PostgreSQL's isn't. `server/store/text.ts`'s `nameContains()` adds `mode: 'insensitive'` on PG only (the type assertion in there is load-bearing — `mode` doesn't exist in the sqlite client's `StringFilter`). Any new keyword search goes through it instead of writing `{ contains }` inline.
- **A build artifact is bound to one provider**: the generated client compiles in one query engine, so `pnpm build` follows the build-time `DB_PROVIDER`, `build:server` refuses to run if the generated client disagrees, and the unused adapter is dropped from `output/package.json` (which is why `server/db.ts` imports both adapters *dynamically* — a static import would survive as a top-level require of a package prod never installs).

**Deploy:** two paths to the same image. `pnpm build && docker build ./output` uses the Dockerfile the build drops into `output/` (deps stage: `npm install --omit=dev` off `output/package.json`, compiling better-sqlite3; runtime stage: those `node_modules` + the artifact, `WORKDIR /app`, `prisma db push` then `node server/index.js`). The repo-root `Dockerfile` is the from-source variant: a build stage that runs `pnpm build`, then the exact same deps + runtime stages over `/app/output` — keep the two in sync (edit `scripts/output-image/Dockerfile`, not `output/`). Only the deps stage runs on the target platform, so better-sqlite3 compiles for the right arch. `NODE_ENV=production`, `HOST=0.0.0.0`, port 3000; no source, no pnpm, no tsx in the runtime image. nginx is gone — the Node server serves `public/` itself. The build stage installs `python3 make g++` because better-sqlite3 has no musl prebuild.
- **Both runtime stages end with a loop that `process.dlopen`s every `*.node` under `node_modules`, and both must keep it.** A native module of the wrong architecture does not stop the container from booting: Node dlopens it only on the first `require`, and `/api/health` never touches the database — so readiness stays 200, the Deployment reports `1/1 Available`, and only real requests 500 with `Error relocating …/better_sqlite3.node: unsupported relocation type 1026`. That is exactly what shipped once, and the cause is the one to remember: **a single-arch base-image tag plus QEMU binfmt makes pulling the wrong architecture completely silent.** Harbor's `library/node:22-alpine` is an arm64-only image someone pushed by hand; `buildah bud --platform linux/amd64` can only fall back to the arm64 manifest, binfmt runs every `RUN` without complaint, and that round installs an aarch64 `.node` into an image labelled amd64. Never read "the build succeeded" as "the architecture is right" — verify a base image with `uname -m` on an amd64 node before adopting its tag. Three independent guards, all in the Dockerfiles: one **multi-arch** reference shared by all stages (`192.168.68.95:31443/docker.io/library/node:22-alpine` — *not* `harbor-core.harbor.svc/library/node`), `ARG TARGETARCH` compared against `process.arch` in the deps and runtime stages, and the dlopen loop as the catch-all. Loop over `*.node` rather than `require('better-sqlite3')`: a postgresql artifact doesn't ship that package. `docs/12-deployment.md` §2.5.1 has the full write-up.

SQLite lives on a volume at `/app/data` (`DATA_DIR=/app/data`); `k8s/deployment.yaml` adds a PVC + auth Secret, targets container port 3000, and stays at `replicas: 1` with `strategy: Recreate`. **Two probe paths, and the split is load-bearing**: liveness/startup hit `/api/health` (shallow — touches no dependency), readiness hits `/api/health/ready` (checks database + shared layer). They fail in opposite directions — a failed readiness drains the Pod from the Service, a failed liveness *restarts the container*, and restarting fixes nothing about a database outage while killing a process that is still holding unstored Y.Doc content. So liveness must stay shallow; a test pins that `/api/health` never touches the database. `terminationGracePeriodSeconds: 60` plus a `preStop: sleep 5` (k8s removes the endpoint and sends SIGTERM **in parallel**, so without the sleep a dying Pod still accepts new WebSocket handshakes), matched on the app side by `SHUTDOWN_FLUSH_TIMEOUT` (20s) around the flush — an unbounded flush against a black-holed database means SIGKILL at the grace deadline, which loses both the write *and* the clean exit. A PostgreSQL image is the same two commands with `DB_PROVIDER=postgresql` set for both `db:generate` and `build` (see the database section — the artifact is provider-bound); on the k8s side that drops the PVC and moves `DATABASE_URL` into the Secret. Going past one replica additionally needs `CLUSTER_MODE=redis` + `REDIS_URL` — that's `k8s/variants/deployment.cluster.yaml` (`replicas: 3`, `RollingUpdate`), see the cluster section above. The *image* is mode-agnostic; only the database provider is baked in.

**Tests (Vitest, `vitest.config.ts`):** two projects in one config — `server` (node env, `server/test/**/*.test.ts`) and `client` (jsdom env + the `vue` plugin and `@/` alias, `src/test/**/*.test.ts`). Both are hermetic: each setup file replaces `globalThis.fetch` with a stub that *rejects*, so any test needing the network must `vi.stubGlobal('fetch', …)` — nothing ever reaches a real Keycloak.
- **Backend.** `server/test/global-setup.ts` wipes `data/test/` and runs the real `prisma db push` against it once per run, so the test schema is built the exact same way production's is; `fileParallelism: false` keeps the shared database safe. Point `TEST_DATABASE_URL` at a PostgreSQL connection string and the same suite runs there instead (`server/test/paths.ts` derives the provider from it) — the PG branch adds `--accept-data-loss` (it can't delete a file, so db push has to be allowed to drop mismatched tables/columns), which is why it must be a dedicated test database — SQLite doesn't need the flag since the whole directory is deleted each run. Since the generated client is provider-bound, global-setup compares its `activeProvider` and re-runs `generate` only when it doesn't match — **and restores the previous provider in its teardown**, because there is only one `server/generated/prisma/` and that generate is destructive: a developer whose `.env` says `postgresql` runs the (sqlite-by-default) suite, and from then on `pnpm dev` picks `adapter-pg` off `.env` and meets a sqlite client — `PrismaClientInitializationError: The Driver Adapter … is not compatible with the provider`. `tsx watch` never heals from it either; every file save just replays the same crash until someone runs `pnpm db:generate` by hand. The cost of the restore is two `generate`s per run for cross-provider developers; pointing `TEST_DATABASE_URL` at a dedicated PG test database removes the switch entirely, which is what a PostgreSQL developer should do. Environment comes entirely from `test.env` in `vitest.config.ts`, and `server/env.ts` is aliased to `server/test/stubs/env.ts` so the developer's own `.env` (real issuer, real client secret) can never leak into a test run.
- **`TEST_*` is the one exception, and `server/test/paths.ts` has to read `.env` itself to honour it.** Vitest only loads `.env` *after* the config is resolved, but `vitest.config.ts` imports `paths.ts` at the top level — so a `TEST_DATABASE_URL` written into `.env` is read too late and the whole run silently stays on SQLite (tables appear in `data/test/app.db`, the PG database you thought you were testing keeps zero relations). `loadTestEnv()` therefore calls `process.loadEnvFile()` on the repo-root `.env` and then **deletes every key it introduced that isn't `TEST_`-prefixed**, so the isolation above still holds; `loadEnvFile` doesn't overwrite existing variables, so a command-line `TEST_DATABASE_URL=… pnpm test:server` still wins.
- **Prisma 7 refuses `db push --accept-data-loss` when it detects it was invoked by an AI agent**, so global-setup's PG branch fails under Claude Code until the user consents and `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION` carries the exact text of their consent message. Pass it on the one command (`PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION="…" pnpm test:server`) — **never** bake it into `global-setup.ts` or `.env`, which would disable the guard for everyone, permanently. A developer running `pnpm test` in their own terminal never hits it. Helpers: `helpers/db.ts` (`resetDb`, `createUser`), `helpers/session.ts` (`signIn` → a ready-to-use `sid` cookie), `helpers/project.ts` (`actor()` → a logged-in browser with `request`/`json` bound to its cookie, plus `createProject` / `createFlow` / `joinViaInvite`), `helpers/oidc.ts` (a fake Keycloak: discovery/JWKS/token/end_session over a stubbed `fetch`, plus a real RSA keypair so `verifyIdToken` is exercised for real). Routes are driven through `app.request()` — the full middleware stack, not mocked handlers.
- **Module-level caches.** `config.ts` (env → consts), `oidc.ts` (10-min discovery/JWKS cache) and `lib/auth.ts` (session singleton) all freeze state at import, so tests that need a different world use `vi.resetModules()` + a dynamic `import()`. `server/test/routes/auth.test.ts` has a `freshApp()` helper for exactly this.
- **Frontend.** `src/test/` covers `lib/utils`, `lib/auth` (the whole `fetchSession`/`apiFetch` contract), the `prompt-input` editor core (`serialize` round-trips + `operations` transforms/undo/batch/muteHistory) and the component itself (`PromptInput.test.ts`: one `<div data-block-path>` per line, the `FEFF`+`<br>` zero-width invariant, and `repairLeafPlaceholders` healing a DOM the browser broke), the real router guard (`@/router` with `/api/auth/me` stubbed), the router guard's full-page bounce to `/login`, and `stores/flow` (`flow.test.ts`: the Y.Doc projection — writes land in the doc, a second `Y.Doc` stands in for a peer so concurrent edits to *different fields of the same node* are shown to merge, undo is proven to skip the peer's changes, and the viewport is proven not to enter the doc; `presence.test.ts`: the pure occupancy/arbitration logic without a socket). `server/test/frontend/guard.test.ts` covers the page gate itself (302 vs 401, the rendered login page, escaping).
- **Component tests** (`src/test/views/`, `@vue/test-utils` + jsdom) mount the real view with only `@/lib/api` stubbed — shadcn-vue and reka-ui run for real, because that's where "clicked it, nothing happened" bugs live. `ProjectHome.test.ts` pins the confirm dialogs: **`AlertDialogAction` closes the dialog *before* the forwarded `@click` runs**, so a confirm dialog needs two refs — one for `open`, one for "which item" — or the handler reads a target that close already cleared and the request is silently never sent. In jsdom: menus/dialogs teleport into `document.body` (not the wrapper), `DropdownMenuTrigger` opens on `click` while `TabsTrigger` switches on `mousedown`, and `PointerEvent` + pointer-capture need stubbing.

**Dependencies — `dependencies` is exactly the production runtime set, everything else is `devDependencies`.** The frontend is bundled into `output/public` and the backend into `output/server/index.js`, so vue/three/tailwind/reka-ui/`@hocuspocus/provider`/`y-protocols`/`lib0` and the whole toolchain (`vite`, `esbuild`, `tsx`, `vue-tsc`, eslint, vitest) are build-time only. `dependencies` holds just the packages the server bundle still needs at runtime: `hono` + `@hono/node-server`, `@hocuspocus/server` + `crossws` + `yjs` (collab server — crossws vendors its own `ws`, so we no longer depend on it directly), `@prisma/client` + both driver adapters (`@prisma/adapter-better-sqlite3`, `@prisma/adapter-pg` — the repo needs both, any one build artifact keeps only one), `ioredis` + `@hocuspocus/extension-redis` (multi-replica mode; both stay in the artifact because the mode is an env switch, not a build flag), `minidenticons` (default avatars are rendered per request, so it is runtime, not build-time), `winston` (the logging layer, see above — it is imported by `server/index.ts`'s very first side-effect import), and the `prisma` CLI (the container runs `prisma db push` at startup). `scripts/build-server.mjs` enforces this: if a package the bundle imports is only in `devDependencies`, the build fails. So when a tool (e.g. the `shadcn-vue` CLI) adds a frontend package to `dependencies`, move it to `devDependencies`.

**Key libraries:** `reka-ui` (headless UI primitives behind shadcn-vue), `@vueuse/core`, `class-variance-authority`, `vue-router` 5, `pinia` (only the flow editor's store) and `vue-sonner` (toasts) on the frontend; `hono` on the backend; `vite` for dev middleware + the frontend build; `tsx` only for `pnpm dev`.

## Conventions

- TypeScript strict mode with `noUnusedLocals`, `noUnusedParameters`, `erasableSyntaxOnly`
- All Vue components use `<script setup lang="ts">`
- Package manager: pnpm. New packages go to `devDependencies` unless the *server* imports them at runtime (see the dependency split above)
- Tests live in `server/test/` and `src/test/`, mirroring the directory they cover (`server/test/routes/auth.test.ts` ↔ `server/routes/auth.ts`). Imports inside `server/test/` keep the explicit `.ts` extension like the rest of `server/`.
- Vitest globals are **not** enabled — import `describe`/`it`/`expect`/`vi` from `vitest` explicitly.
- Test names are written as the behaviour being constrained ("未登录 → 401"), not as the function being called.
- **Time is UTC everywhere except on screen.** Prisma stores `DateTime` as an epoch value (UTC by construction) and every store maps rows out through `toISOString()`, so the wire format is always an ISO string with `Z` — never a pre-formatted, timezone-less string. The frontend never formats a date inline: `src/lib/format.ts` is the only place that builds an `Intl.DateTimeFormat`, and by default it follows the browser (`navigator.languages` for the locale, the runtime default for the timezone) rather than a hard-coded `zh-CN`. Use `formatDateTime` / `formatDate` / `formatTime`, or `formatWith(value, options)` for another granularity; all four take a string/number/`Date`/null and render `-` for anything unparseable.
  - **What "follows the browser" means is now a preference, not a constant** — `src/lib/preferences.ts` (a `useStorage` under `app:display-preferences`, browser-local, never sent to the server) holds locale / timeZone / dateStyle / timeStyle / hourCycle, every one of them defaulting to `AUTO` = follow the browser, which is why turning the setting page on changed nothing about existing output. `format.ts` reads the **reactive** `resolvedDisplayPreferences`, so changing a setting re-renders every already-displayed date with no reload and no per-page wiring. Two rules: a **caller-supplied option always wins** (`formatWith(v, { timeZone: "UTC" })` stays UTC no matter the preference — the preference only fills in what the caller didn't say), and the stored value is **validated on read** against a whitelist (localStorage is user-editable, and a misspelled `dateStyle` makes `Intl` throw `RangeError` and takes the page down). The UI is `src/views/Settings.vue`.
- **On the canvas's own path, time is a *number* — UTC epoch milliseconds, not an ISO string** (`FlowNodeData.createdAt`, `FlowEdgeData.createdAt`). Numbers compare directly with no timezone, format, or parse step in between, and they ride inside the Y.Doc where a formatted string would be dead weight. Don't build ordering on them across clients: these are stamped by whichever browser created the element, so two clients' clocks are two clocks.
- **One click, one request — every write-side interaction goes through `src/composables/useAsyncAction.ts`.** `const { run, pending } = useAsyncAction(fn, { errorMessage })`: `run()` records the action as pending **synchronously**, before the request is even sent, so a second click in the same event-loop turn is dropped on the spot; the template binds `pending` for the visual half (`<Button :loading="pending">`). The guard has to live in the handler, not in the markup — `:disabled` only takes effect on the next render, and half the entry points (`@keydown.enter`, `DropdownMenuItem @select`, an `@blur` that fires alongside an Enter-submit, `AlertDialogAction`) have no button to disable at all. `run` never rejects, so `@click="submit()"` leaves no unhandled rejection; errors go to `toast.error(err.message ?? errorMessage)` unless `onError` is given, which is why the wrapped action bodies carry no `try/catch`. Lists pass `key: (item) => item.id` so each row locks on its own. **Write `@click="submit()"`, not `@click="submit"`** — the latter hands the MouseEvent to the action as its first argument. Reads are deliberately *not* in scope: dropping a duplicate list load would strand the list on stale parameters.
- **Client-generated ids go through `src/lib/id.ts`'s `createId(prefix)`** — `<prefix>_<base36 timestamp>_<random>`. The timestamp prefix keeps ids roughly sortable by creation; the random tail is the part that matters: two clients can add a node in the same millisecond, and a counter-based suffix (`nodes.length`) would hand both the same id and merge them into one object on sync.
