# REQ-AGENT-HITL Agent 人机交互：提问、审批与等待确认

> 状态：**规划中**。
>
> 前置：[REQ-AGENT](20-agent-canvas.md)（画布 agent、会话、任务列表推送、只读查看别人的会话）、
> [REQ-AGENT-SANDBOX](22-agent-sandbox.md)（runner / 网关 / Grant；本篇是它 §9 第 5 期「等待决策与恢复」的需求）、
> [REQ-AGENT-SKILL](23-agent-skills.md)（工具按技能组织）。
>
> 本需求补三件事：**agent 能向发起人提问（带可选项）和请求审批；发起人迟迟不答、甚至关掉浏览器，
> 待确认的操作也作为会话里的一条消息留着，下次打开照样能答、答完 agent 接着干；
> 在项目画布上，这条「等你确认」只推给该回答的那个人。**

## 1. 目标与背景

### 1.1 现状

现在的画布会话**没有任何人机交互**：

- 工具集里没有提问 / 确认类工具；对话流（`@shadecn/shared/agent` 的 AG-UI 子集）只有 `RUN_*`、`TEXT_MESSAGE_*`、`TOOL_CALL_*`
  和三种 CUSTOM（`agent.user-message`、`agent.canvas-change`、`agent.skill-loaded`），没有「等待输入」类事件。
- 模型想问用户，只能用文字问，然后这一轮以 `RUN_FINISHED(success)` 结束、沙箱回收；用户的回答是下一轮 run。
  模型给不出可点的选项，用户也分不清「它在问我」还是「它说完了」。
- 运行期间输入框禁用，只有「停止」（= 杀沙箱）；[REQ-AGENT](20-agent-canvas.md) F7 的「追加指令」未实现。
- 文档里已经要求、但没做的确认：REQ-AGENT §3.9 ② / 验收 8「单 run 删除超过阈值时暂停并等待确认」（现在超额只回给模型一个错误）、
  §7 第 10 条「删除执行中的占位节点是否先确认」；REQ-AGENT-SANDBOX §2 原则 6「决策与高风险确认必须由用户会话提交，run 凭证永远不能自我审批」。

### 1.2 参考：pi 的做法

底层的 `@earendil-works/pi-agent-core` 只是 agent 循环，**没有 UI 概念**；可用的挂钩是 `beforeToolCall`（`{ block, reason }` 拦一次调用）、
工具结果的 `terminate`、`steer()` / follow-up 队列和 `AbortSignal`。交互在上层 `pi-coding-agent`（仓库 `earendil-works/pi`）里：

| pi | 形式 | 说明 |
|---|---|---|
| `ctx.ui.select / confirm / input / editor` | 阻塞对话框 | 在工具 `execute` 或钩子里 `await`，**这一轮不结束**，答复作为工具结果直接回到模型；可带 `timeout`（到点取默认值，界面显示倒计时） |
| `ctx.ui.notify / setStatus / setWidget / setEditorText` | 不阻塞 | 提示、状态栏、输入框上方的文字块、往输入框预填 |
| `question` 示例工具 | 单问题 + 选项 | 选项带 `description`，末尾固定一项「Type something.」切到内联输入；结果回给模型 `User selected: 2. xxx` / `User wrote: …` / `User cancelled`；对话里显示 `✓ 2. xxx` |
| `questionnaire` 示例工具 | 多问题 | 每问 `id` / `label`（标签栏）/ `options` / `allowOther`，标签栏切换 |
| `permission-gate` 示例 | 执行前审批 | `tool_call` 钩子里 `select(["Yes","No"])`，拒绝 → `{ block: true, reason }` |
| `qna` 示例 | 把文字提问变成待填模板 | 从上一条回复抽出问题，以 `Q:` / `A:` 填进输入框 |
| `plan-mode` 示例 | 规划后确认执行 | 只读规划 → `select("Execute the plan" …)` → widget 显示步骤进度 |
| RPC 模式 `extension_ui_request` / `extension_ui_response` | 非终端前端的子协议 | 请求带 `id`，前端回 `value` / `confirmed` / `cancelled`；`custom()` 在 RPC 下不可用 |
| `pi-durable` | 持久化等待 | checkpoint + `waiting` 状态，进程重启后恢复 |

本需求照 pi 的 RPC 子协议设计交互，**但有两处必须不同**：

1. **提问与等待在服务端（网关），不在 runner。** runner 不可信（REQ-AGENT-SANDBOX §2 原则 6），弹不弹、谁答了、答了什么都由服务端判定。
2. **pi 的对话框只活在进程里，关掉终端就没了；这里的待确认必须落库**，人不在时 run 挂起、沙箱回收，人回来答了再恢复（§3.4）。

## 2. 名词

| 名词 | 含义 |
|---|---|
| **交互**（interaction） | agent 一轮里发出的、需要人回应的一次请求。有 id、类型、应答人、状态，落库，是会话里的一条消息 |
| **提问**（ask） | 模型主动发起：调 `ask_user` 工具，带一个或多个问题与可选项 |
| **审批**（approval） | 服务端规则发起：高风险的工具调用执行前拦下，等人批准 / 拒绝。模型不能自己发起，也不能跳过 |
| **应答人** | 唯一有权回应这条交互的人：这一轮的**发起人**（§3.3） |
| **热等待** | 一轮 run 还活着（沙箱在、工具调用挂在网关上）等答复；答了模型在同一轮里接着做 |
| **挂起** | 热等待超时，run 以「等待中」结束、沙箱回收；交互留在会话里等应答 |
| **恢复** | 应答人回应一条挂起的交互后，服务端在同一会话里起新的一轮，从那次工具调用接着做 |

## 3. 方案

### 3.1 交互的种类

**提问 `ask_user`**（新增工具，属于 `canvas` 技能，见 REQ-AGENT-SKILL §4）：

- 参数：`questions: [{ id, label?, prompt, options: [{ label, description? }], allowOther?, multiSelect? }]`，一次 1–4 个问题，每题 2–6 个选项。
  `allowOther` 默认 `true`：选项末尾固定一项「其他…」，选中后出现输入框自由作答。
- 结果回给模型：每题一行，`<id>: 选了「xxx」` / `<id>: 自填「…」` / `<id>: 未回答`；整体取消为「用户取消了提问」，超时挂起后恢复的答复同样格式（§3.4）。
- 单独成批（同一条 assistant 消息里还有别的工具调用就拦下 `ask_user`，别的照常执行）—— 和 `load_skill` 一样，否则一批里提问之后的工具在人回答之前就已经执行了。
- **次数照 pi 的默认行为，不另设上限**：一轮 agent loop 里可以多次调用、问多轮问题（问完根据答复再追问），导演台里的会话同样可用；只受一轮已有的上限约束（轮次 `maxTurns`、工具调用次数），每次提问各占一次工具调用。热等待的总时长另有上限（§3.4 ①）。
  单独成批是相对 pi 唯一的偏离：pi 的 `question` 是 `sequential`，同批里排在它后面的工具会在答复之后执行，但它们是模型**没看到答复时**就定下的；而且挂起时这些排队的调用无处安放。
- 系统提示要求：能自己从画布读到的不要问；只在有多种合理做法、或缺少无法推断的信息时问；问题要能用选项回答。

**审批**（服务端规则，模型不可见、不可绕过）：

| 触发 | 审批卡片上列出 | 批准后 | 拒绝后 |
|---|---|---|---|
| 一轮的删除数将超过阈值（REQ-AGENT §3.9 ②） | 要删的节点 / 连线（名字 + 类型，可点击定位） | 这次调用执行，本轮阈值按批准的数量放宽 | 回给模型「用户拒绝了这次删除」，不执行 |
| 删除执行中的占位节点 —— **仅在执行等级为「谨慎」时**（§3.1.1） | 占位节点与它在跑的任务 | 执行 | 同上 |

审批在**服务端执行工具前**拦下（包工具做 `authorize` 的同一层），不放在 runner 的 `beforeToolCall`。以后新增的高风险操作按同样方式加一行触发规则，并写明它在哪些执行等级下生效。

#### 3.1.1 执行等级

「哪些操作要先问人」不写死，按会话的**执行等级**决定。一部分由服务端规则强制（审批），一部分交给 agent 自主判断（用 `ask_user` 提醒）：

| 等级 | 删除超过单轮阈值 | 删除执行中的占位节点 | 其他有风险的操作（覆盖用户写的内容、大范围移动 / 重排、删除带素材的节点…） |
|---|---|---|---|
| **谨慎** | 审批（强制） | 审批（强制） | 系统提示要求 agent 动手前先 `ask_user` |
| **平衡**（默认） | 审批（强制） | agent 自主：用户没明确要求删它时，先 `ask_user` 提醒「它的任务还在跑，删了会白跑」 | agent 自主判断是否先问 |
| **自主** | 审批（强制） | 直接执行，在回复里说明删了什么 | 直接执行；只在缺少无法推断的信息时问 |

- **删除超过单轮阈值在所有等级都审批**：那是 REQ-AGENT §3.9 ②「靠规则而非模型自觉」的安全线，等级只调它之外的部分；阈值本身也不随等级变。
- 「自主判断」的依据要让 agent 看得到：`read_canvas` / `get_node` 的结果里标出节点有执行中的任务（`data.status`，REQ-AGENT §3.6）、带素材、最近被人改过；当前等级与对应的规则写进系统提示。
- 等级随**会话**保存，在输入框旁切换，改了从下一轮起生效（进行中的那一轮不变）；新会话的默认值取用户人设里的偏好（REQ-AGENT §3.10.5「删除前是否先确认」，人设未实现时为「平衡」）。项目画布上别人只读查看时能看到这个会话的等级。
- 等级只影响「先不先问」，不扩大权限：工具白名单、删除阈值、配额、Grant 都与等级无关。
- **项目最低执行等级**：项目画布上，每个项目有一个「会话最低执行等级」，会话实际生效的等级取「会话等级」与「项目最低等级」中更严的那个（谨慎 > 平衡 > 自主）。本期只有默认值「自主」（= 不额外约束），**不露出设置界面**；数据与判定先做好，以后加界面时不改规则。会话里切到比项目最低等级更宽的档位时，输入框旁显示实际生效的等级并说明原因。个人画布没有项目，不适用。

**通知**（不阻塞，优先级低）：只在对话里显示一行提示，不等回应；本期可不做。

### 3.2 对话里的样子：交互是一条消息

交互作为会话的一种消息（与用户消息、assistant 消息、画布改动、技能加载并列）**落库**，出现在它所在那次工具调用的位置。
刷新、关浏览器再打开、换一台设备打开，看到的都是同一张卡片和同一个状态。

**卡片内容：**

- 提问：问题正文；选项（标签 + 灰字说明），单选为单选组、`multiSelect` 为多选；「其他…」+ 输入框；多题时用标签切换，标签上标出已答 / 未答；底部「提交」「不回答」。
- 审批：一句话说明（「助手想删除 8 个节点，超过了单轮 5 个的上限」）、受影响元素列表（可点击在画布上定位并高亮）、「批准」「拒绝」。

**状态（卡片上显示，落库）：**

| 状态 | 卡片 | 能否操作 |
|---|---|---|
| 等待回答 · 热等待 | 高亮边框 + 剩余时间倒计时（「助手在等你回答，2:00 后暂停」） | 应答人可答 |
| 等待回答 · 已暂停 | 「助手已暂停，回答后继续」+ 等了多久 | 应答人可答，答完自动继续（§3.4） |
| 已回答 | 只读，选中项打勾，自填内容原样显示；审批显示「已批准 / 已拒绝」+ 时间 | 否 |
| 已跳过 | 应答人没答、直接发了新消息（§3.4） | 否 |
| 已取消 | 应答人点了「不回答」，或这一轮被停止 | 否 |
| 已过期 | 挂起超过保留期限（§7） | 否 |
| 已失效 | 应答人失去这张画布的权限 / 画布或会话被删 | 否 |

**输入框：**

- 热等待中，提问卡片在等答复时，输入框提示「回答上面的问题，或直接输入」—— 发送的内容当作「其他」作答（对多题提问，作为整体补充说明）。
  审批在等时输入框禁用，只能批准 / 拒绝 / 停止。
- 挂起中，会话不在跑（不挡发送，REQ-AGENT §3.10.5）：直接发新消息 = 跳过这条交互（§3.4）。
- 别人的会话（项目画布只读查看）：卡片同样显示，但没有任何按钮，写「等待 张三 回答」/「张三 已选择 …」。

### 3.3 谁能回应

- **应答人 = 这一轮的发起人。** 一条交互只有一个应答人，记在交互上。
- 只认应答人自己的用户会话提交（REQ-AGENT-SANDBOX §2 原则 6）：run 令牌调回应接口一律拒绝；别的成员 403。
- **项目管理员不能代为回答或审批。** 管理员能做的仍只是中止那一轮（REQ-AGENT §3.8.4），中止会把交互标为「已取消」。
- 应答人在多个标签页 / 设备上同时打开：**先到先得**，第二个提交得到「这条已经回答过了」，卡片刷新成已回答。回应接口要求带交互 id，一条交互只能被回应一次。

### 3.4 等待、挂起与恢复

一条交互从发出到了结分两段：

**① 热等待（在线时）。**

- 网关收到 `ask_user` / 触发审批后，**先落库**这条交互（状态「等待回答」），再在事件流上发出，然后挂起那次工具调用。
- 应答人在等待窗口（2 分钟）内回应：答复成为那次工具调用的结果，模型在**同一轮**里接着做 —— 上下文不断、不重开沙箱，
  也就是 pi `question` 工具的效果。
- 热等待的时间**不计入**一轮的时长上限（现在是 5 分钟），但一轮里所有热等待加起来不超过 10 分钟（超过后再发出的交互直接挂起）；Grant 的绝对过期时间相应加上这个上限
  （REQ-AGENT-SANDBOX §3「签发时刻 + 时长上限 + 余量」）。热等待期间 run 照常占着**会话**的运行槽位（这个会话里不能再起一轮）、在任务列表里显示为「等待确认」。
- **等待回答时释放节点占用**（REQ-AGENT §3.10.8）：进入热等待或挂起之前，这一轮先释放它占用的全部节点；答复后继续时不预先恢复，下一次写到哪个节点再重新占用，那时被别人占了就按「正在改」处理。
- **等待回答的这段时间不算并发**：热等待中、挂起中的 run 都不计入每用户并发上限（REQ-AGENT §3.10.6），等待期间用户可以在别处发起新任务。
- 答复之后要继续执行，才重新占一个并发名额；**名额已满就排队，等有名额了再继续**（新发起的任务满额时是拒绝，这里是排队 —— 用户已经答了，不该让他再答一遍）。排队期间卡片显示「已回答 · 排队等待执行」，任务列表里显示「排队中」；同一用户的排队按答复先后。热等待中的 run 排队的时间计入热等待总上限，超过就挂起（答复已落库，有名额时按 ③ 恢复，不用再答）。

**② 挂起（人不在时）。**

- 等待窗口到期没人回应 → 这一轮以新的结局「等待中」结束：沙箱回收、Grant 释放、离开任务列表；交互留在会话里，状态「等待回答 · 已暂停」。
- 关浏览器、退出登录本身**不触发**任何事：run 与会话解耦（REQ-AGENT-SANDBOX §2 原则 1），照样等到窗口到期再挂起。
- 这次工具调用在模型上下文里**留空**（只有调用、没有结果），不能像被中止的那批一样补成「已中止」的错误结果 —— 恢复时要把答复填进这个位置。
- 挂起时 runner 本地工作目录里的东西（媒体命令的中间文件）随沙箱一起丢失；已经存进资源存储的产物不受影响。恢复后需要时由模型重做。
- 服务进程崩溃 / 副本下线导致热等待中的 run 消失：交互已经落库，按挂起处理（这就是为什么要「先落库再发出」）。

**③ 恢复。**

- 应答人回应一条挂起的交互：服务端把答复写成那次工具调用的结果，**在同一会话里自动起新的一轮**，从那里接着做（不插入新的用户消息）。
  对话里先出现卡片变成「已回答」，然后是新一轮的输出。隔了多久都一样，**不再弹「继续执行」之类的二次确认**：回答本身就是确认。
- 新一轮按**当下**的权限重新签发 Grant（授权只缩不扩）：应答人已经没有画布写权限 → 不起 run，交互标「已失效」并说明原因。
- 挂起期间画布被别人改过：沿用跨轮画布差异（REQ-AGENT §3.10.2 的 since-last-run），恢复的这一轮开头就能看到。
- 审批恢复时，被审批的那次工具调用**按当下画布重新校验**后再执行（要删的节点可能已经没了）；校验不过就把原因作为结果回给模型，不执行。
- 回应时这张画布上该会话已经有一轮在跑（不会发生在应答人自己身上，但要防）：409，卡片保持等待。
- 恢复同样受每用户并发上限约束：名额满时排队，卡片显示「已回答 · 排队等待执行」，有名额后自动起这一轮（见 ①）。

**④ 跳过与其他结局。**

- 挂起中应答人不答、直接在这个会话里发新消息：交互标「已跳过」，那次工具调用的结果写成「用户没有回答，转而发了新的消息」，紧跟着是新消息，正常起一轮。
- 应答人点「不回答」：热等待中 → 结果「用户取消了提问」/「用户拒绝了」，模型接着做；挂起中 → 同样写结果并恢复一轮，让模型收尾。
- 停止这一轮（发起人或管理员）：交互标「已取消」。
- 挂起超过保留期限（7 天）：标「已过期」，那次工具调用的结果写成「用户超时未回答」；之后在该会话发消息照常继续。
- 删除会话 / 画布、应答人被移出项目：交互标「已失效」，从待确认列表里消失。

### 3.5 推送给应答人

「有东西等你确认」必须**只推给应答人**。项目画布上，现有的 `agent:runs` 是给整个房间的全量广播（REQ-AGENT §3.10.4），不能拿来做这件事：
别的成员不该收到提醒（他们打开会话时照样能只读看到卡片，§3.2）。

**推送内容只有元数据**：交互 id、画布 id / 名称、会话 id / 标题、类型（提问 / 审批）、一句摘要、创建时间、状态。
问题正文与选项要打开会话后按现有权限读取（REQ-AGENT §3.9「对话记录」）。

**待确认的入口随会话面板的开合而变：**

| 应答人此刻 | 表现 |
|---|---|
| 打开着这条交互所在的会话 | 卡片直接出现在对话里（§3.2），不再另行提醒 |
| 没打开那个会话（会话面板关着，或开着别的会话） | 画布**顶部居中**显示**待确认消息堆栈**：每条交互一张小卡片（画布名、会话标题、类型、摘要、等了多久、热等待倒计时 / 已暂停），新的压在上面；**超过 1 条就折叠**成一摞，只露出最新一条并显示总条数，点击展开成列表查看全部（条数多时列表内滚动），再点收起；每条带「转到对话」，点了打开那个会话（必要时先跳到那张画布）并滚到卡片，在那里看上下文、作答。右上角对话按钮在「运行中任务数」之外另有待确认角标（醒目色，与运行动效区分） |
| 不在任何画布页、或不在线 | 收不到推送（推送复用协同连接，见下）；不做外部通知（§6）。下次打开任意画布时拉取待确认列表，消息堆栈里照样出现 |

- 消息堆栈里是该用户**所有**等待回答的交互（跨画布、跨项目），不只是当前画布的；当前画布的排在前面。
- 堆栈里的卡片只做提醒和跳转，**不在堆栈里作答**：回答一律在对话里，看得到上下文。
- 某条交互的会话被打开时，它从堆栈里移走（卡片已在对话里）；会话关上而交互仍在等，回到堆栈。
- 交互了结（已回答 / 已取消 / 已过期 / 已失效）即从堆栈消失。

**通道：复用协同连接。**

- 不新开长连接。服务端把定向消息以无状态消息发到**该用户自己的协同连接**上 —— 不论那条连接连的是哪张画布的房间
  （服务端按连接上的 `context.identity` 选出该用户的连接，只发给它们；不经房间广播，同房间的其他人收不到）。
  客户端发的无状态消息 Hocuspocus 不转发，所以这类消息只可能来自服务端。
- 代价：只在用户开着某张画布（有协同连接）时能收到推送。个人画布同样有协同连接（REQ-AGENT §3.3.2），适用。
- 客户端协同连接每次从断到通，都先 `GET` 一次待确认列表（与任务列表同一原则：只收推送 + 连上时拉一次，不轮询）。
- 状态变化（新增、已回答、已过期、已失效）都推：应答人在一个标签页答了，其它标签页和设备上的堆栈与卡片随之更新。
- 多副本（`CLUSTER_MODE=redis`）下，用户的协同连接可能在别的副本上：定向消息要经共享层送到持有该用户连接的副本
  （不能指望 `broadcastStateless` 的 redis 转发 —— 那是按房间发给所有人的）；热等待中的答复同样要送到持有那一轮 run 的副本，送不到（副本已下线）按挂起处理。

### 3.6 事件流与接口（契约草案）

- **事件**：`CUSTOM agent.interaction`（交互发出，值为落库后的完整交互消息）、`CUSTOM agent.interaction-resolved`（状态变化：已回答 / 已取消 / …，带答复摘要）。
  两者都进补发缓冲，重连后的补发与实时帧逐帧一致（REQ-AGENT §3.10.5 的旁观同样适用）。
- **结局**：`RUN_FINISHED` 的 `outcome` 增加 `{ type: 'waiting', interactionId }`；任务列表项增加「等待确认」状态。
- **回应**：`POST {agentApiPath}/interactions/:interactionId`，体为各题答复（选项下标 / 自填文字）或 `approve` / `reject` / `dismiss`；
  只接受应答人的会话 cookie；重复回应 409。
- **列表**：`GET /api/agent/interactions?status=pending` 返回当前用户作为应答人的待确认交互（跨画布，按当下权限过滤）。
- 若 runner 需要感知等待（例如那次工具调用的超时要放宽），改 runner ↔ 网关协议须升 `RUNNER_PROTOCOL_VERSION`（REQ-AGENT-SANDBOX，`.claude/rules/agent.md`）。

### 3.7 运行中追加指令（REQ-AGENT F7）

和交互同属「运行中人的输入」，一并规划：

- 运行期间输入框不再禁用（热等待审批时除外，§3.2），发送 = 追加指令，在当前这批工具调用结束后、下一次请求模型之前交给模型（pi 的 `steer`）。
- 走与「别人的改动」相同的时机（REQ-AGENT §3.10.2：runner 在 `turn_end` 来取），不做服务端推送；模型正在写不带工具调用的最终回复时到达的指令，排到下一轮开头。
- 对话里按到达顺序显示为用户消息，标注「运行中追加」。

## 4. 功能需求

| 编号 | 需求 |
|---|---|
| H1 | agent 可调 `ask_user` 向发起人提问：1–4 个问题，带可选项（含说明）、可选「其他」自由作答、可多选；单独成批；一轮里可多次提问，次数只受轮次与工具调用上限约束 |
| H2 | 删除超过单轮阈值等高风险操作在服务端执行前拦下，等发起人批准 / 拒绝；模型不能发起、不能绕过；批准后按当下画布重新校验再执行 |
| H2a | 会话有执行等级（谨慎 / 平衡 / 自主，默认平衡）：决定删除执行中的占位节点等操作是服务端强制审批、agent 自主决定是否提问，还是直接执行；删除超阈值在所有等级都审批；项目画布上实际等级不低于项目最低执行等级（本期默认「自主」，无设置界面） |
| H3 | 每条交互先落库再发出，作为会话里的一条消息显示；刷新、重开浏览器、换设备看到同一张卡片和同一个状态 |
| H4 | 热等待窗口内回应：答复回到同一轮，模型接着做；热等待不计入一轮的时长上限，但有总上限 |
| H5 | 窗口到期未回应：这一轮以「等待中」结束、沙箱回收；之后回应则在同一会话自动起新的一轮（无二次确认），从那次工具调用接着做，按当下权限签发 Grant |
| H6 | 挂起中直接发新消息 = 跳过；「不回答」、停止、过期、失权各自落到明确的状态，并给模型对应的结果 |
| H7 | 只有应答人（发起人）能回应；run 令牌与其他成员（含项目管理员）一律拒绝；多端同时回应先到先得 |
| H8 | 「等你确认」只推给应答人，经该用户自己的协同连接定向发送；不在画布页 / 离线的，下次打开画布时拉取；其他成员不收提醒，只在打开会话时只读看到 |
| H9 | 打开着交互所在会话时卡片随对话显示；没打开时在画布上显示待确认消息堆栈（跨画布、可折叠），每条「转到对话」直达会话里的卡片，作答只在对话里 |
| H10 | 多副本下推送与热等待的答复都能送达；持有 run 的副本消失时交互按挂起处理，不丢 |
| H10a | 等待回答（热等待 / 挂起）不计入每用户并发上限；答复后继续执行时名额已满则排队，有名额后自动继续，不用再答 |
| H11 | 运行中可追加指令，在下一次请求模型之前交给模型（REQ-AGENT F7） |

## 5. 验收标准

1. 让 agent「帮我加一个生成节点，风格你问我」：对话里出现提问卡片，选项可点；选第 2 项后，同一轮继续，生成的节点用了所选风格，工具调用日志里 `ask_user` 的结果是 `选了「…」`。
2. 选「其他…」输入文字提交：模型收到 `自填「…」`；在热等待时直接用输入框发送，效果相同。
3. 让 agent 删 8 个节点（阈值 5）：第 6 个起的那次删除被拦下，出现审批卡片列出要删的节点；拒绝 → 画布上节点都在，模型收到拒绝并在回复里说明；重来一次批准 → 节点被删。
4. 伪造的 runner 用 run 令牌调回应接口：被拒，交互仍在等待；项目里另一个成员、项目管理员调回应接口：403。
5. 提问后 2 分钟不答：任务列表里这一轮消失，沙箱进程 / 容器已退出，卡片显示「已暂停，回答后继续」。关掉浏览器第二天再打开这个会话，卡片还在；回答后不经二次确认、自动起新的一轮，模型从提问处接着做，开头带上这期间画布被别人改动的差异。
6. 挂起期间发起人被移出项目：卡片变「已失效」，待确认列表里没有它；回应接口拒绝。
7. 挂起时直接发一条新消息：卡片变「已跳过」，新一轮里模型看到「用户没有回答，转而发了新的消息」和那条新消息。
8. 项目画布，成员甲发起的一轮在等确认：甲开着那个会话时卡片直接出现在对话里、堆栈里没有它；甲关上会话面板后，画布上出现待确认消息堆栈，点「转到对话」回到会话并定位到卡片；甲开着**另一张**画布时同样在堆栈里收到它，「转到对话」跳到那张画布的会话。成员乙同时开着这张画布，**收不到**任何提醒，打开甲的会话能看到只读卡片「等待 甲 回答」。
9. 甲在两个标签页里同时提交不同选项：只有一个生效，另一个提示已回答，两边卡片最终一致。
10. 甲离线期间产生了两条待确认（两张画布）：甲打开任意一张画布后，消息堆栈折叠显示 2 条，展开后分别「转到对话」进入对应会话并定位到卡片；甲不在任何画布页时（如在演示页）收不到推送。
11. 每用户并发上限为 2：甲有一轮在等回答时，还能再发起两轮；这两轮都在跑时甲回答了提问，卡片显示「已回答 · 排队等待执行」，其中一轮结束后这一轮自动继续。
12. 双副本：甲的协同连接在副本 A，run 跑在副本 B；交互发出时甲在 A 上收到定向消息；甲在热等待内回答，答复送达 B，同一轮继续。B 在热等待中被杀，交互变「已暂停」，甲回答后在存活的副本上恢复。
13. 执行等级：「谨慎」下让 agent 删一个执行中的占位节点 → 出现审批卡片；「平衡」下没明确点名要删它时 agent 先用提问卡片提醒，明确点名时直接删；「自主」下直接删并在回复里说明。三种等级下删 8 个节点（阈值 5）都出现审批。
14. 一轮里 agent 先问风格、根据答复再追问尺寸：两张提问卡片依次出现，同一轮完成。
15. 运行中在输入框追加「改成蓝色」：下一次模型请求里出现这条指令，对话里标注「运行中追加」。

## 6. 本期不做

- 外部通知（邮件、IM、浏览器系统通知）、不在画布页时的推送；离线时只在下次打开画布时提示。
- 项目管理员代为回答 / 审批。
- 自定义交互界面（pi 的 `custom()`）；只做提问与审批两种标准卡片。
- 多人审批 / 会签、指定他人回答、把交互转给别人。
- 挂起时保留沙箱内状态（checkpoint 整个 runner）；恢复只基于模型上下文与画布，runner 本地文件不保留。
- 模型发起审批（审批只由服务端规则触发）。
- 撤回本轮（REQ-AGENT §3.5）前的影响确认 —— 那是用户发起的操作，用普通确认弹窗，不走本需求的交互。
