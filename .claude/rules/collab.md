<!-- Realtime collaboration: data layer vs feedback layer, Hocuspocus server, persistence & store-failure rules, presence/awareness, exclusivity, terminal close codes, revocation, write gate, WebSocket Origin check. Moved verbatim from CLAUDE.md; CLAUDE.md links here. -->

- **Collaboration splits into two layers with one question deciding which (`docs/04-realtime-collab.md` §4.0): *should it still be there after a refresh?*** Yes → **data layer**: a Yjs shared type, which means CRDT merge, undo, and persistence. No → **feedback layer**: an awareness field, ephemeral, dropped frames are fine. `useFlowSync(flowId, mode)` owns the doc and its transport; the collab transport (`sync/collab.ts`) owns the one Yjs connection under both — a `HocuspocusProvider` (room `flow:<flowId>` passed as `name`, not in the URL; identity is the httpOnly `sid` cookie the handshake carries, gated server-side in `apps/server/auth/ws.ts`). The same doc also carries a **`y-indexeddb`** cache (db name = room name), which is what makes edits survive going offline and closing the tab — they re-send on reconnect. Loading is therefore gated on *server-synced **or** local cache has content*, and the offline banner ORs in `navigator.onLine` because the provider needs a heartbeat timeout (tens of seconds) to notice a pulled cable. Teardown order matters: provider → indexeddb → doc. **`vite.config.ts` must keep `resolve.dedupe: ['yjs', 'y-protocols']`**: we and the provider each `import * as Y from 'yjs'`, and Vite's prebundling otherwise ships two copies — `instanceof` across them is always false, which would silently turn `@shadecn/shared/flow-doc`'s `value instanceof Y.Map` checks into an empty canvas. and hands out a `session` that changes on reconnect/route-change; the store takes its `doc` and the presence layer takes its `awareness`. Dependency order is a straight line — `selection`/`sync` → `presence` → `canvas` — and `useFlowCanvas` is the **only** thing that knows all three: `useFlowPresence` doesn't import selection or Vue Flow, it just offers "publish" and "read others", which is why a new feedback signal costs one setter plus one computed and touches nothing else.
- **Data layer — the Y.Doc is the source of truth, and the server subscribes to it.** `apps/server/collab/persistence.ts` implements Hocuspocus's `onLoadDocument`/`onStoreDocument`: first joiner loads `Flow.ydoc`, writes are debounced by the framework (2s, 10s ceiling) and skipped entirely when the state vector is unchanged, the derived `graph` projection is written **only in `beforeUnloadDocument`** — not under `onStoreDocument`'s `clientsCount === 0`, because Hocuspocus only re-stores on last-leave if a debounced store is still pending, so "edit, wait two seconds, close the tab" never fires it (verified) — and SIGTERM does `closeConnections()` + a direct per-room store (`flushAllRoomsToDatabase` — **not** `flushPendingStores()`, whose triggered store only reaches our queue after a microtask chain, so a synchronous sample sees an empty queue and the last debounce window is lost) + drains our own write queue. **A store is read → merge → CAS write, and the *merge* is the part that matters.** Writing `Y.encodeStateAsUpdate(doc)` straight into the `ydoc` column is a full overwrite; that is only safe while this process is the sole writer. Under `CLUSTER_MODE=redis` a pub/sub hiccup forks the two instances' documents and the later writer wins outright. **Adding CAS alone does not fix it** — `where: { revision }` proves nobody interleaved between *your* read and *your* write, not that your document is a superset of what is stored: an instance that wrote before you read gives you a fresh `revision`, your CAS passes, and you overwrite it anyway. So each store re-reads `ydoc`, `Y.applyUpdate`s it into the in-memory doc under the `'persistence'` origin (never `local` — it must not enter anyone's undo stack), and *then* CAS-writes; `count === 0` re-reads and retries, up to `MAX_STORE_ATTEMPTS`, after which it throws to the retry table below. The merge is idempotent, so on a single replica it reads back a subset, produces no update event, and costs nothing but the read. Redlock (`lockTimeout: 10_000`, raised from the 1s default that a large doc blows straight through) is now only an optimization — correctness lives in the CAS, which also covers Redis being down entirely. **A failed store MUST propagate — never swallow it, and this is the one rule in this file most likely to get re-broken by a well-meaning `catch`.** Hocuspocus's two data-loss protections are both *triggered by the hook throwing*: `onStoreDocument` throwing makes `storeDocumentHooks` keep the document in memory ("Document stays in memory to avoid data loss"), and `beforeUnloadDocument` throwing makes `unloadDocument` `return` before `documents.delete()`/`destroy()`. The write queue used to `.catch()` the error into a `console.error` and resolve — which silently disarmed both, so one database hiccup during "close the tab" lost that round of edits for good (docs/19 §4.1). Propagating is only two-thirds of it: the doc stays in memory but **nothing ever retries** (`onStoreDocument` is debounce-driven and by then nobody is editing), so failures are registered in `failedStores` and `retryFailedStores()` sweeps them every 30s, serially, clearing each on success — `GET /api/collab/health`'s `owed` is that table's size. The inverse rule holds for the **shared layer**: `sameAsStored` (read) and `rememberStoredVersion` (write) are *cache* operations, so they fail open — worst case is one redundant write, whereas failing the store would stall persistence whenever Redis twitches (§4.2 a). `rememberStoredVersion` must stay `async` even though its body is one line: the shared-layer lazy proxy resolves its implementation on first call and **throws synchronously** when Redis is down, and a synchronous throw sails straight past the caller's `.catch()`. **No y-leveldb** (native module) and no `@hocuspocus/extension-database` (a thin wrapper over the same two hooks): persistence is only load/store, so it writes the app's own `flow` table. **Legacy migration is `onLoadDocument` itself** — a canvas whose `ydoc` is NULL gets its old `graph` JSON poured into the doc on first open, so there is no migration script and no downtime. `Flow.graph` survives as a **read-only projection** the server derives on write (list counts, thumbnails, future read-only previews); the editor never reads it. There is **no per-update audit log** — the old `FlowOperation` table is gone, and with it any notion of history or rollback; `Flow.ydoc` is a converging snapshot (Yjs gc reclaims overwritten content), so nothing accumulates per edit. Since content no longer passes through any REST route, validation moved here too: the quota (`apps/server/collab/quota.ts` — **bytes only**: 1MB/message, 20MB/doc; node and edge counts deliberately have no ceiling, they were a product judgement rather than a guardrail and the byte line already covers the resource side) is measured in `onChange` and enforced in `beforeHandleMessage`, and it **can only refuse before applying**, because an applied-and-broadcast Yjs update is unrecallable. Refusal **never throws** — Hocuspocus closes the connection on a thrown message and the reconnecting provider resends the same message forever; it flips the connection `readOnly` instead (writes get NACKed, reads and awareness keep working). The quota is two-tier: over the *soft* limit only marks the room and still accepts writes (deleting is the only way to shrink back, and deletes are writes too — the mark clears at the next byte re-measure, ≤1s, since measuring means serializing the whole doc and can't run per message), the *hard* ceiling (soft × 1.25) locks the room read-only until it unloads. **The doc limit and the projection limit are two different numbers on purpose** (`COLLAB_LIMITS.document` 20MB ≥ `GRAPH_LIMITS.bytes` 2MB, never the other way round): the projection is JSON that ships inside `GET /api/flows/:id`, the content is binary that only rides the WebSocket, so a doc between the two simply stops refreshing its projection (`deriveProjection` returns null and keeps the previous one — stale list counts, content untouched, and duplicate copies `ydoc` anyway). `onStoreDocument` prunes dangling edges (the legitimate product of one peer deleting a node while another connects to it) under a `'gc'` origin so the cleanup never enters anyone's undo stack. **Anything that mutates the graph must go through the store** — Vue Flow's own defaults will happily bypass it (`deleteKeyCode` under `applyDefault: true` edits its internal nodes/edges directly, so a deleted edge never synced or persisted). `FlowCanvas` passes `:delete-key-code="null"` and `canvas.deleteSelection()` is the single delete path.
- **Feedback layer — awareness carries who's here, where their cursor is, what they're dragging, and what line they're pulling.** `apps/web/src/lib/presence.ts` is the pure, socket-free half (color hashing, defensive parsing of peer state, occupancy arbitration) and keys elements as `node:<id>` / `edge:<id>` so a third kind costs one `ElementKind` value. **The server rewrites the identity in every awareness update** (`beforeHandleAwareness` → `enforceIdentity`): clients may report any cursor/selection they like, but `user.id`/`name`/`avatarUrl` are replaced with what `onConnect` authenticated, so nobody can impersonate a teammate. Two more guards live on the same path: awareness entries are bound to the socket that first published their `clientID` (`dropForeignClients` — forged entries carrying a teammate's `clientID` are dropped, claims released on disconnect), and membership + session are **re-validated every minute** for live connections (`revalidateConnections`) — being removed from a project kicks an open WebSocket too, not just future handshakes. That sweep passes `{ refresh: false }`: it may only *read* the session, never renew it, or an open tab would keep its own session alive forever and idle timeout would stop meaning anything (renewal is the job of real requests — the handshake itself, then the edit-triggered user-state PATCH). **Occupancy arbitration exists and is tested but is deliberately not wired into the canvas right now** — anyone may edit anything concurrently and the CRDT merges it; the node label only *shows* who else is touching it. To reinstate the restriction, feed `presence.lockedKeys` back into the nodes'/edges' `draggable`/`selectable`/`updatable` in `useFlowCanvas`, and write those flags **explicitly as `true` as well as `false`** — Vue Flow merges node props with `Object.assign(existing, incoming)`, so a key you stop sending keeps its old `false` and the element stays dead after the lock lifts. See `docs/04-realtime-collab.md` §4.0.1.
- **One user, one canvas, one connection — and the newest window wins** (`apps/server/collab/exclusive.ts`). Opening the same canvas in a second browser/tab kicks that user's older connections offline — personal canvases included, since they are collab rooms too; the old window gets a non-dismissible 「协作会话已过期，请刷新页面」 (「这张画布已在另一个窗口打开」 on a personal canvas) (`FlowConnectionEndedDialog.vue`) and **stops reconnecting**. The rule is per *room × user*, not per user — having canvas A and canvas B open at once is normal work. Three things it can't be built without. **The holder registry lives in the shared layer** (`SharedMap`), because the two windows are very likely on different replicas and a local-only check kicks nobody; `connected` handles the local half on the spot, a 3s sweep converges the cross-instance half and renews the holder's TTL. **Kicking must close the socket, not just the connection** — Hocuspocus's `connection.close()` detaches the doc connection and sends a CLOSE message but leaves the socket open, and the client's next message (awareness heartbeat, ~30s) is re-authenticated as a *fresh* document connection: the old window resurrects itself and kicks the new one, forever. So it sends both the CLOSE message and a real close frame (`4409` / `session-superseded`), and the client accepts either signal. **The client must stop reconnecting itself** (the collab transport's `onClose` → `provider.disconnect()`), or the retry handshake reads as yet another new window and knocks out the tab the user is actually in; `disconnect()` leaves the doc and awareness intact, so the canvas stays on screen — just unsynced until a refresh takes it back. It is a UX rule, not an access gate (that one is `onConnect` / `revalidateConnections`), so a failing shared layer **fails open**, and with login disabled there is no identity to key on and exclusivity is simply off.
- **Four refusals are terminal, and the client must tell them apart** (the close codes and reasons — `CLOSE_SUPERSEDED` / `CLOSE_UNAUTHORIZED` / `CLOSE_REVOKED` / `CLOSE_QUOTA_LOCKED` and the `CloseReason` type — live in `@shadecn/shared/collab` alongside `COLLAB_PATH`, `FLOW_ROOM_PREFIX`, `STORE_STATE_MESSAGE` and `FLOW_STATE_VECTOR_HEADER`; `apps/server/collab/close.ts` re-exports them and adds the server-side closing helpers; client side `sync/collab.ts`'s `classifyClose`; `docs/04-realtime-collab.md` §4.4): `4409`/`session-superseded` (a newer window took over → refresh), `4401`/`Unauthorized` (session gone → the app-wide `SessionExpiredDialog`, then reconnect in place), `4403`/`permission-revoked` (still logged in, just not allowed in this room — not a project member, canvas deleted → leave), `4413`/`quota-exceeded` (the canvas hit the hard content ceiling and the room was locked and cleared — **the only one that is not about this person**: everyone in the room gets it, and it maps to `too-large` on both kinds of canvas). Two things the copy has to get right: `forbidden` must cover *both* "deleted" and "not a member" in one sentence (the server deliberately doesn't distinguish them) and land on `/projects`, not the project home the second half can't open — **except on a personal canvas**, where `forbidden` can only mean "this canvas is gone" and both the wording and the destination (`/personal`) change; and **the person doing the deleting gets kicked too** (the route revokes before answering 204, so the close often beats the response), which is why `remove()` calls `sync.leave()` *before* the request — otherwise deleting your own canvas reports itself as an accident — and `sync.stay()` if the delete fails, or a later genuine kick would be silent. `authorizeCollab` returns which one (`CollabDenialReason`); collapsing the two is not cosmetic — a viewer whose session idled out *by design* would be told 「你已不是这个项目的成员」. Lumping any of them in with "offline" is worse still: the provider retries forever (`maxAttempts: 0`), the status line keeps promising 「恢复连接后自动同步」, and everything drawn from then on lands in IndexedDB and never leaves.
- **The server signals this over two different paths, and the client must handle both.** ① A connection that was already established gets closed — that goes out **on two legs**, because `connection.close()` detaches the doc connection and sends a CLOSE *message* but leaves the socket open, so the client's next message (awareness heartbeat, 15s) is re-authenticated as a fresh connection and the window resurrects itself; the real close frame is the second leg. ② **The handshake is refused (`onConnect` throws) — no socket close and no close code at all.** Hocuspocus only replies with a `PermissionDenied` message carrying `error.reason ?? 'permission-denied'`, which the provider surfaces as `onAuthenticationFailed({reason})` — **`onClose` never fires**. So the server must throw an error carrying `reason` (`denialError`), and the client must handle `onAuthenticationFailed` and `disconnect()` itself, or an authenticated-but-refused socket spins until the 30s server timeout, reconnects, and spins again — forever, while the UI says 「同步中…」. Path ② is the common one: reopening a canvas after being removed from the project, or reconnecting after the session expired. **Hence `reason` is the discriminator, not `code`** — it is the only thing both paths carry — and both paths funnel into one `endConnection()`. `4401` deliberately does *not* navigate to `/login`: `requestReLogin()` re-logs in inside an iframe so the canvas and its unsynced edits stay on screen, and a watch reconnects once the session is really back (gated on actually-authenticated, since dismissing the dialog also clears `sessionExpired`).
- **Revoking access kicks the live connection on the spot; the periodic sweep is only the backstop** (`apps/server/collab/revocation.ts` + `revokeCollabAccess()`, called by remove-member / delete-project / delete-canvas; `docs/04-realtime-collab.md` §4.2.1). Waiting out a sweep is not merely "late": a removed member can still write for the whole window, those writes merge and persist, and **the people who remain cannot undo them** — `Y.UndoManager`'s `trackedOrigins` only tracks their own `LOCAL_ORIGIN`, so anything arriving over the wire never enters their undo stack, and one `deleteSelection()` empties the canvas. There is no audit log and no restore path — whatever a revoked member destroys is simply gone. So: the writing instance revalidates immediately, and **cross-instance is covered by one shared key** — a fresh token written on every revocation, polled by each instance every `REVOCATION_POLL_INTERVAL` (3s), and a change triggers a full revalidation. One global key + full sweep beats per-project/per-user delivery because revocations are rare while precise routing would need a room→project cache and a read count that scales with rooms. The route **awaits** it, so a 204 from `DELETE …/members/:userId` means the person is genuinely off the canvas. Broadcast failures never block — they degrade to the `REAUTH_INTERVAL` sweep, so a broken shared layer is slower, not leakier. The sweep itself must **fan out across documents and guard against re-entry**; the old serial `await` made `REAUTH_INTERVAL` a lower bound rather than the guarantee it is quoted as.
- **Kicking a connection is not the same as refusing a frame — the write gate is the second, message-level half** (`apps/server/collab/write-gate.ts`, hooked on `beforeSync`; `docs/04-realtime-collab.md` §4.2 ④). Between "the verdict went bad" and "the socket is actually closed" sits the sweep interval, the 3s cross-instance poll, and whatever is already queued behind `closeForGood` — Hocuspocus's `Connection` carries no closed flag and `processMessages` never checks whether the connection is still attached, so those frames apply, broadcast and persist. **`beforeSync`, not `beforeHandleMessage`**: the latter runs on every frame including awareness (a cursor per pointermove), while `beforeSync` fires only inside a sync message *after* the type is read — so only writes pay for auth (`type` separates SyncStep1/read from SyncStep2+Update/write; never gate SyncStep1 or reconnect's own sync handshake breaks), and it runs *before* Hocuspocus's own `readOnly` check, so setting `readOnly` there NACKs the frame in flight. **Never `throw`** (same reason as the quota). **Refusing is only half — the connection must also be closed**: the provider does nothing with `syncStatus=false` (`applySyncStatusMessage` only decrements when `applied`), it never resends, so the rejected edits sit in the local Y.Doc + y-indexeddb until a *reconnect*'s SyncStep1/2 exchange carries them up — which is exactly the existing `classifyClose` → `SessionExpiredDialog` → re-login → `useFlowSync` watch → rebuilt provider path. Don't close and the user logs back in with the edits still stranded in the browser. **Cache the verdict; never batch-delay the frames** — message handling is one serial queue, so awaiting a timer in this hook stalls that connection's awareness heartbeat too and the 30s `timeout` kills it. The cached value is the *Promise*, which doubles as in-flight dedup. **TTL is long (10s) because the urgent half is event-driven**: `revalidateConnections` clears the table at its top, and it is the confluence of all three revocation paths, so a revoked member's next write frame always re-queries (window ≈0) at zero polling cost; the TTL only backstops session expiry, whose detection floor is the access-token lifetime anyway. Net: fewer queries than the 20s sweep, shorter window, and enforced before the Y.Doc rather than by close timing. `prime()` on `connected` (the handshake just authenticated), `forget()` on `onDisconnect`, and **an authorize that throws means allow** — no evidence, no refusal, same as the sweep and session refresh. **What it checks is injected and mandatory** (`createWriteGate({ authorize })`, no default): both project and personal canvases get `collabWriteAuthorize` — it goes through `authorizeCollab`, which for a personal room checks session + canvas still alive + **is the owner**, strictly stronger than the session-only `sessionWriteAuthorize` that was once planned for personal rooms (that helper still has no caller; personal canvases now ride the WebSocket too, see docs/20 §3.3.2). An `if (personal)` inside the gate would make it know what a project is; the channel's shape belongs to whoever mounts the gate.
- **The WebSocket upgrade is outside Hono, so `Origin` is checked by hand** (`isAllowedCollabOrigin` in `apps/server/auth/ws.ts`, called from the `upgrade` listener). WebSocket is not covered by the same-origin policy — any page can open `wss://us/ws/collaboration` and the browser attaches the `sid` cookie, which is CSWSH; `app.ts`'s `cors` only guards `/api/*` and a raw `server.on('upgrade')` sees none of the middleware chain. `SameSite=Lax` on `sid` already stops this in current browsers, but that is the browser covering for us, not a decision in our code. Allow on three grounds: **no `Origin` at all** (non-browser clients — browsers always send one, so this opens nothing), **on the `APP_ORIGINS` whitelist** (`APP_ORIGIN` is always in it; a multi-domain deployment has to let every one of its domains open a collab socket), or **`Origin`'s host equals the request `Host`** (same-origin with a mis-set `APP_ORIGIN`, e.g. dev defaults to `127.0.0.1` while you browse `localhost`; a cross-site attacker can't reach this branch since its `Origin` is its own domain).

**Yjs 协同 (`apps/server/collab/`):** the same HTTP server also serves a Yjs sync endpoint at `ws://host:3000/ws/collaboration` (room name travels in the message, not the path); one room = one `Y.Doc`, held in memory only.
- `collab/hocuspocus.ts` — the collaboration server: [Hocuspocus](https://tiptap.dev/docs/hocuspocus) (`@hocuspocus/server`, MIT) mounted on our own HTTP server. We never call `listen()` (that would open a second port); instead we own the `upgrade` listener, take **only `/ws/collaboration`**, and hand it to crossws, which calls `handleConnection()`. Everything else — notably Vite's HMR socket (`vite-hmr`, path `/`) — we simply don't touch, and Node's multi-listener `upgrade` event delivers it to Vite's own listener; crossws registers no listener of its own, so "don't touch" really means untouched. This replaced a 282-line port of y-websocket's `bin/utils.js` that existed only because upstream `@y/websocket-server` statically imports `y-leveldb` → `leveldown` (no node 22/arm64 prebuild). **The room name travels in the message, not the URL** — that's also why the wire protocol is incompatible with y-websocket and the frontend must use `@hocuspocus/provider`.
- `collab/index.ts` — `attachCollabServer(server, { destroyUnmatchedUpgrades, authorize })`: a `ws` server in `noServer` mode; only `/ws/collaboration` upgrades are accepted. In dev `destroyUnmatchedUpgrades` is `false` — Vite's HMR socket rides the same `upgrade` event (protocol `vite-hmr`, path `/`) and killing unmatched sockets would break hot reload. `authorize` (wired to `auth/ws.ts`) checks the session cookie on the handshake and answers `401` + destroy when anonymous
- **Timings are constants in `hocuspocus.ts`, not env vars, because they are all derived from one fact: the server sends no heartbeat.** `timeout` is *not* a ping interval — Hocuspocus only compares "when did I last hear from this client". What actually holds the connection open is y-protocols' awareness replay: the client re-announces its local state every `outdatedTimeout / 2` = **15s** (`useFlowPresence` publishes on connect, so it always runs), and the server's awareness broadcast does **not** exclude the sender — so there is a 15s round-trip in both directions and a 60s reverse-proxy idle timeout (nginx / k8s Ingress defaults) is already covered without us sending anything. `timeout: 30_000` = two missed beats, matching the provider's own `messageReconnectTimeout` so both ends give up together; tighter than the 60s default because a dead connection still holds the exclusive-holder slot and a ghost cursor, and staying under the proxy's 60s means *we* notice first and run `onDisconnect` instead of the middlebox quietly cutting the tunnel. `REAUTH_INTERVAL: 20_000` is the **backstop** sweep, not the main path — see the revocation bullet below.
- `GET /api/collab/rooms` reports live rooms/connections; `GET /api/collab/health` is the **persistence health** endpoint alerting hangs off (REQ-RESILIENCE §4.5) — failed-store count, how long since the last successful store, write-queue depth, shared-layer status, and **the HTTP status code is the verdict** (200/503) so a `curl`-checks-the-code alert works without parsing JSON. Two judgement calls in it: `failed` is *observed*, not reported (see the logging section — the extension brackets the business hooks, so started-minus-completed is the failure count), and "hasn't stored in a while" is only unhealthy **together with a non-empty write queue**, because stores only happen when someone is editing — the time alone would fire every quiet night. Both endpoints sit behind the auth gate; opening `/health` up for Prometheus is a security-boundary change and deliberately not done here
- Frontend: `new HocuspocusProvider({ url: '/ws/collaboration' as absolute ws:// URL, name: room, document: doc })` — docs stay in memory, so a server restart drops all content
