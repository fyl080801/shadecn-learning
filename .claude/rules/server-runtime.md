<!-- Backend runtime: entry/env/config/app wiring, server directory map, logging, frontend hosting & login page, the build. Moved verbatim from CLAUDE.md; CLAUDE.md links here. -->

**Backend (`apps/server/`) — the single entry point:** Node + [Hono](https://hono.dev) + `@hono/node-server`, run through `tsx` (no build step). It serves the API, the Yjs WebSocket, *and* the frontend. Layout:
- `apps/server/index.ts` — entry. Loads `.env`, `assertAuthConfig()`, builds the http server with `createAdaptorServer` (no `listen` yet), attaches collab + frontend, starts the hourly expired-session sweep, then listens. Handles SIGINT/SIGTERM cleanup, and `shutdown()` carries a re-entry guard because the two signals can arrive back to back
  - **In dev, the process that actually holds the port is a grandchild, so it also has to notice when it has been orphaned.** `pnpm dev` is four layers — `pnpm` → `sh -c` → `tsx watch` → `node apps/server/index.ts` — and only the last one listens (since the monorepo split the root `pnpm dev` is itself a `--filter` delegation, so there is at least one more `pnpm` layer above these; the argument only gets stronger). Ctrl+C in a terminal signals the whole foreground process *group*, so all of them get it; stopping the task from an IDE, killing the top-level pid, or closing the terminal tab reaches only the top layer or two, and the listener survives with the port still bound. It gets reparented to init and nothing ever kills it, so the *next* `pnpm dev` dies with `EADDRINUSE` — and since each failure leaves another one behind, they accumulate (found 29 of them once, the oldest three days old, plus one still holding live browser connections). `watchForOrphan()` therefore samples `process.ppid` every 2s and runs the normal `shutdown()` once it changes, so the Y.Doc still gets flushed on the way out. The timer is `unref()`'d — it is a sentinel, not a reason for the process to stay alive — and the check is dev-only (under an init system the server is PID-1-adjacent by design). This is *not* a bug in the shutdown path: a plain SIGTERM to the listener has always exited cleanly in about a second; the signal simply never reached it.
- `apps/server/env.ts` — side-effect module: `process.loadEnvFile()` on the repo-root `.env` (real env vars win). Imported first by `config.ts` and `index.ts`; no dotenv dependency
- `apps/server/runtime.ts` — `isBundle` / `moduleDir` / `appRoot`. `__APP_BUNDLE__` is defined by the esbuild build, so the bundle knows it is a bundle: the app root is then `process.cwd()` (the repo root locally, `/app` in the container) instead of `apps/server/`'s grandparent (from source it is two levels up)
- `apps/server/config.ts` — `rootDir` / `outputDir` / `staticDir` / `isDev` / `port` / `host` / `isApiPath()` / `dataDir` / `dbProvider` / `databaseUrl` / `ensureDatabaseDir()` / `appOrigin` / `appOrigins` / `isAllowedOrigin()` / `resolveOrigin()` / `callbackUriFor()` / `secureCookieFor()` / `authConfig` / `authEnabled` / `assertAuthConfig()` / `clusterMode` / `isClustered` / `redisUrl` / `redisKeyPrefix` / `instanceId` / `assertClusterConfig()`. `isDev` is `NODE_ENV !== 'production'`; `staticDir` defaults to `output/public` (next to the bundle when bundled) and `STATIC_DIR` overrides it
- `apps/server/app.ts` — Hono app typed as `Hono<{ Bindings: HttpBindings; Variables: AuthVariables }>` (the frontend middleware needs node's raw `req`/`res` via `c.env`; the auth middleware puts `session`/`user` in `Variables`). Logger + CORS, `withSession` then a `requireAuth` gate on everything under `/api/*` except `PUBLIC_API` (`/api/health`, `/api/auth`), route mounting, 404/error handlers. Exports `AppType` for optional `hc<AppType>()` RPC typing on the frontend
- `apps/server/db.ts` — the MikroORM singleton (`orm`, created by a top-level `await createOrm()`, cached on `globalThis` so `tsx watch` doesn't leak connections) and `db()` = `orm.em.fork()`. **Fork once per operation (or per group that must share a transaction)**; `allowGlobalContext` stays off and there is no RequestContext middleware, so the store layer is self-contained and works outside requests (collab persistence, sweeps). `init` does discovery only and connects on the first query, so a dead database doesn't stop the process booting
- `apps/server/db/` — the data layer's own code: `entities/{auth,canvas}.ts` (the ten entities, `defineEntity`; the rules for writing them are in `entities/columns.ts`), `orm.ts` (`createOrm()` — picks the driver at runtime), `query.ts` (`containsIgnoreCase()`), `schema-sync.ts` (diff + lossy-change guard) and `sync-cli.ts` (the `db:push` / `db-sync.js` entry)
- `apps/server/auth/` — the OIDC/session layer (see below)
- `apps/server/frontend/` — how the UI gets served (see below)
- `apps/server/routes/` — one Hono sub-app per resource, mounted under `/api/*`. Routes are chained (`new Hono().get(...).post(...)`) so `AppType` stays inferable
- `apps/server/store/` — data layer; routes never touch the ORM. `store/notes.ts` is still an in-memory `Map` (the API-shape sample); `store/projects.ts` and `store/flows.ts` are the real database-backed ones. `store/flow-types.ts` holds the server-only half of the graph types — `parseGraph`/`parseTransactions`/`parseUserStatePatch`, `GRAPH_LIMITS`, the Op types (the graph structure types themselves are in `@shadecn/shared/flow-graph`); case-insensitive search goes through `apps/server/db/query.ts`'s `containsIgnoreCase()`, the one place that papers over a SQLite/PostgreSQL behaviour difference
- `apps/server/auth/project.ts` — project-scoped authorization: `requireProjectMember` / `requireProjectAdmin` / `requireFlowMember`. **Non-members get 404, not 403** (don't leak existence); a member lacking the role gets 403. `currentUserId()` also mints a fixed local dev user when `authEnabled` is false, so the feature runs without a Keycloak
- `apps/server/collab/` — Yjs collaboration over WebSocket (see below)
- `apps/server/cluster/` — the single-replica / multi-replica switch (see below)
- `apps/server/logger/` — winston, **injected rather than instrumented** (see below)
- `apps/server/tsconfig.json` — separate TS project (Node types, no DOM), referenced from the root `tsconfig.json` (as are `apps/web` and `packages/shared`). Imports inside `apps/server/` use explicit `.ts` extensions

**Logging (`apps/server/logger/`) — winston, and the rule is *keep writing `console.*`*.** The whole layer is injected at four wiring points; there is **no `logger.info()` anywhere in business code**, and adding one is the thing not to do. Write `console.warn('[collab] …')` exactly as the existing 49 call sites do — `console.ts` intercepts `console.*`, parses the `[prefix]` into a structured `module` field, attaches the request context, and hands it to winston. That interception is the load-bearing piece: it is what let the whole codebase become structured logging with zero diffs, and it is why third-party output (ioredis) is collected too. The four mount points, one line each: `index.ts` imports `./logger/install.ts` **second, right after `./env.ts`** (a side-effect module, not a function call — ESM hoists imports, so a call in the module body would run *after* every other module has already initialised and logged); `app.ts` uses `httpLogger()` in place of `hono/logger` (it also opens the `AsyncLocalStorage` that gives every downstream log a `requestId`); `db/orm.ts` passes `loggerFactory: ormLoggerFactory` (`logger/db.ts`; MikroORM calls `logQuery()` for every statement with the SQL, timing and row count — **it logs SQL text but never parameter values**: the `query-params` namespace is permanently off, which is what makes MikroORM hand over the `?`-placeholder SQL instead of the interpolated one, and `logQuery` only reads `query`/`took`/`results`/`affected`, never the `params`/`formatted` that also ride in the context; the ORM's own `debug` and `slowQueryThreshold` stay unused so `LOG_SLOW_QUERY_MS` is the one threshold); `collab/hocuspocus.ts` puts `collabLogging()` in the extensions array. That last one is the interesting one: Hocuspocus pushes the `new Hocuspocus({...})` hooks onto the *end* of the extension list, so a `priority`-tagged logging extension brackets the business hooks — `onStoreDocument` (start) and `afterStoreDocument` (only reached if the whole chain succeeded) mean **`started - completed` is the failed-persist count, derived purely by observation**, which is what REQ-RESILIENCE §4.5 asks for. Noise control is a design constraint, not an afterthought: per-update and per-frame events are *counted*, never printed (one node drag is dozens of updates), and summarised once a minute; `LOG_HTTP` defaults to `api` so dev's few-hundred Vite module requests stay out; nothing in a hook may throw (the hook chain is serial — an observer that throws kills the quota/auth hooks behind it) and nothing may call `Y.encodeStateAsUpdate()` just to print a byte count (it serializes up to 20MB). Config is `LOG_LEVEL` / `LOG_FORMAT` / `LOG_DIR` / `LOG_HTTP` / `LOG_SLOW_MS` / `LOG_SLOW_QUERY_MS`; winston is silent under `NODE_ENV=test`, and since tests never import `apps/server/index.ts`, the console interception never touches them.

**Frontend hosting (`apps/server/frontend/`):** `attachFrontend(app, server)` registers a catch-all *after* the `/api` routes, so API routes always win and everything else falls through to the UI.
- **`frontend/guard.ts` — the page gate, and what it guards is "you can't *see* the UI", not "you can't fetch the bytes".** Mounted by `app.ts` right after the `/api` routes, so before the frontend catch-all. An anonymous **document request** (`Sec-Fetch-Mode: navigate` or `Accept: text/html`) for anything other than `/login`, `/favicon.ico`, `/vite.svg` gets a 302 to `/login?redirect=<path>`; **every non-navigation request passes through** — `/assets/*.js`, `/assets/*.css`, dev's `/src/**` and `/@vite/*`. Assets have to be public because **the login page is itself an entry of the frontend bundle** (below); gating them would leave the login page staring at a blank screen. Serving them costs nothing, because booting the SPA needs `index.html`, and *that* is a navigation the first rule already turned away. `GET /login` still lives here but now does exactly one thing: 302 the already-logged-in away (`safeRedirect` on `?redirect=`), then `next()` to let the frontend layer serve the page
- **The login page is the frontend's *second Vite entry*, not a server-rendered string and not a SPA route.** `login.html` + `apps/web/src/login/` sit alongside `index.html` in `vite.config.ts`'s `rollupOptions.input` (MPA). It cannot be a SPA route — anonymous browsers never receive `index.html`, so a login screen that needs the SPA to boot could never render. It reads what it needs itself: providers from `GET /api/auth/config` (public), `?redirect=` and `?error=` from `location.search`. `?redirect=` is passed straight through to `/api/auth/login`, where `safeRedirect` validates it — the in-site check is **not** reimplemented on the client. This replaced a hand-written HTML string whose palette and GitHub icon had to be kept in sync by hand, and had already drifted (`--primary` was `0.985` on one side and `0.922` on the other); both entries now share the same chunks, so the duplication is gone. The cost, stated plainly: the page went from a 5.3KB self-contained zero-JS document to ~62KB gzip that needs JS to render, most of it the Tailwind CSS chunk shared with the app (~20KB gzip, already cached once you're inside). Serving it is a one-line branch in both `frontend/dev.ts` (through `transformIndexHtml`) and `frontend/static.ts`
- **`login.html` carries the same inline theme script as `index.html`** — reading `app:theme` before first paint. Both copies must change together; it is the one thing a second entry cannot share, because it has to run before any module loads. It also fixed a real mismatch: the old server-rendered page only knew `prefers-color-scheme`, so anyone whose app theme disagreed with their OS saw the login page in the wrong one
- `frontend/dev.ts` (dev only, dynamically imported so Vite never loads in prod) — `createServer({ root, appType: 'custom', server: { middlewareMode: true, hmr: { server } } })`. Vite's connect middleware chain is run against `c.env.incoming/outgoing` and the handler returns `RESPONSE_ALREADY_SENT`; if the chain calls `next()`, the SPA fallback renders `index.html` through `vite.transformIndexHtml`. `hmr.server` is what makes HMR ride the same port — with only `middlewareMode: {server}` Vite would still open port 24678
- `frontend/static.ts` (prod) — `serveStatic({ root: <staticDir relative to cwd> })` + `index.html` fallback for unknown paths
- `vite.config.ts` is still the config of record (plugins, `@/` alias) — it's read both by `vite build` and by the middleware-mode `createServer`. `build.outDir` is `output/public`, i.e. the frontend builds straight into the backend's static directory. It has no `server.proxy` anymore because there is nothing to proxy to

**Build (`apps/server/scripts/build-server.mjs`) — `output/` is a self-contained, runnable app directory.** `pnpm build` (`pnpm build:client` then `pnpm build:server`) fills it with `public/` (frontend, from `vite build`), `server/index.js` (backend, esbuild bundle, ESM/node22), `server/db-sync.js` (the schema-sync entry, `apps/server/db/sync-cli.ts` — a second esbuild entry point in the same build, sharing chunks with the first), and — copied verbatim from `apps/server/scripts/output-image/` — `Dockerfile`, `.dockerignore`, `README.md`. Copy `output/` anywhere and `npm install --omit=dev && npm run db:push && npm start` runs it; `docker build ./output` images it. No repo source needed.
- `output/package.json` is generated: its `dependencies` are derived from esbuild's *external* list (metafile) — the packages the bundle actually imports, read against `apps/server/package.json` — each pinned to the version installed at build time. That includes **both** `@mikro-orm/sqlite` and `@mikro-orm/postgresql` (their drivers, better-sqlite3 and pg, come in as their pinned dependencies — the bundle never imports them directly). `vite` is filtered out (`DEV_ONLY`) because it only appears in the never-loaded dev chunk. Its scripts are `start`, `db:push` (`node server/db-sync.js`) and `db:push:force`. `node_modules` is deliberately not shipped: better-sqlite3 is native and its binary must match the target platform.
- Relative imports are inlined, **and so are workspace packages (`@shadecn/*`, via the `externalizePackages` plugin)**, so there is no `tsx` and no CLI tool at runtime.
- **One artifact serves both databases.** Nothing is provider-specific at build time any more: `pnpm build` ignores `DB_PROVIDER`, and the same artifact / image connects to SQLite or PostgreSQL depending on the runtime env. Don't reintroduce a per-provider build.
- Two non-negotiables in the esbuild call: `splitting: true`, so `frontend/index.ts`'s `await import('./dev.ts')` stays a real dynamic import and `vite` never becomes a top-level static import (it is not installed in prod); and `define: { __APP_BUNDLE__: true }`, which is how `apps/server/runtime.ts` tells bundle from source.
