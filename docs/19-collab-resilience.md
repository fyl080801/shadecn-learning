## 1. 目标

现在的协同链路对**客户端侧**的故障（断网、刷新、关标签页、会话过期、被顶下线）考虑得很完整，
每一种都有明确的信号、明确的出路和明确的文案。但对**服务端自己**的故障 ——
数据库写不进去、Redis 挂了、进程被 SIGKILL、副本分叉 —— 几乎没有对应处理，
而且**失败是静默的**：界面照样显示「已同步」，用户照样在画。

本需求要达到三件事，按重要性排序：

1. **失败要能被发现**。这一条**已完成**（§4.5）：结构化日志 + `GET /api/collab/health`。
   在它之前，下面所有故障对运维和用户都是不可见的 —— 所以它必须排在最前面，
   否则后面几条修没修好都看不出来。
2. **失败不能被当成成功**。**已完成**（§4.1）：我们曾主动吞掉异常，把上游 Hocuspocus
   自带的「存不进去就别卸载文档」保护绕过去了 —— 那是真丢数据，不是延迟。
   现在异常照抛、失败记账、恢复后自动补写。
3. **降级要是降级，不是停摆**。共享层（Redis）在设计上是**缓存**。
   我们这一侧的两处（§4.2 a）已经改成 fail-open；上游 redlock 那一处（§4.2 b）还在，
   但 §4.3 的读-合并-CAS 让它不再是正确性依赖 —— Redis 挂掉时落库会滞后，不会覆盖内容。

## 2. 现状：已经有的兜底

先说清楚哪些是好的，避免把已有的机制重做一遍。

| 故障 | 现有兜底 | 位置 |

## 3. 判断口径

贯穿全文的一条：**「同步」和「保存」是两件事**。

- **同步** = 改动到了服务端**内存**里的 Y.Doc，并广播给了房间里其他人。
- **保存** = 改动落进了 `Flow.ydoc` 的字节。

前端现在只有前者的信号（`FlowTransport.synced`，且协同模式下 `pending` 恒为 `false`），
而下面几乎所有故障的表现形式都是「同步成功、保存失败」。这是本需求存在的根本原因。

## 4. 缺口

### 4.1 写队列吞掉落库异常，绕过了 Hocuspocus 的数据保护

> **已修复。** `enqueue` 照实往外抛 + 欠账登记 + 定期重试；
> 用例在 `server/test/collab/persistence.test.ts` 的「落库失败」一组。

**原来的现象。** 数据库写失败时内容会真的丢，且没有任何痕迹。

**成因。** `persistence.ts` 的 `enqueue` 对 task 的失败只 `console.error`，
返回的是一个**已 resolve** 的 promise；`storeFlowState` `await` 的正是它。于是：

1. 我们的 `onStoreDocument` 正常返回；
2. Hocuspocus 认为存好了 —— 它自己 `storeDocumentHooks` 里那段
   *"Document stays in memory to avoid data loss"* 的 catch **根本不会触发**；
3. 紧接着 `setTimeout(() => unloadDocument(document))`，最后一个人已离开就把文档摘出内存；
4. `beforeUnloadDocument` 再写一次，同样失败、同样被吞 —— 内容没了。

也就是说：**数据库抖动期间关掉页面 = 这一轮编辑永久丢失**。
只有那台浏览器的 IndexedDB 里还剩一份，且要等那个人再打开同一张画布才推得回去 ——
换台设备、清过浏览器数据，就没有第二个副本了。

**修法分三步**，缺一步都不成立：

1. **让异常抛出去**（`enqueue` 不再 catch）。这样两条卸载路径都被堵住：
   `onStoreDocument` 抛 → `storeDocumentHooks` 的 catch 保留文档在内存；
   `beforeUnloadDocument` 抛 → `unloadDocument` 直接 `return`，文档既不 `delete` 也不 `destroy`。
   **上游那两道保护本来就是靠 hook 抛异常触发的** —— 我们等于把自己关掉的开关打开。
2. **登记欠账**（`failedStores`）。光留在内存不够：`onStoreDocument` 由防抖触发，
   而这时房间里往往已经没人编辑了，**没有任何东西会再叫它一次**。
   内容就一直悬着，直到进程退出 —— 那要是一次 SIGKILL，就全没了。
3. **定期重试**（`retryFailedStores`，30 秒一轮，串行）。数据库恢复之后自动补齐。
   平时这一轮什么也不做：欠账表是空的，函数第一行就返回。

**顺带修掉的两处同类问题**（都是「缓存失败被当成内容写失败」）：
`sameAsStored` 的共享层读、`rememberStoredVersion` 的共享层写，
现在都不再让整次落库失败 —— 它们写的是缓存，最坏结果是多写一次库。
后者还有个坑值得记下来：**共享层的懒代理是同步抛出的**（第一次调用才解析实现），
而 `rememberStoredVersion` 当时不是 `async` 函数，所以挂在它上面的 `.catch()` 根本接不到，
异常一路炸穿。改成 `async` 才把同步抛转成 rejection。这个是写测试时才暴露出来的。

**队列没有被堵死**：`previous.then(task, task)` 本来就是「前一个失败后一个照跑」，
清理那步改成先 `.catch()` 再 `.finally()`，免得给进程留下没人处理的 rejection。

**代价**：数据库长时间不可用时房间不卸载、内存不释放。可接受 —— 这正是上游选择的权衡
（宁可占内存也不丢），而配额那道关管着单房间的规模上限。`GET /api/collab/health` 的
`owed` 字段会把这件事报出来。

### 4.2 Redis 一抖，落库整个停摆

共享层在设计上是缓存（`persistence.ts` 里那张 `flow-state-vector` 表的注释自己写着
「它是纯缓存：没了最多多写一次库，不会丢内容」），但有两条路把它的失败升级成了致命错误。

**a) 纯缓存的读失败没有 catch。** ~~`sameAsStored` 里 `storedVersions.get()` 裸 await，
多副本下这是一次 Redis 读，命令 reject 就把整个 `storeFlowState` 抛掉。~~

> **已修复**（随 §4.1 一起）：读失败当作「没存过」照写一次，写失败（`rememberStoredVersion`）
> 也不再算落库失败。共享层是缓存，最坏结果是多写一次库。

**b) redlock 拿不到锁就 rethrow。** `@hocuspocus/extension-redis` 的 `onStoreDocument`
只把 quorum 错误转成 `SkipFurtherHooksError`（那是正常的「另一个实例正在存」），
其余错误（连接断开、超时）一律 `throw`。它在 hook 链里排在我们前面，所以
**Redis 不可用期间，多副本模式下所有画布停止持久化**，而界面全程显示「已同步」。
这时滚动重启一次，内存里所有房间的编辑就全指望客户端回来补了。

> 这条没法在上游之外直接修掉，所以对应的要求是：**必须能观测到**（§4.5），
> 并且让协同落库有一条不依赖 redlock 正确性的兜底 —— 也就是下一条的 CAS。

### 4.3 协同落库是全量覆盖写，没有 CAS；redlock 的 TTL 是 1 秒

> **已修复。** 落库改成**读 → 合并 → CAS 写回**，`lockTimeout` 显式配成 10 秒。
> 用例在 `server/test/collab/persistence.test.ts` 的「落库的跨副本并发」一组。

**原来的问题。** `storeFlowState` 用 `updateMany({ where: { id } })` 把
`Y.encodeStateAsUpdate(doc)` 整段盖进 `ydoc`。单副本下这没问题 —— 这个进程是唯一的写者，
内存那份一定是库里那份的超集。多副本下就不成立了，而**唯一的跨副本保护是
extension-redis 那把 redlock**，它有两个洞：`lockTimeout` 默认只有 **1000ms**
（一次落库读+合并+写，文档大一点、库慢一点就超过一秒，锁提前过期，两个实例同时写同一行），
以及 Redis 故障期间锁机制根本不存在（§4.2 b）。

**修法里最关键的一点：光加 CAS 是不够的。**

`where: { revision }` 保证的是「我读到之后没人插过队」，**不是**「我手里的内容是库里内容的超集」。
别的实例在我读 `revision` **之前**写完的话，我读到的是新 revision，CAS 会顺利通过，
然后我照样用一份缺内容的文档盖上去 —— 数据一样丢，而且看起来一切正常。

所以两件事必须一起做：

1. **把库里那份读回来 `Y.applyUpdate` 进内存文档** —— 保证写回去的是超集；
2. **CAS**（`where: { revision }`，`count === 0` 就重读重来）—— 保证「合并到写回」这一段没人插队。

合并用 Yjs 自己的语义，所以幂等：单副本下读回来的是子集，`applyUpdate` 不产生任何新内容、
也就不触发 update 事件，**零副作用**；真有分叉时它才产生一次更新，而那一次正该广播给本实例的
客户端 —— 他们本来就缺着那部分内容。这也是为什么测试里能断言「合并是双向的」。

事务 origin 用 `'persistence'`（和 `onLoadDocument` 一致）而不是 `local`，所以合并进来的内容
不进任何人的撤销栈。

**redlock 降级成优化，不再是正确性依赖。** `lockTimeout: 10_000` 只是**减少**撞车；
真撞上了由读-合并-CAS 兜底 —— 它连 Redis 整个挂掉的情况也覆盖，
而这正是 §4.2 b 没法在上游之外直接修掉时，我们能给的那条兜底。

**成本**：每次落库多一次读（读的量级和写相同，所以落库开销大约翻倍）。
落库本来就是 2–10 秒一次的防抖动作，这个代价可以接受；换来的是「多副本下内容不会被覆盖」。
连续 `MAX_STORE_ATTEMPTS`（3）次都被抢先就抛出去，交给 §4.1 的欠账重试 —— 内容一点没丢。

### 4.4 「已保存」这个词现在是不成立的

> **便宜版已做。** 服务端在落库状态**翻转**时用 stateless 消息广播给房间，
> 前端把状态栏改成「服务器暂时无法保存，改动已同步给协作者」。
> 用例在 `server/test/collab/persistence.test.ts`（何时该说）
> 与 `src/test/composables/flowSync.test.ts`（消息怎么解）。

§4.1–4.3 的失败模式全都长成同一个样子：**界面写着已同步，字节其实只在内存里**。
前端原本没有任何信号能区分这两者。

**现在的形态**：`persistence.ts` 暴露 `onStoreStateChange(listener)`，
`hocuspocus.ts` 挂上去、把状态 `broadcastStateless` 给房间；
前端 `sync/collab.ts` 的 `onStateless` 解析出来喂给 `saveFailed`，
`useFlowDocument` 的 `saveState` 多一个分支。四个判断值得记下来：

- **只在翻转时广播**（好→坏、坏→好），不是每次落库都广播。落库正常时是 2–10 秒一次，
  逐次通知等于往房间里灌噪音；一直失败时逐次通知同样没有新信息。
- **新连接接入时补发一次**（`connected` 里读 `isStoreFailing`）。只在翻转时广播的代价是
  后进房间的人错过了那一次 —— 不补发的话他会对着一张写着「已同步」的画布继续画。
- **前端换传输时把 `saveFailed` 清掉**。它说的是「**那台**服务器存不进去」，
  重连之后是一次全新的判断；留着旧值的话，一次普通重连就能让界面永久停在「无法保存」。
- **解析必须防御着写**。stateless 是通用旁路通道，将来可能驮别的东西，
  而一条读不懂的消息**绝不能**变成异常 —— 那会打断整条连接的消息处理。
  有一组用例专门喂各种畸形 payload。

措辞上刻意不吓人、也不给按钮：用户这会儿什么都做不了，重试是服务端自动的
（恢复后再广播一次，那行字自己就消失）。它要传达的只有一件事 —— **现在别关页面**。
也没有把它做成 `fatal`：那一档是「不会自己好」，而这个会。

**没做的完整版**：`afterStoreDocument` 广播**已持久化的状态向量**，前端拿它和本地 doc 的 SV
比对，把「已同步」和「已保存」拆成两个独立状态显示。那才是彻底诚实的显示 ——
现在这版只能说「出事了」，说不出「你最后 3 秒的编辑还没落库」。
代价是每次落库都要广播一条带 SV 的消息，且前端要维护一份比对逻辑。等有人真的需要再说。

**同一类问题在客户端还有一处，已一并修掉**：`sync/index.ts` 里 `IndexeddbPersistence`
的构造和 `whenSynced` 都没有接异常。无痕模式、浏览器禁用 IndexedDB、配额写满时，
「断网不丢」这个承诺会悄无声息地失效 —— 而它恰恰是整个容灾故事的地基。

现在两处都接住（构造函数会**同步抛**，`whenSynced` 会 reject，所以 `try/catch` 和
`.catch()` 缺一不可），并且分两档处理：**进场 toast 一次**（否则一个从不断网的人
永远不知道自己少了这层保护），**断线时状态栏改口** —— 从「已离线，改动存在本地」
换成「已离线，且这台浏览器存不下草稿 —— 刷新会丢失未同步的改动」。
在线时不占状态栏：那时本地缓存用不上也没影响，内容照样同步出去了。

顺带把这段判断拆成了纯函数 `sync-text.ts` 的 `syncTextOf`。原因是可测性：
`useFlowDocument` 要 router、要组件实例、`watch(flowId, …, {immediate:true})` 一挂上就发请求，
为了钉几句文案搭那一整套环境不划算；而把判断抄进测试里再断言，测的是复制品，
改了实现照样绿 —— **那种测试比没有更糟**。

### 4.5 发现不了就谈不上容灾

> **已做** —— 日志层（`server/logger/`，winston，零入侵注入）+ `GET /api/collab/health`。
> 剩下的是**运维动作**：在监控系统里配一条针对这个端点的告警。

原本的问题是：落库失败、写队列深度、Redis 断连、redlock 冲突全部只落在 stdout，
`GET /api/collab/rooms` 也只报房间数和连接数。§4.1~4.3 的故障没有任何人会知道。

现在的形态：

- **日志**（`server/logger/`）—— 落库失败、慢查询、连接进出、房间生命周期都是结构化日志。
  接管 `console.*` 得来，业务代码一行没改，写法照旧是 `console.warn('[collab] …')`。
- **端点** `GET /api/collab/health` —— **状态码本身就是结论**（200 / 503），
  最土的告警（curl 判状态码）也接得上，不必解析 JSON。响应里有：

  | 字段 | 含义 | 来源 |
  |---|---|---|
  | `store.started` / `completed` / `failed` | 落库开始 / 完成 / **失败**次数（进程启动以来累计） | `collabLogStats()` |
  | `store.lastOkAt` / `sinceLastOkMs` / `stale` | 最近一次成功落库是什么时候、隔了多久 | 同上 |
  | `pending` | 还有几张画布的写排着队 | `persistence.ts` 的 `pendingWriteCount()` |
  | `cluster` | 共享层（Redis）现在好不好使 | `clusterHealth()` |
  | `rooms` | 在线房间数与连接数 | `collabStats()` |

两个判定细节值得记下来：

- **`failed` 是观察出来的，不是谁上报的**。Hocuspocus 把业务 hook 固定排在 extension 链
  最后，日志 extension 带 `priority` 排在最前，于是 `onStoreDocument`（开始）与
  `afterStoreDocument`（只有整条链成功才到）**一头一尾夹住落库** ——
  两个计数的差就是失败次数，业务代码里一行 try/catch 都不用加。
- **「很久没落库」必须和 `pending` 一起判**，否则天天误报：落库是有编辑才发生的，
  没人编辑时本来就不落库。队列里压着东西、又超过 5 分钟没有一次成功 —— 那才是真出事了。

**还没做的两件事**，都是有意留的：

1. **告警规则本身**。端点给的是事实，「失败几次算事故、隔多久该叫人」是运维策略。
2. **免鉴权访问**。`/health` 在登录闸门之内（`app.ts` 的 `PUBLIC_API` 只放行
   `/api/health` 和 `/api/auth`）。响应里没有用户数据也没有房间名，本可以放开，
   但那是一次**安全边界变更**，该单独评估而不是顺手做掉。要给 Prometheus 抓，
   正确形态是另开一条带 token 的口子，或者把 readiness 拆成 `/api/health/ready`（§4.6 第 3 条）——
   两者都该和 §4.6 一起做。

### 4.6 k8s 侧的三个具体缺口

> **已修复**（三条都做了）。用例在 `server/test/routes/health.test.ts`；
> 两份清单都过了 `kubectl apply --dry-run=client`。

1. **~~没有 `terminationGracePeriodSeconds`，也没有 `preStop`~~** —— 现在两份清单都有
   `terminationGracePeriodSeconds: 60` + `preStop: sleep 5`。
   默认的 30 秒在房间多或数据库慢时不够，超时被 SIGKILL **比不 flush 还糟**：
   既没写进去，也没干净退出。preStop 那 5 秒是为了让 endpoint 先摘干净 ——
   k8s 里 SIGTERM 和摘流是**并行**的，不睡这一下，正在死的 Pod 还会接到新的 WebSocket 握手。
2. **~~落库没有整体超时~~** —— `server/index.ts` 的 `SHUTDOWN_FLUSH_TIMEOUT`（20 秒）
   把 `flushAllRoomsToDatabase` + `flushCollabWrites` 整段包住。
   放在这里而不是 `flushCollabWrites` 内部：**退出的时间预算是一个整体**，
   和 `terminationGracePeriodSeconds` 直接对应，拆成两个各自的超时反而说不清总账。
   超时就认了往下走 —— 再等也写不进去，而内容还在客户端的 IndexedDB 里，下次打开会推上来。
   （Prisma 侧仍没有 statement timeout，写队列仍无界；那是 §4.3 之后再看的事。）
3. **~~readiness 不反映依赖健康~~** —— 拆成了两条路径：

   | 路径 | 探针 | 查什么 |
   |---|---|---|
   | `/api/health` | liveness + startup | **什么都不查**，只回答「进程还在跑吗」 |
   | `/api/health/ready` | readiness | 数据库 `SELECT 1` + 共享层状态 |

   **拆开是因为两者失败时该发生的事完全相反**：readiness 失败 → 摘流量（数据库连不上时正该如此）；
   liveness 失败 → **重启容器**，而重启治不了数据库故障，只会把一个本来还能提供只读服务、
   还握着未落库内容的进程杀掉，然后在 CrashLoopBackOff 里反复重启，把故障放大一圈。
   所以 liveness 必须保持浅探针 —— 有一条用例专门钉「`/api/health` 一次数据库都不碰」。

   两个细节：依赖探测自己带 2 秒超时（`prisma.$queryRaw` 没有默认上界，数据库进黑洞时
   会一直挂着），而探针的 `timeoutSeconds: 3` 比它宽，好让**服务端先超时**、原因落进日志；
   响应里**只有「通没通」**，连接串和错误码只进日志 —— 这个端点匿名可读（kubelet 不带 cookie）。

### 4.7 恢复预案本身是缺的

> **仍未做**（唯一还在的大项）。下面是做之前必须先定下来的几条规则，
> 每一条都有实测支撑 —— 定错了，备份本身会变成新的数据损坏源。

#### 4.7.1 备份必须存 `ydoc` 二进制，绝不能存 `graph` JSON

这是整节里最反直觉、也最贵的一条。`graph` 那一列是人能读的 JSON，看着正是备份该有的样子，
而它恰恰**不能**用来恢复。

原因不是「JSON 有损」，而是 **Yjs 的身份模型**：从 JSON 重建文档会得到一条
**全新的 clientID**，也就是一条和原来毫无关系的平行历史。而恢复发生的那一刻，
用户浏览器的 IndexedDB 里正躺着一条**真实的**历史。两条历史合并时，同一个 key 的胜负
由 clientID 大小决出 —— 也就是随机。

拿 `sample/画布数据参考/` 那份真实画布实测（733 节点 / 573 边）：

```
服务器 doc  clientID=2179665252  label="图片参考"
客户端 doc  clientID=2864946292  label="客户端改的"     ← 这一笔还在他的 IndexedDB 里
恢复的 doc  clientID=3174713418  label="图片参考"       ← 从同一份 JSON 重建

合并之后    label="图片参考"     → 客户端的编辑被静默丢掉了
```

**跑 200 次：客户端的编辑活下来 105 次（53%）。**「随机丢编辑」是字面意思，不是修辞。

对照组：备份存 `ydoc` 字节、恢复时 `Y.applyUpdate`，那一笔编辑 **100% 活下来** ——
因为那是同一条历史的延续，而不是旁边硬造的第二条。

**落到操作上**：`pg_dump` / PVC 快照就够了，`ydoc` 是 `BYTEA`/`BLOB`，原样进原样出，
天然满足这条。要做的只是**别为了可读性把 `graph` 当备份**。
未来的画布版本快照（`docs/README.md` 优化项 4）同理：存二进制，
且「恢复到某版本」要走**当前文档上的一次 Yjs 事务**，而不是重建文档。

#### 4.7.2 对照：旧数据**不需要**迁移脚本

同一个原理，答案却相反，所以放在一起记。

`Flow.graph` 有值、`ydoc` 为 `NULL` 的老画布**已经在自动迁移**：`stateFromRow`
在 `onLoadDocument` 里现场把 graph JSON 灌进一个新 Y.Doc，每张画布在第一次被打开时
各自完成，没打开过的原样躺着 —— 没有迁移脚本，没有停机窗口，也没有「迁移到一半」的中间态。

**为什么这里从 JSON 重建是安全的，而 4.7.1 不安全**：老画布从来没有过 Yjs 客户端状态，
那条全新的历史是它的**第一条**历史，没有第二条可以撞。备份恢复的时刻则不然。

写迁移脚本反而更糟：要么和 `stateFromRow` 重复一套规则（两条路径打开同一张老画布
可能得到不一样的东西），要么就是把已经在跑的事情再跑一遍。

#### 4.7.3 恢复的顺序不能错

内容的事实源是**内存里的 Y.Doc**，`loadFlowState` 只在房间首次加载时读一次库。
所以直接恢复数据库备份，只要房间还开着，下一次 `storeFlowState` 就把恢复的内容盖回去。

正确顺序只有一个：**先让房间卸载（或直接重启进程）→ 再恢复数据 → 再放人进来**。

§4.3 的读-合并-CAS **不改变这一点**：合并的结果是「内存 ∪ 库」，而恢复备份想要的往往是
「只要库里那份」—— 合并只会让被恢复掉的内容又回来。这是个容易想当然的地方。

#### 4.7.4 还没做的

- **定时备份本身**（`pg_dump` CronJob / PVC 快照），以及保留策略。
  需要集群里 NFS / PG 的现状输入，属于运维动作。
- **恢复演练**。没演练过的预案等于没有。
- 单副本是 `Recreate` + SQLite 单文件，部署即停机，且无热备 ——
  这是已知的架构选择（见 REQ-CLUSTER），但作为容灾清单该被显式记下来。

#### 4.7.5 顺带量出来的一个数

那份 733 节点的真实画布转成本项目的格式后：

| | 大小 | 占上限 |
|---|---|---|
| 原始 JSON | 1506.5 KB | — |
| `ydoc` 二进制 | 1430.4 KB | 20MB 的 **7.0%** |
| `graph` 投影 JSON | 1450.6 KB | 2MB 的 **70.8%** |

内容侧余量很足，**投影侧只剩 30%**。这个规模的画布再长 1.4 倍，`deriveProjection`
就会返回 null，列表页的节点计数会停在旧值不动（内容不受影响，是设计好的降级）。
真要承载这一类数据，`GRAPH_LIMITS.bytes` 需要先重新评估 —— 记在这里，免得到时候当成 bug 查。
