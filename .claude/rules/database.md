**Database (`apps/server/db/entities/*.ts`, MikroORM 7, SQLite *or* PostgreSQL):** `User` (unique on `(issuer, subject)` — now the *primary identity*'s redundant copy rather than the only identity; roles as a JSON string), `UserIdentity` (one login method, unique on `(provider, subject)` — its `email` is display-only and joins nothing), `Session` (`provider` says which implementation renews it; its `id` is the cookie token's HMAC and is **set by the caller**, never auto-generated), `AuthRequest` (`provider` dispatches the single callback, `linkUserId` turns the flow from login into account-linking), `PendingLink` (a link waiting for the user to confirm *which* third-party account it is; `user` unique, so a retry replaces it); plus `Project`, `ProjectMember` (unique on `(project, user)` — the creator's admin row is written for real, never inferred from `createdBy`), `ProjectInvite` (the project's one share link — `project` is unique; token stored in the clear: it *is* the credential you hand out; unlimited uses, `expiresAt` is the only gate, and "reset" just swaps the token in place), `Flow` (`ydoc` = the Yjs state as bytes and **the source of truth for content**; `graph` = a JSON projection the server derives from it for list counts and previews — both are **lazy** columns, so a list query never loads them and code that needs them says `populate: ['ydoc']` / `fields: [...]`; `revision` = a monotonic write counter, *not* a client lock — it is the server's own CAS), and `FlowUserState` (per-user view state, unique on `(flow, user, key)` — one row per state partition, value is a JSON string; `viewport` is the first partition and adding another one is a new key, not a schema change); plus the canvas agent's three (`db/entities/agent.ts`, REQ-AGENT): `AgentConversation` (one conversation of one user on one canvas — real FKs to `flow` and `user` with cascade; `messages` / `llmMessages` are **lazy** JSON-string columns, the list reads only title / summary / `messageCount`), and the audit log `AgentRun` (id = the runId the SSE stream carries) + `AgentToolCall` (one row per tool call; `args` is `digestArgs` output — ids and string *lengths*, never content), whose `conversationId` / `flowId` / `userId` / `runId` are **plain text with no FK on purpose**: an audit trail must survive deleting the conversation or the canvas it describes. Tables and columns follow MikroORM's default `UnderscoreNamingStrategy` (`user_identity`, `avatar_url`), and **foreign keys are relation properties** (`user`, `project`, `flow`, `createdBy`, `personalOwner` → `user_id`, …): filter with `{ user: userId }`, read with `row.user.id`, `populate` when you need the other side's fields. Only the owning side is defined — there are no inverse collections (`defineEntity`'s type inference degrades to `any` on mutual references, and every query starts from the table holding the FK, e.g. "my projects" is a `ProjectMember` query). `Flow.createdById`, `ProjectInvite.createdById`, `ProjectMember.invitedById` and `AuthRequest.linkUserId` are plain text columns with no FK, as before. The DB lives at `$DATA_DIR/app.db` (`DATA_DIR` defaults to `<repo>/data`, gitignored), `DATABASE_URL` overrides it outright, and relative `file:` paths resolve against the repo root — not the cwd; `mkdir -p` of the parent happens before opening, since better-sqlite3 won't create it.

**Two databases, one entity definition, one artifact (`docs/05-data-persistence.md`).** Which one you get is `DB_PROVIDER` (`sqlite` | `postgresql`), or — when unset — the scheme of `DATABASE_URL` (`file:` vs `postgres(ql)://`), defaulting to sqlite. A `DB_PROVIDER` that contradicts the URL's scheme, an unknown value, or `postgresql` with no `DATABASE_URL` all **throw at startup** rather than guessing. That resolution exists **once**, in `apps/server/config.ts` (`dbProvider` / `databaseUrl`) — the server and the schema-sync CLI both read it. It only decides which driver `db/orm.ts` **dynamically imports** (`@mikro-orm/sqlite` drags in the native better-sqlite3, `@mikro-orm/postgresql` drags in pg — a static import would make every process load both). A Prisma-style `?schema=public` on the PG URL is still accepted: `orm.ts` strips it and passes it as MikroORM's `schema` option (pg itself doesn't understand it).
- **Entity rules — each one is a measured difference between the two databases, not a style choice** (`db/entities/columns.ts` has them in the header): **strings are always `p.text()`, never `p.string()`** (that is `varchar(255)` on PG and unbounded on SQLite — tokens and avatar URLs fit on one and fail on the other); **only five types**: text / integer / boolean / datetime / blob — no json, enum, array or native `columnType`, JSON stays a string; **nullable scalars use `strictNullable()`** (plain `nullable()` types as `T | null | undefined` and leaks `undefined` into the API types) — and since `em.create` doesn't fill unset nullable props, **write `null` explicitly in any `create` whose entity you map straight into a response**; **timestamps get their defaults in the app** (`onCreate`/`onUpdate`), never a DB default — `current_timestamp` stores differently on the two sides; ids are app-generated UUID text (`idColumn()` / `newId()`).
- **Prisma habits that are now bugs.** `nativeUpdate` / `em.insert` / `em.upsert` **don't run `onCreate`/`onUpdate`**: every `nativeUpdate` that changes content must write `updatedAt: new Date()` itself (Prisma's `@updatedAt` did it in `updateMany`; the CAS writes in `collab/persistence.ts` and `collab/flow-writer.ts` are the ones that matter — miss it and edited canvases never move in "recently modified"), and every `upsert` must pass its own `id` + `createdAt` and restrict `onConflictMergeFields`, or the conflict branch rewrites the id too. CAS is `nativeUpdate(Flow, { id, revision: read }, { revision: read + 1, … })` and its return value is the affected-row count. Nested writes and `$transaction([...])` became `em.transactional(async (em) => …)`. Unique conflicts throw `UniqueConstraintViolationException` on both databases (was P2002) — catch **only** that one in the "lost the race, re-read" branches. There is no P2025: `nativeUpdate`/`nativeDelete` on a missing row return 0, so the old `.catch(() => undefined)` around deletes is gone, and the OAuth callback's one-shot consume now means "the request that deleted the row" (`nativeDelete` returned 1) — a concurrent replay of the same `oidc_tx` loses.
- **There are no migration files, and schema sync has its own lossy-change guard (`apps/server/db/schema-sync.ts`).** `pnpm db:push` (`tsx db/sync-cli.ts`), the container's `node server/db-sync.js` and the test global-setup all run the same code: `getUpdateSchemaSQL()` → classify every statement → `schema.execute()` the very same text. **MikroORM's `schema.update({ safe: true })` is not a guard** (measured): on SQLite any column change (type, nullability, default) is a `__temp_alter` table rebuild that `safe` doesn't see, and on PG `safe` only skips `drop column` while `alter column … type` goes through. So the guard refuses drop table / drop column / `alter column … type` / any `__temp_alter` rebuild / renames (MikroORM guesses renames heuristically) / truncate-delete, prints each statement with its category and exits 1 without executing anything; create table, add column, create/drop index, add constraint and PG nullability/default changes pass. `--force` (= `pnpm db:push:force`, the old `--accept-data-loss`) lets everything through. **Tables that aren't entities are ignored** in normal mode (`dropTables: false`) and only listed as a warning — e.g. the old Prisma tables (`"User"`, `"Session"`…) still sitting in a dev PostgreSQL; they differ in case from the new ones and don't collide — while `--force` drops them along with everything else. The reason there are no migrations is unchanged: they'd be written twice in two dialects, and SQLite can't alter a column, for no existing data. **The costs**: no history, no rollback, and a lossy change makes the bare sync refuse; both Dockerfiles and the artifact's `db:push` deliberately omit `--force` (better a failed container start than silent data loss), so assess whether an entity change is lossy *before* shipping it — on SQLite even making a column nullable is a rebuild. `db:push:force` stays a *separate command* rather than a flag on `pnpm dev`, because the point of the refusal is that a human sees it once. The guard's matcher is unit-tested against SQL that MikroORM 7.2.5 *actually emitted* on both databases, plus plan-only cases against the real test DB (`apps/server/test/db/schema-sync.test.ts`) — one of which pins "the entities and a freshly synced DB produce an empty diff", because an entity MikroORM can't diff stably would make every startup trip the guard.
- **The one behavioural difference that needed code**: case-insensitive search. SQLite's `LIKE` is case-insensitive for ASCII, PostgreSQL's isn't, and MikroORM's `$ilike` is PG-only (a syntax error on SQLite). `apps/server/db/query.ts`'s `containsIgnoreCase(column, keyword)` emits `lower(col) like lower(?) escape '\'` through a `raw()` key (the alias callback makes it work inside nested relation filters too) and escapes `%`/`_`/`\` in the keyword. Any new keyword search goes through it — never `$like`/`$ilike` inline. Note it takes the **column** name, not the property name.
